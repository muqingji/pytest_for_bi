## 1. 一页总结

服务单需求自动化测试（qa_agent）要解决的问题不是“让模型写几个测试用例”，而是把 QA 从需求到质量结论的全过程变成一套可追踪、可复现、可审计的流水线。

核心做法：

1. **先冻结输入**：需求、技术方案、代码 ChangeSet、OpenAPI、策略和知识版本全部绑定固定哈希。
2. **Agent 只做判断**：需求分析、技术分析、变更分析、测试设计、独立审查均输出结构化 Artifact。
3. **程序做校验和执行**：Schema、来源、权限、路径、环境、命令、断言和哈希由确定性节点处理。
4. **人工只在关键点签核**：G01 确认范围，G02 确认 Test Case IR，G03 确认自动化候选。
5. **结果必须留证据**：执行请求、响应、断言、日志、失败归因、豁免和报告全部可回放。

一句话概括：

> **Agent 提供语义判断，程序负责可信执行，人工负责关键口径确认，系统保证每一步可追溯。**

## 2. 为什么需要这套系统

| 问题 | 具体表现 | qa_agent 的应对 |
| --- | --- | --- |
| 需求口径漂移 | 需求文档、交互说明、技术方案和代码实现说法不一致 | A02/A03/A05/A06 独立分析后做对齐 |
| 测试范围靠经验 | 低风险和高风险需求使用相似测试深度 | N24 按风险和策略确定必测层 |
| 用例缺少证据 | 用例步骤和需求、代码变更无法回溯 | Test Intent / Test Case IR 强制来源引用 |
| 生成和审查耦合 | 自己生成、自己检查，缺少制衡 | A08 生成、A09 审查；A14 生成、A18 复核 |
| 自动化越权风险 | 直接改业务仓库、访问生产、写外部系统 | 默认 artifact-only，业务仓库只读 |
| 执行结果不可信 | 只知道“通过/失败”，缺少环境与证据绑定 | N07 环境预检，N08 受控执行，N09 归一证据 |
| 质量结论不可解释 | 报告无法回答为什么能过或为什么阻断 | N11 基于策略、证据、失败和豁免输出结论 |

系统不是完全替代 QA，而是把重复性分析和证据整理交给系统，让人专注于业务口径、风险取舍、关键审批和真正模糊的问题。

## 3. 核心概念

| 概念 | 说明 |
| --- | --- |
| Workflow | 一个需求对应一个稳定工作流 |
| Run | 一次触发产生一次运行；重跑不覆盖历史 |
| INPUT-FREEZE | 冻结本轮输入和版本，输入变化后下游 Artifact 失效 |
| Artifact | Agent 或节点的唯一正式输出，包含 Schema、哈希、状态、证据和 Producer |
| Agent | `A*` 节点，负责语义理解、设计、审查或建议 |
| 确定性节点 | `N*` 节点，由程序执行路由、校验、编译、执行、聚合和决策 |
| Human Gate | `G*` 人工停顿点，需要有效人工评论或决策 |
| Stage Card | C1-C8 八张阶段卡，是内部状态的展示视图，不是调度事实源 |
| Multica | 编排与协作控制面，承载父卡、阶段卡、Agent Run、评论和附件 |

## 6. C1：需求分析与变更对齐

### 6.1 做了什么

1. **INPUT-FREEZE**：固定需求、技术方案、业务仓库 commit、契约、策略和知识快照，生成 `source_snapshot_id`。
2. **N00 路由**：用确定性模板选择工作流模式和执行深度；只有规则无法判断时才调用 A01。
3. **A02 / A03 / A05 并行分析**：
   - A02：需求事实、业务规则、边界和开放问题；
   - A03：技术方案、接口、数据和可测性；
   - A05：服务端 ChangeSet、接口影响和代码证据。
4. **A06 对齐**：汇总三个分析结果，找需求、方案和实现差异，输出需要人工确认的问题。

## 7. C2：范围确认与测试策略

### 7.1 G01 为什么必须人工

A06 常见问题包括：

- 需求文案和交互说明不一致；
- 不支持场景是否穷尽不确定；
- 多个限制同时命中时提示优先级不明确；
- 多个指标名时展示一个还是全部；
- 实现缺少接口或联调证据。

这些不能由 Agent 猜，也不能默认放行，所以进入 G01。

### 7.2 G01 有效性规则

- 白名单成员本人评论；
- 评论绑定当前 request hash；
- 所有待处置问题都有明确结论；
- 系统评论和 Agent 评论无效；
- 只改卡片状态不是审批。

### 7.3 N24 风险与测试策略

G01 通过后，N24 生成风险等级、必测层、测试深度和是否需要契约 / E2E / 非功能测试。

## 8. C3：测试设计与审核

### 8.1 测试四层模型

```text
Test Intent
  -> Test Case IR
  -> Automation Manifest
  -> Execution Plan
```

| 层 | 解决什么问题 |
| --- | --- |
| Test Intent | 为什么测、防什么风险 |
| Test Case IR | 框架无关的测试主模型 |
| Automation Manifest | 怎么变成代码候选 |
| Execution Plan | 怎么选择、执行和收口 |

### 8.2 A08 / A09 / N04 / G02 分工

- **A08**：生成 Test Intent 和 Test Case IR。
- **A09**：独立审查 Oracle、覆盖义务、来源和缺口。
- **N04**：契约校验，失败则回流 A08 修正。
- **G02**：人工审核最终 Case。

### 8.3 修正闭环

```text
A08 生成
  -> A09 审查
  -> N04 校验
  -> 失败则 A08 定向修正
  -> 自动预算耗尽则人工恢复
  -> G02 通过后进入 N25
```

## 10. C5：自动化与测试数据准备

### 10.1 自动化候选链路

```text
A14/A15 生成候选
  -> A18 独立审查
  -> N05 确定性检查
  -> G03 人工确认
  -> N29 隔离落盘
```

关键边界：

- 候选默认只写 Artifact；
- 不写业务仓库；
- 不创建 MR；
- 不访问生产；
- 网络操作必须绑定已验证契约。

### 10.2 A22 / N28 / N27 测试数据链路

- **A22**：从 Case 语义推断资源和数据意图。
- **N28**：根据 BI 能力目录生成资源 DAG。
- **N27**：校验 namespace、setup/cleanup、资源 ID、readiness 和 Secret 边界。

执行生命周期：

```text
setup 创建隔离资源
  -> readiness 只读回查
  -> test 执行验证
  -> finally cleanup 删除资源
  -> residue 检查无残留
```

## 11. C6：环境预检与执行

### 11.1 N07 / N16 / N08

- 最小环境变量；

- 日志脱敏；

### 13.3 A05 首次运行报错

第一次 A05 Run 失败：

```text
the web_search tool is not supported
```

原因是 Agent 尝试调用 `web_search`，但当前 Multica Runtime 不支持该工具，Provider 返回 invalid request。

处理方式：

1. 保留失败记录；
2. 在 A05 任务说明中限制只能读取附件和正文冻结材料；
3. 明确禁止 `web_search`；
4. 重跑 A05；
5. 第二次成功产出 `a05-backend-change-analysis.json`。

### 13.4 G01 项目绑定报错

A06 完成后曾出现：

```text
G01 issue belongs to another Multica project
```

原因是默认 G01 Adapter 策略仍指向旧项目，而本轮 C2 阶段卡属于新项目，且新项目不在 `review_project_ids` 中。

处理方式：

1. 创建本轮运行级 G01 Adapter 策略；
2. 将新项目 ID 加入 `review_project_ids`；
3. 重新扫描；
4. G01 正常绑定 QAA-516，当前等待人工评论。

## 14. 可信机制

### 14.1 Artifact Envelope

每个正式输出包含 workflow run、source snapshot、producer、schema version、payload、status、evidence refs、facts / inferences / assumptions、blocking questions 和 artifact hash。

### 14.2 输入冻结

Agent 输出摄入时重新校验 Issue、Run、附件、Prompt、模型、工具轨迹、输入 Bundle hash 和上游 Artifact hash。

### 14.3 人工 Gate

请求、决策和结果三份文档全部内容寻址：

```text
review request
  -> human decision
  -> gate outcome
  -> downstream dispatch
```

### 14.4 分发监管

统一 monitor 检查跨 Run 分发、重复分发、Gate 绕过、计划外节点和审计链篡改。异常时进入 `suspended_accuracy_violation`，必须显式确认后才能恢复。

## 15. 安全与边界

| 边界 | 当前规则 |
| --- | --- |
| 业务代码仓库 | 只读采集，禁止提交、MR、评论、流水线写入 |
| Agent 输出 | 必须通过契约和工具轨迹校验后入库 |
| 人工审批 | 只认白名单人工评论，Agent 不能代批 |
| Secret | 只按策略注入环境变量，不写 Artifact 和日志 |
| 自动化候选 | artifact-only，默认不落业务仓库 |
| 外部系统 | TAPD/MR/发布/通知 Adapter 未完成前只能 pending/blocked |
| 生产执行 | 当前 Runner 不是生产隔离环境 |
| 质量结论 | 不能把 `completed_with_gaps` 解释为生产放行 |

## 18. 常见问题

### Q1：为什么要用多 Agent，而不是一个大 Agent？

一个大 Agent 容易上下文膨胀、责任混杂、生成和审查失衡。系统把需求分析、技术分析、变更分析、测试设计、独立审查、自动化生成、独立复核拆开，每个 Agent 只消费必要输入。

### Q2：Agent 输出错了怎么办？

输出必须经过契约校验、来源校验、独立审查和确定性门禁。失败会拒收入库或进入修正闭环，不会因为卡片状态被改成 done 就自动放行。

### Q3：为什么流程停在 G01？

G01 是业务范围和口径确认点。A06 发现的问题需要产品/QA 明确口径，Agent 不能代签。

### Q4：为什么不是所有 Case 都自动执行？

系统先判断 Case 可执行性。缺少契约、数据能力、Oracle 或生命周期证据时会分类为 `manual_only`、`capability_missing` 或 `invalid_case`，不会生成看似可运行的自动化。

### Q5：这次运行为什么有报错？

主要有两类：

1. A05 调用了当前 Runtime 不支持的 `web_search`，第一次失败；禁止外部搜索后重跑成功。
2. G01 Adapter 最初绑定旧项目，新项目卡片被策略拒绝；加入本轮项目白名单后已修复。

这类报错说明门禁有效：问题被保留、定位并修复，没有被静默跳过。
