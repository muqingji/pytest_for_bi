# QA 多 Agent 质量系统简要方案

> 本文档用于快速理解和评审整体方案。后续实现 Agent、定义 Schema、配置权限和验收时，
> 以 [QA_AGENT_DESIGN.md](QA_AGENT_DESIGN.md) 为准。

## 1. 建设目标

这套系统不是单纯用大模型生成测试 Case，而是要接入真实研发流程，形成从需求进入到
质量结论输出的闭环：

1. 读取需求文档、技术方案、前端 MR 和后端 MR。
2. 找出需求、方案和代码实现之间的差异与风险。
3. 生成可追踪、可执行、预期明确的测试 Case。
4. 拆分前端、后端、契约、E2E 和非功能测试。
5. 生成并审查自动化代码。
6. 在受控测试环境中执行测试并收集证据。
7. 对失败进行聚类和归因。
8. 按确定性规则给出质量结论。
9. 将人工修正沉淀到离线评估集，持续提升 Agent。

## 2. 总体分工

- **Multica**：负责流程路由、状态、并行汇合、重试、Gate、权限、资源锁和恢复。
- **Agent**：负责理解需求、识别风险、设计 Case、生成代码、审查和失败归因。
- **确定性节点**：负责下载、Schema 校验、代码检查、执行测试、统计和质量决策。
- **人工 Gate**：负责处理高风险、冲突、代码合入和测试修复等关键决策。

核心原则是：Agent 负责语义判断，程序负责确定性执行；生成与审查分离；质量放行不能由
模型自行决定。

并行分支必须等待本次流程实际启用的全部分支完成后再汇合。未启用分支记录为
`skipped_by_policy`，不能被当成测试通过。

N04 未通过时不能进入 G02。系统必须保留当前 Test IR，按照问题类型返回 A06、A07 或
A08 定向补充；修改后的 Test IR 必须重新经过 A09 和 N04。连续修正超过预算时暂停并
转人工处理，不能带着校验问题继续执行。

## 4. Agent 能力分组

| 能力组 | Agent | 主要职责 |
| --- | --- | --- |
| 路由 | A01 | 根据新需求、MR、发布或 Bug 选择流程 |
| 输入与可测性 | A02-A05、A21 | 分析需求、方案、可测性和前后端代码变更 |
| 对齐与风险 | A06-A07 | 找出冲突、遗漏、影响范围并制定测试策略 |
| 测试设计 | A08-A12 | 生成 Test IR、审查 Oracle、拆分 Case、选择本次测试集合 |
| 自动化生成 | A13-A17-* | 生成前端、后端、契约、E2E 和专项非功能测试 |
| 自动化审查 | A18-* | 按测试类型独立审查代码和断言 |
| 失败归因 | A19 | 聚类失败并区分产品、自动化、数据和环境问题 |
| 报告 | A20 | 解释覆盖、执行结果、遗留风险和质量结论 |

其中 A09 的“测试防范覆盖”指需求、业务规则、风险、异常、边界、权限和状态变化等测试
设计覆盖，不是代码覆盖率。

## 5. 核心数据契约

Agent 之间不传递聊天历史，只传递版本化 JSON Artifact。

系统还必须维护测试资产目录和影响关系图，将需求、Case、自动化代码、接口、模块、历史
Bug 和执行结果关联起来。A12 的测试选择必须使用冻结的资产快照，不能临时猜测。

### Artifact Envelope

所有输出统一记录：工作流 ID、输入快照、Agent/模型/Prompt 版本、状态、证据引用和
内容哈希，保证结果可追溯、可复现。

### Test IR

Test IR 是测试设计的唯一主模型，至少包含：

- Case ID、父子关系、测试层级、风险和优先级。
- 需求、方案、契约或代码来源。
- 前置条件、测试数据、步骤、预期和清理方式。
- 每个预期结果对应的 Oracle、断言方式和证据来源。
- 自动化框架、目标仓库和执行环境。

需求不能直接生成 pytest 或 Playwright，必须先形成并审核 Test IR。

### Execution Plan

N15 将 A12 的选择结果确定性编译为 `generate_new`、`update_existing`、`run_existing`、
`manual_run` 或 `skip`。已有且有效的自动化直接执行，只有新增或受影响的资产才生成代码。

## 6. 五个关键 Gate

| Gate | 解决的问题 |
| --- | --- |
| G01 范围确认 | 输入缺失，或需求、方案、代码存在高风险冲突 |
| G02 Test IR 审核 | Case 是否覆盖需求，预期是否明确且可判定 |
| G03 自动化 MR Gate | 自动化代码是否忠实实现 Test IR，是否允许执行或合入 |
| G04 测试修复 Gate | 定位器、字段或测试代码修改是否真实合理，防止为了通过而改断言 |
| G05 质量豁免 Gate | 是否接受指定版本的限时风险，且不修改原质量结论 |

系统建设初期五个 Gate 全部开启。评估证明低风险场景稳定后，才能按策略逐步减少人工
审批，高风险场景继续保留人工确认。

## 7. 支持的工作流

| 模式 | 主要结果 |
| --- | --- |
| 新需求测试设计 | 完整 Test IR、覆盖矩阵和自动化计划 |
| MR 增量测试 | 变更影响、增量 Case 和受影响回归集合 |
| 发布回归 | 回归执行结果、遗留风险和质量结论 |
| Bug 复现与固化 | 最小复现 Case、修复验证和自动化回归 |
| 上线后验证 | 经授权的只读冒烟、SLO 信号和线上缺陷反馈 |

实际流程由风险驱动。低风险变更可以裁剪不需要的分支；权限、资金、删除、公共服务、
数据迁移等高风险变更必须增加契约、E2E、非功能测试和人工 Gate。

## 8. 质量结论

最终结论由版本化规则计算，不由 Agent 自由判断：

| 结论 | 含义 |
| --- | --- |
| `passed` | 满足全部强制质量规则 |
| `passed_with_warning` | 没有阻塞项，但存在明确遗留风险 |
| `blocked` | 强制 Case 失败、环境版本错误或高风险需求未覆盖 |
| `inconclusive` | 证据不足，暂时无法形成可靠结论 |

产品断言失败默认不重试。只有明确的环境、网络或临时工具错误可以在预算内重试。
质量豁免只能改变发布处置，不能把 `blocked` 修改成 `passed`。

## 9. 推荐落地顺序

1. 先定义 Artifact Envelope、Test IR、Oracle、Execution Plan 和 Schema 兼容规则。
2. 建设测试资产目录、Case 生命周期和影响关系图最小版本。
3. 打通 Multica 的状态、Gate、Secret、资源锁、审计和恢复能力。
4. 实现需求、方案、可测性和 MR 分析 Agent。
5. 实现对齐、风险、测试设计、Oracle 审查和 Case 拆分闭环。
6. 建立真实历史需求、MR、Case 和 Bug 的离线评估集。
7. 实现测试选择、精确路由、自动化生成和专项代码审查。
8. 最后接入自动化/人工执行、环境修复、失败归因和确定性质量门禁。

每完成一个 Agent，都必须独立验证 Schema、证据引用、权限边界、异常处理和未见样本上的
效果，达到验收阈值后才能作为下游 Agent 的稳定输入。

## 10. 不可突破的边界

- 不允许 Agent 绕过 Test IR 直接生成正式自动化资产。
- 不允许生成 Agent 审查并批准自己的代码。
- 不允许通过删除断言、放宽断言或静默自愈掩盖产品失败。
- 不允许 Secret、Token、Cookie 或生产数据进入 Prompt 和报告。
- 不允许未审批的生产写操作和不可逆操作。
- 不允许环境版本与目标 MR 不一致时给出正式放行结论。
- 不允许把 `skip`、未完成人工测试或被隔离的关键 Case 记为通过。
- 不允许质量豁免修改 N11 的原始质量结论。
- 不允许一次上游故障被错误创建成大量重复 Bug。
- 不允许人工修正直接在线改变生产 Agent，必须经过离线评估和版本发布。

## 11. 系统完成标志

当系统能够将任意质量结论追溯到冻结的需求、方案、MR、环境、测试资产快照、Test IR、
执行计划、自动化/人工证据和豁免记录，并且高风险场景具备人工门禁、失败不被掩盖、
Agent 升级经过独立评估时，才可以认为它具备进入真实研发流程的基础条件。
