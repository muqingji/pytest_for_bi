# 智能提醒助手：全流程实施步骤

## 1. 文档目的

本文档用于拆解“智能提醒助手”面试题从题目理解到最终提交的完整实施流程，明确每一个阶段需要完成的工作、阶段产出以及进入下一阶段的条件。

本文档关注的是实施顺序和阶段职责，不直接替代最终 PRD、技术方案、测试报告或项目 README。

## 2. 总体流程

```text
题目理解
→ 需求分析
→ 产品方案
→ 验收标准
→ 技术方案
→ 开发任务拆分
→ 编码实现
→ 单元测试
→ 集成与功能测试
→ 缺陷修复
→ 质量准出
→ 文档与提交
```

## 3. 第一阶段：需求分析

这是当前首先需要完成的阶段。

### 3.1 需要完成的工作

1. 提取题目中的已知事实和数据。
2. 找出数据口径不清楚的地方。
3. 识别核心业务问题，而不是直接设计功能。
4. 分析目标用户及其主要痛点。
5. 拆解业务目标和指标。
6. 记录为了继续设计而必须作出的假设。
7. 分析时间、技术栈和提交形式等约束条件。

### 3.2 阶段产出

- 题目事实清单。
- 未知问题清单。
- 假设清单。
- 用户问题定义。
- 指标测算。
- 初步需求范围。

### 3.3 完成标志

能够用一到两句话说清楚：

> 为哪类用户、解决什么问题、希望改善什么指标。

## 4. 第二阶段：产品方案设计

需求分析完成后，不要立即编码，应先明确产品如何工作。

### 4.1 需要完成的工作

1. 确定首期目标用户。
2. 明确 MVP 做什么、不做什么。
3. 设计用户使用流程。
4. 设计提醒触发流程。
5. 定义提醒策略和优先级。
6. 补充频控、免打扰、关闭提醒等异常场景。
7. 设计页面或简单原型。
8. 明确 V1 和 V2 的边界。

### 4.2 阶段产出

- MVP 范围清单。
- 用户流程图。
- 提醒决策流程图。
- 页面草图或原型。
- 核心规则表。
- 非目标清单。

### 4.3 完成标志

对任意一个模拟用户，都能解释：

- 系统是否提醒。
- 系统何时提醒。
- 系统通过什么方式提醒。
- 系统为什么作出这个决定。

## 5. 第三阶段：编写 PRD

产品方案确定后，将分析和决策整理成正式需求文档。

### 5.1 PRD 建议内容

1. 背景与问题。
2. 已知数据和关键假设。
3. 产品目标与非目标。
4. 目标用户。
5. 用户故事。
6. 核心流程。
7. 功能需求。
8. 提醒规则。
9. 异常和边界场景。
10. 数据埋点。
11. 指标与实验方案。
12. 验收标准。
13. MVP 与后续规划。
14. 风险和限制。

### 5.2 阶段产出

- 可提交的 PRD 初稿。

### 5.3 完成标志

- 开发人员只阅读 PRD，就能理解应该实现什么。
- 测试人员只阅读 PRD，就能理解应该如何验证。
- 每个关键假设和方案取舍都有明确说明。

## 6. 第四阶段：定义验收标准

验收标准应该在技术设计和编码前完成。

### 6.1 需要完成的工作

1. 为每个核心功能定义正常流程。
2. 定义异常流程。
3. 定义业务边界。
4. 定义输入、操作和预期结果。
5. 建立需求与测试的对应关系。

### 6.2 验收标准示例格式

可以使用 Given/When/Then：

```text
Given 用户今日任务尚未完成
And 用户允许接收提醒
When 到达系统计算出的提醒时间
Then 系统生成提醒
And 保存提醒记录
```

### 6.3 阶段产出

- 验收标准清单。
- 核心测试场景清单。
- 需求追踪表。

### 6.4 完成标志

每一项核心需求都有明确、可观察、可测试的预期结果。

## 7. 第五阶段：技术方案设计

产品需求和验收标准明确后，再决定如何实现。

### 7.1 需要完成的工作

1. 选择技术栈。
2. 设计整体架构。
3. 划分前端、后端和核心业务模块。
4. 设计数据模型。
5. 设计提醒决策引擎。
6. 设计接口。
7. 设计调度方式。
8. 设计幂等和重复提醒控制。
9. 设计行为事件和埋点。
10. 明确 Demo 简化项与生产方案的区别。

### 7.2 阶段产出

- 技术架构图。
- 模块职责说明。
- 数据模型。
- API 清单。
- 状态流转说明。
- 核心时序图。
- 关键技术取舍记录。

### 7.3 完成标志

每个功能都能找到对应的模块、数据和接口，不存在编码到一半才决定核心实现方式的情况。

## 8. 第六阶段：开发任务拆分

技术方案完成后，将开发工作拆成可以独立执行和验收的任务。

### 8.1 推荐任务顺序

1. 初始化项目和开发工具。
2. 定义领域模型和测试数据。
3. 实现提醒决策引擎。
4. 实现数据存储。
5. 实现提醒决策接口。
6. 实现调度或时间模拟。
7. 实现提醒发送模拟。
8. 实现行为事件记录。
9. 实现前端任务页面。
10. 实现提醒设置页面。
11. 实现决策结果或提醒记录展示。
12. 补充 README 和演示数据。

### 8.2 每个开发任务需要包含

- 输入。
- 输出。
- 前置依赖。
- 验收条件。
- 优先级。
- 预计时间。

### 8.3 优先级划分

- **Must**：缺少后无法形成核心业务闭环。
- **Should**：能够显著提升方案完整度，但时间不足时可以降级。
- **Could**：用于展示扩展能力，不影响核心功能成立。

### 8.4 阶段产出

- 开发任务列表。
- 实现顺序。
- MVP 优先级。
- 时间预算。

### 8.5 完成标志

任意时刻时间不足时，都知道应该删除哪些低优先级内容，并且不会破坏核心业务闭环。

## 9. 第七阶段：编码实现

编码应围绕业务闭环逐步推进，不建议先写完全部后端，再统一编写前端。

### 9.1 核心业务闭环

```text
用户与任务数据
→ 生成提醒决策
→ 模拟发送
→ 记录行为事件
→ 页面展示结果
```

### 9.2 推荐开发顺序

1. 先实现纯函数形式的决策引擎。
2. 为决策引擎补充单元测试。
3. 接入数据模型。
4. 接入 API。
5. 接入调度或模拟时间。
6. 接入发送渠道模拟。
7. 实现前端操作和展示。
8. 打通完整演示流程。
9. 每完成一个模块就执行相关测试。

### 9.3 阶段产出

- 可运行的 MVP。
- 核心自动化测试。
- 演示数据。

### 9.4 完成标志

项目能够完整演示一次：

```text
输入用户状态
→ 作出提醒决策
→ 发送提醒
→ 记录用户行为
→ 展示处理结果
```

## 10. 第八阶段：测试

测试分为单元测试、集成测试、功能测试和探索性测试四层。

### 10.1 单元测试

重点验证：

- 用户分层计算。
- 提醒时间计算。
- 决策规则优先级。
- 免打扰逻辑。
- 每日频控。
- 幂等控制。
- 边界时间。
- 默认策略。

### 10.2 集成测试

重点验证：

- API 与决策引擎的集成。
- 数据存储与状态更新。
- 调度与发送模块的协作。
- 事件记录与策略版本。
- 任务完成后取消提醒。

### 10.3 功能测试

重点验证完整用户场景：

- 自驱型用户。
- 被动型用户。
- 流失型用户。
- 通知权限关闭。
- 免打扰时段。
- 已完成任务。
- 重复调度。
- 发送失败。

### 10.4 探索性测试

主动尝试以下异常操作：

- 快速重复点击。
- 修改系统时间。
- 刷新和重新启动。
- 使用缺失数据。
- 传入非法参数。
- 测试临界时间。
- 重复执行相同任务。

### 10.5 阶段产出

- 测试报告。
- 测试执行结果。
- 缺陷清单。
- 覆盖率结果。

### 10.6 完成标志

核心流程、边界流程和失败流程都有明确的验证证据。

## 11. 第九阶段：缺陷修复与回归

### 11.1 需要完成的工作

1. 按严重程度整理缺陷。
2. 优先修复阻断和严重问题。
3. 为每个缺陷修复补充回归测试。
4. 重新执行核心自动化测试。
5. 重新执行端到端演示场景。
6. 更新已知限制。

### 11.2 阶段产出

- 缺陷记录。
- 修复记录。
- 回归测试结果。
- 已知问题列表。

### 11.3 完成标志

- 不存在阻断项目运行或核心演示的缺陷。
- 严重缺陷已经修复并通过回归测试。
- 未修复问题均已记录影响范围和规避方式。

## 12. 第十阶段：质量准出

提交前逐项检查：

- PRD 是否完整。
- 核心功能是否全部可运行。
- 验收标准是否全部通过。
- 自动化测试是否通过。
- 是否存在严重缺陷。
- 全新环境能否完成安装和启动。
- README 是否准确。
- 演示数据是否可用。
- 是否包含密钥或本地绝对路径。
- ZIP 是否包含无关依赖或缓存。
- PRD、代码和测试是否保持一致。

### 12.1 完成标志

换一台机器、换一个评审者，不需要作者口头解释也能运行和理解项目。

## 13. 第十一阶段：最终提交

### 13.1 推荐交付结构

```text
项目根目录
├── README.md
├── PRD.md
├── AI_USAGE.md
├── package.json / go.mod
├── src/
├── tests/
├── docs/
│   ├── architecture.md
│   ├── test-report.md
│   └── screenshots/
└── demo-data/
```

### 13.2 提交前操作

1. 删除密钥、缓存、日志和无关依赖。
2. 按照 README 从零执行一次项目。
3. 执行全部自动化测试。
4. 检查 PRD 和代码实现是否一致。
5. 按照平台要求的名称打包 ZIP。
6. 解压 ZIP 后再次执行安装、启动和测试。
7. 确认无误后再正式提交。

由于平台只允许提交一次，最终上传前必须完成解压验证。

## 14. 建议的当前推进顺序

当前应先完成“第一阶段：需求分析”。在开始编码前，应依次完成：

1. 需求分析。
2. 产品方案设计。
3. PRD。
4. 验收标准。
5. 技术方案。
6. 开发任务拆分。

完成以上阶段后，再进入编码、测试和质量准出。

## 15. 阶段检查总表

| 阶段 | 核心问题 | 主要产出 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 需求分析 | 为什么做、为谁做 | 事实、假设、问题和目标 | 能清楚定义用户、问题和指标 |
| 产品方案 | 做什么、不做什么 | MVP、流程、规则和原型 | 任意用户场景都有确定决策 |
| PRD | 如何完整表达需求 | PRD 初稿 | 开发和测试都能理解需求 |
| 验收标准 | 怎么判断做对了 | 验收清单、测试场景 | 每项需求都可观察和测试 |
| 技术方案 | 如何实现 | 架构、数据、接口和时序 | 每项功能都有技术落点 |
| 任务拆分 | 先做什么、后做什么 | 任务列表和优先级 | 可按任务直接开始编码 |
| 编码实现 | 如何形成业务闭环 | 可运行 MVP | 主流程可以完整演示 |
| 测试 | 如何证明质量 | 测试结果和缺陷清单 | 主流程、边界和失败路径通过 |
| 缺陷修复 | 如何消除风险 | 修复记录和回归结果 | 无阻断或严重缺陷 |
| 质量准出 | 是否可以提交 | 准出检查结果 | 全新环境可以独立运行 |
| 最终提交 | 如何让评审顺利体验 | PRD、代码和说明文档 | ZIP 解压验证通过 |
