背景比方案更重要。通过背景说明价值收益，没价值的项目不应浪费资源。
内部平台产品最常见的收益是“降本增效”，即解决某些业务流程中的问题，通过业务流程改变 / 增加系统工具，简化、甚至完全改变某些流程和角色，降低组织成本、提升运转效率。

• 结论

  当前 PRD 的 P0/P1/P2 边界已经比之前清晰，站内提醒、后台、激励召回等没有再混入 P0。但从产品评审角度看，仍有几处不能直接冻结，主要问题集中在指标口径、数据前提、回流场景价值和 P0 范围偏大。

  高优先级问题

  1. 指标口径前后不一致

  PRD 第 2.3 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:60)声明“所有比例指标按用户数去重”，但到达率又定义为：

  > 成功送达 Push 的数量 / Push 发送数量

  这实际上是发送量口径，不是用户数口径。

  另外，任务开始率、任务完成率都以“成功触达用户”为分母。这样会产生选择偏差：不同策略的送达能力不同，只有成功送达的人才进入分母，不能准确衡量实验组整体效果。

  建议明确区分：

  - 结果指标：按实验分组后的全部符合条件用户统计，采用意向性分析。
  - 渠道指标：发送量、送达量、打开量可以按消息量统计。
  - 触达后指标：可以作为辅助指标，但不能作为唯一的任务完成效果依据。

  2. PRD 依赖了题目没有明确提供的用户行为数据

  PRD 第 3.3 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:135)要求读取：

  - inactive_days
  - days_since_last_open
  - complete_days_7d
  - reminder_attributed_complete_days_7d
  - open_days_prev_7d

  但题目原文只明确提供了整体用户比例、Push 数据和活跃时间段，没有确认已有：

  - 用户级 App 打开历史；
  - 本次打开前的 last_open_at；
  - 任务开始/完成时间；
  - 提醒归因完成事件；
  - Push 送达、打开回执；
  - AppOpened 同步事件。

  PRD 将这些能力直接写成“已有历史行为数据”或可读取数据，存在把设计假设写成既有能力的问题。尤其是回流判断依赖“本次打开前的上一次打开时间”，这是本期 P0 的硬依赖。

  建议在 PRD 中增加“上线前必须确认的业务数据依赖”，并明确：

  - 数据不存在时的降级策略；
  - 数据延迟或读取失败时是否继续提醒；
  - AppOpened 事件由谁产生；
  - reminder_attributed_complete_days_7d 如何归因。

  3. P0 仍然偏大，“稍后提醒”会显著扩大影响范围

  PRD 第 5.3、7.7 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:266)保留了：

  - Push 点击后的 App 交互；
  - 一小时后再次排程；
  - 每天最多 2 次 Push；
  - 延后提醒不再提供二次入口；
  - 重新检查任务、免打扰、截止时间和频控。

  这已经不是单纯的“智能提醒资格判断”，而是新增了一个 Push 交互闭环和第二次触达策略，涉及 App 点击回传、排程、频控、内容状态和事件链路。

  它不是错误设计，但对 MVP 来说明显扩大了范围。建议二选一：

  - 严格 MVP：先移出“稍后提醒”，只验证一次 Push 的相关性和打开率；
  - 保留 P0：必须把“每天最多 2 次 Push”、用户主动触发不计入系统频控、失败重试和重复点击作为独立的产品确认项。

  中优先级问题

  4. 回流型被列为 P0，但首日实际“不发送任何提醒”

  PRD 第 3.3、5.3、7.2 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:156)规定：

  - 回流首日不发送 Push；
  - 不生成任何 Push 排程；
  - 次日才恢复常规 Push。

  但第 5.3 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:262)又说：

  > 本期 MVP 聚焦当天有未完成任务的被动型学生与回流型学生，在合适时间收到一次受控提醒。

  这两句话存在语义冲突。回流用户首日没有提醒，FR-002 也没有真正执行提醒时间计算。

  建议将表述改为：

  > P0 重点服务被动型用户；回流型用户本期只实现回流识别、首日降温和次日恢复 Push 资格，不承诺回流首日触达。

  同时，FR-002 的用户范围不应直接写“回流型学生”，应明确为“回流次日起的常规 Push 评估”。

  5. 提醒时间规则使用了未定义的输入字段

  PRD 第 7.2 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:328)要求：

  > 优先参考最近任务开始/完成时间，其次参考 App 打开时间。

  但第 3.3.1 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:139)的行为信号表中没有定义：

  - 最近任务开始时间；
  - 最近任务完成时间；
  - 这些数据的统计窗口；
  - 多次任务行为如何取值；
  - 行为数据不足时如何排序。

  这会导致技术方案只能自行补字段或猜测。需要补充信号定义，或者把 P0 简化为“App 活跃时间 + 默认窗口 + 任务截止时间”。

  6. 多个默认值不是题目事实，却被写成已确认决策

  PRD 第 7.2、7.3 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:338)写死了：

  - 默认发送时间 19:30；
  - 兜底时间 17:00；
  - 默认免打扰 21:30–07:00；
  - 智能提醒开关默认开启。

  其中活跃时段 16:00–18:00、19:00–21:00来自题目，但具体 19:30、17:00、21:30–07:00 和默认开启并不是题目原始事实。

  这些可以作为设计假设，但如果没有人工明确确认，不应在第 13.1 节写成“已确认事项”。至少应标记：

  > 当前为 MVP 默认假设，需上线前通过用户设置和数据验证。

  7. 失败重试和“不能再次触达”的表达冲突

  AC-007 (code-repo-analysis/智能提醒助手/需求拆解/验收标准/验收标准.md:65)同时要求：

  - 发送失败最多重试一次；
  - 不在当天追加第二次触达。

  重试本身会产生第二次发送尝试，需要区分：

  - 第二次发送尝试；
  - 第二条独立提醒；
  - 第二次成功触达。

  建议改为：

  > 明确失败最多重试一次，但不得新增独立排程或第二条业务提醒；重试必须复用同一幂等键。

  8. 护栏指标定义不完整

  PRD 第 2.3 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:69)中的以下指标没有分母、统计周期和用户去重规则：

  - 重复提醒率；
  - 通知关闭率；
  - 投诉率；
  - 卸载率；
  - 退订率。

  目前只能作为观察项，不能作为可验收指标。建议明确它们全部属于上线后监控，不进入 MVP 验收，或者补齐计算口径。

  9. 实验字段进入 P0 埋点，但实验方案又被排除在 P0 外

  PRD 第 10.2 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:493)把 experiment_group 作为公共字段，但第 13.1 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:655)又说实验分流比例、周期
  和上线阈值属于非 P0。

  需要明确：

  - experiment_group 是否由既有实验平台提供；
  - 本期是否真的支持实验分组；
  - 如果没有实验平台，字段应为可选，不应成为 P0 的实现前提。

  低优先级问题

  10. 用户流程存在重复文案

  PRD 第 4.3 节 (code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:213)中“完成全部必做任务”重复出现一次，属于文档质量问题。

  11. 5 稿和 9 稿的确认状态仍有残留不一致

  5 稿仍保留“回流判定窗口与阈值待确认”的表述，而 9 稿第 13.1 节已经写成已确认。5 稿底部还写着“下游待同步文档”，但当前 PRD、验收标准和技术方案实际上已经同步过。

  这不会直接影响实现，但会影响评审者判断哪个文档是最终事实源。

  建议冻结前先处理

  最低限度建议先修正这 5 项：

  1. 统一到达率和完成率的用户/消息口径。
  2. 补齐用户行为数据和 AppOpened 的前置依赖。
  3. 明确回流型首日“不触达”的 P0 定位。
  4. 补齐个性化时间规则的输入字段。
  5. 重新确认“稍后提醒”是否真的要留在 MVP。

  当前 PRD 的结构检查和 AC/技术方案自动回查可以通过，但这些脚本主要检查编号、章节和映射关系，不能替代上述产品逻辑审查。
