# BI 数据链路 · 宣讲讲稿

> 配合 `BI数据链路-流程图.html` 使用。按 HTML 的章节顺序逐段讲，每段都标了时长与"这一段的记忆锚点"。

---

## 〇、开场（1 分钟）

**开场白参考：**

> 今天讲一条链路：一条业务数据从"用户改了一单"到"报表上看见数字"，中间到底走了哪些路。
>
> 我会按四个问题讲——数据**存在哪里**、**怎么进来**、**怎么算出来**、**怎么出结果**。每讲一段，都会说清楚"这段断了会怎样"，因为排障的时候，现象往往长得一模一样，但根因完全在不同的段。

**先给结论（指着 HTML 首页的蓝色横幅讲）：**

> 整条链路一句话：业务库数据一变，事件经消息队列通知数仓，数仓把增量拉到 ClickHouse 明细层，再发一个计算事件，聚合服务找出受影响的图，把结果写进聚合层。**用户查报表时读的是预先算好的结果，不是现算。**
>
> 这一句话解释了 BI 的全部脾气：为什么它快，为什么它会有延迟，为什么它偶尔会"对不上"。

---

## 一、数据存在哪里（4 分钟）

**记忆锚点：配置在 PG，数据在 CH，两者不在一个库。**

讲三层递进：

1. **先讲"三个库"**（指着四张卡片）
   - PostgreSQL 管**配置**：报表定义、维度规则、目标、权限表。
   - ClickHouse 管**数据和聚合结果**：报表真正查的就是这层。
   - 另一个 PostgreSQL 管**引擎元数据**：最关键是**拓扑表**——它决定一次查询用哪个槽位、读哪张表。
   - 再加一个日志库，排障用。

2. **补两个硬约束**（指着红色提示框）
   - BI 数据库是**双方言**，查的时候必须显式说清查的是 ClickHouse 侧还是 PostgreSQL 侧。
   - 两个库之间**不能 JOIN**，所以对数只能两边分别查、再人工比对。

3. **点出设计后果**（这是这一节的落点）
   > 「改了配置」和「数据生效」是**两条独立链路**。配置改完不会自动写进物理表——后面讲的"配置改了但报表没变"，根源就在这里。

**这一段要留给听众的印象**：BI 不是"一个数据库"，是三个库各管一段。

---

## 二、数仓分层（3 分钟）

**记忆锚点：ODS → DWD → DWS，报表只查 DWS。**

- 顺着分层图从上往下讲一遍，每层一句话就够：
  - **ODS**：从业务库同步过来的明细，是数据入口。
  - **DWD**：整理成增量 ID 宽表，方便聚合。
  - **DWS**：**聚合结果就落在这里，报表查的就是它。**
  - 应用统计层：排行榜这类预置分析直接读。
  - 拓扑与运行时层：排障必经之路。

- **重点讲一个细节**：日志聚合表有 **v1 到 v7 七个版本**。
  > 这不是历史包袱，是**列式 schema 演进的证据**——新增指标类型时扩展新表，而不是去改老表。这对线上稳定性很关键。

- **然后讲聚合表的列**（这是理解后面一切问题的钥匙）：
  - 维度值按**固定槽位**落列：`dim_string_1`…`dim_string_N`。
  - 指标落成 ClickHouse 的**聚合状态列**：`agg_sum_N` / `agg_count_N` / `agg_uniq_N`。
  - **关键一句**：聚合列存的是**中间态，不是最终值**，直接查出来是乱码，必须用 `finalizeAggregation()` 解码。很多"数据错乱"的误报就出在这里。

## 三、数据怎么进来（5 分钟）

**记忆锚点：每一步都是异步的。**

- 顺着六步流程讲。中间重点强调**第 6 步**：
  > 第 5 步写完明细，第 6 步发一个"计算事件"，通知聚合层开始算。**这一步是"同步"和"计算"的分界线**——前面是搬数据，后面是算数据。

- **讲"四种时间戳对齐法"**（这是这一段最实用的方法论）：
  > 用户说"数据没更新"，不要凭感觉。取四个时间点：源数据写入时间、同步消费时间、数据到达 ClickHouse 的时间、聚合完成时间。**差值落在哪一段，问题就在哪一段。**

- **补一个现场能用的细节**：
  > 这一步有现成接口——上层服务会调数仓的「查询最近计算时间」，前端拿它提示用户"数据更新到几点"。**用户看到的时间提示，就是这条链路算出来的。**

- **三条支线快速带过**，但第三条要停一下：
  - 手动补算：消息丢了或算失败时运维手动补触发。
  - 视图变更建表：用户保存图时，数仓**先建表、暂不填数**。
  - **字段一致性比对**：检查"报表字段配置 vs ClickHouse 表结构"是否一致。
  > 第三条很关键：**配置改了不会自动同步到物理表**，要靠这个比对接口发现差异后触发重建。这就是下一节"槽位漂移"的伏笔。

- **最后补两条容易吵架的**：
  - 全量补数如果没先停增量，**旧快照会覆盖新数据**。
  - 计算字段重算是**另一条独立链路**，"汇总值几分钟没变"是最终一致性没收敛，**不是计算 Bug**。

## 四、数据怎么算出来（6 分钟，本节为重点）

**记忆锚点：三份元数据决定读哪一列。**

- **先讲三件套**：
  - 字段槽位映射：业务字段 ↔ 物理槽位。
  - 聚合规则：哪些字段参与、怎么分配槽位。
  - 拓扑表：决定查询用哪些槽位、读哪张表。

- **然后讲那个必须记住的因果链**（指着红色框，放慢语速）：
  > **字段配置变更 → 槽位重新分配 → 拓扑未重建 → 查询用错槽位 → 统计值错误或全零。**
  >
  > 这是 BI 最经典的一类问题，从 2019 年一直持续到 2024 年。根因是规则增删改时的**并发竞争导致槽位分配冲突**，还有停用/启用规则共享槽位。

- **讲聚合实计算的五步**，其中两步要点出来：
  - 第 3 步"查拓扑找受影响视图"用了**分片 + 线程池** → 解释了为什么大批量变更时会**互相争抢资源**。
  - 第 4 步有**全量 / 增量**两种策略 → 解释了为什么有时延迟明显更长。

- **讲指标编译表**，重点两行：
  - 金额用 **Decimal** 不用 Float。
  - 去重分**精确**和**近似**：近似去重走 HyperLogLog，**有 1–2% 误差**。**和业务对不上时，先查这里，再怀疑数据。**

- **讲六个偏差来源**，可以只挑三个最有故事性的：
  - **槽位重复**：差值不是"少了"而是"多了不相关的值"。
  - **主题未检测开启**：**统计图全部显示 0**。
  - **多对多重复计数**：客户数被放大数倍。

- **最后两个高发区**（时间口径 + 拼表），时间紧可以只讲拼表：
  - 时间：默认 UTC、跨年周归属、闰年对齐，三个坑。
  - 拼表：**低基数笛卡尔积爆炸**——只用"客户名称"做关联维度，会产生平方级膨胀。修复要**补高基数唯一键**。

## 五、查询怎么出结果（5 分钟）

**记忆锚点：拓扑 → 权限 → 渲染，三段断裂现象不同。**

- **先讲三段式**，每段一句：
  - 拓扑段：读定义、查拓扑、生成 SQL。断了 → 提示"初始化中""数据量过大"。
  - 权限段：在 SQL 内按权限编码过滤。断了 → **框架在、图在、只是没数（`--`）**。
  - 渲染段：序列化、绘制。断了 → 白屏、样式错乱。

- **然后讲三条消歧规则**（这一页最容易被点头）：
  > 白屏 + 控制台有 JS 报错 → 前端。
  > 一直转圈 → 后端超时。
  > **框架正常、图在、只是没数 → 不是白屏，先走权限。**
  >
  > 这条最省事：很多"白屏"工单，其实是权限问题，页面根本没有报错。

- **权限的三层缓存**（讲的时候强调"三个时长不是一个量级"）：
  - 加进部门/角色/用户组：最长 **6 小时**。
  - 后台勾对象功能/数据权限：最长 **2 小时**。
  - 单张图/驾驶舱授权：**10–30 分钟**。
  > 窗口内属于**设计如此**。这是"改完权限看不到图"最大的误报来源——很多人拿 10 分钟的期待去等 6 小时的缓存。

- **性能**：四个观察指标 + 四类高频问题，快速带过即可。

- **收尾讲已知盲区**：
  > ClickHouse 查询日志**可能没记录全部查询**。查不到不代表没发生，要下沉到容器级日志。这也是我们排障时经常踩的坑。

## 六、端到端总时序 + 速查表（2 分钟）

- 时序表**不用逐行念**，挑第 6、9 两行：
  > 第 6 行是聚合计算，第 9 行是权限过滤——这两行对应最常被误报的两类问题。

- **速查表**用于收尾或答疑，可以只念三行：
  - 为什么报表快 → 读的是预聚合结果。
  - 为什么改配置后报表没变 → 配置在 PG、数据在 CH，不会自动同步。
  - 为什么"没数"不是白屏 → 走权限口径。

## 七、结束语（30 秒）

> 回到最开始那句话：BI 的数据是**算出来的、存起来的**，不是**查出来的**。
>
> 所以遇到问题先问一句：**是数据没进来，还是没算完，还是算错了，还是被人挡住了？** 这四个问题，正好对应今天讲的四段链路。

## 八、可能被追问的问题与应答

| 追问 | 应答要点 |
| --- | --- |
| 为什么不直接从业务库查，非要同步一份？ | 业务库要扛交易，分析查询会拖垮它；而且分析需要宽表和多对象关联，列存数仓在扫描和聚合上有数量级的优势。 |
| 为什么要有聚合层，不直接查明细？ | 统计图/报表的查询模式是"按维度汇总"，预聚合把计算从查询时前移到写入时，这是 BI 能秒开的原因。 |
| 数据延迟多久算正常？ | 取决于同步频率与聚合窗口。要点是先确认"是否还在聚合窗口内"，窗口内属于正常延迟，不要当故障。 |
| 为什么统计图全是 0？ | 先查主题是否被检测开启（底层主题注册/发现机制的已知缺陷），再查拓扑槽位是否漂移。不要先怀疑数据。 |
| 为什么聚合值查出来是乱码？ | 聚合列存的是 ClickHouse 的聚合中间态，必须用 `finalizeAggregation()` 解码。 |
| 为什么同一个指标两次查询结果不一样？ | 检查去重函数：近似去重走 HyperLogLog 有 1–2% 误差；也可能数据正在聚合窗口内，结果还在收敛。 |
| 改完权限为什么还看不到？ | 先判是哪一层：组织成员 6 小时、PaaS 权限点 2 小时、单图授权 10–30 分钟。窗口内是设计如此。 |
| 报表"白屏"是 BI 的问题吗？ | 先分三类：白屏+控制台报错=前端；一直转圈=后端超时；**框架在但没数=权限**。三类根因完全不同。 |
| 数据对不上，怎么查？ | 先确认范围（源有仓无 / 仓有源无 / 行数一致但值不同），再沿链路追因。注意 PG 与 CH 无法 JOIN，只能分别查后比对。 |
| 你说的这些数字有实测依据吗？ | 阈值来自既有知识库与实战归纳，属于经验基线，不是实时测量。要下结论还是要按当次环境的实际数据来。 |
