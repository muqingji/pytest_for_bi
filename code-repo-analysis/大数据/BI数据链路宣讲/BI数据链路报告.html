总览

BI 的数据不是"业务库连过来直接查"，而是一条事件驱动、分层落库、预聚合加速的链路。

业务库数据变更 → 变更事件（MQ） → 数仓读增量 → 写入 ClickHouse 明细层 → 发计算事件 → 聚合服务算受影响视图 → 写入 ClickHouse 聚合层 → 报表出数

用户查报表时读的是预先算好的聚合结果，不是现算。这一句话解释了 BI 的全部特性。

快

报表读预聚合结果，不做全表扫描。

有延迟

同步与聚合都是异步的，天然存在时间差。

会"对不上"

配置与数据分属不同库，聚合还有窗口与状态。

排查要分层

断在哪一段现象都一样，根因却完全不同。

① 数据存在哪里

三个库分工，另有一个日志库。记住一句：配置在 PostgreSQL，数据在 ClickHouse，两者不在同一个库。

PostgreSQLbi · 业务库
  • 报表 / 统计图定义
  • 维度规则、目标规则
  • 数据权限表
  • 视图字段 / 筛选 / 属性
ClickHousebi · 数仓
  • ODS / DWD 明细
  • DWS 聚合结果
  • 日志聚合（多版本）
  • 排行榜、用户行为统计
PostgreSQLbi-system · 引擎元数据
  • 拓扑表（决定读哪列）
  • 聚合规则、字段槽位映射
  • 指标元数据
  • 调度任务、同步日志
ClickHousebiz-app-log · 日志
  • 数仓同步服务日志
  • 聚合服务运行日志
  • 排障取证入口
两个必须记住的约束
1）BI 数据库是双方言：查询时必须显式指定「ClickHouse 侧」或「PostgreSQL 侧」，不指定会命中错误的库。
2）PostgreSQL 与 ClickHouse 无法 JOIN：对数类排查只能两个库分别查，再在分析侧比对。
设计后果：「改了配置」和「数据生效」是两条独立链路。配置改完并不会自动写进物理表——这正是一大类"配置改了但报表没变"问题的根源。

③ 数据怎么进来

整条链路每一步都是异步的——这就是"数据改了但报表还没变"的根本原因。

1业务库数据变更新增客户、改订单状态
→
2变更事件投递上游经消息队列投递变更事件，支持灰度分流
→
3数仓消费事件解析业务库 / 数仓连接与 schema
→
4分页读增量按「业务库+schema」查同步配置、算批次号，按修改时间 / 主键读 PG 增量
→
5写入 CH 明细层先反查历史数据，再批量写入，按分区路由
→
6发送计算事件通知聚合层开始计算 —— 同步与计算的分界线

定位延迟：四种时间戳对齐法

不要凭感觉，取四个时间点，差值落在哪一段就是哪一段的问题。

① 源数据写入业务库已落库
取不到 = 源头问题，BI 无解
→
② 同步消费数仓已消费
滞后 = 事件没到 / 消费阻塞
→
③ CH 到达已写入明细层
滞后 = 写入被拒 / 合并积压
→
④ 聚合完成聚合已算完
滞后 = 聚合失败 / 窗口未关 / 重试中
这一步有现成接口：上层服务会调用数仓的「查询最近计算时间」接口，前端用它提示用户"数据更新到几点"。用户看到的时间提示，就是这条链路算出来的。

三条容易忽略的支线

支线触发方式用途
手动补算运维接口消息丢了或计算失败时，手动补触发一次聚合
视图变更建表用户保存报表 / 统计图 → 消息队列数仓预建 ClickHouse 聚合表（先建表，暂不填数）
字段一致性比对上层服务调用检查"报表字段配置 vs ClickHouse 表结构"是否一致，不一致则重建

第三条是理解"槽位漂移"的关键：配置改了不会自动同步到物理表，要靠比对接口发现差异后触发重建。

全量补数 vs 增量同步

历史补数时若未先停增量任务，全量写入的旧快照会覆盖增量已同步的新数据。

  • 全量写影子表，对账一致后再原子切换表名
  • 增量按单调递增版本号比较，旧快照不回退新版本

计算字段重算：另一条独立链路

明细批量变更后，重算任务经调度进入队列，由计算服务执行后回写。高并发下会限流并转发备用队列。

典型表现：从对象已保存，但主对象汇总值几分钟没变。这是最终一致性未收敛，不是计算 Bug。

④ 数据怎么算出来

聚合不是"对着原始表跑 SQL"，而是由三份元数据决定读哪一列、用哪个槽位。

元字段槽位映射业务字段 ↔ 物理槽位
+
元聚合规则哪些字段参与、如何分配槽位
+
元拓扑表决定查询用哪些槽位、读哪张表
=
!槽位漂移风险配置变更 → 槽位重分配 → 拓扑未重建 → 读错列
最经典的一类缺陷：字段配置变更 → 槽位重新分配 → 拓扑未重建 → 查询用错槽位 → 统计值错误或全零。该问题从 2019 持续到 2024，根因是规则增删改时的并发竞争导致槽位分配冲突，以及停用 / 启用规则共享槽位。

聚合实计算的执行路径

1加分布式锁防止同一批次重复计算
→
2构建变更上下文确定本批次涉及哪些对象与字段
→
3查拓扑找受影响视图得到需重算的统计图 / 报表清单
→
4生成并执行聚合 SQL全量或增量，写入 CH 聚合表
→
5更新状态与日志失败自动重试，有明确次数上限

第 3 步的"分片 + 线程池"设计，解释了为什么大批量变更时会互相争抢资源；第 4 步的"全量 / 增量"两种策略，解释了为什么有时延迟明显更长。

指标如何编译成聚合状态

聚合类型物理列ClickHouse 类型注意事项
求和agg_sum_NAggregateFunction(sum, Nullable(Decimal))金额用 Decimal，不用 Float
计数agg_count_NAggregateFunction(sum, Nullable(Int64))注意 COUNT(*) 与 COUNT(col) 的 NULL 差异
精确去重agg_uniq_NAggregateFunction(uniqExact, …)精确
近似去重——uniq() → HyperLogLog约 1–2% 误差，与业务对不上先查这里

计算偏差的六个来源

来源机理典型现象
聚合消费阻塞部分变更事件未被聚合统计图与前台数字不一致
输入数据丢失变更日志在某时间窗丢失，输入不完整统计图条数比明细少
归属部门粒度平铺与层级的 GROUP BY 处理不当选了多个子部门只显示一个
槽位重复多字段共享同一槽位，存值互相覆盖差值不是"少"，而是"多了不相关的值"
主题未检测开启底层主题注册 / 发现机制缺陷统计图全部显示 0
多对多重复计数计数未去重客户数被放大数倍

时间口径与拼表：另外两个高发区

时间口径

  • 时间转换默认 UTC，中国时间必须显式指定时区；按日 / 周 / 月截断时时区参数极易漏
  • 跨年周归属：底层用 ISO-8601 周，跨年那一周被判给下一年，按自然年过滤时整周丢失
  • 闰年同比环比：跨闰年 2 月时日期对齐会错位

拼表（多表拼接）

  • 低基数笛卡尔积爆炸：仅用"客户名称"这类低基数高重复字段做唯一关联维度，产生平方级膨胀，内存超限或查询超时
  • 修复要求：补充高基数唯一键（业务主键 + 单据主键）作为联合维度
  • 一对多行膨胀：多对多未去重导致行数翻倍，需先聚合再 JOIN

⑤ 查询怎么出结果

一次统计图点击，走的是「拓扑 → 权限 → 渲染」三段式。三段断裂现象看起来都是"报表没数据"，但根因完全不同。

① 拓扑段
  • 读视图定义
  • 查拓扑表确定槽位与目标表
  • 生成 ClickHouse SQL
断裂现象：页面提示"初始化中""数据量过大"
② 权限段
  • 在 SQL 内按权限编码过滤行
  • 报表走主业务对象权限
  • 统计图走主题对象权限
断裂现象：框架正常、图在、只是没数（--）
③ 渲染段
  • 结果序列化
  • 前端组件绘制
  • 导出 / 订阅走同一份结果
断裂现象：白屏、样式错乱
宣讲必讲的三条消歧规则
· 白屏 + 浏览器控制台有 JS 报错 → 前端问题
· 一直转圈 → 后端 API 超时
· 框架正常、图在、只是没数（--）→ 不是白屏，先走权限口径

权限：三层缓存，三个时长

"改完权限看不到图"是最大的误报来源——因为不同层级的变更，生效窗口根本不是同一个量级。

变更类型生效窗口
把员工加入部门 / 角色 / 用户组最长 6 小时
后台给角色勾选对象功能 / 数据权限最长 2 小时
单张图 / 驾驶舱授权给某人10–30 分钟

窗口内属于设计如此，超窗口才需要深入排查。另：若数仓侧权限编码为空，非管理员用户看不到统计数据；"是否包含离职员工"配置只作用于负责人及负责人主属部门类字段，不管创建人、自定义人员、归属部门。

性能：瓶颈通常在扫描量与内存

看四个指标

  • 查询耗时：报表正常基线在 10 秒以内
  • 扫描行数 vs 返回行数：比值过高 = 过滤不足或分区裁剪失效
  • 内存峰值：是否接近上限（OOM 前兆）
  • 是否命中预聚合：未命中说明在现算

四类高频问题

  • DDL 并发超时：大表加列需重建数据块，并发互相持锁
  • 双维度查询：计算量指数级增长，需预聚合优化
  • 大文本分组 OOM：数百万行可消耗数十 GB 内存
  • 合并操作并发：强制合并打满 CPU，影响全局

三种输出形态与各自的坑

形态典型故障
页面渲染白屏（前端）/ 转圈超时（后端慢查询）/ 框架在没数（权限）
导出大文件内存溢出、切片丢失、百万行触发网关超时、高基数列 OOM
订阅推送串行渲染导致大批量推送延迟数小时；当天改推送时点次日才生效
已知盲区：ClickHouse 查询日志可能因配置限制未记录所有查询，线上频繁出现"日志不全导致排查困难"。此时要下沉到容器级日志或上层服务日志。另外该日志若不清理会打满系统盘。

⑦ 速查表

宣讲时最容易被追问的几个机制，一句话备好。

机制一句话解释
为什么报表快读的是预聚合结果（聚合状态列），不是现算
为什么会有延迟同步、聚合、刷新全是异步链路，天然有时间差
为什么聚合值查出来是乱码聚合列存的是 ClickHouse 中间态，必须 finalizeAggregation() 解码
为什么改配置后报表没变配置在 PG、数据在 CH，改配置不会自动改物理表，要靠拓扑重建 + 字段比对
为什么统计图全 0先查主题是否被检测开启，再查拓扑槽位是否漂移
为什么改完权限看不到图权限有三层缓存三个时长，窗口内是设计如此
为什么"没数"不是白屏框架在、图在、只是没值 → 走权限口径；白屏通常是前端 JS 报错
为什么金额有时翻倍折叠引擎后台合并未完成前的重复计数，查询端要注入折叠逻辑
为什么日志查不到ClickHouse 查询日志可能未记录全部查询，需下沉到容器级日志

⑧ 风险与治理

按数据域划分的结构性风险，以及对应的治理方向。

风险域结构性风险治理方向
存储小 Part 堆积、副本只读、Mutation 堆积写入端攒批；废弃单条更新，改版本号追加写入
