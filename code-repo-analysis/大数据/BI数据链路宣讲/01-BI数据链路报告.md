## 一、总览：一句话看懂

BI 的数据不是"业务库连过来直接查"，而是**一条事件驱动、分层落库、预聚合加速的链路**：

> 业务库数据一变 → 变更事件经消息队列通知数仓 → 数仓把增量拉到 ClickHouse 明细层 → 再发一个计算事件 → 聚合服务找出受影响的统计图 → 把聚合结果写进 ClickHouse 聚合层 → 用户查报表时读的是**预先算好的聚合结果**，不是现算。

理解这条链路，就理解了 BI 的四个特性：

| 特性 | 原因 |
| --- | --- |
| **快** | 报表读的是预聚合结果，不是全表扫描 |
| **有延迟** | 同步和聚合都是异步的，天然存在时间差 |
| **会"对不上"** | 配置（PostgreSQL）与数据（ClickHouse）分离，且聚合有窗口与状态 |
| **排查要分层** | 断在哪一段，现象看起来都一样（"报表没数"），根因完全不同 |

## 二、数据存在哪里

### 2.1 三个库，各管一段

BI 的数据**不在一个库里**，而是三个库分工，另有一个日志库：

| 数据域 | 引擎 | 职责 | 典型内容 |
| --- | --- | --- | --- |
| `bi`（PostgreSQL） | PostgreSQL | BI 业务配置与元数据 | 报表/统计图定义、维度规则、目标、权限表 |
| `bi`（ClickHouse） | ClickHouse | **数仓与聚合结果** | 聚合数据、日志聚合、宽表、排行榜 |
| `bi-system`（PostgreSQL） | PostgreSQL | 同步与聚合引擎元数据 | 拓扑表、聚合规则、调度任务 |
| `biz-app-log` | ClickHouse | 服务运行日志 | 数仓/同步服务日志 |

**必须记住的一条硬约束**：`bi` 是**双方言 biz**，使用时必须显式指定 `bi-clickhouse` 或 `bi-postgresql`。不指定会命中错误的库。[字典]

**这个设计带来一个关键后果**：配置和数据**异构分离**——"改了配置"和"数据生效"是两条独立的链路，而且 PostgreSQL 与 ClickHouse 之间**无法 JOIN**，对数类排查只能在两个库分别查、再在分析侧比对。[字典] + [推断]

### 2.2 数仓的四层

ClickHouse 侧按数仓标准分层建模，从表命名就能看出层次：[代码] + [字典]

| 层 | 职责 | 代表表 |
| --- | --- | --- |
| **ODS 明细层** | 从业务库同步过来的原始/增量明细 | ODS 明细表、贴源层表 |
| **DWD 明细层** | 增量 ID 宽表，做明细加工 | 增量宽表 |
| **DWS 聚合层** | **报表/统计图真正查询的数据** | 聚合数据表、日志聚合表（多版本）、聚合历史表、同步状态表 |
| **应用统计层** | 面向场景的预置统计 | 排行榜年/季/月/周/日表、用户行为统计表 |

另有一层容易被忽略但很关键：**拓扑与运行时层**——查询日志、视图访问日志、聚合运行日志。排障时几乎是必经之路。[字典]

> **注意 schema 会演进**：日志聚合表存在 v1 到 v7 共七个版本，每版本的聚合状态列组合不同。这是**列式 schema 演进的直接证据**——新增指标类型时按版本扩展新物理表，而不是修改老表。[字典]

### 2.3 聚合表的列为什么长这样

聚合数据主表是整条链路最重要的落点，它的列设计解释了"BI 为什么快、以及为什么会错"：[字典]

| 列族 | 内容 | 说明 |
| --- | --- | --- |
| 归属 | 租户 ID、视图 ID、视图版本 | 一行的身份：哪个租户的哪张图的哪个版本 |
| 时间 | 日期列 | 类型是字符串，比较时必须显式转换为日期 |
| **维度槽位** | `dim_string_1` … `dim_string_N` | 维度值按**固定槽位**落列 |
| **聚合状态** | `agg_sum_N` / `agg_count_N` / `agg_uniq_N` | 类型是 ClickHouse 的 `AggregateFunction` |
| 数据权限 | 权限编码列 | 行级权限过滤靠它 |
| 生命周期 | 生命状态列 | 员工/记录是否有效 |
| 互联 | `out_*` 系列 | 上下游互联企业的下游侧字段 |
| 幂等 | 行哈希列 | 用于批次的插入/覆盖判定 |

**两个必须理解的点：**

- **聚合列是"状态"不是"值"**。它存的是 ClickHouse 聚合中间态（二进制），直接查询出来是乱码，必须用 `finalizeAggregation()` 解码。这是最容易被误判成"数据错乱"的坑。[字典] + [知识库]
- **维度是"槽位化"的**。物理列是固定编号的槽位，业务字段与槽位的映射关系存在元数据库里。所以**改字段配置 = 重新分配槽位 = 物理列语义改变**，这直接引出了后文一整类缺陷。[字典] + [场景]

### 2.4 存储侧的物理约束

ClickHouse 是列存 OLAP 引擎，写入有硬约束，这是"入库慢、报表停更"的结构性原因：[代码] + [场景]

| 约束 | 现象 | 治理方向 |
| --- | --- | --- |
| 高频小批量写入产生大量小 Part | 后台合并追不上，写入被拒绝，甚至副本转只读、复制队列阻塞 | 写入端**攒批**（每 5 秒或满数千条） |
| 异步写入未等落盘确认 | 断电丢失内存缓冲中的最后一批数据 | 核心数据开启落盘确认 |
| 把 OLAP 当 OLTP 用 | 单条 `ALTER UPDATE` 产生重型 Mutation，堆积后磁盘 IO 打满、全量报表超时 | **废弃单条 Mutation**，改版本号追加写入 |
| 折叠引擎的可见性延迟 | 后台异步 Merge 未完成前，查询会**重复计数** | 查询端统一注入 `FINAL` 或折叠逻辑 |

ClickHouse 表引擎主要是 `ReplicatedReplacingMergeTree` / `ReplicatedMergeTree` / `ReplicatedAggregatingMergeTree`，分区策略为 **INC / STOCK / CAL** 三类，并配置 TTL 过期清理，跨租户按多实例路由。[代码]

## 三、数据怎么进来的

### 3.1 主链路

```
业务库数据变更
   ↓ 变更事件（消息队列）
数仓服务消费事件
   ↓ 从业务库（PostgreSQL）分页读增量
写入 ClickHouse 明细层（ODS）
   ↓ 发送「计算事件」
聚合服务（DWS）消费计算事件
   ↓ 聚合计算
写入 ClickHouse 聚合层（DWS）
   ↓ 发送「视图刷新事件」
报表 / 统计图数据就绪
```

这条链路的每一步都是**异步**的，这是"数据改了但报表还没变"的根本原因。[代码]

### 3.2 逐段拆解

**第一段：变更事件进来**

上游（PaaS / CRM）的数据变更经消息队列投递，数仓的变更事件消费者接收。消费者解析出业务库连接、数仓连接、schema 等信息，并支持灰度 topic 分流。[代码]

**第二段：从业务库读增量**

同步服务按「业务库 + schema」查同步配置，计算批次号，然后**分页读 PostgreSQL 的增量数据**（按修改时间或主键过滤）。这一步是"源头"，如果源数据没读到，后面全都是空的。[代码]

**第三段：写进 ClickHouse 明细层**

增量写入器负责批量落库：先反查 ClickHouse 历史数据，再批量写入。写入按分区策略路由，并受 TTL 管理。[代码]

**第四段：发计算事件**

同步完成后，同步服务组装计算消息（含批次号等）发到消息队列，通知聚合层开始计算。**这一步是"同步"与"计算"的分界线**。[代码]

### 3.3 定位延迟：四种时间戳对齐法

拿到"数据没更新"，不要凭感觉，直接取四个时间点，差值落在哪一段就是哪一段的问题：[知识库]

| 时间点 | 含义 | 取不到说明 |
| --- | --- | --- |
| 源数据写入时间 | 业务库已落库 | 源头问题，BI 无解 |
| 同步消费时间 | 数仓已消费 | 事件没到 / 消费阻塞 |
| ClickHouse 到达时间 | 已写入明细层 | 写入被拒 / 合并积压 |
| 聚合完成时间 | 聚合已算完 | 聚合失败 / 窗口未关闭 / 重试中 |

其中"聚合算到几点"是有现成接口的——上层服务会调用数仓的「查询最近计算时间」接口，前端用它提示用户数据更新时间。[代码]

### 3.4 另外三条容易忽略的支线

| 支线 | 触发方式 | 用途 |
| --- | --- | --- |
| **手动补算** | 运维接口 | 消息丢了或计算失败时，手动补触发一次聚合 |
| **视图变更建表** | 用户保存报表/统计图 → 消息队列 | 数仓**预建** ClickHouse 聚合表（先建表，暂不填数） |
| **字段一致性比对** | 上层服务调用 | 检查"报表字段配置 vs ClickHouse 表结构"是否一致，不一致则重建 |

> 第三条是理解"槽位漂移"问题的关键：**配置改了并不会自动同步到物理表**，需要靠比对接口发现差异后触发重建。[代码]

### 3.5 全量补数与增量同步的冲突

对数仓做历史补数时，若未先停增量任务，**全量写入的旧快照会覆盖增量已同步的新数据**。[场景]

规范做法有两条：

1. 全量写入**影子表**，对账一致后再原子切换表名；
2. 增量消费按单调递增的版本号比较，保证新版本不会被旧快照回退。

### 3.6 计算字段重算是一条独立链路

除了主链路，还有一条**计算字段重算链路**：明细批量变更后，重算任务经调度进入消息队列，由计算服务执行后回写。高并发下会触发限流并转发到备用队列。[知识库]

它的典型表现是"从对象已保存，但主对象的汇总值几分钟没变"。**这是最终一致性未收敛，不是数据计算 Bug**，不要直接断言计算错误。

## 四、数据怎么算出来的

### 4.1 聚合由三份元数据共同决定

聚合不是"对着原始表跑 SQL"，而是由三份元数据决定**读哪一列、用哪个槽位**：[字典] + [代码]

| 元数据 | 归属 | 作用 |
| --- | --- | --- |
| 字段槽位映射 | 元数据库 | 业务字段 ↔ **物理槽位**的映射 |
| 聚合规则 | 元数据库 | 哪些字段参与聚合、如何分配槽位 |
| **拓扑表** | 元数据库 | 决定一个图查询时用哪些槽位、读哪张表 |
| 指标元数据 | 元数据库 | 指标的聚合函数类型 |

**关键因果链：字段配置变更 → 槽位重新分配 → 拓扑未重建 → 查询用错槽位 → 统计值错误或全零。**

这是 BI 域最经典的一类缺陷，从 2019 持续到 2024。根因是规则创建/删除/修改时的**并发竞争导致槽位分配冲突**，以及停用/启用规则共享槽位。[知识库]

> **补充**：拓扑表是"预建表"机制的一部分——用户保存图时数仓就先把 ClickHouse 聚合表建好（不填数），等数据同步完再填。但如果槽位变了而拓扑没更新，就会出现"表在、槽位错"的情况。[代码]

### 4.2 指标如何编译成聚合状态

按指标的聚合函数类型，编译成不同的物理状态列：[字典]

| 聚合类型 | 物理列 | ClickHouse 类型 | 注意事项 |
| --- | --- | --- | --- |
| sum | `agg_sum_N` | `AggregateFunction(sum, Nullable(Decimal))` | 金额用 Decimal，不用 Float |
| count | `agg_count_N` | `AggregateFunction(sum, Nullable(Int64))` | 注意 `COUNT(*)` 与 `COUNT(col)` 的 NULL 差异 |
| 精确去重 | `agg_uniq_N` | `AggregateFunction(uniqExact, ...)` | 精确 |
| 近似去重 | —— | `uniq()` 走 HyperLogLog | **约 1–2% 误差**，与业务对不上先查这里 |

取值的唯一正确写法是 `finalizeAggregation(列名)`。[知识库]

### 4.3 计算偏差的六个来源

| 来源 | 机理 | 典型现象 |
| --- | --- | --- |
| 聚合消费阻塞 | 部分变更事件未被聚合 | 统计图与前台数字不一致 |
| 输入数据丢失 | 变更日志在某时间窗丢失，输入不完整 | 统计图条数比明细少 |
| 归属部门粒度 | 平铺与层级的 GROUP BY 处理不当 | 选了多个子部门只显示一个 |
| 槽位重复 | 多字段共享同一槽位，存值互相覆盖 | 差值不是"少"而是"多了不相关值" |
| 主题未检测开启 | 底层主题注册/发现机制缺陷 | **统计图全部显示 0** |
| 多对多重复计数 | 计数未去重 | 客户数被放大数倍 |

### 4.4 聚合实计算的真实执行路径

聚合服务的执行过程可以概括为五步：[代码]

1. **加分布式锁**——防止同一批次重复计算；
2. **查同步信息与构建变更上下文**——确定本批次涉及哪些对象和字段；
3. **找出受影响的视图**——查拓扑表，得到需要重算的统计图/报表清单；
4. **生成并执行聚合 SQL**——按视图逐个生成全量或增量聚合 SQL，写入 ClickHouse 聚合表；
5. **更新状态与日志**——写聚合运行日志，失败自动重试（有明确上限）。

其中第 3 步的"分片 + 线程池"设计解释了为什么大批量变更时会**互相争抢资源**；第 4 步的"全量/增量"两种策略则解释了为什么有时延迟明显更长。[代码]

### 4.5 时间口径是聚合误差的另一高发区

- 时间转换**默认 UTC**，中国时间必须显式指定时区；按日/周/月截断时**时区参数极易漏**。[知识库]
- **跨年周归属**：底层用 ISO-8601 周，跨年那一周会被判给下一年，按自然年过滤时**整周丢失**。[场景]
- **闰年同比环比**：跨闰年 2 月时日期对齐会错位。[场景]

### 4.6 拼表是计算复杂度最高的形态

多表拼接把多对象字段拼成宽表，两类结构性风险：[场景]

- **低基数笛卡尔积爆炸**：仅用"客户名称"这类低基数、高重复度字段作为唯一公共维度做 JOIN，会产生平方级膨胀，直接内存超限或查询超时。修复要求**补充高基数唯一键**（业务主键 + 单据主键）作为联合维度。
- **一对多行膨胀**：多对多关联未去重导致行数翻倍，需要**先聚合再 JOIN**。

## 五、查询怎么出结果

### 5.1 三段式：拓扑 → 权限 → 渲染

一次统计图点击的完整路径：[代码] + [字典] + [推断]

| 段 | 做什么 | 断裂时的现象 |
| --- | --- | --- |
| **拓扑** | 读视图定义，查拓扑表确定槽位与目标表，生成 ClickHouse SQL | 页面提示"初始化中""数据量过大" |
| **权限** | 在 SQL 内用权限编码过滤行 | **框架正常、图在、只是没数（`--`）** |
| **渲染** | 序列化结果，前端组件绘制 | 白屏、样式错乱 |

**关键消歧规则**（宣讲必讲）：[知识库]

| 现象 | 归类 |
| --- | --- |
| 白屏 + 浏览器控制台有 JS 报错 | 前端问题 |
| 一直转圈 | 后端 API 超时 |
| **框架正常、图在、只是没数（`--`）** | **不是白屏，先走权限口径** |

### 5.2 权限过滤发生在查询内

数据权限不是把结果过滤掉，而是**在 SQL 里按权限编码过滤行**：[知识库]

- 报表/交叉表的数据权限走**主业务对象**；统计图走**主题对象**——两者不同，对数时口径必须分开。
- 权限源在元数据库；若数仓侧权限编码为空，**非管理员用户看不到统计数据**。
- "是否包含离职员工"配置**只作用于**负责人及负责人主属部门类字段，**不管**创建人、自定义人员、归属部门。

**权限变更有三层缓存，三个时长，不能用同一个标准套**：[知识库]

| 变更类型 | 生效窗口 |
| --- | --- |
| 把员工加入部门/角色/用户组 | 最长 **6 小时** |
| 后台给角色勾选对象功能/数据权限 | 最长 **2 小时** |
| 单张图/驾驶舱授权给某人 | **10–30 分钟** |

窗口内属于**设计如此**，超窗口才需要深入排查。这是"改完权限看不到图"类工单的**最大误报来源**。

### 5.3 性能瓶颈通常在扫描量与内存

| 指标 | 关注点 |
| --- | --- |
| 查询耗时 | 报表查询正常基线在 **10 秒以内** |
| 扫描行数 vs 返回行数 | 比值过高说明过滤不足或分区裁剪失效 |
| 内存峰值 | 是否接近上限（OOM 前兆） |
| 是否命中预聚合 | 未命中说明在现算，成本高 |

**线上高频的四类性能问题**：[场景] + [知识库]

1. **DDL 并发超时**——建字段提示"请尽量避免在业务高峰期新建字段"。根因是大表加列需要重建数据块，多个 DDL 并发互相持锁；历史字段改名会阻塞后续所有 DDL。短期解法是把历史槽位从"改名"改为"删除"。
2. **双维度查询**——双维度分组导致计算量指数级增长，需要预聚合优化。
3. **大文本字段分组 OOM**——对大文本做哈希聚合，数百万行可消耗数十 GB 内存。
4. **合并操作并发**——强制合并会打满 CPU，影响全局查询。

### 5.4 三种输出形态与各自的坑

| 形态 | 典型故障 |
| --- | --- |
| **页面渲染** | 白屏（前端）/ 转圈超时（后端慢查询）/ 框架在没数（权限） |
| **导出** | 大文件内存溢出、切片丢失、百万行触发网关超时、高基数列 OOM |
| **订阅推送** | 串行渲染导致大批量推送延迟数小时；**当天改推送时点次日才生效** |

### 5.5 可观测性与已知盲区

排障入口包括：查询日志、视图访问日志、聚合运行日志（含耗时与批次）、以及 ClickHouse 自身的查询日志。[字典]

**已知盲区**：ClickHouse 的查询日志**可能因配置限制未记录所有查询**，线上频繁出现"日志不全导致排查困难"的情况。此时不能依赖它，要下沉到容器级日志或上层服务日志。另外该日志若不清理会**打满系统盘**。[知识库] + [场景]

## 七、风险与治理清单

| 风险域 | 结构性风险 | 治理方向 |
| --- | --- | --- |
| 存储 | 小 Part 堆积、副本只读、Mutation 堆积 | 写入端攒批；废弃单条更新，改版本号追加写入 |
| 存储 | 折叠引擎未合并前重复计数 | 查询端统一注入折叠逻辑 |
| 入库 | 全量补数覆盖增量位点 | 影子表 + 对账 + 原子切换；增量按版本号单调比较 |
| 入库 | 主库 DDL 导致同步断流 | 开启 schema 自动演进；DDL 变更纳入发布门禁 |
| 计算 | 槽位重复、并发分配冲突 | 槽位分配加锁；停用规则立即释放槽位 |
| 计算 | 配置变更后拓扑不重建 | 变更后强制触发拓扑重建与字段比对 |
| 计算 | 近似去重与业务对不上 | 需精确时统一改为精确去重 |
| 查询 | 拼表低基数笛卡尔积 | 建模器接笛卡尔积预警；强制高基数唯一键 |
| 权限 | 三层缓存被当成 Bug | 先判层与窗口，窗口内收口"设计如此" |
| 可观测 | 查询日志不全、日志打满磁盘 | 补容器级日志；配置清理策略 |
