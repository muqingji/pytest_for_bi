# 智能提醒助手：产品方案

> 文档状态：方案草稿，供 MVP 产品范围评审使用。  
> 本文只记录产品需求和产品决策。测试数据、Demo 操作、自动化测试和技术实现分别见测试方案与技术方案。

## 1. 方案摘要

### 1.1 要解决的问题

部分付费学生不会主动打开 App，或打开后没有完成当天学习任务，导致学习中断。当前每天 18:00 统一发送一条固定 Push，无法根据任务状态、用户活跃时段和提醒偏好选择合适的提醒时机。

### 1.2 产品定位

“智能提醒”是一个根据学生任务状态、历史学习习惯和提醒设置，为当天未完成任务的学生提供适时提醒的产品能力。

首版采用透明、可解释的策略判断，不以复杂模型或大模型生成内容作为产品价值的前提。

### 1.3 MVP版本策略判断

首期重点服务被动型学生：这类学生在提醒后有较大概率回来完成任务，是最适合验证提醒价值的人群。

- 自驱型学生：重点是避免不必要打扰。
- 被动型学生：重点是根据其更可能学习的时间进行提醒。
- 流失型学生：暂不通过增加提醒频次解决，避免形成反感，后续进入独立召回策略。

## 2. 已知事实与设计假设

### 2.1 题目已知事实

| 项目 | 数据 |
| --- | --- |
| DAU | 约 50 万 |
| 有每日任务的付费学生 | 约 30 万 |
| 当天未完成任务的学生 | 约 12 万，占 40% |
| 当前任务完成率 | 按学生口径推算为 60% |
| 当前 Push 到达率 | 约 60% |
| 到达后的打开率 | 约 8% |
| 打开后的任务完成率 | 约 45% |
| 主要活跃时段 | 16:00–18:00、19:00–21:00 |
| 业务目标 | 任务完成率提升至 75%，Push 打开率提升至 15%+ |

### 2.2 设计假设

1. “任务完成率”定义为：当天完成全部必做任务的付费学生数 / 当天有任务的付费学生数。
2. 12 万未完成学生与当天完成学生互为补集，因此当前任务完成率按 60% 推算。
3. 每位学生每天有一组可以判断完成状态的必做任务。
4. 学生有设备时区，产品按照学生本地时间执行提醒。
5. Push 权限状态和用户提醒偏好可以被提醒服务读取。
6. 每日任务日历由任务系统提供，周中、周末或节假日都可能存在当日任务；系统每天都评估提醒资格，但仅对当日存在未完成必做任务且满足提醒规则的学生发送提醒，没有任务或休息日不发送。
6. 打开率和完成率的归因窗口尚未明确，正式接入前需要和业务确认。

## 3. 目标与非目标

### 3.1 业务目标

- 整体任务完成率从当前 60% 提升至 75%。
- Push 打开率从当前约 8% 提升至 15% 以上。
- 在提升打开率的同时，控制重复提醒和用户打扰。

### 3.2 智能提醒的产品贡献目标

智能提醒不是完成整体业务目标的唯一手段。本方案的产品贡献目标是：在符合提醒条件的目标用户中，相比固定时间提醒或不提醒的对照组，验证智能提醒对 Push 打开率和任务完成率带来的可归因增量。

75% 和 15%+ 是整体业务目标，不要求单一功能独立承担全部增量。智能提醒的实际贡献通过线上对照实验评估，并同时观察重复提醒、退订和投诉等护栏指标。

### 3.3 产品目标

- 判断学生当天是否需要提醒。
- 在学生更可能学习的时间发送提醒。
- 让学生可以关闭提醒、设置免打扰或延后提醒。
- 在任务完成后停止未完成提醒。
- 让提醒内容与当前剩余任务相关。
- 让产品能够解释提醒或不提醒的原因。

### 3.4 过程指标

- Push 到达率。
- Push 打开率。
- 提醒后任务开始率。
- 提醒后任务完成率。
- 从提醒到开始学习的耗时。

### 3.5 护栏指标

- 每日提醒次数。
- 通知关闭率和提醒退订率。
- 重复提醒率。
- 用户投诉率和 App 卸载率。
- 免打扰时段内发送率。

其中，每日频控、重复提醒控制、免打扰和权限关闭属于 MVP 产品约束；通知关闭率、退订率、投诉率和卸载率依赖线上数据，属于上线后的监控指标。

### 3.6 非目标

- 不在首期实现复杂机器学习模型、多臂老虎机或自动策略训练。
- 不生成学习内容，不实现聊天式辅导。
- 不替代任务系统、课程系统或真实 Push 通道。
- 不在首期实现完整流失召回、家长端、老师端和跨端消息中心。
- 不搭建完整运营后台、用户批量管理和线上指标平台。

## 4. 目标用户与用户故事

### 4.1 用户分层

| 用户类型 | 特征 | 产品策略 |
| --- | --- | --- |
| 自驱型，约 40% | 大多数日子主动完成任务 | 已完成不提醒；未完成时最多低打扰提醒 |
| 被动型，约 35% | 看到提醒后通常会回来学习 | 首期重点服务，按活跃习惯和截止时间提醒 |
| 流失型，约 25% | 连续多日未打开或提醒无效 | 不增加提醒频次，后续进入独立召回策略 |

### 4.2 用户故事

1. 作为有未完成任务的学生，我希望在更可能学习的时间收到提醒。
2. 作为已经完成任务的学生，我不希望继续收到未完成任务提醒。
3. 作为暂时不能学习的学生，我希望关闭或延后提醒。
4. 作为使用产品的学生，我希望提醒内容告诉我还有多少任务以及如何进入任务页。
5. 作为产品负责人，我希望知道提醒是否有效以及是否造成了额外打扰。

## 5. 核心产品流程

### 5.1 学生侧流程

~~~text
打开 App
→ 查看今日任务和完成进度
→ 查看或调整提醒设置
→ 在合适时间收到提醒
→ 点击提醒进入今日任务
→ 开始学习
→ 完成任务
~~~

### 5.2 产品决策流程

~~~text
判断今日是否有未完成任务
→ 判断用户是否允许提醒
→ 判断是否已经完成或达到提醒上限
→ 判断当前是否处于免打扰时段
→ 选择合适的提醒时间和渠道
→ 发送与剩余任务相关的提醒
→ 用户返回任务页完成学习
~~~

## 6. 提醒产品规则

### 6.1 不提醒的情况

- 用户关闭智能提醒。
- 今日任务已经全部完成。
- 任务已经过期。
- 当天已经达到提醒上限。

### 6.2 延后或降级的情况

- 当前处于用户设置的免打扰时段：延后到下一个可用时间。
- 用户未授权系统 Push 时，不发送 Push；用户进入 App 后，在今日任务相关页面展示简短的站内提醒。若站内提醒也不可用，则跳过本次提醒并记录原因。
- 连续多日未打开：不提高提醒频次，进入低频召回候选。
- 缺少历史行为：使用默认活跃时段，不因数据缺失而完全失去提醒机会。

### 6.3 提醒时间

产品优先参考以下时间信息：

1. 用户最近常完成任务的时间段。
2. 用户最近常打开 App 的时间段。
3. 默认活跃时段 16:00–18:00 和 19:00–21:00。
4. 任务截止时间前的最后可用窗口。

提醒时间必须满足：不在免打扰时段、不超过每日上限、不晚于任务截止时间。

### 6.4 提醒频控

- 每位学生每天最多接收 1 次 Push。
- 用户点击提醒但未完成任务时，当天不立即重复发送。
- 用户主动选择延后时，只在当天剩余可用时间内重新安排。
- 任务完成后停止当天剩余的未完成提醒。

### 6.5 提醒内容

首期使用结构化内容：

~~~text
标题：今天还有 {remaining_count} 项学习任务
正文：预计用时 {estimated_minutes} 分钟，现在开始刚刚好
按钮：去完成任务
~~~

内容要求：

- 内容必须反映当前剩余任务状态。
- 不使用恐吓、羞辱或制造焦虑的表达。
- 不展示不必要的敏感信息。
- 点击旧提醒时展示最新任务状态。

## 7. 产品 MVP 范围评审

### 7.1 选择标准

一个功能进入 MVP，至少满足以下一项：

- 直接验证“Push 打开率从 8% 提升到 15%+”这一核心假设。
- 是学生提醒流程的必要环节。
- 是防止用户打扰或错误提醒的产品约束。
- 能显著帮助评审者理解产品行为，且不需要复杂基础设施。

测试数据、模拟时间、Mock 发送和单元测试不属于产品功能，分别记录在测试方案和技术方案中。

任务系统、任务完成统计、任务入口和 Push 基础能力属于题目背景中的既有能力。本题不新建任务详情页、做题流程、任务完成统计或 Push 基础设施；这些能力只作为智能提醒服务的外部输入和调用出口。

### 7.2 产品需求候选

| 产品需求 | 优先级 | 说明 |
| --- | --- | --- |
| 用户提醒开关 | P0 | 用户控制提醒的基础能力 |
| 免打扰设置 | P0 | 核心打扰控制能力 |
| 被动型用户的个性化提醒时间 | P0 | 直接验证核心假设 |
| 已完成任务不提醒 | P0 | 避免明显错误和无效打扰 |
| 每日提醒上限 | P0 | 产品频控约束 |
| Push 关闭后的站内提醒降级 | P0 | 用户已确认需要轻量化降级能力 |
| “稍后提醒” | P0 | 用户已确认保留，固定为一小时后提醒 |
| 当前提醒记录查看 | P1 | 提升可解释性和用户理解，可在核心闭环后实现 |
| 流失型用户召回策略 | P2 | 不是首期核心人群 |
| 真实 Push 厂商配置 | P2 | 依赖外部系统，本地 Demo 使用 Mock |
| 完整后台管理平台 | P2 | 本题不实现，不影响学生提醒核心闭环 |

### 7.3 优先级与 MVP 冻结规则

进入 PRD 前，以 P0/P1/P2 作为唯一的产品优先级：

| 标记 | 含义 | 处理方式 |
| --- | --- | --- |
| P0 | 本期 MVP 必须实现 | 写入 PRD、技术方案和验收标准，并完成代码和测试 |
| P1 | P0 完成后再实现 | 可以进入本次提交，但不阻塞 MVP 准出 |
| P2 | 后续规划或本题不实现 | 只记录边界和原因，不进入本期验收 |

本题的 MVP 范围为全部 P0 项。P1 项是否实现不改变 MVP 定义；P2 项不进入本次核心实现。

### 7.4 既有能力与外部依赖

以下能力由现有 App 或业务服务提供，不属于本题新增功能，也不参与 P0/P1/P2 优先级排序：

- 每日学习任务及必做任务定义。
- 任务完成状态和每日任务完成率统计。
- 任务详情页、做题流程和任务完成回传。
- 既有 Push 通道及发送基础设施。
- 提醒点击后的任务入口或 Deep Link。

本题只消费任务状态和任务入口，并在现有 Push 或站内消息能力之上实现提醒资格判断、时机选择、频控、免打扰、延后提醒和渠道编排。

## 8. 已确认产品决策

以下决策作为本次 MVP 的冻结输入：

1. 首期重点服务当天有未完成任务的被动型学生。
2. 每位学生每天最多接收 1 次 Push。
3. 用户未授权系统 Push 时，不发送 Push；用户进入 App 后，在今日任务相关页面展示简短的站内提醒。若站内提醒也不可用，则跳过本次提醒并记录原因。
4. 用户可以编辑提醒开关和免打扰时间，修改后立即影响后续提醒决策。
5. 保留“稍后提醒”，操作固定为点击后 1 小时后再次提醒，不开放时间间隔配置。
6. 完成全部必做任务才算当天完成；未进入任务详情或未完成全部必做任务均视为未完成，不关注题目对错。
