# 智能提醒助手：题目分析与实施拆解

## 1. 分析结论

从面试官视角看，这道题不是在考“能不能写一个定时 Push”，而是在考候选人能否把一个模糊业务问题完整地做成可运行、可验证、可迭代的产品。

平台明确要求候选人独立完成，允许使用 AI 辅助理解、检查和提效，但不允许让 AI 代写 PRD 或整个项目。因此，本文用于提供分析框架和评审视角，具体产品决策、PRD 内容和代码实现仍应由候选人独立完成。

## 2. 面试官真正考察的能力

平台公开的评审标准包括四个方面：

1. **产品能力**：是否找到了真正的问题，是否理解用户和业务，并做出合理取舍。
2. **工程开发能力**：代码是否清晰、稳定、可运行，是否真正支撑产品方案。
3. **AI 应用能力**：能否合理使用 AI 提高分析、设计、编码和测试效率。
4. **表达完整性**：PRD 是否清楚，假设、范围、方案和验证方式能否被快速理解。

题目还重点考察 Owner 意识：不仅提出功能，还要主动发现数据口径、目标可行性、打扰风险、隐私问题和上线后的验证方法。

## 3. 题目数据与关键矛盾

题面给出的主要数据如下：

- DAU 约 50 万。
- 付费学生约 30 万，且有每日学习任务。
- 约 40% 的付费学生当天未完成任务，即约 12 万人。
- 当前每日任务完成率为 60%。
- 目标任务完成率为 75%。
- 当前每天 18:00 统一发送一条固定 Push。
- Push 到达率约 60%。
- 到达用户中的打开率约 8%。
- 打开 Push 后的任务完成率约 45%。
- Push 打开率目标为 15% 以上。

### 3.1 业务目标测算

按照 30 万付费学生计算：

- 当前完成用户数：30 万 × 60% = 18 万。
- 目标完成用户数：30 万 × 75% = 22.5 万。
- 每天需要净增加约 4.5 万名完成用户。

一个必须主动指出的关键问题是：仅将 Push 打开率从 8% 提升到 15%，大概率不足以贡献新增 4.5 万次任务完成。

此外，题目没有完全说明 Push 指标的统计口径。例如：

- Push 是发送给全部付费学生，还是仅发送给当天未完成任务的学生？
- 到达率的分母是发送用户数还是设备数？
- 打开率的分母是发送量还是成功到达量？
- “打开后完成”采用多长的归因窗口？

PRD 中应明确区分：

- 已知事实。
- 未知信息。
- 为继续设计而采用的合理假设。
- 假设变化会如何影响方案和测算。

不要承诺“一个提醒功能直接将完成率提升到 75%”。更专业的表达是：智能提醒承担其中可归因的一部分，整体任务完成率还可能受到任务体验、内容质量、激励机制等因素影响。

## 4. 需求完善阶段

在进入技术设计前，应先完成产品决策，并说明每项决策的依据。

### 4.1 目标用户

题目将学生分为三类：

- 自驱型：每天主动完成任务，约 40%。
- 被动型：需要提醒才完成任务，约 35%。
- 流失型：提醒后仍不回来，约 25%。

需要明确首期重点服务哪一类学生。MVP 不应尝试同时解决所有人群的问题。

### 4.2 关键产品问题

需求分析至少应回答：

- 什么情况下应该提醒？
- 什么情况下绝对不应该提醒？
- “合适时机”依据什么判断：历史活跃时间、任务进度、任务截止时间还是用户偏好？
- 通知权限关闭后如何处理？
- 学生是否可以关闭、延后或调整提醒？
- 每日最多提醒几次？
- 是否需要免打扰时段？
- 连续多日未打开 App 的用户应继续提醒，还是进入单独的召回策略？
- 已完成任务、刚退出 App、刚收到提醒时如何避免重复打扰？
- 面对未成年人，如何做到数据最小化和可控授权？

### 4.3 指标体系

建议将指标分为三层：

#### 北极星指标

- 每日任务完成率。

#### 过程指标

- Push 到达率。
- Push 打开率。
- 提醒后任务开始率。
- 提醒后任务完成率。
- 从提醒到开始学习的耗时。

#### 护栏指标

- 通知权限关闭率。
- 提醒退订率。
- 用户投诉率。
- App 卸载率。
- 重复提醒率。
- 非目标时段打扰率。

## 5. MVP 范围建议

平台建议投入 2–6 小时。面试官更希望看到一个小而完整的闭环，而不是大量未完成的功能。

合理的 MVP 可以覆盖：

- 今日任务及完成状态。
- 用户提醒偏好和免打扰设置。
- 一个可解释的提醒决策引擎。
- 根据用户画像、任务状态和时间生成提醒决策。
- 提醒记录、点击和任务完成事件。
- 用模拟数据演示不同学生场景。
- 可快速推进时间的 Demo 模式，避免演示时等待真实提醒时间。

“智能”不等于必须调用大模型。首版采用可解释、可测试的规则策略通常更加专业。决策引擎可以输出：

```text
是否提醒 + 提醒时间 + 提醒渠道 + 决策原因 + 策略版本
```

机器学习、动态优化或多臂老虎机可以作为 V2。不要为了体现 AI 而增加一个与业务问题无关的聊天机器人。

## 6. 技术方案设计

### 6.1 建议的系统职责划分

```text
用户与任务数据
      ↓
特征计算
      ↓
提醒决策引擎
      ↓
调度与幂等控制
      ↓
Push 渠道适配（站内提醒为 P1 预留）
      ↓
曝光、点击、完成事件
      ↓
指标与实验分析
```

### 6.2 核心技术设计点

技术方案至少应说明：

- 核心领域模型：用户、任务、提醒偏好、提醒决策、发送记录、行为事件。
- 决策引擎的输入、输出及规则优先级。
- 幂等键设计，防止调度任务重跑造成重复发送。
- 发送失败是否重试，以及如何避免重复发送。
- 时区、跨天和任务截止时间的处理方式。
- 用户关闭通知、任务已完成等场景的兜底逻辑。
- 关键埋点事件和 `strategy_version`，保证效果可以归因。
- 哪些属于生产级设计，哪些在 Demo 中使用内存、Mock 或本地数据库简化。

### 6.3 技术栈取舍

题目允许使用 Golang、TypeScript/React 任一或组合。时间有限时，应优先选择最熟悉的一套技术栈，不要为了表现“全栈”而同时引入两套后端体系。

技术方案的专业性主要来自：

- 边界清晰。
- 核心逻辑可测试。
- 工程可以实际运行。
- 简化项被明确记录。

## 7. 开发实施原则

开发时应优先打通核心闭环：

1. 构造用户、任务和行为数据。
2. 计算提醒决策所需特征。
3. 执行提醒策略并生成可解释的决策结果。
4. 模拟发送提醒。
5. 记录曝光、点击、完成等事件。
6. 在界面或日志中展示决策原因与最终结果。

避免将主要时间投入视觉装饰。界面应服务于演示核心业务判断和工程实现。

## 8. 单元测试设计

单元测试应重点覆盖决策引擎，而不是只测试按钮是否可以点击。

建议覆盖以下场景：

- 已完成任务的用户不再提醒。
- 自驱型用户减少不必要的打扰。
- 被动型用户在合适时间收到提醒。
- 流失用户不会被高频轰炸。
- 免打扰时段不发送提醒。
- 每日频控正确生效。
- 通知权限关闭时不调用 Push、跳过提醒并记录未触达原因。
- 相同任务不会重复发送提醒。
- 跨天、临界时间和任务截止时间行为正确。
- 发送失败后的重试符合幂等要求。
- 缺失行为数据时能够采用合理的默认策略。

测试重点应放在业务分支、边界条件和失败路径，不必为了数字追求没有意义的 100% 覆盖率。

## 9. 功能测试设计

建议准备 3–5 个端到端演示场景。每个场景都应清楚展示：

```text
用户输入 → 任务状态 → 策略判断 → 提醒结果 → 行为事件
```

场景至少覆盖：

- 自驱型用户已经完成任务。
- 被动型用户在常用学习时段仍未完成任务。
- 用户处于免打扰时间。
- 用户关闭 Push 权限。
- 连续多日不活跃用户进入特殊策略。

功能测试还应验证埋点数据、策略版本和提醒记录，而不仅是页面结果。

## 10. 质量准出标准

提交前建议设定明确的准出标准：

- 核心验收标准全部通过。
- 核心策略测试覆盖充分，重点业务分支均有自动化测试。
- 不存在阻断级和严重缺陷。
- 安装、启动、测试命令已在全新环境中验证。
- ZIP 中不包含密钥、缓存、构建垃圾和 `node_modules`。
- README 能让评审者在几分钟内运行项目。
- 已知限制和 V2 计划被清楚记录。
- PRD 中的需求、代码实现和测试用例能够相互对应。

## 11. PRD 推荐结构

可以按照以下结构独立填写 PRD：

1. 执行摘要。
2. 已知事实、未知信息和关键假设。
3. 问题定义与指标测算。
4. 用户分层和首期目标人群。
5. 产品目标、非目标和护栏指标。
6. 用户故事与核心流程。
7. 提醒策略和异常场景。
8. MVP 范围与 V2。
9. 数据埋点与 A/B 实验方案。
10. 技术架构与关键接口。
11. 验收标准和测试策略。
12. 风险、隐私和已知限制。
13. AI 协作说明。

## 12. 如何体现 AI 协作能力

建议在文档附录中简要说明：

- AI 帮助完成了哪些工作，例如需求反驳、测试补充、代码审查。
- 哪些核心产品与技术判断由候选人本人作出。
- AI 输出出现过哪些问题，以及如何验证和修正。
- 最终执行了哪些自动化检查。

这比笼统地写“本项目由 AI 辅助开发”更有说服力，也符合平台强调的独立判断要求。

## 13. 推荐的 5 小时执行节奏

| 时间 | 工作内容 | 阶段产出 |
| --- | --- | --- |
| 0–40 分钟 | 数据测算、假设识别、目标人群和 MVP 取舍 | 决策记录、范围定义 |
| 40–80 分钟 | 编写 PRD 骨架、验收标准和技术方案 | 可执行的 PRD 初稿 |
| 80–220 分钟 | 实现核心业务闭环 | 可运行的 MVP |
| 220–270 分钟 | 补充核心单元测试和异常场景 | 自动化测试结果 |
| 270–300 分钟 | 全新环境运行、功能验收、整理 README 和 ZIP | 最终提交包 |

## 14. 常见失分点

- 只做漂亮 UI，没有真正实现提醒决策。
- 对所有用户采用相同时间、相同内容的提醒。
- 为体现 AI 而强行接入大模型，却没有解决业务问题。
- 没有频控、免打扰、幂等和失败处理。
- 只实现成功路径，没有边界条件和异常场景。
- 没有定义指标口径和实验方案。
- PRD、代码和测试互相脱节。
- 引入过多框架和基础设施，导致核心功能没有完成。
- 将 75% 目标直接归功于提醒功能，没有说明可归因范围。

## 15. 最终评审视角

真正能够拉开差距的，不是功能数量，而是以下几点：

- 主动识别数据口径和目标可行性问题。
- 明确写出假设，并说明为什么这样假设。
- 聚焦最值得解决的目标用户，而不是服务所有人。
- 使用简单、可解释、可测试的策略完成 MVP。
- 同时考虑用户价值、业务效果和打扰风险。
- 让需求、设计、代码、测试和指标形成完整闭环。
- 清楚说明 AI 做了什么、本人做了什么以及如何验证结果。

最终交付应体现的是候选人的真实判断、完成质量和负责态度，而不是功能复杂度。
