# 智能提醒助手后端技术方案（MVP 版）

> 文档状态：1 稿（评审稿）  
> 需求基线：`智能提醒助手PRD-MVP(1稿).md`  
> 本期范围：FR-001、FR-002、FR-003、FR-004、FR-005、FR-007、FR-008，以及横切事件链路 AC-011  
> 文档定位：面向技术评审和跨团队协作；字段、枚举和代码级细节以 `docs/api/reminder-service.openapi.yaml` 与细粒度技术方案为准

## 1. 需求背景

当前 App 已有每日任务、任务完成状态、任务入口和每天 18:00 固定 Push，但固定时间、统一文案且不检查任务状态，存在已完成仍提醒、提醒时机不合适、重复打扰和无法归因等问题。

本期在既有任务与 Push 能力之上建设智能提醒闭环：根据任务状态、用户分层、提醒设置和频控判断资格，选择提醒时间，在发送前复核最新状态，并通过事件链路支持问题定位和效果归因。本期只使用 Push，不新建任务系统、任务页面、Push 厂商配置中心或运营后台。

## 2. 目标

技术目标如下：

1. 完成本期 7 个 P0 功能，且每个功能都有模块、入口、数据落点、失败处理和验收映射。
2. 在决策和发送两个时点校验任务与设置，避免已完成、过期、关闭提醒或处于免打扰时仍被触达。
3. 通过持久化幂等、唯一约束和发送前频控，保证系统主动 Push 每人每天最多 1 次；用户主动延后的 Push 最多 1 次，因此每天最多 2 次 Push。
4. 用 `decision_id`、`strategy_version` 和 `event_id` 串联决策、排程、发送、打开、开始和完成事件。
5. 对任务、设置、行为和 Push 依赖给出明确的失败关闭或降级策略，并支持灰度、监控和回滚。

以下不属于本期目标：FR-006 站内提醒、FR-009 提醒记录查看、流失用户召回、真实 Push 厂商配置、运营后台、激励机制，以及实验比例、周期和上线阈值的产品决策。

## 3. 整体架构

### 3.1 技术选型（选）

| 领域 | MVP 方案 | 说明 |
| --- | --- | --- |
| 服务实现 | Go 1.22+，内部 HTTP/JSON 入口 | 复用现有项目实现，规则保持确定性和可测试 |
| 持久化 | Repository 抽象；当前可运行交付使用 SQLite | 决策、排程、发送与事件必须通过事务和唯一约束保证一致性；生产数据库待接入确认 |
| 调度 | 每日评估、到期发送、异常状态核对三个任务入口 | 当前交付提供一次性执行入口，生产调度平台待确认 |
| 渠道 | 既有 Push 能力 | MVP 不引入站内提醒或其他替代渠道 |
| 事件 | 事件发布端口 + 本地事件表 | 本服务事件先可靠落库；生产事件总线和外部事件来源待联调确认 |
| 缓存 | 不作为业务事实源 | 频控、幂等、任务完成和发送状态以持久化记录及上游实时状态为准 |

### 3.2 应用架构

```text
触发层：每日评估 / AppOpened / 任务或设置变化 / 到期调度 / 稍后提醒
                               |
应用层：提醒评估 -------- 提醒发送 -------- 延后提醒
           |                   |                |
领域层：用户分层 / 资格规则 / 时间规划 / 频控 / 内容渲染 / 状态机
                               |
端口层：任务 / 用户设置 / 行为 / Push / 事件 / 时钟 / 持久化
                               |
适配层：既有业务服务、既有 Push、数据库、事件系统
```

应用层只编排流程，领域层承载规则，适配层隔离外部系统。用户分层按每次评估所读取的行为数据实时计算，不保存为跨日固定标签。

### 3.3 逻辑流程图（选）

```text
评估触发
  -> 读取任务、用户设置、Push 权限和行为摘要
  -> 按固定顺序计算用户分层和提醒资格
  -> 按行为优先级计算候选时间
  -> 校验免打扰、截止时间和每日频控
  -> 幂等保存决策与排程

排程到期
  -> 抢占排程
  -> 重新读取任务、设置和 Push 权限
  -> 校验频控并用最新任务快照生成内容
  -> 调用既有 Push
  -> 保存投递结果并记录事件

用户点击稍后提醒
  -> 校验原决策、任务、设置、Push 权限、截止时间和当日总次数
  -> 幂等创建一小时后的 SNOOZE 排程
  -> 到期后复用发送流程，且不再提供稍后提醒入口
```

### 3.4 模块划分

| 模块 | 主要职责 | 入口 | 数据落点 | 失败边界 |
| --- | --- | --- | --- | --- |
| 提醒评估 | 分层、资格判断、时间规划、初始排程 | 每日评估、`AppOpened`、任务或设置变化 | 决策、排程、事件 | 强依赖失败时不建可发送排程；行为异常时降级 |
| 到期发送 | 抢占、二次校验、内容渲染、Push 调用 | 到期调度 | 排程、投递、事件 | 并发抢占失败立即结束；未知状态先核对再决定是否重试 |
| 延后提醒 | 一小时后重排、次数控制、请求幂等 | 用户点击稍后提醒 | 延后请求、排程、事件 | 不满足条件时返回明确原因，不创建排程 |
| 规则领域 | 分层、资格、时间、免打扰和频控 | 由应用层调用 | 无独立存储 | 输入不足时返回可解释结果，不直接调用外部服务 |
| 外部适配 | 任务、用户、行为、Push 和事件系统接入 | 端口调用 | 外部系统 | 按强弱依赖策略隔离故障 |
| 可观测性 | 结构化日志、指标和事件关联 | 全链路 | 日志、指标、事件 | 不记录姓名、手机号、任务正文、成绩等敏感信息 |

## 4. 详细方案

### 4.1 关键交互流程

#### 4.1.1 提醒评估

评估覆盖 FR-001、FR-002、FR-003、FR-004、FR-005 和 FR-008。系统依次执行以下规则，命中拒绝条件即停止并保存原因：

1. 无必做任务返回 `NO_TASK`；全部必做任务已完成返回 `TASK_COMPLETED`；任务已过期返回 `TASK_EXPIRED`。
2. 智能提醒关闭返回 `REMINDER_DISABLED`。设置不存在或字段缺失时使用 PRD 默认值；设置读取失败时失败关闭。
3. 按固定顺序判定数据不足、流失型、回流型、自驱型、被动型，五类互斥且穷尽。
4. 系统主动 Push 已达每日上限时返回 `DAILY_CAP_REACHED`。
5. 从最近行为中按“任务完成 > 任务开始 > App 活跃 > 默认窗口”选择时间；同一来源存在并列窗口时稳定选择同一结果。默认活跃窗口为用户本地时间 16:00–18:00 和 19:00–21:00。
6. 候选时间必须满足用户本地时区、免打扰和任务截止约束。无有效行为时先取 19:30；若处于免打扰或晚于任务截止前 1 小时则回退 17:00；仍不可用时返回 `QUIET_HOURS` 或 `INSUFFICIENT_TIME`。
7. Push 不可用返回 `NO_AVAILABLE_CHANNEL`；全部通过时返回 `ELIGIBLE`，幂等保存一条决策和一条初始 Push 排程。

分层实现口径：

| 顺序 | 分层 | 判定 | 技术处理 |
| --- | --- | --- | --- |
| 1 | 数据不足 | `history_days_available < 3` | 按被动型处理，使用默认窗口并记录 `INSUFFICIENT_HISTORY` |
| 2 | 流失型 | `inactive_days >= 3` | 不生成主动 Push 排程，记录 `USER_INACTIVE` |
| 3 | 回流型 | `AppOpened` 前一次打开距当天至少 3 个本地自然日 | 回流首日不发送、不排程，记录 `RETURNING_FIRST_DAY`；次日重新评估 |
| 4 | 自驱型 | 最近 7 天完成天数至少 5，且提醒归因完成天数不超过 1 | 已完成不提醒；未完成最多生成一条系统主动 Push，不增加额外触达 |
| 5 | 被动型 | 其余用户 | 按行为时间、免打扰和截止时间生成排程 |

异常与降级：

- 任务、提醒设置或 Push 权限读取失败属于强依赖失败，本次不创建可发送排程，等待后续触发重试。
- 行为读取超时、字段缺失、延迟超限或版本不兼容属于弱依赖异常，使用可用信号或默认窗口，记录 `BEHAVIOR_DATA_DEGRADED`；不得用不完整数据命中回流或提醒归因规则。
- 重复评估以 `(user_id, task_date, strategy_version)` 幂等返回已有决策；数据库并发冲突回读已有结果，不生成第二条排程。
- 用户完成任务或关闭提醒后，取消当天所有尚未发送的排程并保留取消记录。

#### 4.1.2 到期发送

到期任务先通过条件更新抢占排程，再依次重新读取任务、用户设置和 Push 权限，检查频控，使用最新任务快照渲染文案，最后调用 Push。文案使用 PRD 模板中的剩余任务数和预计用时，点击进入既有任务入口；不得包含任务正文、成绩或其他非必要敏感信息。

发送异常按以下规则处理：

| 异常 | 处理 | 防重复措施 |
| --- | --- | --- |
| 排程已被其他执行器抢占 | 当前执行结束 | 状态条件更新保证只有一个执行器获得发送权 |
| 发送前任务已完成、过期或提醒已关闭 | 取消排程并记录原因，不调用 Push | 取消状态为终态 |
| 发送前进入免打扰 | 调整到可用时间；无可用时间则取消 | 更新原排程版本，不新增并行可发送排程 |
| 任务或设置读取失败 | 释放本次执行，保留后续重试机会 | 不使用旧任务快照发送 |
| Push 未授权 | 不调用 Push，记录 `NO_AVAILABLE_CHANNEL` | 当天不改走其他渠道 |
| Push 明确失败 | 复用同一幂等键，最多增加一次发送尝试；仍失败则记录 `NO_AVAILABLE_CHANNEL` | 重试不新增独立排程或第二条业务提醒 |
| Push 返回未知状态 | 标记未知并查询渠道状态；确认前禁止重发 | 核对任务处理未知状态，避免重复触达 |

发送前读取到的最新任务快照是内容变量的唯一来源。任务快照无法取得或内容变量非法时失败关闭，不发送旧内容或未替换占位符。MVP 内容沿用 PRD 模板：“今天还有 {remaining_count} 项学习任务”“预计用时 {estimated_minutes} 分钟，现在开始刚刚好”，按钮为“去完成任务”。文案使用鼓励表达，不使用恐吓、羞辱或制造焦虑的措辞。

#### 4.1.3 一小时后再提醒

延后入口覆盖 FR-007。请求通过后创建原 `decision_id` 下的一条 `SNOOZE` 排程，计划时间为请求时刻后一小时。该排程使用 Push，不占每日 1 次系统主动 Push 上限，但计入每天最多 2 次 Push 的总上限。

创建前重新检查原决策归属、任务未完成、提醒开启、Push 可用、免打扰、任务截止时间和当日总次数。距离截止不足一小时或没有可用时段时返回 `INSUFFICIENT_TIME` 或 `QUIET_HOURS`，不强行排程。

同一 `request_id + decision_id` 重复请求返回原排程；同一决策使用新请求再次延后返回 `INVALID_REQUEST`。延后 Push 不再携带“稍后提醒”入口，从服务端和客户端同时限制第三次 Push。

#### 4.1.4 事件链路

提醒服务负责记录决策、排程、取消、延后、发送、失败和设置变化事件；既有 App、任务系统和 Push 回执提供打开、任务开始、任务完成和送达事件。统一信封包含 `event_id`、`event_name`、`event_time`、`schema_version`、`source`、`user_id`、`task_date` 和 `timezone`；关联提醒的事件必须再包含 `decision_id` 和 `strategy_version`，按需携带 `channel`，既有实验平台提供时填写 `experiment_group`。`event_id` 用于消费与重放去重。

本期事件集合与 PRD 10.3 一致：`reminder_decision_created`、`reminder_scheduled`、`reminder_cancelled`、`reminder_snoozed`、`reminder_sent`、`reminder_failed`、`reminder_delivered`、`reminder_opened`、`task_started`、`task_completed`、`reminder_preference_updated`。其中外部系统事件的产生能力属于上线前联调前提，不在提醒服务内重复建设。

事件发布失败不得反向触发第二次 Push。本地交付先写事件表；生产事件总线、重放和死信能力在上线接入时确认。

### 4.2 状态机（选）

```text
决策：CREATED -> SCHEDULED -> CANCELLED

排程：SCHEDULED -> CLAIMED -> SENDING -> SENT
          |           |          |  -> RETRY_WAIT -> SCHEDULED
          |           |          |  -> UNKNOWN -> 状态核对
          +-----------+----------+  -> FAILED / CANCELLED
```

- `CANCELLED`、`SENT`、`FAILED` 为终态；任务完成对应取消原因 `TASK_COMPLETED`，不另设“已完成提醒”状态。
- 状态推进使用条件更新，只有符合前置状态的执行器可以迁移，防止并发覆盖。
- 未知状态不立即重发，先通过渠道查询或核对任务确认结果；无法确认时保留人工或后续任务处理入口。
- 延后提醒创建新的排程版本，不修改已经发送的初始投递事实。

### 4.3 接口定义

#### 4.3.1 API 接口文档地址

字段级契约见 `docs/api/reminder-service.openapi.yaml`。MVP 提供三个受保护的内部 HTTP/JSON 入口，不作为公开客户端 API：

| 接口 | 用途 | 主要调用方 | 幂等依据 |
| --- | --- | --- | --- |
| `POST /internal/v1/reminders/evaluate` | 单用户单任务日资格评估 | 每日评估、`AppOpened`、任务或设置变化处理器 | 请求标识及用户、任务日、策略版本唯一键 |
| `POST /internal/v1/reminders/dispatch-due` | 扫描并处理到期排程 | 内部调度平台 | 排程抢占、投递幂等键 |
| `POST /internal/v1/reminders/{decision_id}/snooze` | 创建一小时后的延后 Push | App 经既有网关调用 | 请求标识与决策唯一键 |

接口只返回决策、批次或延后处理结果，不返回任务正文、成绩等敏感数据。本期不新增后台角色和管理权限；学生侧继续使用既有提醒设置入口和任务入口。生产服务身份、mTLS、调用方权限、超时和限流参数需在联调前按现有基础设施确认；当前本地入口使用受限监听地址与静态鉴权替身，不代表生产鉴权已经接通。

#### 4.3.2 RPC 接口

本期没有新增独立 RPC 协议，应用内部通过端口访问既有任务、用户设置、行为、Push 与事件服务。核心依赖契约如下：

| 依赖 | 读取或调用内容 | 强弱依赖 | 异常处理 |
| --- | --- | --- | --- |
| 任务系统 | 必做任务、完成状态、截止时间、剩余数、预计用时、任务入口 | 强 | 评估或发送失败关闭，不用旧任务状态继续发送 |
| 用户设置 | 智能提醒开关、免打扰、用户时区 | 强 | 记录不存在用默认值；调用失败不发送 |
| 行为数据 | 打开历史、任务开始/完成窗口、分层信号 | 弱 | 使用可用信号或默认窗口并记录降级原因 |
| Push 权限与渠道 | 权限状态、发送、发送状态查询 | 强 | 未授权不调用；明确失败有限重试；未知状态先查询 |
| 事件系统 | 生命周期事件发布与外部事件消费 | 旁路 | 发布失败不重复触达，生产补发能力待接入确认 |

业务拒绝和降级使用 PRD 10.4 的原因码：`ELIGIBLE`、`NO_TASK`、`TASK_COMPLETED`、`TASK_EXPIRED`、`REMINDER_DISABLED`、`DAILY_CAP_REACHED`、`QUIET_HOURS`、`INSUFFICIENT_TIME`、`NO_AVAILABLE_CHANNEL`、`USER_INACTIVE`、`INSUFFICIENT_HISTORY`、`BEHAVIOR_DATA_DEGRADED`、`RETURNING_FIRST_DAY`、`DEFAULT_WINDOW`。参数非法、未鉴权、依赖超时和内部错误使用接口错误码表达。任何未识别的下游返回不得当作发送成功，也不得直接重发。

### 4.4 定时任务/刷数据方案

#### 4.4.1 任务功能及设计

| 任务 | 功能 | 执行约束 |
| --- | --- | --- |
| 每日评估 | 分批为当日有任务用户生成决策和排程 | 支持重复执行；用户、任务日、策略版本唯一键防重 |
| 到期发送 | 扫描到期排程并执行发送前复核 | 小批量抢占，避免长事务；失败有限重试 |
| 状态核对 | 处理 Push 未知状态和异常中断记录 | 核对前不重发，不改变明确终态 |

任务执行频率、分片、租约和单批大小属于生产容量参数，上线前根据真实用户量与渠道限额压测后确定。

#### 4.4.2 上线及回滚方案

上线先部署存储结构和服务，再验证只读依赖，最后通过服务级开关按小流量启用智能排程。回滚时先关闭智能提醒总开关，停止创建新排程并取消未发送的智能排程，再恢复既有 18:00 固定 Push；同一用户同一天只能命中一种策略，避免回滚期间重复触达。

数据库变更采用向前兼容方式，回滚应用时保留已产生的决策、排程、投递和事件记录，不通过删除数据回滚。权限、调度和生产数据库迁移方式需在上线评审时确认。

#### 4.4.3 监控指标设计

监控至少覆盖评估量与拒绝原因分布、排程积压、发送成功/失败/未知量、强依赖失败、行为数据降级、重复拦截、事件写入失败，以及既有 Push 到达率和任务入口可用性。告警阈值不能由本方案臆定，需在压测和灰度基线形成后配置。

### 4.5 数据库/消息队列

#### 4.5.1 Schema 设计

MVP 使用五类逻辑表，本文只描述职责和关键约束，字段类型以迁移脚本和细粒度技术方案为准。

| 逻辑表 | 用途 | 关键唯一约束 |
| --- | --- | --- |
| `reminder_decision` | 保存每日提醒决策、原因、计划时间、分层和策略版本 | `(user_id, task_date, strategy_version)` |
| `reminder_schedule` | 保存初始或延后排程及状态 | `(decision_id, schedule_version)` |
| `reminder_snooze_request` | 保存延后请求与返回排程的幂等关系 | `(request_id, decision_id)`；同一决策最多一个 SNOOZE 版本 |
| `reminder_delivery` | 保存渠道调用、尝试次数和结果 | `idempotency_key` |
| `reminder_event` | 保存事件信封和非敏感业务字段 | `event_id` |

决策与初始排程、延后请求与延后排程分别在同一事务中写入。唯一约束冲突按幂等命中处理，不通过“先查后写”单独保证并发安全。历史任务和行为数据继续由既有系统维护，本期不迁移。

消息队列不是当前本地交付的前置条件；生产接入时必须确认事件总线、消费幂等、有限重试、死信和重放能力。事件重放只补事件，不再次调用 Push。

### 4.6 缓存设计（选）

本期不使用缓存保存频控、幂等、任务完成或发送事实。未来若为读取性能增加缓存，只能缓存用户设置或行为摘要，并设置有效期；缓存缺失、逐出或版本不一致时回源，不能绕过发送前任务和设置复核。

### 4.7 配置中心（选）

P0 使用以下 MVP 默认值：用户提醒默认开启、免打扰 21:30 至次日 07:00、默认发送 19:30、回退 17:00、系统主动 Push 每日上限 1 次、分层历史窗口 7 天、数据不足阈值 3 天、流失阈值 3 天、自驱完成阈值 5 天、提醒归因完成阈值 1 天。用户时区取用户档案。

服务级灰度总开关与用户级智能提醒开关是两个独立概念：前者控制系统是否创建智能排程，后者表达单个用户偏好，不能混用。

行为窗口与分层阈值的运行时配置能力为 P1，本期 P0 固定使用上述值；P1 实施时需同时支持组合校验、配置版本记录、窗口无关的行为摘要字段和回查测试。19:30、17:00 及回退条件按 MVP PRD 作为可配置设计参数管理，其生产配置载体与变更流程在上线前确认。

## 5. 测试建议

### 5.1 环境及可测性

测试环境使用可控时钟、用户本地时区、任务/行为/设置 Fixture 和可配置 Push 替身，能够稳定构造跨午夜免打扰、截止时间、依赖超时、发送失败和未知状态。生产联调环境需支持任务、用户、Push 和事件系统的隔离数据，具体泳道与权限在接入时确认。

### 5.2 功能测试建议

测试必须覆盖：五类用户分层及阈值边界；19:30 到 17:00 的回退；跨午夜免打扰；已完成、无任务和过期短路；设置立即生效；重复评估与并发发送；Push 未授权、明确失败和未知状态；一小时后延后、重复请求及第二次延后拒绝；发送前最新内容；完整事件关联。

本期验收范围为 AC-001 至 AC-003、AC-005 至 AC-018。AC-004 随 FR-006 为 P1，不进入 MVP 验收。

### 5.3 回归测试建议（选）

重点回归既有 18:00 固定 Push 的实验组/对照组互斥、任务完成状态读取、任务 Deep Link、Push 权限读取和设置入口。验证关闭智能策略并恢复固定 Push 时，同一用户同一天不会收到两条独立业务提醒。

### 5.4 性能测试建议（选）

按约 30 万有每日任务用户的规模验证每日评估完成时长、到期排程峰值、数据库唯一键冲突、排程积压和 Push 下游限额。真实 QPS、批大小、并发度与告警阈值必须来自压测和下游配额，本文不预设生产结论。

## 6. 变更保障设计

### 6.1 业务监控

| 监控对象 | 核心指标 | 用途 |
| --- | --- | --- |
| 决策 | 评估成功率、各原因码数量、五类分层数量 | 发现规则或输入数据异常 |
| 排程 | 创建量、取消量、积压量、延迟 | 发现调度延迟和取消异常 |
| Push | 发送、失败、未知、到达、打开数量 | 发现渠道故障并对照既有基线 |
| 频控 | 每日上限拦截、幂等命中、唯一键冲突 | 发现重复触达风险 |
| 依赖 | 任务/设置/权限失败、行为降级量 | 区分强依赖中断与弱依赖降级 |
| 业务护栏 | 重复提醒率、任务入口成功率、通知关闭率 | 防止体验和既有入口劣化 |

日志和指标统一携带请求标识；可关联提醒的记录携带 `decision_id` 和 `strategy_version`，不得记录非必要敏感信息。效果指标沿用 MVP PRD 2.3 的分子、分母和用户本地 `task_date` 口径；Push 未授权、发送失败或回流首日不排程的用户不能从实验组符合条件用户分母中剔除。

### 6.2 灰度和应急方案

功能默认由服务级开关控制，先在测试用户和小流量范围验证，再逐步放量。灰度期间实验组使用智能提醒，对照组继续使用固定 18:00 Push，两个策略互斥。

出现重复触达、已完成仍提醒、免打扰失效、任务入口劣化、强依赖大面积失败或渠道异常时，立即关闭智能排程开关，停止新增排程并取消未发送记录；是否恢复固定 Push 由同一策略分流结果控制，不能直接全量叠加。

### 6.3 上线方案

上线顺序为：数据结构与迁移验证 -> 服务部署但关闭开关 -> 外部依赖只读校验 -> 调度和监控验证 -> 小流量开启 -> 观察护栏指标后逐级放量。每一级必须验证任务状态、设置、频控、Push 结果和事件关联。

生产数据库、调度平台、Push 幂等与状态查询、事件总线、实验分流和告警阈值未确认前，不得宣称完成生产联调或全量上线。

#### 6.3.1 止损方案

一键关闭服务级智能提醒开关；停止评估任务；取消未发送智能排程；保留历史记录用于审计；按用户策略恢复既有固定 Push。已发送 Push 无法撤回，因此频控、唯一约束和发送前复核是主要预防措施。

#### 6.3.2 补偿逻辑

本功能不涉及资金、有价资源或任务进度写入，不设计业务补偿。Push 发送失败只允许在原投递记录和原幂等键上有限重试；事件失败只补事件，不补发 Push，避免补偿造成重复触达。

## 7. 新增数据中心成本评估

### 7.1 评估结论

主要增量来自每日决策、排程、投递和事件记录，以及对任务、用户、行为和 Push 服务的读取。按约 30 万有任务用户每日一次评估估算，决策记录上限约 30 万条/日、约 900 万条/月；事件量随资格命中和生命周期事件数量增长。当前没有生产存储单价、真实事件倍率和保留周期，无法给出金额结论，需在生产架构与留存策略确认后完成成本评审。

### 7.2 成本控制措施

采用批量评估和发送、拒绝条件提前短路、事件字段最小化、禁止记录任务正文和成绩、避免重复排程与重复投递。生产分区、归档、保留周期和容量水位根据真实数据量确定，不将本地 SQLite 参数作为生产容量承诺。
