### 1.2 需求摘要

在既有任务系统、任务入口和 Push 能力之上，新增提醒资格判断、个性化时间计算、设置生效、频控、稍后排程、结构化内容和事件关联能力；本期 P0 为 Push 单渠道闭环，不调用、不设计、不验收站内提醒（FR-006 移入 P1，见 9.3）；本期不新建任务系统、任务页面、Push 厂商配置中心或运营后台。

## 2. 目标

### 2.1 技术目标

1. 用确定性规则实现 PRD 的 P0 需求 FR-001 至 FR-005、FR-007、FR-008，并让每条 P0 需求都有明确的模块、触发入口、持久化落点和异常处理；FR-006（站内提醒）为 P1，本期只保留边界说明。
2. 在排程创建和实际发送两个时点复核任务与设置，避免已完成任务、免打扰或关闭提醒后继续触达。
3. 使用持久化唯一约束、条件更新和渠道幂等键，保证重复评估、并发发送和失败重试不突破每日系统主动 Push 上限（默认 1 次）与 snooze 延后上限（同一天最多 2 次 Push）。
4. 通过 `decision_id`、`strategy_version` 和 `event_id` 关联决策、排程、发送及用户行为，支持问题定位和效果归因。
5. 将任务、用户偏好、行为、Push 和事件系统隔离为端口，便于本地替身测试和生产适配；站内提醒端口（`InAppNotifier`）只保留 P1 预留定义，本期不实现适配器。

## 3. 整体架构

### 3.1 技术选型

| 领域 | 方案 | 取舍 |
| --- | --- | --- |
| 服务 | Go 1.22+，HTTP/RPC 触发 + 调度入口 | 规则和状态机使用标准库，减少 MVP 依赖 |
| 持久化 | `database/sql` + `modernc.org/sqlite` | 本次可运行交付使用纯 Go SQLite 驱动，避免 CGO；决策、排程、发送和事件通过事务、条件更新和唯一约束保证一致性；未来生产数据库适配器另行确认 |
| 事件 | `EventPublisher` 端口 | 生产接入既有事件系统；本地可使用内存实现 |
| 渠道 | `PushSender`（P0）；`InAppNotifier`（P1 预留，不实现适配器） | 复用既有能力，不引入厂商 SDK 或新配置中心 |
| 时钟 | `Clock` 接口 | 生产使用系统时钟，测试使用可控时钟 |
| 缓存 | 首期不作为事实源 | 频控和幂等必须由持久化层保证；缓存只能做读取加速 |

### 3.2 应用架构

```text
触发层：Evaluate / AppOpened / Dispatch / Snooze / PreferenceChanged
                  |
应用层：ReminderEvaluator - ReminderScheduler - ReminderDispatcher
                  |
领域层：SegmentEvaluator / EligibilityRule / TimePlanner / FrequencyGuard / StateMachine
                  |
端口层：Task / UserPreference / Behavior / ReminderRepository
                  |         PushSender / EventPublisher / Clock
                  |         InAppNotifier（P1 预留，本期不实现）
                  |
适配器：既有任务服务、用户服务、Push 服务、数据库、事件系统
```

调用依赖单向流动：transport/scheduler -> application -> domain/port -> adapter。领域层不依赖数据库、HTTP 或具体渠道 SDK。

### 3.3 逻辑流程图

```text
每日评估或任务/设置变化
  -> 读取任务、行为、偏好和当日使用量，按 PRD 3.3 现算用户分层
  -> EligibilityRule 判断资格
  -> TimePlanner 计算候选时间和 `push` 渠道
  -> ReminderRepository 幂等保存决策与排程
  -> 到期 worker 抢占排程
  -> 再次读取任务和偏好，校验过期、完成、免打扰、频控
  -> Push 可用则发送；Push 未授权或发送失败则跳过本次提醒并记录未触达原因，不追加第二次触达
  -> 写入发送和事件状态

AppOpened（用户打开 App）
  -> 读取最新任务、行为、偏好和当日触达状态
  -> 计算本次打开前上一次打开距今天的间隔 `days_since_last_open`
  -> 命中回流首日（间隔 ≥ 3 天）时当天不发送提醒、不生成 Push 排程，记录 `RETURNING_FIRST_DAY`
  -> 未命中回流首日时按常规分层、设置与频控判断是否生成 Push 排程
```

### 3.4 模块划分

| 模块 | 职责 | 入口 | 主要落点 | 异常边界 |
| --- | --- | --- | --- | --- |
| `domain/reminder` | 资格判断、时间计算、渠道选择（本期仅 `push`）、状态迁移 | 应用层调用 | 决策对象、排程对象 | 输入不完整返回明确原因，不调用外部服务 |
| `application/evaluate` | 组织评估和幂等落库 | 每日任务、`AppOpened` 同步通道、状态变化事件、内部接口 | `reminder_decision`、`reminder_schedule` | 依赖超时失败关闭，不创建可发送排程；回流首日不创建任何渠道排程 |
| `application/dispatch` | 抢占、发送前复核、重试、状态回写 | 到期扫描/延迟队列 | `reminder_delivery`、事件表 | 明确失败最多重试一次，未知状态先查询不盲发 |
| `application/snooze` | 一小时后重排并重新校验 | 用户点击稍后提醒 | 新排程版本、snooze 事件 | 无可用时间或触达资格失效则取消并返回原因 |
| `adapter/task` | 读取任务状态、截止时间和入口 | `TaskRepository` | 外部任务系统 | 超时和不可用按失败关闭处理 |
| `adapter/user` | 读取用户画像、行为和提醒设置 | `PreferenceRepository`、`BehaviorRepository` | 本地 Fixture 适配器；生产接入外部用户服务 | 设置读取失败不发送；行为读取失败按默认窗口降级 |
| `adapter/channel` | Push 发送、状态查询与发送记录 | `PushSender`（`InAppNotifier` 为 P1 预留，本期不实现） | 发送记录 | 渠道失败、未知、不可用分别处理；未授权或发送失败跳过本次提醒并记录未触达原因，不静默改用其他渠道 |
| `adapter/storage` | SQLite 连接、版本化迁移和事务封装 | 各 Repository 调用 | SQLite 文件和迁移记录 | 迁移失败阻止启动；连接失败快速失败，不使用内存替代业务事实 |
| `port` | 定义任务、用户、行为、渠道、事件、鉴权和时钟端口 | 应用层依赖注入 | Go 接口和值对象 | 端口只表达契约，不包含具体外部调用 |
| `repository` | 事务、唯一约束、条件更新 | 各应用用例 | 四类业务表 | 并发冲突返回幂等命中或状态冲突 |
| `transport/http` | 提供本地 HTTP/JSON 触发入口，承载 `AppOpened` 同步通道 | 本地 Demo 或受保护内部调用 | `internal/transport/http/dto` 的请求/响应 DTO 与 golden 契约用例 | 本地仅绑定回环地址，由 `http.enabled` 控制；不注册生产服务，不生成对外 IDL |
| `scheduler` | 提供评估、到期发送和 reconcile 的一次性执行入口 | CLI 或本地 HTTP 调用 | 调度运行结果 | 单进程单分片；不内置无限重试或长事务 |
| `observability` | 结构化日志、计数指标和事件关联字段 | 各应用用例 | stdout/本地测试记录 | 观测失败不改变业务状态，不记录敏感字段 |

## 4. 详细方案

### 4.1 关键交互流程

#### 4.1.1 提醒评估：FR-001、FR-002、FR-003、FR-004、FR-005、FR-008

正常链路：

```text
Evaluate(user_id, task_date)
 -> TaskRepository.GetDailyTask
 -> PreferenceRepository.GetLatest
 -> UserRepository.GetProfile
 -> BehaviorRepository.GetRecent(7d)
 -> ReminderRepository.GetDailyUsage
 -> EligibilityRule.Check
 -> TimePlanner.Plan
 -> ContentRenderer.Render(latest task snapshot)
 -> ReminderRepository.CreateDecisionAndSchedule
```

判定顺序固定为：

1. 任务不存在或无必做任务：记录 `NO_TASK`，不创建可发送排程。
2. 全部必做任务已完成：记录 `TASK_COMPLETED`，取消未发送排程。
3. 当前日期晚于截止时间：记录 `TASK_EXPIRED`，不发送普通提醒。
4. 用户关闭智能提醒：记录 `REMINDER_DISABLED`，取消未发送排程。
5. 用户分层按 PRD 3.3 的判定顺序现场计算，结果不落库为固定标签：历史数据不足 3 天时按被动型处理并记录 `INSUFFICIENT_HISTORY`；流失型（`inactive_days` ≥ 3）不进入主动 Push 排程，记录 `USER_INACTIVE`；AppOpened 事件中，回流型（本次打开前上一次打开距今天的间隔 `days_since_last_open` ≥ 3）当天不发送提醒、不生成 Push 排程并记录 `RETURNING_FIRST_DAY`，不占用当日 Push 用量。次日由每日评估恢复常规 Push 资格，仍需重新通过任务、设置、免打扰和频控校验；“回流首日取最近 1–2 天活跃时段”本期无生效场景，随 FR-006 列为 P1。
6. 当日系统主动 Push 已达到上限（默认 1 次）：记录 `DAILY_CAP_REACHED`，不创建第二条系统主动 Push 排程；用户主动触发的“稍后提醒”Push 单独计数，不占用该上限。
7. 其余用户计算时间：优先使用最近 7 天任务完成时间，其次使用 App 打开时间；不足时使用默认窗口并记录 `DEFAULT_WINDOW`。
8. 候选时间处于免打扰区间时，移动到下一个可用窗口；没有可用窗口时记录 `QUIET_HOURS` 或 `INSUFFICIENT_TIME`。

失败与边界链路：

- 任务、偏好或行为依赖超时：本次评估失败关闭，不发送；写入依赖错误指标，等待下一次任务或事件重试。
- 行为历史缺失：不视为系统错误，使用默认窗口，不阻断提醒机会。
- 跨午夜免打扰：按用户本地日期拆分区间，计算下一个可用时间，不能用服务器时区直接比较。
- 截止时间不足一小时：`Snooze` 不强行创建排程，返回 `INSUFFICIENT_TIME`。
- 重复评估：以 `(user_id, task_date, strategy_version)` 唯一键幂等 upsert，返回已有 `decision_id`。
- 数据库写入冲突：事务回滚并读取已存在记录；不得产生第二个可发送排程。

#### 4.1.2 到期发送：FR-004、FR-005、FR-008

正常链路：

```text
DispatchDue(now)
 -> ClaimSchedule(status=SCHEDULED, scheduled_at<=now)
 -> 再读 TaskRepository 和 PreferenceRepository
 -> FrequencyGuard.Check
 -> ContentRenderer.Render(latest task state)
 -> PushSender.Send(idempotency_key, payload) -> UpdateDeliveryStatus
 -> Publish delivery events
```

本期只有 Push 一条投递分支；站内投递分支（`InAppNotifier`）随 FR-006 列为 P1，不在本期链路内。

异常链路：

- 排程已被其他 worker 抢占：条件更新失败，当前 worker 结束，不重复调用渠道。
- 发送前任务完成、过期、关闭提醒或进入免打扰：条件更新为 `CANCELLED`，记录对应原因，不调用渠道。
- Push 明确失败：保留同一 `idempotency_key`，最多重试一次；超过次数为 `FAILED`，不再重试。
- Push 返回未知状态：标记 `UNKNOWN`，调用渠道查询接口；查询前禁止再次发送，无法确认时交由 reconcile，不突破当日系统主动 Push 上限。
- Push 未授权（用户关闭系统 Push）：不调用 Push，排程置 `CANCELLED` 并记录 `NO_AVAILABLE_CHANNEL`，跳过本次提醒，不在当天追加第二次触达。
- Push 明确发送失败且重试耗尽：排程置 `FAILED` 并记录原因，不降级到其他渠道；本期没有可用替代渠道，缺口记入监控。
- 回流首日等评估阶段已拒绝的情形：不创建排程，调度阶段不为其产生任何渠道投递。
- 本期不实现 Push 未触达后的站内承接；该承接随 FR-006 列为 P1，届时按 4.3.2.5 的适配器契约补充链路与用例。
- 任务服务不可用：失败关闭本次发送，排程标记依赖错误；不使用旧任务快照发送可能过期的文案。

#### 4.1.3 稍后提醒：FR-007

`Snooze(user_id, decision_id)` 读取最新任务、偏好、当日使用量和当前时间，计算一小时后的本地时间，再次执行免打扰、截止时间、任务完成和频控判断。新的排程使用原 `decision_id` 加递增 `schedule_version` 关联原提醒。

- 未完成任务、仍有可用时间且 Push 可用：创建新的 Push 排程（`schedule_type=SNOOZE`）并写入 `reminder_snoozed`。
- 任务已完成、过期、提醒关闭、无可用时间：不创建新排程，返回原因并记录事件。
- 延后提醒使用 Push 渠道，且**不占用当日 1 次系统主动 Push 上限**：该次提醒由用户主动触发，按 `schedule_type=SNOOZE` 独立计量；据此同一用户同一天最多 2 次 Push（1 次系统主动 + 1 次用户触发的延后提醒）。
- 延后提醒产生的这次 Push **不再提供“稍后提醒”入口**：payload 不带该按钮，服务端只接受 `schedule_type=INITIAL` 排程发起 snooze；对同一 `decision_id` 的第二次 snooze 直接拒绝并返回 `INVALID_REQUEST`（该请求在入口层即属非法调用，见 4.3.4），延后链条最多一段，不产生第三次 Push。
- Push 不可用（未授权或发送失败）时返回 `NO_AVAILABLE_CHANNEL`，跳过本次延后提醒，不静默改用其他渠道。
- 重复点击使用 `(decision_id, snooze_request_id)` 幂等键；同一请求只产生一个新排程。

#### 4.1.4 事件与任务完成回传：AC-011

所有事件写入 `reminder_event`，事件发布失败不阻塞已完成的渠道状态，但由 outbox 或 reconcile 补发。任务完成事件只关联既有任务系统的事实，不由提醒服务修改任务完成状态。

#### 4.1.5 异常处理矩阵

| 异常点 | 检测 | 处理 | 数据保护 |
| --- | --- | --- | --- |
| 任务读取超时 | context deadline | 失败关闭本次评估 | 不使用旧任务快照 |
| 任务服务不可用 | 连接错误 | 取消发送，等待重评估 | 不创建可发送排程 |
| 任务数据格式错误 | schema 校验失败 | 记录 `INVALID_TASK_DATA` | 拒绝渲染内容 |
| 任务无必做项 | 资格判断 | 记录 `NO_TASK` | 不写可发送排程 |
| 任务已完成 | 状态复核 | 取消排程 | 不调用渠道 |
| 任务即将过期 | 时间比较 | 记录 `INSUFFICIENT_TIME` | 不发送过期提醒 |
| 任务已过期 | 截止时间比较 | 记录 `TASK_EXPIRED` | 不重试渠道 |
| 偏好读取超时 | context deadline | 失败关闭发送 | 不采用旧偏好 |
| 偏好服务不可用 | 连接错误 | 等待下一次评估 | 不发送提醒 |
| 提醒开关关闭 | 最新设置 | 取消排程 | 写入取消原因 |
| 免打扰开始 | 时区计算 | 延后排程 | 重新检查截止时间 |
| 免打扰跨午夜 | 本地日期拆分 | 计算下一个窗口 | 不使用服务器时区 |
| 免打扰配置非法 | 参数校验 | 使用安全默认并记录错误 | 不在未知时间发送 |
| 行为历史缺失 | 空结果 | 使用默认窗口 | 标记 `DEFAULT_WINDOW` |
| 行为服务超时 | 超时错误 | 降级默认窗口 | 不阻断可解释决策 |
| 行为数据时间异常 | 时间范围校验 | 丢弃异常样本 | 不影响其他历史样本 |
| 历史数据不足 3 天 | `history_days_available` 校验 | 按被动型处理并使用默认窗口 | 记录 `INSUFFICIENT_HISTORY`，不误判为流失 |
| 流失型用户 | `inactive_days` ≥ 3 | 结束主动 Push 决策 | 不提高发送频次，次日行为变化后重新判定 |
| 回流型用户 | AppOpened 事件中，本次打开前上一次打开距今天的间隔 `days_since_last_open` ≥ 3 | 当天不发送提醒、不生成 Push 排程，记录 `RETURNING_FIRST_DAY` 且不占用当日 Push 用量 | 不受流失策略拦截，不产生双重打扰；不落任何渠道排程 |

| 决策重复创建 | 唯一键冲突 | 读取已有决策 | 不产生第二个 decision_id |
| 决策事务失败 | commit 错误 | 回滚并重试评估 | 不留下半条排程 |

### 4.2 状态机

#### 4.2.1 决策状态

决策、排程、渠道投递和用户行为使用独立状态，避免一个状态字段承载多个生命周期。

```text
决策：EVALUATED -> SCHEDULED -> COMPLETED
                  |             |
                  +----------> CANCELLED

排程：SCHEDULED -> CLAIMED -> SENDING -> RETRY_WAIT -> CLAIMED
      |             |           |  |
      +----------> CANCELLED     |  +-> UNKNOWN -> RECONCILING
                                 +-----> SENT/FAILED

站内排程（P1 预留，本期不产生）：WAIT_IN_APP -> DELIVERED_TO_IN_APP -> DISPLAYED -> OPENED
              |                    |               |
              +--------------------+---------------+-------> CANCELLED
```

| 状态 | 进入条件 | 允许下一状态 |
| --- | --- | --- |
| `EVALUATED` | 评估完成且未立即拒绝 | `SCHEDULED`、`CANCELLED` |
| `EVALUATED` | 资格评估完成并已生成决策 | `SCHEDULED`、`CANCELLED` |
| `SCHEDULED` | 排程持久化成功 | 由排程状态推进；决策本身不直接进入投递状态 |
| `COMPLETED` | 任务系统确认全部必做任务完成 | 终态 |
| `CANCELLED` | 完成、过期、关闭、频控或无渠道 | 终态 |
| `DELIVERED_TO_IN_APP`（P1 预留） | 已调用既有站内消息能力且投递成功 | `DISPLAYED`（有曝光回执时）、`CANCELLED` |
| `DISPLAYED`（P1 预留） | 收到曝光回执，或既有能力只回传点击时的投递成功态 | `OPENED`、`CANCELLED` |
| `OPENED`（P1 预留） | 收到点击回执 | 终态 |

本期排程状态为 `SCHEDULED`、`CLAIMED`、`SENDING`、`RETRY_WAIT`、`CANCELLED`；投递状态为 `SENDING`、`SENT`、`DELIVERED`、`FAILED`、`UNKNOWN`、`RECONCILING`。站内排程状态 `WAIT_IN_APP`、`DELIVERED_TO_IN_APP`、`DISPLAYED`、`OPENED` 为 P1 预留，本期不产生。`task_completed` 只通过事件记录表达，不写入决策或投递状态。

状态更新必须带版本号或条件，例如 `WHERE id=? AND status='SCHEDULED'`。租约超时后只能由 reconcile 释放，不能由多个 worker 同时发送。

### 4.3 接口定义

#### 4.3.1 API 接口文档地址

**已确认：本期不注册真实内部服务，也不生成对外 IDL。** 交付形态为单进程装配（`cmd/reminder-service`）加可选本地 HTTP 入口，入口只监听 `127.0.0.1`，由配置项 `http.enabled` 控制；调度使用进程内触发，单机单分片。注册服务名/PSM、泳道与环境、服务发现、超时配置和容量水位属于生产接入动作，不经本项目决定，接入时按既有服务规范映射，端口-适配器结构保证应用层不需要改动。

**已确认：协议为 HTTP/JSON，本期不引入 thrift/proto。** 理由是本期只有三个内部接口，调用方是本地调度入口和经既有网关转发的 App，没有跨语言 RPC 需求；仓库内也不存在本服务的 IDL 工程。报文结构固化在 `internal/transport/http/dto`，字段名和枚举值用 golden 用例锁定，用契约测试替代独立 IDL；路径已带 `/v1/`，字段只增不删不改名，确需改名或删除时必须升版本。若后续评审要求补 IDL，只允许用 proto 作为契约来源并生成同一套 DTO，协议仍保持 HTTP/JSON，不改为 RPC。

接口定义不得允许客户端传入 `should_remind`、`channel` 或 `reason_code` 等服务端决策字段。鉴权、超时、重试和限流按下列已确认默认值实现，并标注为**待压测校准**，不是线上实测结论：

| 项目 | 本期本地实现 | 生产接入要求 |
| --- | --- | --- |
| 鉴权 | `Authenticator` 端口 + 静态令牌白名单，仅回环地址 | 服务身份或 mTLS，调用方身份与 `user_id` 归属校验 |
| 超时 | 单请求硬超时：`evaluate` 5s、`snooze` 2s、`dispatch-due` 10s，超时按 `DEPENDENCY_TIMEOUT` 处理 | 按既有网关和服务规范调整，不在本地宣称最终值 |
| 重试 | 写请求不自动重试，由调用方复用 `request_id` 重放；读请求仅查询状态 | 遵循上游调度重试策略，仍以幂等键兜底 |
| 限流 | 令牌桶：`evaluate`/`snooze` 按调用方 QPS + 用户级 1 QPS；`dispatch-due` 由本地批量 50、单 worker 约束 | 接入服务级限流和下游 quota 后再定阈值 |

#### 4.3.2 内部 HTTP/RPC 接口

##### 4.3.2.1 EvaluateReminder

| 项目 | 定义 |
| --- | --- |
| 方法/路径 | `POST /internal/v1/reminders/evaluate`（本地 HTTP/JSON 入口） |
| 入口 | 每日分片任务、`AppOpened` 同步通道、任务状态变化事件、偏好变化事件 |
| 限流 | 本地单进程按用户串行；单请求只处理一个用户；阈值见 4.3.1 限流行 |
| 鉴权 | 与 4.3.1 一致；不接受客户端直接传入决策字段 |
| 幂等 | `request_id` + `(user_id, task_date, strategy_version)` |

```go
type EvaluateReminderRequest struct {
    RequestID  string `json:"request_id"`   // 调用请求唯一 ID
    UserID     string `json:"user_id"`      // 匿名用户 ID
    TaskDate   string `json:"task_date"`    // 用户本地任务日期，YYYY-MM-DD
    Trigger    string `json:"trigger"`      // DAILY_BATCH、APP_OPENED、TASK_CHANGED、PREFERENCE_CHANGED
    LastOpenAt string `json:"last_open_at"` // 仅 APP_OPENED 必填；本次打开前的最近一次打开时间，RFC3339，无历史为空串
}

type EvaluateReminderResponse struct {
    DecisionID string `json:"decision_id"` // 决策 ID；幂等命中时返回已有 ID
    Status     string `json:"status"`      // CREATED、REUSED、REJECTED
    ReasonCode string `json:"reason_code"` // 服务端计算的原因码
}
```

`Trigger=APP_OPENED` 时服务端用请求携带的“打开前”`last_open_at` 计算 `days_since_last_open`，不读取已被本次打开覆盖的最新记录，避免回流首日判定被自身打开行为抹掉。`LastOpenAt` 与 `Trigger` 不匹配时返回 `INVALID_REQUEST`，不做降级猜测。

##### 4.3.2.2 DispatchDue

| 项目 | 定义 |
| --- | --- |
| 方法/路径 | `POST /internal/v1/reminders/dispatch-due`（本地 HTTP/JSON 入口） |
| 入口 | `reminder_dispatch` 调度任务 |
| 限流 | 本地默认批量 50、单 worker；Mock 渠道最多 10 次/秒；禁止无限并发 |
| 鉴权 | 本地仅绑定回环地址；生产接入要求调度服务身份鉴权 |

##### 4.3.2.3 SnoozeReminder

| 项目 | 定义 |
| --- | --- |
| 方法/路径 | `POST /internal/v1/reminders/{decision_id}/snooze`（本地 HTTP/JSON 入口） |
| 入口 | 用户点击“稍后提醒”后由 App 通过既有网关转发 |
| 限流 | 用户维度限流，重复请求必须幂等 |
| 鉴权 | 本地请求必须提供并校验 `user_id` 与决策归属；生产接入使用用户身份或服务间鉴权 |
| 幂等 | `request_id` + `decision_id` 唯一键；同一请求重试必须复用 `request_id`；`SCHEDULED` 状态的重复 snooze 返回已有排程 |
| 频控 | `SNOOZE` 排程按 `schedule_type=SNOOZE` 独立计量，不占用当日系统主动 Push 上限；对 `schedule_type=SNOOZE` 排程发起 snooze 返回 `INVALID_REQUEST` |

type SnoozeReminderRequest struct {

所有内部接口使用统一错误响应：

```go
type ErrorResponse struct {
    Code      string `json:"code"`       // 业务错误码
    Message   string `json:"message"`    // 不含敏感信息的可读描述

    RequestID string `json:"request_id"` // 请求追踪 ID

```
`UNKNOWN` 类错误必须通过查询或 reconcile 收敛，不能仅依据 `Retryable=true` 直接重发。

##### 4.3.2.4 AppOpened / PreferenceChanged / ReminderEvent

**已确认：`AppOpened` 使用同步评估 + 异步事件双通道。** 回流首日判定必须在用户当次打开 App 时完成（当天不发送提醒、不生成 Push 排程，见 PRD 3.3.2），若只走异步投递，判定会顺延到次日，AC-016 当次不生效。因此：

| 通道 | 承担能力 | 本期实现 |
| --- | --- | --- |
| 同步（主通道） | App 进入今日任务相关页面时调用 `EvaluateReminder`，`Trigger=APP_OPENED` 并携带打开前的 `last_open_at`，保证回流首日判定当次会话生效 | 由 `transport/http` 提供；P95 ≤ 2s，超时按 `DEPENDENCY_TIMEOUT` 失败关闭，不影响 App 主流程 |
| 异步（旁路） | 同一打开行为发布 `AppOpened` 事件，供审计、补算和指标统计，不承担当次会话的时延要求 | 版本化 JSON Fixture 或进程内事件入口；端到端 P95 ≤ 5s |

`PreferenceChanged` 和任务开始/完成事件只走异步通道；若生产只能提供异步 `AppOpened`，回流首日判定会顺延到下一次触发，AC-016 的时点口径需同步调整。P1 的站内提醒展示（FR-006）另行核对既有能力能否在用户进入承载页面前完成投递，本期不依赖该能力。`AppOpened` 的 `days_since_last_open` 必须在更新“最近一次打开”记录之前计算，行为服务需显式返回该值或返回打开前的 `last_open_at` 由提醒服务计算。

事件统一信封字段：`event_id`、`event_name`、`event_time`、`schema_version`、`source`、`user_id`（匿名）、`task_date`、`timezone`，加各事件自身的业务 payload。本契约口径：`event_id` 作为 `reminder_event` 唯一键去重，同一 `event_id` 重复投递按幂等忽略；重放窗口 ≥ 7 天；投递失败走有限重试，超限进入死信并告警，不触发补偿性渠道发送。本地交付不接入 MQ 或真实事件总线，生产接入时再把同一契约映射到既有事件系统，并核验来源身份、签名、重放、重试和死信能力。事件只包含匿名用户 ID、任务日期、设置版本和必要状态，不传任务正文、成绩、姓名或手机号。

##### 4.3.2.5 InAppNotifier 站内提醒适配器契约（P1 预留，本期不实现）

**本期不实现本节契约。** 站内提醒随 FR-006 移出 P0；本节保留 P1 承接所需的适配器口径，供后续实施时直接复用。

**P1 已确认口径：站内提醒不新增 App/Web 接口。** 展示由既有站内消息能力在其承载页面上完成，点击后经既有 Deep Link 落到今日任务页；提醒服务只负责复核、占用额度、投递和消费回执。因此本节定义的是适配器契约，不是对 App 的 HTTP 接口；既有能力的接口形态与字段名属于生产联调输入（见 9.3）。

P1 投递入参（适配器映射到既有站内消息接口）：

| 字段 | 说明 |
| --- | --- |
| `dedupe_key` | 幂等去重键，建议 `user_id + task_date + IN_APP + decision_id`；重复投递按幂等命中处理，不重复占用额度 |
| `user_id` | 匿名用户 ID |
| `carrier_page` | 承载页面标识（如今日任务页、任务详情页），取值限定为既有能力已支持的枚举；无可用承载页面即 `NO_AVAILABLE_CHANNEL` |
| `content_template` + 变量 | 文案模板与任务数、预计用时等变量；敏感字段不得进入 |
| `deep_link` | 落到今日任务页，复用既有任务入口链路，不新建落地页 |
| `decision_id` | 关联决策，供回执回传后归因 |
| `expire_at` | 当日 24:00（用户本地时区），过期不再展示 |

P1 回执消费分档，决定状态推进与触达口径：

| 既有能力回执 | 状态推进 | 指标口径 |
| --- | --- | --- |
| 曝光与点击都回传 | `DELIVERED_TO_IN_APP -> DISPLAYED -> OPENED` | 站内触达以 `DISPLAYED` 计，点击以 `OPENED` 计 |
| 只回传点击 | 投递成功即置 `DISPLAYED`，点击置 `OPENED` | 站内触达按投递成功计，指标标注为“投递量 + 点击量” |
| 无回执 | 停在 `DELIVERED_TO_IN_APP`，视为终态触达 | 站内触达按投递成功计，不产出曝光率与点击率 |

P1 回执事件沿用 4.3.2.4 的统一信封，业务 payload 至少包含 `decision_id`、`carrier_page`、`event_type`（`IMPRESSION`/`CLICK`）与 `client_event_id`；`client_event_id` 作为唯一键去重，重复回执幂等忽略。投递被拒、承载页面不可用、站内服务不可用或投递超时，统一记为 `NO_AVAILABLE_CHANNEL`，不转 Push、不补发第二次。投递需落在 `AppOpened` 同步通道预算内（P95 ≤ 2s），超出预算则不投递并记录原因，避免拖慢 App 主流程。

#### 4.3.4 错误码与上下游异常

| 错误码 | 分类 | 处理 |
| --- | --- | --- |
| `REMINDER_ALREADY_EXISTS` | 正常幂等 | 返回已有决策或排程，不重试 |
| `DAILY_CAP_REACHED` | 正常业务拒绝 | 结束本次发送，不重试 |
| `TASK_COMPLETED` | 正常业务拒绝 | 取消排程，不发送 |
| `TASK_EXPIRED` | 正常业务拒绝 | 取消排程，不发送 |
| `REMINDER_DISABLED` | 正常业务拒绝 | 取消未发送排程 |
| `QUIET_HOURS` | 正常延后 | 计算下一个可用窗口 |
| `NO_AVAILABLE_CHANNEL` | 正常业务拒绝 | 不重试 Push，记录渠道不可用；本期含义为 Push 未授权或发送失败，站内承接列为 P1 |
| `DEPENDENCY_TIMEOUT` | 可重试错误 | 本次失败关闭，下一次评估重试，不能直接发送旧快照 |
| `DEPENDENCY_UNAVAILABLE` | 可重试错误 | 熔断或等待下一次调度 |
| `CHANNEL_SEND_FAILED` | 明确渠道错误 | 最多一次重试，保持幂等键 |
| `CHANNEL_STATUS_UNKNOWN` | 未知状态 | 查询状态，禁止盲目重发 |
| `INVALID_REQUEST` | 调用错误 | 拒绝并告警，不重试 |

下游 provider code 到内部 `error_code` 的映射口径如下，用于适配器统一收敛外部错误，避免把厂商错误码透传到接口层。真实厂商错误码枚举属于生产联调输入，接入前必须补全并冻结；未在表中列出的厂商错误码一律按 `CHANNEL_STATUS_UNKNOWN` 进入 reconcile，不得默认重发。

| 下游场景 | 下游返回（示例形态） | 内部 `error_code` | 是否重试 |
| --- | --- | --- | --- |
| 请求超时、连接中断 | timeout / connection reset | `DEPENDENCY_TIMEOUT` | 由调用方重放，不盲目重发渠道 |
| 下游 5xx、熔断、限流拒绝 | 服务不可用、429/quota | `DEPENDENCY_UNAVAILABLE` | 延后重试或降速，不突破 quota |
| 渠道明确拒绝（凭证失效、参数非法、目标不可达） | 渠道业务错误码 | `CHANNEL_SEND_FAILED` | 最多一次，幂等键不变；凭证失效关闭 Push 渠道 |
| 渠道返回结果不确定或回执不合法 | 空响应、schema 校验失败 | `CHANNEL_STATUS_UNKNOWN` | 先查询状态，禁止盲目重发 |
| 请求参数缺失或前后矛盾（如 `Trigger` 与 `LastOpenAt` 不匹配） | 本地校验失败 | `INVALID_REQUEST` | 不重试，告警 |
| 业务规则拒绝（完成、过期、关闭、频控、无渠道） | 本地规则判定 | `TASK_COMPLETED`、`TASK_EXPIRED`、`REMINDER_DISABLED`、`DAILY_CAP_REACHED`、`NO_AVAILABLE_CHANNEL`、`RETURNING_FIRST_DAY` | 不重试 |

外部依赖按强弱处理：任务状态和用户设置是发送前强依赖，不可用时失败关闭；行为历史是弱依赖，读取失败使用默认窗口；Push 是发送渠道依赖，明确失败可有限重试，未知状态必须先查询；事件系统是异步弱依赖，写 outbox 后由 publisher 重试，不阻塞渠道状态。

### 4.4 定时任务/刷数据方案

#### 4.4.1 任务功能及设计

| 任务 | 触发方式 | 分片与幂等 | 重跑与积压处理 | 监控 |
| --- | --- | --- | --- | --- |
| `reminder_evaluate` | 本地 CLI/HTTP 一次性执行；回流首日由本地 `AppOpened` 事件触发 | 单进程单分片；唯一键保证重复评估幂等 | 单批 100 个用户；失败请求可重复执行；不跨日补发 | 评估成功率、耗时、原因码分布、事件处理延迟 |
| `reminder_dispatch` | 本地 CLI/HTTP 一次性扫描到期排程 | 单 worker 使用 `ClaimSchedule` 租约和条件更新 | 单批 50 条；按最早排程优先；不无限重试 | 抢占、发送、重试、未知数 |
| `reminder_reconcile` | 本地 CLI/HTTP 一次性扫描 UNKNOWN/outbox | `event_id` 和 delivery key 幂等 | 只查询未知状态，不新增 Push；失败留待下一次手动执行 | UNKNOWN 收敛时间、outbox 积压 |

本地默认单进程、单分片、评估批量 100、dispatch 批量 50、租约 2 分钟、Mock 渠道上限 10 次/秒；命令是一次性执行，不内置常驻定时器。调度器只调用应用服务，不直接写业务表。生产调度平台的执行间隔、分片和 quota 仍需接入时按外部平台事实核验。

#### 4.4.2 上线及回滚方案

先发布 SQLite 迁移和只读适配器，保持 `feature_enabled=false`；完成下游联调和测试后再开启评估与 dispatch。关闭总开关后停止新智能排程，保留历史记录并恢复固定 Push 对照策略。数据库只新增表和索引，不删除历史任务或发送记录。

本地 SQLite 文件按最小权限创建，应用不读取外部凭证；本地 HTTP 仅绑定回环地址。生产部署时再申请服务身份、数据库最小权限、调度执行权限和下游凭证，所有调用下游的任务配置超时和限流，不能通过无限重试保护本服务。

#### 4.4.3 监控指标设计

| 任务 | 指标 | 告警方向 |
| --- | --- | --- |
| `reminder_evaluate` | 评估失败率、分片完成率、重复命中数、原因码突增 | 失败率、重复命中和积压超阈值 |
| `reminder_dispatch` | 抢占数、发送成功率、取消数、重试数、UNKNOWN 数 | UNKNOWN、重复发送、发送失败突增 |
| `reminder_reconcile` | 查询成功率、未知状态收敛时间、outbox 积压 | 长时间未收敛或积压增长 |

### 6.2 灰度和应急方案

1. `feature_enabled` 默认关闭；本地 Demo 仅使用预置 Fixture，不接入实验分流或真实用户灰度。
2. 生产灰度组使用智能提醒，对照组继续使用固定 18:00 Push，同一用户同一天只能命中一种策略；灰度组内系统主动 Push 每天最多 1 次，用户触发的延后提醒独立计量；实验比例和上线阈值不在本地交付中宣称。
3. 发现重复发送、已完成仍提醒、下游异常或指标劣化时，关闭总开关和智能 dispatch。
4. 关闭后停止新增智能排程，固定 Push 恢复；历史决策、发送和事件记录保留。
5. 本期只有 Push 一个渠道，可独立关闭；站内提醒渠道开关为 P1 预留。任何渠道开关都不允许静默切换为未经频控校验的其他渠道。

### 6.3 上线方案

1. 先完成数据库表、索引和 repository 验证，不开启功能开关。
2. 部署只读依赖适配器和规则服务，完成 Mock、集成测试和监控配置。
3. 小流量开启 `reminder_evaluate`，确认资格分布、重复命中和排程积压。
4. 开启 `reminder_dispatch`，先观察 Push 失败、UNKNOWN、到达和打开链路。
5. 分阶段扩大用户范围，每阶段确认无重复发送和既有功能回退。
6. 达到业务确认的实验和质量阈值后再全量；未达到则关闭开关并恢复固定 Push。

#### 6.3.1 止损方案

- 总开关：停止智能评估和 dispatch。
- 渠道开关：本期只关闭 Push；站内投递开关为 P1 预留。
- 数据库保护：唯一键、条件更新和发送前二次校验作为最后防线。
- 数据修复：只允许受控脚本修复错误状态，禁止直接删除发送记录。
- UNKNOWN 保护：未知发送结果只查询和补记，不自动盲发。

#### 6.3.2 补偿逻辑

本功能不涉及积分、金额或其他有价资源，不设计奖励补偿。事件投递失败使用 outbox/reconcile 补记，不产生第二次渠道发送；若业务未来要求重发，必须生成新的业务请求并再次通过每日频控和幂等校验。

## 7. 新增数据中心成本评估

### 7.1 评估结论

本次可运行交付使用 SQLite 文件、单进程调度和本地日志，不新增独立数据库、消息队列或监控平台，增量数据中心成本按本地磁盘和进程资源计，不虚构线上金额。逻辑容量仍按 30 万用户每日 30 万条决策、最多 300 万条事件上限估算，用于验证表结构和归档边界，不是线上压测结果。未来生产成本取决于数据库、调度、日志和保留策略，需另行评估。
