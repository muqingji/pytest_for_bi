# 智能提醒助手 Go 后端技术方案

> 文档状态：评审稿
> 实现语言：Go
> 本期范围：PRD 中全部 P0 MVP 需求
> 说明：本文描述技术设计和实现边界，不包含完整业务代码。外部系统接口以适配器隔离，具体服务名称、协议和生产配置待接入时确认。

## 1. 需求背景

### 1.1 相关文档

- 产品需求：[智能提醒助手PRD(9稿).md](../智能提醒助手PRD(9稿).md)
- 验收标准：[验收标准.md](../需求拆解/验收标准/验收标准.md)

### 1.2 需求范围

智能提醒服务在既有任务系统和 Push 能力之上，完成提醒资格判断、提醒时间计算、排程、频控、渠道选择、延后提醒和事件记录。首期服务当天有未完成任务的被动型学生；已完成任务不提醒，每位学生每天最多发送一次 Push。

以下能力是外部依赖，不在本期新建：

- 每日任务、必做任务定义和任务完成状态。
- 任务详情页、做题流程、任务完成回传和完成率统计。
- Push 发送基础设施和操作系统 Push 权限。
- App 站内提醒展示能力。

## 2. 目标

### 2.1 技术目标

1. 用可解释的规则引擎实现 P0 提醒决策。
2. 将决策、排程、发送和用户行为通过 `decision_id` 关联，支持问题排查和效果归因。
3. 通过持久化唯一约束、幂等键和状态机，保证重复调度、并发执行和发送重试不突破每日 Push 上限。
4. 通过适配器隔离任务系统、用户配置、Push 和站内提醒，便于本地测试和后续替换生产依赖。
5. 支持灰度关闭和固定 Push 回退，不修改历史任务数据和历史发送记录。

### 2.2 非目标

- 不实现任务页面、做题流程、任务完成统计或 Push 厂商配置中心。
- 不实现流失型用户召回策略、P1 提醒记录页面和完整运营后台。
- 不在本期引入机器学习模型；提醒时间采用确定性规则。

## 3. 整体架构

### 3.1 技术选型

| 领域 | 方案 | 说明 |
| --- | --- | --- |
| 服务语言 | Go 1.22+ | 版本以项目仓库基线为准，核心决策逻辑使用标准库和可注入接口 |
| 服务形态 | Go 常驻服务 + 定时调度入口 | 调度器可由现有任务平台触发，具体平台待确认 |

## 4. 详细方案

### 4.1 关键交互流程

#### 4.1.1 提醒评估

```text
Trigger -> ReminderEvaluator: Evaluate(user_id, task_date)
ReminderEvaluator -> TaskRepository: GetDailyTask
TaskRepository --> ReminderEvaluator: task status/deadline/entry
ReminderEvaluator -> UserPreferenceRepository: GetSegment/Preference/PushPermission
UserPreferenceRepository --> ReminderEvaluator: user data
ReminderEvaluator -> BehaviorRepository: GetRecentBehavior(7d)
BehaviorRepository --> ReminderEvaluator: completion/open history
ReminderEvaluator -> ReminderRepository: GetDailyUsage
ReminderRepository --> ReminderEvaluator: sent/scheduled state
ReminderEvaluator -> EligibilityRule: Check
EligibilityRule --> ReminderEvaluator: eligible or reason
ReminderEvaluator -> TimePlanner: Plan
TimePlanner --> ReminderEvaluator: scheduled_at/channel
ReminderEvaluator -> ReminderRepository: CreateDecisionAndSchedule
ReminderRepository --> ReminderEvaluator: decision_id/idempotent result
```

处理规则：

1. 任务不存在、已完成、已过期、用户关闭提醒或达到频控时，返回不可提醒原因，不创建可发送排程。
2. 被动型用户进入正常提醒策略；流失型用户不通过增加本功能频次召回，记录 `USER_INACTIVE` 并结束本次主动 Push 决策。
3. 用户历史行为优先使用最近 7 天任务完成时间，其次使用 App 打开时间；无足够数据时使用默认活跃窗口。
4. 候选时间必须避开免打扰时间，并预留完成任务所需时间；没有可用时间时记录 `INSUFFICIENT_TIME`。
5. 保存决策和排程时使用数据库唯一约束，重复触发返回已有决策，不重复创建。

#### 4.1.2 到期发送

```text
Scheduler -> DispatchHandler: DispatchDue(now)
DispatchHandler -> ReminderRepository: ClaimSchedule(schedule_id)
ReminderRepository --> DispatchHandler: schedule lease/result
DispatchHandler -> TaskRepository: GetDailyTask(latest)
DispatchHandler -> PreferenceRepository: GetLatestPreference
DispatchHandler -> FrequencyGuard: CheckLatestState
FrequencyGuard --> DispatchHandler: send/cancel/reason
DispatchHandler -> PushSender: Send(idempotency_key, payload)
PushSender --> DispatchHandler: accepted/delivered/failed/unknown
DispatchHandler -> ReminderRepository: UpdateDeliveryStatus
DispatchHandler -> EventPublisher: Publish lifecycle event
```

异常链路：

- 任务系统超时或不可用：采用失败关闭，不发送提醒；记录依赖错误并等待下一次评估。
- 用户在排程后完成任务：取消排程，记录 `TASK_COMPLETED`。
- 用户在排程后关闭提醒或进入免打扰：取消或顺延排程，使用最新设置。
- Push 返回明确失败：按 AC-007 最多重试一次，使用相同幂等键。
- Push 返回未知状态：不立即盲目重发，先查询既有渠道状态；无法确认时标记 `UNKNOWN`，由人工或补偿任务处理，不能突破每日上限。
- 站内提醒不可用：不调用 Push 替代发送，记录 `NO_AVAILABLE_CHANNEL`。

#### 4.1.3 稍后提醒

1. `Snooze` 请求校验当前用户、决策状态和任务日期。
2. 读取最新任务状态、提醒设置、截止时间和当天 Push 使用情况。
3. 计算一小时后的时间；若进入免打扰、超过截止时间或不满足频控，则取消并返回原因。
4. 若当天已经发送过 Push，默认使用站内提醒；该渠道关系待业务确认，任何实现不得发送第二次 Push。
5. 生成新的排程事件，保留原 `decision_id` 关联并增加 `schedule_version`。

### 4.2 状态机

#### 4.2.1 排程状态

```text
SCHEDULED
   ├─> CLAIMED -> SENDING -> SENT -> DELIVERED -> OPENED -> COMPLETED
   ├─> CLAIMED -> CANCELLED
   ├─> SENDING -> RETRY_WAIT -> CLAIMED
   └─> SENDING -> UNKNOWN
```

| 状态 | 含义 | 允许的下一状态 |
| --- | --- | --- |
| `SCHEDULED` | 已创建、等待到期 | `CLAIMED`、`CANCELLED` |
| `CLAIMED` | 已被一个发送 worker 抢占 | `SENDING`、`CANCELLED` |
| `SENDING` | 正在调用渠道 | `SENT`、`RETRY_WAIT`、`UNKNOWN` |
| `RETRY_WAIT` | 等待一次重试 | `CLAIMED`、`FAILED` |
| `SENT` | 渠道接受发送 | `DELIVERED`、`UNKNOWN` |
| `DELIVERED` | 渠道确认送达 | `OPENED`、`COMPLETED` |
| `OPENED` | 用户打开提醒 | `COMPLETED` |
| `COMPLETED` | 任务系统确认全部必做任务完成 | 终态 |
| `CANCELLED` | 被任务状态、设置或频控取消 | 终态 |
| `FAILED` | 已耗尽重试次数 | 终态 |
| `UNKNOWN` | 渠道结果无法确认 | 需查询或人工处理 |

状态更新必须带当前版本号或使用条件更新，例如 `WHERE status = 'SCHEDULED'`，避免多个 worker 同时发送。

##### 4.3.2.1 Go 领域接口

```go
type TaskRepository interface {

	ClaimSchedule(ctx context.Context, scheduleID string, now time.Time) (ReminderSchedule, error)
	UpdateSchedule(ctx context.Context, update ScheduleUpdate) error

type ReminderEngine interface {
```

##### 4.3.2.2 内部 HTTP/RPC 候选接口

| 接口 | 方法 | 用途 | 鉴权 | 限流 |
| --- | --- | --- | --- | --- |
| `/internal/v1/reminders/evaluate` | POST | 触发指定用户和日期的提醒评估 | 服务间鉴权 | 按调用方和用户限流 |
| `/internal/v1/reminders/{decision_id}/snooze` | POST | 一小时后重新排程 | 用户身份或服务间鉴权 | 用户维度限流 |
| `/internal/v1/reminders/dispatch-due` | POST | 调度器触发到期发送 | 服务间鉴权 | 调度任务维度限流 |
| `/internal/v1/reminders/events` | POST | 接收渠道打开、到达和任务完成事件 | 服务间鉴权/签名 | 按来源限流 |

请求字段示例：

```json
{
  "user_id": "u_123",
  "task_date": "2026-09-20",
  "decision_id": "d_123",
  "request_id": "r_123"
}
```

安全要求：

- 仅允许服务间调用；生产使用现有 mTLS、服务身份或网关鉴权能力，具体方案待确认。
- 所有请求携带 `request_id`，日志中使用匿名用户 ID，不记录任务正文和成绩。
- 事件回调需要校验来源签名或服务身份，并通过 `event_id` 去重。
- 不允许客户端传入 `should_remind`、`channel` 等决策结果；这些字段只能由服务计算。

##### 4.3.2.3 错误码和处理

| 错误码 | 类型 | 处理 |
| --- | --- | --- |
| `REMINDER_ALREADY_EXISTS` | 正常幂等 | 返回已有 `decision_id`，不重复创建 |
| `DAILY_CAP_REACHED` | 正常业务拒绝 | 不重试，记录决策原因 |
| `TASK_COMPLETED` | 正常业务拒绝 | 取消排程，不发送 |
| `TASK_EXPIRED` | 正常业务拒绝 | 不发送，记录原因 |
| `REMINDER_DISABLED` | 正常业务拒绝 | 不发送，取消未发送排程 |
| `QUIET_HOURS` | 正常业务延后 | 计算下一个可用窗口 |
| `NO_AVAILABLE_CHANNEL` | 正常业务拒绝 | 不重试，记录渠道不可用 |
| `DEPENDENCY_TIMEOUT` | 可重试 | 按调用方重试策略处理，评估失败时不发送 |
| `DEPENDENCY_UNAVAILABLE` | 可重试 | 熔断或等待下一次调度，不发送 |
| `CHANNEL_SEND_FAILED` | 可重试 | 最多重试一次，保持相同幂等键 |
| `CHANNEL_STATUS_UNKNOWN` | 未知状态 | 查询渠道状态，禁止直接重复发送 |
| `INVALID_REQUEST` | 参数错误 | 不重试，告警并修正调用方 |

### 4.4 定时任务/刷数据方案

#### 4.4.1 任务功能及设计

本期包含三类调度入口：

| 任务 | 触发方式 | 职责 | 兼容性/时长要求 |
| --- | --- | --- | --- |
| `reminder_evaluate` | 每日任务或任务/设置变化事件 | 创建当日决策和排程 | 按用户分片，重复执行必须幂等 |
| `reminder_dispatch` | 高频到期扫描或延迟队列 | 抢占到期排程并发送 | 单批处理设置上限，避免长事务 |
| `reminder_reconcile` | 定时低频任务 | 查询未知发送状态和补记事件 | 不直接新增 Push 发送，先查询渠道状态 |

具体调度平台和执行间隔待确认。调度器只能调用应用服务，不直接写业务表。

#### 4.4.2 上线及回滚方案

- 先部署代码和表结构，再打开灰度开关；关闭开关后停止智能排程，恢复固定 Push。
- 新旧数据只追加，不修改历史任务完成和历史 Push 记录。
- 任务失败可重跑，依赖唯一键和状态条件更新避免重复发送。
- 调度任务使用服务身份和最小数据库权限；权限申请和有效期按公司平台流程确认。
- 上线前配置调用下游的 QPS 上限和超时，不能以无限重试保护本服务。

#### 4.4.3 监控指标设计

| 任务 | 指标 | 目标/告警建议 |
| --- | --- | --- |
| `reminder_evaluate` | 评估成功率、不可提醒原因分布、重复命中数 | 失败率和重复命中需告警，阈值待确认 |
| `reminder_dispatch` | 抢占数、发送成功率、重试数、未知状态数 | 未知状态和重复发送数重点告警 |
| `reminder_reconcile` | 查询成功率、未知状态收敛时间 | 长时间未收敛需告警 |

### 4.5 数据库/消息队列

本期不新增独立消息队列。应用通过 `EventPublisher` 对接既有事件系统；如果既有事件系统无法保证投递，可在数据库中增加 outbox 表，由异步 publisher 投递。outbox 是否需要以及具体消息系统待接入时确认。

#### 4.5.1 Schema 设计

数据库类型待确认，以下为逻辑模型。所有时间字段使用 UTC 存储，展示和规则计算使用用户时区。

##### `reminder_decision`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(64) | `decision_id`，主键 |
| `user_id` | varchar(64) | 匿名用户 ID |
| `task_date` | date | 用户任务日期 |
| `should_remind` | boolean | 是否满足提醒条件 |
| `scheduled_at` | timestamp | 计划时间，UTC |
| `channel` | varchar(16) | `push`/`in_app` |
| `reason_code` | varchar(64) | 决策原因 |
| `strategy_version` | varchar(32) | 策略版本 |
| `dedupe_key` | varchar(255) | 幂等键 |
| `status` | varchar(32) | 决策状态 |
| `created_at`/`updated_at` | timestamp | 审计时间 |

唯一索引：`(user_id, task_date, strategy_version)`。`CreateDecision` 采用幂等 upsert：同一用户、日期和策略版本重复评估时复用 `decision_id`，更新尚未发送决策的最新状态，并追加评估事件；不会创建第二条当日基础决策。如产品确认同日允许多次不同阶段排程，则由 `schedule_version` 扩展排程唯一键；在确认前不开放第二次 Push。

##### `reminder_schedule`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(64) | 排程 ID，主键 |
| `decision_id` | varchar(64) | 关联决策 |

##### 数据量估算

按 30 万名有任务学生、每天最多一次决策估算：

- 决策记录上限约 30 万条/日；按 30 天保留约 900 万条。
- 发送和行为事件量取决于事件链路，按每个决策 10 条事件进行容量预估约 300 万条/日。
- 以上为容量上限估算，不代表真实线上发送量；保留周期、分库分表和归档策略待基础设施评审。

### 4.6 缓存设计

本期不使用缓存作为频控或状态事实来源。原因是每日 Push 上限和排程幂等必须在持久化层有唯一约束。若线上 QPS 评估后需要缓存，可使用 Redis 做短期读取加速或分布式锁，但必须具备数据库校验和失效兜底，不能依赖缓存单独判定是否可发送。

## 5. 测试建议

### 5.1 环境及可测性

| 场景 | 可测性设计 |
| --- | --- |
| 当前时间、免打扰和任务截止时间 | 注入 `Clock`，测试可固定或推进时间 |
| 任务、用户、行为数据 | 使用 `TaskRepository`、`UserPreferenceRepository`、`BehaviorRepository` 的内存实现或测试替身 |
| Push 发送 | 使用 `PushSender` Mock，记录请求、幂等键和调用次数 |
| 站内提醒 | 使用 `InAppNotifier` Mock，控制可用/不可用结果 |
| 数据库唯一约束和并发 | 使用测试数据库或具备唯一约束语义的 repository fake，并发执行同一请求 |
| 发送未知状态 | Mock 返回 `unknown`，验证不直接重发 |
| 任务完成回传 | 通过任务仓储更新状态后再次触发 dispatch |

测试环境、BOE/PPE 泳道和真实下游服务名待接入时确认；本地测试不依赖真实 Push。

### 5.2 功能测试建议

重点覆盖：

- 被动型用户有未完成任务时生成提醒。
- 无任务、已完成、过期、关闭提醒、免打扰和频控场景不发送。
- 缺少行为数据时使用默认窗口并记录 `DEFAULT_WINDOW`。
- Push 关闭时不调用 Push，进入 App 后按规则展示站内提醒。
- 站内提醒不可用时记录 `NO_AVAILABLE_CHANNEL`。
- 重复调度、并发调度和发送失败重试不重复发送。
- 排程发送前完成任务时取消发送。
- 用户修改提醒设置后，未发送排程按最新设置处理。
- “稍后提醒”一小时后重新校验所有条件。
- 提醒内容使用最新任务数和预计用时，不包含敏感字段。

### 5.3 回归测试建议

需要回归以下既有能力：

1. 固定 Push 对照策略仍可正常发送。
2. 任务详情页和既有 Deep Link 可正常打开。
3. 任务完成回传和每日完成率统计不受影响。
4. Push 权限状态读取不产生第二套权限数据。
5. 历史 Push 记录、任务完成数据和行为数据不被修改。

### 5.4 性能测试建议

重点验证评估和 dispatch 在批量用户场景下的吞吐、下游调用峰值和数据库索引命中情况。具体峰值 QPS 依据调度平台分片和真实用户规模评估；在未完成容量评估前，不设定生产性能结论。

## 6. 变更保障设计

### 6.1 业务监控

| 场景/模块 | 监控指标 | 告警建议 | 备注 |
| --- | --- | --- | --- |
| 提醒评估 | 评估量、可提醒率、各原因码占比 | 失败率和异常原因突增告警 | 原因码必须可查询 |
| 排程 | 创建量、取消量、到期积压、重复命中 | 重复命中数不应大于 0；积压超时告警 | 按 task_date 分组 |
| Push | 调用量、成功率、到达率、打开率 | 失败率、未知状态和重复发送告警 | 具体阈值待确认 |
| 站内提醒 | 可展示量、展示量、点击量、不可用量 | `NO_AVAILABLE_CHANNEL` 突增告警 | 不调用 Push 替代 |
| 任务链路 | 提醒后开始率、完成率、入口失败数 | 入口或完成回传异常告警 | 任务系统为事实来源 |
| 数据一致性 | 决策/排程/发送/事件关联缺失数 | 关联缺失需告警 | 通过 `decision_id` 关联 |

### 6.2 灰度和应急方案

1. `feature_enabled` 默认关闭，先对白名单或小比例用户开启；分流规则和比例待确认。
2. 实验组使用智能提醒，对照组继续使用固定 18:00 Push，同一用户同一天只能命中一种策略。
3. 发现重复发送、已完成仍提醒、下游异常或指标明显劣化时，关闭总开关并停止智能排程。
4. 关闭智能提醒后，历史决策、发送和事件记录保留，固定 Push 恢复发送。
5. 数据库变更只新增表和索引；回滚代码时保留数据，避免删除历史记录。

### 6.3 上线方案

1. 完成数据库变更和 repository 验证。
2. 部署只读依赖适配器和决策服务，关闭功能开关。
3. 完成下游联调、Mock/测试环境验证和监控配置。
4. 对白名单开启，观察评估、发送、重复和失败指标。
5. 分阶段扩大用户范围；每个阶段确认无重复发送和历史功能回退。
6. 达到业务确认的上线阈值后扩大范围；阈值待确认。

#### 6.3.1 止损方案

- 总开关：停止智能提醒评估和 dispatch。
- 渠道开关：分别关闭 Push 或站内提醒渠道。
- 频控保护：数据库唯一约束和发送前二次校验作为最后防线。
- 数据修复：只允许通过受控脚本修复错误状态，禁止直接删除发送记录。

#### 6.3.2 补偿逻辑

本功能没有积分、金额或其他有价资源，不设计资金补偿。对于 Push 未知状态，只做渠道状态查询和事件补记，不通过补偿任务再次发送；如业务确认需要重发，必须使用新的业务决策并重新通过每日频控校验。

## 7. 新增数据中心成本评估

### 7.1 评估结论

预计新增成本主要来自提醒决策、排程、发送记录和事件记录的存储及调度计算。按 30 万名有任务学生、每日最多一次决策估算，决策记录约 30 万条/日，事件量按每个决策 10 条进行容量上限预估约 300 万条/日。

当前无法获得数据库、消息队列和日志平台的单价，暂不虚构金额。预计不会引入大规模计算或模型推理成本；最终月度成本、保留周期和分区策略需结合基础设施报价确认。

### 7.2 成本控制措施

- 事件只记录必要字段，不保存任务正文、成绩和个人敏感信息。
- 决策、发送和事件表按保留周期归档，避免无限增长。
- 调度任务分批执行并限制下游 QPS。
- 不引入独立 Push 厂商配置中心和机器学习服务。
