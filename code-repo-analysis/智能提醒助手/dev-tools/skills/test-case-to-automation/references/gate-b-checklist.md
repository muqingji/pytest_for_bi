# 门禁 B 复核清单

阶段三把结果交给用户复核时，逐项确认并显式说明，不要只给一句“已完成”。

## 1. 产物清单

- 新建 / 修改的文件逐个列出，并说明每个文件新增或改了哪些 case。
- 没有改动 `tests/common/`、`testenv/fixtures/users.json`、IDL 与 Go 代码；若确有改动必须单独声明并说明理由。

## 2. 数量与分类

- 用例文档 TC 总数 = 可执行 case 数 + 条件可自动化数 + 不可自动化数，三个数字对得上。
- `pending` 用例数与清单一致，每条都有能读懂的原因。
- case id 没有与已有数据冲突。

## 3. 回查证据

- 确定性回查命令与退出码（0 / 1）。
- 收集校验命令与实际输出（收集到的用例数）。
- `make test-selftest` 的结论。
- 被测服务是否可达；不可达时说明“业务用例会整体 skip，本次没有业务结论”。

## 4. 不静默确认

- 每条不可自动化用例都有原因、证据与替代覆盖方式。
- 每条数据缺口都指向具体 fixture 或建议新增，而不是“后续再看”。
- 没有把带有未确认预期的用例写成看起来会通过的断言。

## 5. 状态更新

- 用户确认通过后，把 `测试方案/自动化映射报告.md` 的状态改为「已通过门禁 B」并补全回查结论。
- 用户要求修改时，回到阶段二改，重新跑回查并重新提交门禁 B。
