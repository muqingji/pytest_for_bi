# 测试场景与用例设计

从需求文档推导测试场景，经 AI 评审与人工确认后生成测试用例，业务代码完成后按代码补全，再评审通过后封板。用户要求设计场景、编写用例、按代码补用例或封板时，使用本 skill。

## Goal

产出两份可评审、可追溯、可供下游直接消费的文档：

1. **场景清单**：从 PRD、验收标准、技术方案推导出的测试场景，每条带优先级与文档出处。
2. **用例清单**：每条用例含场景、前置条件、测试步骤、预期结果与优先级；前置条件按固定字段名输出，形成交给数据构造环节的输入契约。

三个不变式：

- **不臆想**：场景与用例的每一条判定都能指回文档原文（`文件:行号`）。指不回去的写进“待确认”，不自行补默认值、阈值或口径。
- **不越权**：优先级只允许 P0/P1/P2，且不得高于其来源需求；本期范围以 PRD 13.1 与测试方案为准，不擅自扩围。
- **不静默**：任何跨阶段变更都留下变更记录并重新走门禁，不悄悄改已审批内容。

## When to Use

适用：

- “基于 PRD / 技术方案设计测试场景”。
- “把这些场景写成测试用例”。
- “业务代码写完了，按代码补充用例、评估影响范围”。
- “用例评审通过，封板留存”。

不适用：

- 执行测试、跑命令、写测试报告（用 `test-plan-to-test-report`）。
- 实现业务代码（用 `tech-design-implementation`）。
- 编写或修改 PRD、验收标准、技术方案（分别用 `prd-refinement`、`prd-to-acceptance-criteria`、`prd-to-tech-design`）。
- 定义测试数据取值本身（用数据构造说明；本 skill 只输出“需要什么前置条件”）。

## 权威来源与顺序

固定阅读顺序与用途：

| 来源 | 用途 |
| --- | --- |
| PRD | 需求规则、判定顺序、原因码、默认值与范围边界；需求优先级的唯一来源 |
| 验收标准 | `AC-xxx` 场景，作为场景推导的主干 |
| 技术方案 | 契约、状态流转、异常与降级链路、未决项；决定场景“能不能测、在哪一层测” |
| 测试方案 | 测试分层与 Demo 流程，决定场景落在哪一层 |
| 数据构造说明 | 已有 fixture 的事实源；用于判断前置条件能不能复用现有数据 |
| 业务代码（阶段五起） | 实际分支、边界实现与影响面，用于补漏用例 |

冲突处理：PRD 与验收标准冲突时以 PRD 为准并记录；文档与代码冲突时不自行判定谁对，记录差异并按人工门禁停止。

## 门禁的两步推进

三道门禁都按同一步骤推进：

1. **AI 评审**：调用 `test-case-review` 按对应强度评审，产出 `测试用例评审报告.md`。存在未处理阻塞项时不得提交人工确认。
2. **人工确认**：把 AI 评审结论、阻塞项处理结果、待裁定项与用户裁定记录一并提交用户；用户明确通过才等于门禁通过。

| 门禁 | 阶段 | AI 评审强度 | 评审范围 |
| --- | --- | --- | --- |
| A | 阶段二 | quick | 覆盖缺口与错引用 |
| B | 阶段四，以及阶段五补全后 | standard | 全量评审 |
| C | 阶段六 | 增量 | 变更点与受影响项 |

硬性约束：

- AI 评审的“通过”只表示可以提交人工确认，不构成门禁通过。
- 待裁定项必须在人工确认前已有用户裁定记录，不得把未决口径带进人工确认。
- 用户要求跳过 AI 评审时，按“人工确认触发条件”停止并请求确认；用户坚持跳过时，在门禁记录里写明跳过理由，不得静默跳过。

## Workflow

### 阶段一：推导测试场景

按 `references/source-traceability.md` 逐条抽取，产出场景清单：

1. 从验收标准的每条 AC 抽取主干场景。
2. 从 PRD 的规则、判定顺序、边界与原因码补分支场景。
3. 从技术方案的异常、降级、幂等与并发链路补工程场景。
4. 按 `references/design-techniques.md` 给每条场景定 `场景类型`，并逐维度做 `等价类` 划分：
   - 骨架三类必做且必须做等价类划分：正常场景、异常场景、边界场景；
   - 性能场景、回归场景本期可简化写或跳过，但必须在清单里显式登记，不许留空；
   - 无效等价类逐条单独成用例，不合并，避免遮蔽。
5. 按 `references/review-checklists.md` 第 1 节自检覆盖维度：前置不满足、终止或取消、幂等与并发、频控上限、失败与异常、时间边界、数据边界、设置变更。

每条场景必须写全：编号、名称、优先级、来源（`文件:行号`）、关联 AC/FR、场景类型、等价类、覆盖维度、判定点。**来源写不出来的场景不许进清单**，只能进“待确认”并说明缺哪份文档的哪条规定。

默认值与阈值（例如具体发送时刻、免打扰区间、流失天数）一律标注为设计假设并引用其出处，不得表述为题目事实或已确认结论。

### 阶段二：门禁 A —— 场景审批

先按 `test-case-review` 的 quick 强度做 AI 评审，只核验覆盖缺口与错引用；再把场景清单与评审结论交给用户确认，同时给出：覆盖矩阵（AC/FR 到场景）、未覆盖项与原因、待确认清单。

AI 评审阻塞项清零、用户明确通过后，才进入阶段三。用户要求增删改时，改完重新提交本门禁。**不得以“先做着，回头再确认”为由跳过。**

### 阶段三：生成测试用例

按 `references/test-case-template.md` 为每条场景写用例：

- 一条用例只验证一个判定点；多判定点拆开。
- 用例继承所属场景的 `场景类型` 与 `等价类`；每条用例对应一个等价类，多个用例覆盖同一等价类属于重复设计，需要合并或写明差异。
- 每条用例含：编号、场景、优先级、前置条件、测试步骤、预期结果、来源、自动化映射（可后补）。
- 前置条件按结构化字段写（用户类型、任务状态、行为信号、提醒设置、当日用量、外部依赖），字段名与数据构造说明对齐，作为数据构造环节的输入契约。
- 预期结果是可观察值（状态、字段、原因码、记录数、时间约束），不写“正常”“符合预期”。
- 用例优先级不得高于其场景优先级。

数据缺口单独成节：列出每条用例需要但现有 fixture 没有的前置数据，标注建议新增的 fixture 标识，交给数据构造环节处理。

### 阶段四：门禁 B —— 用例评审

先按 `test-case-review` 的 standard 强度做 AI 评审，全量评审；再把用例清单与评审结论交给用户评审，同时给出：场景到用例的覆盖关系、每条场景的用例数、前置数据缺口清单、预期结果中依赖未决项的部分。

AI 评审阻塞项清零、用户明确通过后，才进入阶段五。评审意见逐条落回文档，不改判、不口头带过；待裁定项须有用户裁定记录后才可继续。

### 阶段五：业务代码完成后补全与影响范围评估

业务代码实现完成后，按 `references/impact-analysis-guide.md` 补用例：

1. 核对代码实际分支与文档推导的一致性，补“文档没写但代码里有”的分支。
2. 评估本轮实现影响到的既有场景，标注影响范围（受影响场景、回归范围、无需回归的结论）。
3. 补充的用例必须区分来源类型：文档推导 / 代码补充，便于后续追溯。

补全后重新执行门禁 B。

### 阶段六：门禁 C —— 封板

先按 `test-case-review` 的增量强度复审变更点与受影响项，再提交用户确认。

条件全部满足才可封板：三道门禁的 AI 评审阻塞项均为 0、人工确认均已通过、回查脚本阻塞项为 0、待确认项已闭环或明确记为未闭环风险、影响范围已评估。

封板产出：冻结版本号、封板日期、封板时的用例总数与优先级分布、未闭环项清单、变更规则。封板后任何改动走“变更申请 → 影响范围 → 重新评审 → 版本递增”，不得直接编辑。

## 人工确认触发条件

出现以下任一情况时停止并请求确认：

- 场景或用例的判定点指不回文档原文；
- PRD、验收标准、技术方案、代码四者之间口径冲突；
- 需要引用默认值、阈值或统计口径，但文档未给出或标注为“待确认”；
- 某条场景无法判定通过与否，或缺少可观察的判定依据；
- 用户要求跳过门禁 A/B/C 中任意一个，或要求跳过门禁里的 AI 评审；
- 阶段五发现代码行为与文档不一致，需要决定改代码还是改文档；
- 需要扩大本期范围（引入 P1/P2 场景、新渠道、新环境依赖）；
- 骨架三类（正常、异常、边界）中某类无法做等价类划分，或某类完全没有场景；
- 性能与回归场景无法登记（既不能简化写也不能说明跳过原因）；
- 封板后收到改动请求。

确认请求必须说明：证据（`文件:行号`）、受影响的场景与用例、影响范围、候选方案、需要用户作出的确切决定。用户回答前不得继续。

## Output

| 项目 | 要求 |
| --- | --- |
| 产物 | 场景清单、用例清单、封板记录；本 skill 的回查报告与 `test-case-review` 的评审报告默认随消息给出 |
| 默认路径 | `<需求目录>/测试方案/测试场景清单.md`、`<需求目录>/测试方案/测试用例.md`、`<需求目录>/测试方案/用例封板记录.md`；已有同名文件时沿用，不擅自改名或搬移 |
| 编号 | 场景 `SC-0NN`，用例 `TC-0NN`，全局唯一且不因删改而回收 |
| 必填字段 | 场景：优先级、来源、关联 AC/FR、场景类型、等价类、覆盖维度、判定点；用例：场景、优先级、等价类、前置条件、测试步骤、预期结果、来源 |
| 溯源格式 | `文件路径:行号`，多个用顿号分隔；路径相对仓库根目录 |
| 回查报告 | 分“阻塞项 / 建议项 / 待确认”，每条带 `文件:行号` 与修复建议 |
| 结尾 | 一句话结论：当前处于哪个阶段、是否可以进入下一阶段、未闭环风险 |

不要创建与已有文档重复的测试计划，不要写入测试数据具体取值，不要给出未经评审的用例结论。
