# 溯源规则：怎么算“有依据”，怎么算“臆想”

阶段一推导场景、阶段三写用例、回查脚本判定时统一按本文执行。

## 1. 溯源格式

统一写 `文件路径:行号`，路径相对仓库根目录，多个用顿号分隔：

~~~text
来源：code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md:301、code-repo-analysis/智能提醒助手/技术方案/技术方案.md:412
~~~

允许补充章节名帮助人阅读，但行号必须保留，因为回查脚本按行号校验文件与范围：

~~~text
来源：技术方案/技术方案.md:412（4.3.2.1 请求校验规则）
~~~

行号指向“规定本身”，不指向引用它的地方。例如判定依据来自 PRD 7.2 的默认时刻规则，就指向 7.2 那一行，不要指向验收标准里复述它的 AC。

## 2. 判定分级

| 级别 | 判定 | 处理 |
| --- | --- | --- |
| 明确依据 | 文档直接写了这条规则、边界或原因码 | 写进场景清单，标注来源 |
| 可推导 | 由两条以上明确依据按文档给出的判定顺序组合得出 | 写进场景清单，来源写全两条，并在判定点里说明推导关系 |
| 设计假设 | 文档写了取值但自己标注为“待上线验证”“设计假设” | 允许进清单，但必须在来源里带上该标注，且不得表述为已确认结论 |
| 无依据 | 文档没写，或只有“合理推测” | **不进清单**，进“待确认”并写明缺哪份文档的哪条规定 |
| 冲突 | 两份文档口径不一致 | 不进清单，按人工门禁停止，请用户裁定 |

## 3. 常见的臆想形态

推导时逐条自查，命中即改：

- **自行补默认值**：文档只给了活跃时段，却把“默认发送 19:30”当成事实写进判定点。正确做法是引用该默认值的原始出处置信度，并标注它是设计假设。
- **把待确认写成已确认**：文档写“回流判定窗口与阈值待确认”，用例却按某个阈值断言。
- **补文档没给的统计口径**：给比例指标自行规定分母、窗口或去重方式。
- **把实现细节当需求**：从技术方案里挑了字段名，就声称需求规定了该字段。
- **反向推理**：因为代码这样实现了，就断言需求如此。阶段五之前一律不读代码作为需求依据。
- **平滑掉矛盾**：发现两份文档不一致时，选一个“看起来更合理”的继续写，而不是上报。
- **扩围**：把 P1/P2 的能力写成 P0 场景，或把“不进入本期验收”的条目做成用例。

## 4. 多来源场景的写法

一条场景同时依赖需求规则与技术约束时，来源按“需求在前、工程在后”排列，判定点分开写：

~~~text
### SC-014 发送前任务完成则取消发送
- 优先级：P0
- 来源：需求拆解/验收标准/验收标准.md:108、技术方案/技术方案.md:520
- 关联需求：AC-010、FR-004
- 覆盖维度：终止或取消
- 判定点：排程在发送前重新读取任务状态；任务已完成时取消发送且不产生第二次成功触达
~~~

## 5. 待确认清单的写法

每条待确认要写清四件事，缺一件就不算登记完整：

| 字段 | 说明 |
| --- | --- |
| 缺口 | 哪份文档的哪条规定缺失或含糊（带 `文件:行号`） |
| 影响 | 没有它就无法确定哪些场景或用例的判定点 |
| 候选 | 可行选项，以及各自的代价 |
| 需要谁定 | 产品、技术还是测试口径 |

登记进待确认的场景不占用 `SC-` 编号，避免后续被误当成已审批内容；用户裁定后再正式编号入册。
