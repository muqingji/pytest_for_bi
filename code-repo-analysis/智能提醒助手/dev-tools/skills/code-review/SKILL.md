# Code Review Skill

## 目标

对智能提醒助手的代码变更进行证据驱动的代码审查，优先发现会造成错误提醒、重复触达、数据丢失、状态错乱、隐私泄露或虚假准出的缺陷。

默认是只读审查，不修改业务代码、PRD、验收标准、技术方案或测试；用户明确要求修复时，另行进入实现流程。

只读审查不产出代码修复，但审查记录和结论必须留档：每次审查都要把范围、基线、findings 和执行结果写入 md 评审报告，见「CR 记录留档」。

## 当前系统上下文

项目是 Go 后端服务，当前代码按以下边界组织：

```text
domain/reminder
  领域规则、时间计算、决策和值对象
application/evaluate
  评估编排、偏好变化处理、事件记录
port
  任务、偏好、行为、提醒仓储和时钟接口
adapter/task、adapter/user
  本地任务、用户偏好和行为 Fixture/替身
adapter/storage
  SQLite、迁移、决策/排程/事件持久化
cmd/reminder-service
  CLI 装配和本地 Demo 入口
```

当前 P0 范围是 FR-001、FR-002、FR-003、FR-004、FR-005、FR-007、FR-008；FR-006、FR-009 为 P1，P2 不应被当成本期已实现。

当前重点代码入口：

- `internal/domain/reminder/types.go`

- `internal/application/evaluate/preference.go`

## 权威输入

审查前必须读取：

1. 最新确认的 PRD：`code-repo-analysis/智能提醒助手/智能提醒助手PRD(9稿).md`
2. 验收标准：`code-repo-analysis/智能提醒助手/需求拆解/验收标准/验收标准.md`
3. 技术方案：`code-repo-analysis/智能提醒助手/技术方案/技术方案.md`
4. 测试方案和测试数据构造说明；
5. 本轮功能的 `docs/implementation/FR-*.md`；
6. `AI_USAGE.md`；
7. 变更前后代码、迁移、配置、测试和运行脚本。

面向人阅读的 MVP PRD 只能作为辅助材料；如果它与 9 稿 PRD、验收标准或技术方案冲突，以已确认的正式文档为准，并报告冲突。

## 审查前置检查

先执行：

```bash
git status --short --branch
git diff --check
git diff --stat
git diff -- <目标文件>
rg --files internal cmd docs/implementation tests
```

审查前必须确定：

- 变更基线和审查范围；
- 哪些未提交改动属于用户已有工作，不能当作本轮缺陷；
- 目标 FR、AC、技术方案章节和 3.4 模块；
- 依赖的前置 FR 是否已经通过准出门禁；
- 是否存在新增迁移、状态、事件、配置或外部接口。

如果变更归属不清、代码与用户未提交修改重叠，先记录为审查限制，不得擅自恢复、清理或覆盖文件。

## 审查原则

1. 先看正确性和风险，再看风格。
2. 每个 finding 必须有文件和行号、可复核证据、实际影响和修复方向。
3. 不把“脚本通过”“覆盖率 100%”当成语义正确的证明。
4. 不把 Mock 联调描述为真实外部服务联调。
5. 不因代码看起来合理而放宽 PRD、AC、技术方案中的约束。
6. 不把文档中没有定义的默认值、重试、状态或兼容行为视为合理实现。
7. 只报告能够导致错误、回归、不可运维或验收失真的问题；纯格式问题降到最后。
8. 如果没有发现问题，必须明确说明审查范围、执行过的检查和剩余风险，不能只说“LGTM”。
9. 业务代码的中文注解属于可走读性和可维护性审查范围；先判断关键业务原因是否可被准确理解，再判断注释风格。

## 严重级别

- **P0**：会造成错误或重复触达、数据不可恢复、跨用户/跨任务数据泄露、核心状态永久错误、迁移破坏已有数据，或违反已确认的核心业务规则。
- **P1**：会在正常依赖失败、重试、并发、跨时区、重复事件或生产配置下产生错误结果，或会阻塞本 FR 的可靠上线。
- **P2**：边界条件、可观测性、回滚、维护性或测试证据不足，短期不一定触发核心故障但应修复。
- **P3**：低风险可维护性或表达问题，不影响当前行为。

## 必查风险面

### 1. FR/AC/技术方案追踪

- 代码是否只实现本轮 FR 和已确认 AC；
- 实际模块是否属于技术方案 3.4；
- 是否把 P1/P2、待确认项或人读版 PRD 当成已批准行为；
- AC 的正常路径、拒绝路径、重试和幂等是否都有代码和测试；
- 文档中的状态、原因码、字段名是否与代码和 IDL一致。

### 2. 领域规则和时间

- 资格判定顺序是否为：任务存在 -> 完成 -> 过期 -> 设置 -> 分层 -> 频控 -> 时间；
- 分层优先级、流失/回流首日、自驱型上限是否保持互斥；
- FR-002 的窗口来源是否为：任务完成 > 任务开始 > App 活跃 > 默认窗口；
- 19:30 -> 17:00 回退是否检查免打扰和截止前 1 小时；
- 候选窗口被拒后是否正确记录来源和降级原因；
- IANA 时区、跨午夜免打扰、用户本地 `task_date`、夏令时是否正确；
- 非法日期、非法时区、非法时间窗口是否明确拒绝或按文档定义降级，不能静默用服务器当前日期/UTC；
- 行为数据异常是否保留可用信号，并禁止用不完整信号命中回流/归因规则。

### 3. 决策、排程和状态机

- 评估重复是否返回同一个 `decision_id`；
- 决策版本、排程版本、`schedule_type` 是否单调且语义一致；
- 取消是否只影响未发送/可取消状态，不能撤销已发送事实；
- `COMPLETED`、`CANCELLED`、`TASK_COMPLETED` 等状态和原因码是否有生产者、消费者和持久化映射；
- 偏好变化、任务完成、回流首日、频控拒绝是否会遗留可发送排程；
- Dispatch、Snooze、PreferenceChanged 是否共享同一套状态和幂等约束。

### 4. 持久化、迁移和并发

- 唯一键是否覆盖业务幂等键，而不是只依赖 Go 代码判断；
- 条件更新是否带版本/状态条件，是否可能覆盖并发更新；
- 事务是否覆盖决策、排程和必要事件；
- 事务提交失败、唯一键冲突、数据库锁、context 取消是否有可重试且不重复的处理；
- SQLite 迁移是否可从旧版本升级、失败回滚、重复执行和空库执行；
- 迁移是否保留已有约束、索引、外键和可空性；
- 读取/写入时间格式、NULL、枚举和旧数据兼容是否明确；
- `GetDailyUsage` 是否区分 `INITIAL` 与 `SNOOZE`，避免 Snooze 消耗系统主动 Push 上限；
- 逻辑删除、取消排程和历史记录保留是否符合技术方案。

### 5. 事件、幂等和可重放性

- 所有需要关联的事件是否含 `decision_id`、`strategy_version`、`event_id` 和正确的公共信封字段；
- 没有决策的 `AppOpened`、偏好变更等事件是否允许空关联字段；
- 事件落库失败时，已提交的决策是否会产生无法补发的事件缺口；
- 重复事件是否只去重业务副作用，而不是只忽略 INSERT 后继续执行取消、重评估或发送；
- 事件发布失败是否有 outbox/reconcile 或明确的失败语义；
- payload 是否只含允许字段，不含任务正文、成绩、姓名、手机号、Token 等敏感数据；
- `experiment_group`、`channel`、`timezone` 的缺省值是否与契约一致。

### 6. 偏好变更和外部依赖

- `ReminderPreference` 是否区分用户开关、Push 开关、免打扰、每日上限和时区；
- 用户开关是否与服务级 `feature_enabled` 灰度开关混淆；
- 偏好读取失败是否失败关闭，是否错误使用旧缓存；
- 偏好变更事件是否在读取最新来源前就产生不可逆副作用；
- 重复偏好事件是否幂等；
- 关闭提醒是否取消所有可取消排程，免打扰变化是否按最新设置重排；
- 外部任务、用户、行为和 Push 依赖失败时，是否区分强依赖失败和行为弱依赖降级。

### 7. Dispatch、Push、重试和 Snooze

当代码声称实现 FR-004、FR-005 或 FR-007 时，必须检查：

- 发送前是否重新读取任务和偏好；
- `SCHEDULED -> CLAIMED -> SENDING -> SENT/DELIVERED/FAILED/UNKNOWN` 状态迁移是否原子；
- worker 抢占是否使用条件更新和租约；
- 明确失败是否最多重试一次且复用同一幂等键；
- UNKNOWN 是否先查状态再决定是否重试；
- Push 未授权是否不调用渠道并记录 `NO_AVAILABLE_CHANNEL`；
- Snooze 是否一小时后、最多一段、同一请求幂等、第二次返回 `INVALID_REQUEST`；
- Snooze 是否独立计量且不占 `INITIAL` 每日上限；
- 延后提醒 payload 是否不再包含“稍后提醒”入口。

### 8. 测试和准出证据

- 测试是否断言业务结果、状态、数据库记录和事件，而不只是函数返回或 Mock 调用；
- 是否覆盖边界：历史 2/3 天、流失 2/3 天、回流 2/3 天、免打扰起止、截止前 1 小时、并列窗口、跨午夜和非法配置；
- 是否覆盖重复请求、重复事件、并发评估、数据库唯一冲突、发送失败和 context 取消；
- 100% 覆盖率是否覆盖本轮修改代码，而不是缩小包范围、排除文件或只运行 happy path；
- 集成测试是否全部通过且没有 skip/ignore；
- 进度记录中的命令和结果是否真实、可复现、与当前代码版本对应；
- 回查脚本通过后是否仍做人工语义核对。

### 9. 业务代码中文注解

- 新增或修改的业务规则、状态流转、降级/回退、幂等/并发、安全/隐私边界和外部依赖失败语义旁，是否有准确、详细的中文注解；
- 注解是否说明“为什么这样做、违反时会怎样、对应哪条 FR/AC 或技术方案约束”，而不是重复代码语法；
- 领域层、应用编排、持久化事务、迁移兼容和状态机分支是否能通过注解完成代码走读；
- 公共类型、接口和方法是否说明业务含义、输入约束、失败语义和副作用；
- 注解是否与当前实现同步，是否存在复制旧规则、描述已删除分支或与代码相反的注释；
- 是否只在必要位置详细注解，避免给简单赋值、循环或显而易见的语句堆积无效注释；
- 关键业务代码只有英文注释、模板化注释或完全没有注释时，至少报告 P2；如果缺少注解导致状态、降级或安全行为无法可靠走读，按 P1 处理。

## 当前代码的重点审查假设

以下不是自动判定为缺陷，而是当前仓库中应优先验证的风险：

1. `Service.Evaluate` 先提交决策/排程，再单独写 `reminder_decision_created` 事件；事件写入失败时要验证重试是否能够补发，而不是因为决策已存在而永久跳过事件。
2. `PreferenceChangedHandler` 先写偏好事件，再取消排程和重新评估；重复事件不能只靠 `INSERT OR IGNORE` 去重，否则可能继续触发取消和重评估副作用。
3. `plannedTime` 当前只保留一个行为来源候选，并把默认候选追加到列表；要验证行为候选不可用时的来源降级、`DEFAULT_WINDOW` 原因码和可解释性。
4. 非法时区和非法任务日期不能静默回退到 UTC 或当前日期；必须对照技术方案的输入校验和降级口径。
5. 决策更新和排程替换要验证并发版本条件；仅使用单连接或事务顺序不能替代业务级防丢更新。
6. `GetDailyUsage` 要验证未来 `SNOOZE` 排程/投递不会被算入系统主动 Push 用量。
7. 当前领域类型只有 `SCHEDULED` 排程状态和 `INITIAL` 排程类型；如果变更声称实现 Dispatch 或 Snooze，必须检查是否补齐了技术方案要求的状态机，而不是只增加入口函数。
8. 当前本地 MemoryRepository、SQLite 和 Mock 联调不能证明真实用户服务、调度平台、事件总线或 Push 厂商能力已经满足契约。

## 运行检查

按风险和变更范围选择命令，不能声称未运行的结果：

```bash
gofmt -d <changed-go-files>
go test -count=1 ./...
go test -race ./...
go vet ./...
go build ./...
go test -covermode=atomic -coverprofile=/tmp/code-review.cover ./...
go tool cover -func=/tmp/code-review.cover
python3 dev-tools/skills/prd-to-tech-design/scripts/check_tech_design.py \
  --design <技术方案.md> --prd <PRD.md> --prd <验收标准.md>
python3 dev-tools/skills/prd-to-acceptance-criteria/scripts/check_acceptance_criteria.py \
  --ac <验收标准.md> --prd <PRD.md>
```

迁移或并发相关变更必须额外执行：

- 空库迁移；
- 旧版本数据库升级；
- 重复迁移和失败回滚；
- 并发评估/重复请求测试；
- context 取消和数据库锁错误路径。

## Findings 输出格式

审查结论必须先列 findings，再给简短总结，并按「CR 记录留档」同步写入 md 评审报告；对话里的结论不能替代留档文件。每条 finding 使用以下格式：

```text
[P0/P1/P2/P3] 标题
位置：绝对路径:行号
证据：具体代码、文档或测试结果
影响：触发条件、错误行为和影响范围
建议：最小修复方向；如涉及产品或技术方案冲突，停止并请求人工确认
```

排序规则：P0 -> P1 -> P2 -> P3；同级按数据正确性、状态/幂等、外部依赖、测试和维护性排序。

最后补充：

- 审查范围和基线；
- 未发现的问题类型；
- 已运行命令和真实结果；
- 剩余风险和未验证项；
- 是否建议合并、需要修复后再审查，或因文档冲突阻塞。

## CR 记录留档

审查记录和结论必须落盘，不能只存在于对话里：

| 项目 | 要求 |
| --- | --- |
| 产物 | 一份 CR 评审报告 md；只写报告，不改代码、PRD、验收标准、技术方案或测试 |
| 默认路径 | `code-repo-analysis/智能提醒助手/docs/review/代码评审报告-<范围标识>.md`；`<范围标识>` 用 FR 编号或横切主题（如 `FR-005`、`HTTP本地入口`）；已有同名文件时沿用并递增版本，历史结论不覆盖 |
| 意见编号 | `CR-0NN`，全局唯一，处理完成后不回收编号 |
| 必填字段 | 级别（P0-P3）、位置（`文件:行号`，路径相对仓库根目录）、证据、影响、建议、状态（未处理/已处理/不处理并附裁定记录） |
| 报告结构 | 审查对象与基线、审查范围与限制、结论、findings、已执行命令与真实结果、未执行或未覆盖的检查、剩余风险与未验证项、人工确认项、复审记录 |
| 时效 | 记录必须对应当前代码版本；基线、工作区状态或命令结果变化后，重跑受影响检查并更新报告，不保留过期结论 |
| 表述要求 | 不美化结论：失败、跳过、未执行和未验证项按实际记录；不写“建议完善”这类无落点意见 |
| 结尾 | 一句话结论：findings 按级别计数、是否存在阻塞项、是否建议合并 |

留档不改变只读边界：报告写入失败时按实际说明，不得用对话结论冒充已落盘的评审记录。

## 人工确认门禁

出现以下情况不得用代码猜测解决：

- PRD、验收标准、技术方案或 IDL 冲突；
- 需要新增产品规则、字段、状态、默认值、重试或外部能力；
- 迁移会改变已有数据语义或不可逆；
- 真实外部服务能力未知；
- 测试结果与业务预期不一致；
- 修复建议会扩大当前 FR 范围。

确认请求必须给出证据、受影响的 FR/AC、影响、候选方案、推荐方案、需要回写的文档和需要重跑的检查。

## 不应做的事

- 不修改代码来让审查通过；
- 不删除用户未提交的修改；
- 不通过降低覆盖率统计范围、加忽略标记或跳过测试来伪造准出；
- 不把本地 Fixture、Fake 或 Mock 结果描述为生产能力；
- 不把“没有发现问题”写成“没有风险”；
- 不创建宽泛的重构计划代替具体 finding；
- 不把 findings 或结论只留在对话里而不写 md 评审报告，也不因为留档需要就修改被审查代码；
- 不通过删除、弱化或改写未处理 finding、失败结果来让报告看起来通过。
- 不以“代码能运行”为理由跳过业务代码中文注解审查；也不要求为显而易见的语法添加无意义注释。
