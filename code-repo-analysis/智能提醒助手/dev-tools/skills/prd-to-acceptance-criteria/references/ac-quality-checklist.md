# 验收标准质量清单

第 4 步回查与第 5 步人工审查共用。标注"阻塞"的项未解决时，验收标准不能进入评审。每条结论都要给出行号证据。

## 1. 可追溯（阻塞）

| 检查点 | 说明 |
| --- | --- |
| 每条 P0 需求是否至少有一条 AC | 缺一条即阻塞 |
| 每条 AC 是否可反查到需求规则 | 反查不到说明 AC 是凭空写的，需补来源或删除 |
| AC 编号是否唯一且连续 | 重号阻塞；跳号建议修正 |
| 非本期需求（P1/P2）是否被写进验收范围 | 写入即阻塞，应移出或标注不验收 |

## 2. 可判定（阻塞）

| 检查点 | 不合格特征 |
| --- | --- |
| 结论是否具体 | "及时提醒""体验友好""尽量延后" |
| 是否有判定依据 | 无原因码、无状态词、无数量约束、无时间约束 |
| 是否单一结论 | 一条 AC 里用多个 And 串起互不相关的多套规则 |
| 是否可复现 | 依赖"大概""可能""视情况"这类描述 |

## 3. 覆盖度（缺失即阻塞）

按 `ac-writing-guide.md` 第 6 节覆盖矩阵逐项确认。以下维度缺失视为阻塞：

- 前置不满足（无数据、无权限、已关闭）。
- 已完成或已失效。
- 重复调度与并发幂等。
- 失败与未知状态处理。
- 设置变更后未执行动作的处理。

以下维度缺失为建议补充：时间边界、用户主动操作、数据与隐私。

## 4. 不越界（阻塞）

| 检查点 | 越界特征 |
| --- | --- |
| 是否写了页面操作步骤 | "打开首页 → 点击右上角 → 选择时间" |
| 是否写了实现细节 | 表名、接口路径、幂等键、字段类型、缓存 |
| 是否写了线上指标 | 到达率、打开率、完成率提升阈值 |
| 是否复述 PRD 规则原文 | 大段规则表照搬 |

## 5. 冗余（建议）

| 检查点 | 说明 |
| --- | --- |
| 同一规则是否写了多条 AC | 合并或明确边界差异 |
| 多条 AC 的条件与结论是否高度重叠 | 保留一条，其余删除 |
| 是否与 PRD 现有映射表冲突 | 以 PRD 为准并更新映射 |

## 6. 可测性（建议）

| 检查点 | 说明 |
| --- | --- |
| 每条 AC 能否列出可构造的数据 | 需要伪造的外部状态应在数据构造说明中登记 |
| 是否依赖不可控的外部条件 | 如真实 Push 厂商、真实用户行为，应改为可注入或可模拟 |
| 时间相关 AC 是否说明时区与基准时间 | 涉及跨天、临界时间的必须说明 |

## 7. 人工判断项

脚本无法判断，必须由审查者确认：

1. 颗粒度是否合适：一条 AC 是否大到无法判定，或小到只是实现细节。
2. 拆分是否符合业务直觉：按判定结果拆，而不是按页面拆。
3. 是否遗漏业务方真正关心的验收点（如对账、申诉、运营查看）。
4. 与 PRD 的口径是否一致：原因码、事件名、字段名、上限值。
5. 是否存在"写得很全但没人会验"的 AC（无数据、无手段、无责任人）。
