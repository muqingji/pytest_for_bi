# 最终测试报告与准出

在开发、评审、修复和测试活动完成后，汇总已有事实证据，生成一份可复核的最终测试报告并作出准出判断。

## Goal

报告必须回答三个问题：本次交付包含什么、证据证明了什么、当前是否可以准出。至少汇总：

1. 需求信息；
2. 单元测试与覆盖率；
3. 集成测试；
4. CR 结论；
5. 测试 Case；
6. 自动化执行报告；
7. Bug 信息；
8. 最终测试结论；
9. 准出决定。

本 Skill 只汇总和裁决，不修改需求、业务代码、测试用例、CR 或 Bug 状态。证据缺失、互相冲突或已经过期时，如实登记并降低准出结论，不猜测、不复用无法确认对应当前代码版本的结果。

## When to Use

适用：

- “生成最终测试报告 / 准出报告”。
- “汇总单测、集成测试、自动化、CR 和 Bug 情况”。
- “判断本次版本能不能准出 / 上线 / 交付”。

不适用：

- 执行测试或补测试代码：使用 `test-plan-to-test-report`。
- 将文本用例转成自动化：使用 `test-case-to-automation`。
- 代码评审：使用 `code-review`。
- 修复 Bug 或 CR finding：使用 `bug-fix`。

## 输入与证据优先级

先定位本次版本、分支或提交范围，再读取与该范围匹配的最新证据。文件时间新不等于证据一定有效；报告必须核对其测试对象、分支、提交或工作区说明。

| 信息 | 首选证据 |
| --- | --- |
| 需求信息 | 已确认 PRD、验收标准、技术方案、本轮 FR/AC 范围 |
| 单元测试与覆盖率 | 当前版本的测试命令原始输出、覆盖率文件或测试报告 |
| 集成测试 | 最新且范围匹配的集成测试报告及其命令结果 |
| CR 结论 | 最新代码评审报告；逐条 finding 状态与最终结论 |
| 测试 Case | 封板测试用例、评审报告、AC/TC 追踪关系 |
| 自动化执行 | pytest/Go 测试执行结果、Allure 或项目测试报告；区分通过、失败、跳过、未执行 |
| Bug 信息 | Bug 台账、修复记录、回归结果和未关闭缺陷 |

同一事项出现冲突时，以与当前代码基线匹配、可复现且证据更直接的记录为准，并在报告中列出冲突。不得把 Mock、本地替身或跳过用例写成真实渠道验证通过。

## Workflow

### 1. 固定准出范围

记录项目、版本/分支/提交、报告时间、需求/FR/AC、本次包含与不包含的能力。无法确认代码基线时，结论不得为“准出”。

### 2. 建立证据清单

逐项列出输入文件和生成时间，核对证据是否对应当前范围。不存在的证据写“缺失”，未执行的检查写“未执行”，不得用其他层级测试替代。

### 3. 汇总八类信息

按 [release-report-template.md](references/release-report-template.md) 填写各章节。所有数字保留分母和四态统计，例如 `通过 20 / 失败 0 / 跳过 3 / 未执行 2`；覆盖率写实际口径、数值和项目门槛。

CR 与 Bug 必须逐条统计状态。测试 Case 必须给出总数、P0/P1 数、自动化映射情况和需求覆盖缺口；不能只列几个示例用例。

### 4. 执行准出门禁

逐条填写门禁表，再确定最终结论：

| 门禁 | 无条件准出要求 |
| --- | --- |
| 需求范围 | 本次范围、验收标准和代码基线明确，无阻塞性未决项 |
| 单元测试 | 全量通过，失败 0；覆盖率达到项目明确门槛，项目未定义门槛时不得自行发明 |
| 集成测试 | 本次关键链路全部执行且失败 0，关键用例不得跳过 |
| CR | 结论允许合并/发布，P0/P1 finding 全部关闭，无待人工确认的阻塞项 |
| 测试 Case | 本期 FR/AC 均有用例或经批准的排除理由，P0/P1 用例已执行 |
| 自动化执行 | 失败 0；跳过和未执行项均已分类，关键路径无 pending |
| Bug | P0/P1 为 0；其他未关闭 Bug 已评估且不阻塞本次范围 |

结论规则：

- **准出**：全部门禁通过，无阻塞项，无需例外审批。
- **有条件准出**：只有可接受的非关键风险未关闭，并且已有明确的例外审批人、批准记录、到期时间、补验/修复计划和回退方案。Skill 不得自行批准例外；缺任一信息时判为“不准出”。
- **不准出**：任一硬门禁失败、证据缺失/过期/冲突导致无法判断，或存在未获批准的例外项。

### 5. 回查报告

运行：

```bash
python3 dev-tools/skills/test-release-report/scripts/check_release_report.py \
  --report "docs/<项目名>-最终测试准出报告-YYYYMMDD-HHMMSS.md" \
  --project-root .
```

阻塞项必须为 0。脚本只验证结构与明显的状态矛盾，最终结论仍必须逐项对照原始证据复核。

## Output

| 项目 | 要求 |
| --- | --- |
| 报告路径 | `docs/<项目名>-最终测试准出报告-YYYYMMDD-HHMMSS.md` |
| 命名规则 | 时间戳取首次生成报告时的项目时区；同一次流程沿用该文件，新一轮准出不得覆盖历史报告 |
| 最终结论 | 只能是“准出”“有条件准出”“不准出”之一 |
| 证据 | 每项结论指向项目内文件和具体章节/行，或记录可复现命令与实际结果 |
| 未完成项 | 写清责任人、处理计划和期限；缺信息时明确写“未确认” |
