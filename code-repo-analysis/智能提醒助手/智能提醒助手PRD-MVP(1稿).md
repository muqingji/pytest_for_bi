## 一、背景

### 1.1 业务情况

我们是一款 AI 教育产品，学生需要在 App 中完成每日学习任务，例如看课、做题。App 已经具备每日任务、任务完成状态统计和任务入口，也已经有每天 18:00 统一发送固定 Push 的能力。有每日任务的付费学生约 30 万，DAU 约 50 万。

### 1.2 当前问题

部分学生不会主动打开 App 完成当天任务，导致学习中断、学习效果下降。约 40%（12 万）的学生当天未完成任务即离开 App，或者当天根本没有打开 App。

### 1.3 现有数据

| 数据 | 现状 |
| --- | --- |
| 用户规模 | DAU 约 50 万，付费学生（有每日任务）约 30 万 |
| 未完成规模 | 约 40%（12 万）学生当天未完成任务即离开或未打开 |
| 任务完成率 | 按学生口径约 60% |
| 现有提醒 | 每天 18:00 统一发送「你还有学习任务未完成」 |
| Push 到达率 / 打开率 | 到达率约 60%（部分用户关闭通知权限）；到达用户中打开率约 8%，打开后任务完成率约 45% |
| 活跃时段 | 日均在线约 25 分钟；16:00–18:00 占 35%，19:00–21:00 占 45% |
| 长期未打开 | 约 30% 的学生连续 3 天以上未打开 App |
| 用户构成 | 自驱型约 40%、被动型约 35%、流失型约 25% |

### 1.4 现在的临时方案与不足

现在唯一的提醒手段是每天 18:00 对全部用户发送同一条固定 Push，学生只能在系统设置里整体关闭通知权限，App 内没有开关或免打扰设置。

| 问题 | 现状表现 | 造成的后果 |
| --- | --- | --- |
| 不判断任务状态 | 已完成当天任务的用户照样收到提醒 | 无效打扰，用户信任下降 |
| 不区分人群 | 自驱型、被动型、流失型收到同样的提醒 | 自驱型被打扰，流失型被无效轰炸 |
| 不选择时机 | 所有用户在 18:00 收到提醒，忽略个人作息 | 提醒落在不看手机或不该被打扰的时间 |
| 没有频次上限和免打扰 | 系统没有统一控制触达次数和时间段 | 重复骚扰风险不可控 |
| 不考虑渠道可用性 | 通知权限关闭的用户仍会进入发送流程 | 白跑发送链路，也难以解释触达失败原因 |
| 无法归因 | 没有把「提醒」和「打开」「完成」串起来的记录 | 无法判断提醒有没有效果，也无法定位问题 |

## 二、目标

### 2.1 业务目标

- 每日任务完成率从当前 60% 提升至 75%。
- Push 打开率从约 8% 提升至 15% 以上。
- 在提升提醒效果的同时，控制重复提醒和用户打扰。

### 2.2 本功能目标与贡献

75% 和 15%+ 是业务整体目标，智能提醒不是达成它的唯一手段。本功能聚焦「符合提醒条件的目标用户」，通过对照实验验证智能提醒相对固定时间提醒带来的可归因增量；整体业务目标不直接作为本功能的验收门槛。

### 2.3 指标定义

指标按实验分组后的符合条件用户统计，归属日期使用用户本地时区的 `task_date`。

| 层级 | 指标 | 计算口径 | 用途 |
| --- | --- | --- | --- |
| 结果 | 每日任务完成率 | 当天完成全部必做任务的学生数 / 当天至少有一项必做任务的付费学生数；无任务日不计入分母 | 与 60% 基线同口径对比 |
| 结果 | Push 打开率 | 当天打开 Push 的去重用户数 / 当天 Push 成功送达的去重用户数 | 描述渠道表现，不作为完成效果的唯一依据 |
| 过程 | 到达率 | 成功送达的 Push 消息数 / Push 发送消息数，另按去重用户数补充 | 判断渠道是否正常 |
| 过程 | 提醒后任务开始率 | 归因窗口内由提醒入口开始任务的去重用户数 / 当日符合条件用户数 | 判断提醒是否促使用户开始学习 |
| 过程 | 提醒后任务完成率 | 归因窗口内完成全部必做任务的去重用户数 / 当日符合条件用户数 | 判断提醒是否带来完成增量 |
| 护栏 | 重复提醒率 | 同一用户同一天收到 2 条及以上独立业务提醒的用户数 / 当天收到至少 1 条的用户数 | 验证频控是否生效 |
| 护栏 | 通知关闭率 | 周期内关闭 Push 或智能提醒的用户数 / 周期开始时对应设置为开启的用户数，按周观察 | 监控打扰是否引起反感 |
| 护栏 | 投诉、卸载和退订 | 周期内发生对应事件的去重用户数 / 周期内被纳入评估的去重用户数 | 监控体验风险 |

口径说明：结果指标以实验分组时全部符合条件的用户为分母，用户未授权 Push、发送失败或回流首日不排程时仍保留在分母中，避免渠道不可用拉高效果结论。护栏指标用于上线后监控，不作为本期验收门槛。

## 三、资源概念说明

### 3.1 本次新增概念

| 概念 | 定义 |
| --- | --- |
| 提醒资格 | 根据任务状态、用户分层、提醒设置、频控、免打扰和任务有效期，判断用户当天是否具备被提醒的条件 |
| 个性化提醒时间 | 结合用户最近任务行为、App 活跃时间和任务截止时间计算出的当天提醒时间 |
| 提醒决策 | 一次判断的完整结果，包含是否提醒、计划时间、渠道、原因码和策略版本 |
| 延后提醒 | 用户点击「稍后提醒」后，把当前提醒重新安排到 1 小时后的能力 |
| 提醒策略版本 | 标识当前使用的规则集合，用于效果归因和问题追踪 |
| 用户分层 | 按行为数据实时计算的五类人群（数据不足、流失型、回流型、自驱型、被动型），决定提醒策略；结果不落库为固定标签 |

### 3.2 既有能力与外部依赖

以下能力由现有 App 或业务服务提供，**属于本次接入依赖，不属于本期新建范围**：

- 每日学习任务及必做任务定义。
- 任务完成状态和每日任务完成率统计。
- 任务详情页、做题流程和任务完成回传。
- 既有 Push 通道及发送基础设施。
- 提醒点击后的任务入口或 Deep Link。
- 系统 Push 权限状态（由操作系统和既有 App 权限体系管理，本功能只读取）。

本功能只消费任务状态和任务入口，在既有 Push 能力之上实现提醒资格判断、时机选择、频控、免打扰和延后提醒。

### 3.3 用户分层定义与判定规则

分层决定提醒策略。分层结果在每日评估或 App 打开事件触发的评估中按行为数据实时计算，**不落库为固定标签**，用户行为变化当天即可生效。

#### 3.3.1 用于分层判定的用户行为信号

| 信号 | 取值 | 含义与口径 | 在判定中的作用 |
| --- | --- | --- | --- |
| `history_days_available` | 0–7 | 可读取的历史行为天数 | 第 1 步：< 3 天时按被动型处理并记录 `INSUFFICIENT_HISTORY` |
| `inactive_days` | ≥ 0 | 距评估时点的连续未打开天数 | 第 2 步：≥ 3 时不进入主动 Push 排程 |
| `days_since_last_open` | ≥ 0 或空 | 本次打开 App 前，上一次打开距今天的本地日期间隔；仅在 App 打开事件中计算，无历史打开记录时为空 | 第 3 步：当日已打开且 ≥ 3 时命中回流首日 |
| `complete_days_7d` | 0–7 | 最近 7 天完成全部必做任务的天数 | 第 4 步：≥ 5 天 |
| `reminder_attributed_complete_days_7d` | 0–7 | 最近 7 天中「收到提醒后完成」的天数 | 第 4 步：≤ 1 天 |
| `open_days_prev_7d` | 0–7 | 再往前 7 天（T-3 至 T-9）打开 App 的天数 | 仅作历史打开窗口的审计信号，**不参与分层判定** |

自驱型判定使用 7 天窗口，因为 3 天样本过小，用户容易在自驱型与被动型之间反复切换。窗口长度是本期默认值，可配置。

#### 3.3.2 分层判定顺序与对应提醒策略

按以下顺序判定，**命中即结束**，五种结果互斥且穷尽。

| 顺序 | 人群 | 判定规则 | 本期策略 |
| --- | --- | --- | --- |
| 1 | 数据不足 | `history_days_available` < 3 | 按被动型处理并使用默认活跃窗口，记录 `INSUFFICIENT_HISTORY` |
| 2 | 流失型 | `inactive_days` ≥ 3 | 不进入主动 Push 排程，记录 `USER_INACTIVE`，由 P2 召回策略承接 |
| 3 | 回流型 | 当日已打开 App（`inactive_days` = 0），且 `days_since_last_open` ≥ 3 | 当天不发送提醒、不生成 Push 排程，记录 `RETURNING_FIRST_DAY`；次日起恢复常规 Push 资格 |
| 4 | 自驱型 | `complete_days_7d` ≥ 5 且 `reminder_attributed_complete_days_7d` ≤ 1 | 已完成不提醒；未完成时最多生成一条系统主动 Push，不额外增加触达 |
| 5 | 被动型 | 其余（有打开、完成产出低） | 本期重点服务：按任务行为、App 活跃习惯与任务截止时间提醒 |

规则要点：

1. **判定顺序不可交换。** 先判数据不足、再判流失，避免新用户被误判为流失型而失去提醒机会。
2. **回流型排在流失型之后。** 用户重新打开 App 后 `inactive_days` 归零，当天即从流失型转为回流型，不需要观察期或人工干预。
3. **回流判定用显式首日条件**，不用 `open_days_prev_7d` = 0 推算；后者的窗口在次日仍然成立，会让用户持续命中回流型而无法恢复常规 Push。
4. **回流首日做降温处理。** 用户当天已经主动打开 App，再叠加 Push 会造成同一天两次打扰，因此首日不发送提醒；次日起重新校验任务、设置、免打扰和频控后恢复常规 Push 资格。
5. **阈值是 MVP 设计假设。** 流失 3 天、自驱型完成 5 天、提醒归因完成 1 天、完成窗口 7 天均为可配置默认值，需上线前结合真实行为分布校准。

#### 3.3.3 分层判定示例：回流用户

| 日期 | 用户行为 | 分层结果 | 提醒策略 |
| --- | --- | --- | --- |
| T-10 至 T-4 | 每天打开并完成任务 | 自驱型 | 已完成，不提醒 |
| T-3 至 T-1 | 未打开 App | 流失型 | 不进入主动 Push 排程 |
| T（今天） | 打开 App 并进入任务页 | 回流型（`inactive_days` = 0 且 `days_since_last_open` ≥ 3） | 当天不发送提醒、不生成 Push 排程，记录 `RETURNING_FIRST_DAY` |
| T+1 | 进入次日每日评估 | 按常规规则重新判定 | 恢复常规 Push 资格，仍需通过任务、设置、免打扰和频控校验 |

### 3.4 上线前必须确认的数据前提

题目原文只提供了总体规模、Push 结果和活跃时段，没有确认以下用户级数据已经在现有系统中稳定可读。它们是本期上线前的接入前提，**不代表已经具备生产能力**。

| 数据或事件 | 本期用途 | 缺失或读取失败时的处理 |
| --- | --- | --- |
| App 打开历史、打开前 `last_open_at`、`AppOpened` 事件 | 计算 `inactive_days`、`days_since_last_open`，识别流失与回流首日 | 无历史时按数据不足处理；缺少打开前时间时不判定回流，按普通评估继续并记录数据不可用 |
| 最近任务开始 / 完成时间段 | 个性化提醒时间 | 无有效样本时依次回退到 App 活跃时间和默认窗口 |
| App 活跃时间段 | 个性化提醒时间 | 不可用时使用默认窗口 |
| 提醒归因完成事件 | 判断 `reminder_attributed_complete_days_7d` | 关联缺失时该次完成不计入提醒归因，保留总体完成结果 |
| Push 送达与打开回执 | 渠道指标与触达后辅助指标 | 送达未确认不计入成功送达分母，不影响结果指标按实验分组统计 |
| 稍后提醒的点击回传 | 触发 1 小时后 Push 排程（FR-007） | 回传缺失时不生成延后排程；重复点击幂等返回原排程，不产生第三次 Push |

上线前需要向对应提供方确认以上数据的产生方、同步时效、用户本地时区口径和历史留存。

依赖强弱规则：**行为数据是弱依赖**，读取失败时按被动型和默认窗口生成可解释结果，并记录数据降级原因；**任务状态、提醒设置和 Push 权限是强依赖**，读取失败时不生成可发送排程。

## 四、业务流程梳理

### 4.1 参与角色和职责

| 角色或系统 | 职责 |
| --- | --- |
| 学生 | 完成每日任务；查看和调整提醒设置；接收、打开或延后提醒 |
| 既有任务系统 | 提供当日任务、必做任务、完成状态、截止时间和任务入口 |
| 智能提醒服务 | 判断提醒资格；计算提醒时间；校验免打扰、截止时间和频控；保存决策与排程；记录事件 |
| 既有 Push 服务 | 按智能提醒服务的结果发送 Push，并返回发送和到达状态 |
| 数据与事件系统 | 记录决策、发送、到达、打开、开始和完成事件 |

### 4.2 服务流程

```text
每日评估或状态变化触发
→ 读取既有任务状态、用户历史行为和提醒设置
→ 判断提醒资格
→ 计算个性化提醒时间
→ 校验免打扰、任务截止时间和每日频控
→ 生成并保存提醒决策与排程
→ 到达计划时间前再次检查任务和用户状态
→ Push 可用时调用既有 Push；Push 未授权或发送失败时跳过本次提醒并记录未触达原因
→ 记录决策、发送、到达、打开和任务完成事件
→ 任务完成后取消当天尚未发送的提醒
```

### 4.3 用户流程

```text
打开 App
→ 查看今日任务和完成进度
→ 查看或调整提醒设置
→ 在合适时间收到 Push
→ 点击提醒进入既有任务入口
→ 开始学习
→ 完成全部必做任务
```

用户不需要每次打开 App 都调整提醒设置，设置入口由现有 App 页面承载。

## 五、方案简述

### 5.1 业务流程变化

用户使用流程见 4.3，本节只说明本期相对现状的变化。

| 环节 | 现状 | 本期调整 |
| --- | --- | --- |
| 提醒触发 | 每天 18:00 对所有用户发送固定 Push | 先判断任务状态、用户分层、提醒设置和频控；回流首日由 App 打开事件触发评估，当天不发送、不生成 Push 排程 |
| 提醒时间 | 所有用户同一时间接收 | 结合用户近期学习行为和任务截止时间安排提醒 |
| 提醒渠道 | 主要使用 Push | 本期只使用 Push 单渠道；Push 未授权或发送失败时跳过本次提醒并记录未触达原因 |
| 任务完成后的处理 | 固定 Push 可能继续发送 | 任务完成后取消当天尚未发送的提醒 |
| 效果评估 | 没有统一的提醒决策链路 | 记录决策、发送、到达、打开和任务完成事件，支持按 `decision_id` 归因 |

### 5.2 方案原则

1. 本期重点服务当天有未完成任务的被动型学生，以及重新打开 App 的回流型学生；回流首日不发送提醒，避免与用户主动打开形成双重打扰。
2. 自驱型学生重点控制无效打扰。
3. 流失型学生不通过提高提醒频次解决，由独立召回策略承接；重新打开 App 后按回流型恢复常规提醒。
4. 任务完成系统和 Push 基础能力复用现有能力，本期不新建。
5. 首期采用可解释、可测试的规则策略，不以大模型或复杂机器学习为前提。
6. 每位学生每天最多接收 1 次系统主动 Push；用户主动触发的「稍后提醒」不计入该上限，据此每天最多 2 次 Push。

### 5.3 本期 MVP 核心场景

| 场景编号 | 用户场景 | 触发条件 | 系统行为 | 预期结果 | 对应需求 |
| --- | --- | --- | --- | --- | --- |
| MVP-001 | 被动型学生有未完成任务 | 当日存在未完成必做任务，用户允许提醒且未达上限 | 结合历史行为、默认活跃窗口和截止时间生成排程 | 在可用时间发送一次提醒 | FR-001、FR-002、FR-008 |
| MVP-002 | 用户已完成或没有有效任务 | 任务全部完成、无任务或任务已过期 | 不创建可发送提醒；已有未发送排程取消 | 不产生无效提醒 | FR-001、FR-004 |
| MVP-003 | 用户处于免打扰时段 | 当前时间落在用户设置的免打扰区间 | 延后到下一个可用窗口，并重新检查截止时间 | 免打扰期间不发送 | FR-002、FR-003 |
| MVP-004 | 用户关闭系统 Push | Push 权限不可用 | 不调用 Push，跳过本次提醒并记录未触达原因 | 不重复调用 Push，缺口记入监控 | FR-001、FR-005 |
| MVP-005 | 用户主动选择稍后提醒 | 当天仍有未完成任务，用户点击「稍后提醒」 | 计划 1 小时后通过 Push 再次提醒，重新检查任务、免打扰、截止时间和频控 | 提供一次不占当日系统主动上限的延后机会，延后提醒不再提供二次入口 | FR-007 |
| MVP-006 | 调度重复或并发执行 | 同一用户同一天重复评估或发送 | 用决策幂等和每日 Push 上限拦截重复动作 | 最多发送一次 Push，不产生重复记录 | FR-005 |
| MVP-007 | 用户在提醒前完成任务或修改设置 | 排程尚未发送时任务完成、关闭提醒或修改免打扰 | 发送前二次校验并取消或调整排程 | 使用最新状态，避免过期提醒 | FR-003、FR-004、FR-005 |
| MVP-008 | 流失用户重新打开 App | 连续 3 天以上未打开的用户当天打开 App | App 打开事件触发回流评估；当天不发送、不生成 Push 排程；次日恢复常规 Push 资格 | 回流当天不被流失策略拦截，也不产生双重打扰 | FR-001、FR-002 |

## 六、风险与影响评估

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 提醒时间计算错误 | 用户在不合适的时间收到提醒，打开率下降 | 使用可解释规则，默认窗口兜底，并记录策略版本便于回溯 |
| 已完成任务仍被提醒 | 明显打扰，引发投诉 | 发送前再次读取任务状态；任务完成后取消未发送提醒 |
| 免打扰设置未生效 | 用户信任受损 | 设置修改后立即影响后续决策，并覆盖免打扰起止的临界时间 |
| 重复调度导致重复发送 | 同一用户被重复打扰 | 决策幂等 + 每日系统主动 Push 上限双重拦截 |
| 流失型用户被过度召回 | 退订、投诉或卸载增加 | 不通过提高提醒频次解决，进入 P2 召回策略 |
| 用户关闭 Push 后无法触达 | 本期没有替代渠道，Push 不可用的用户当天不会被触达 | 本期接受该缺口并记入监控；站内承接列入 P1 |
| 既有 18:00 固定 Push 与智能提醒重复触达 | 用户同时收到两条提醒 | 同一用户同一天只命中一种策略，并对固定 Push 做防重复处理 |
| 点击提醒后任务入口异常 | 打开后无法进入任务，影响打开后完成率 | 继续使用既有任务入口，不因本次接入改变入口链路 |
| 指标口径不一致 | 无法判断功能效果 | 上线前确认打开率和完成率的分母、归因窗口与统计周期 |
| 未成年人隐私风险 | 合规和信任风险 | 不记录姓名、手机号、任务正文、成绩等非必要信息 |

## 七、方案详情

### 7.0 提醒决策总览

系统对每个用户每天做一次提醒决策。判定按固定顺序执行，**命中即停止**并记录对应原因码。

| 顺序 | 判定 | 不通过时的原因码 | 结果 |
| --- | --- | --- | --- |
| 1 | 当天是否存在必做任务 | `NO_TASK` | 不生成可发送排程 |
| 2 | 必做任务是否已全部完成 | `TASK_COMPLETED` | 不生成新提醒，取消未发送排程 |
| 3 | 当前时间是否已晚于任务截止时间 | `TASK_EXPIRED` | 不发送普通提醒 |
| 4 | 用户是否关闭智能提醒 | `REMINDER_DISABLED` | 不生成提醒，取消未发送排程 |
| 5 | 用户分层（见 3.3.2） | `USER_INACTIVE` / `RETURNING_FIRST_DAY` | 按分层策略处理 |
| 6 | 当天系统主动 Push 是否已达上限 | `DAILY_CAP_REACHED` | 不创建第二条系统主动 Push 排程 |
| 7 | 提醒时间是否可用 | `QUIET_HOURS` / `INSUFFICIENT_TIME` | 移动到下一个可用窗口，或返回不可提醒原因 |
| 8 | Push 渠道是否可用 | `NO_AVAILABLE_CHANNEL` | 跳过本次提醒，记录未触达原因 |

通过全部判定的用户记录 `ELIGIBLE`，并生成一条系统主动 Push 排程。

### 7.1 FR-001 提醒资格判断

**做什么**：每天评估一次用户是否满足提醒条件，只有全部条件满足才生成提醒。

> 优先级 P0 ｜ 用户：当天有学习任务的学生 ｜ 前置条件：系统能读取任务状态、用户分层所需行为和提醒设置 ｜ 预期结果：只有当日存在未完成必做任务、用户允许提醒、任务有效且未达频控时，才生成提醒资格

**提醒条件（必须同时满足）**：

1. 当天存在必做任务，且未全部完成。
2. 用户没有关闭智能提醒，也没有关闭 Push。
3. 当前时间未晚于任务截止时间。
4. 当天系统主动 Push 未达到上限。
5. 计算出的提醒时间不违反免打扰设置。
6. 用户分层结果允许进入主动 Push 排程（排除流失型和回流首日）。

**边界与异常**：

- 周中、周末和节假日都可能有当日任务；**没有任务或休息日不发送提醒**。
- 任务、提醒设置或 Push 权限读取失败时，本次不生成可发送排程，等待下一次评估重试。
- 行为数据读取失败不视为系统错误：按被动型和默认窗口生成可解释结果，并记录数据降级原因。
- 同一用户同一天重复评估时，使用决策幂等返回已有结果，不新增第二条提醒。

### 7.2 FR-002 个性化提醒时间

**做什么**：为每个用户算出当天更可能被看到、且不违反约束的提醒时间。

> 优先级 P0 ｜ 用户：符合提醒资格的被动型学生；回流型用户从次日起恢复常规评估 ｜ 前置条件：存在有效历史行为，或可用默认活跃窗口 ｜ 预期结果：生成当天的提醒时间；无法生成可用时间时返回对应原因码，不发送提醒

**时间段选择顺序**（多个窗口频次相同时，按同一顺序取前者）：

1. 最近 7 天**任务开始**时间段中出现频次最高的窗口。
2. 最近 7 天**任务完成**时间段中出现频次最高的窗口。
3. 最近 7 天 **App 活跃**时间段中出现频次最高的窗口。
4. 以上都无有效样本时，使用默认活跃窗口 **16:00–18:00** 和 **19:00–21:00**，并记录 `DEFAULT_WINDOW`。

**无有效行为数据时的默认发送时刻（MVP 设计假设）**：

- 默认取用户本地 **19:30**，因为题目给出的 19:00–21:00 是占比最高的活跃时段。
- 当 19:30 落在免打扰区间，或晚于「任务截止前 1 小时」时，回退到 16:00–18:00 窗口内的 **17:00**。
- 两个时刻都不可用时：因免打扰导致不可用记录 `QUIET_HOURS`，因剩余时间不足记录 `INSUFFICIENT_TIME`，均不发送提醒。
- 19:30、17:00 和回退条件是本期设计假设与可配置参数，需上线前结合真实行为和任务截止分布验证。

**边界与异常**：

- 时间计算必须按**用户本地时区**处理；跨午夜的免打扰区间按本地日期拆分，不能用服务器时区直接比较。
- 候选时间落在免打扰区间时，移动到下一个可用窗口；没有可用窗口则记录对应原因码。
- 候选时间必须早于任务截止时间；剩余可用时间不足时记录 `INSUFFICIENT_TIME`。
- 回流首日当天不发送提醒、不生成 Push 排程，因此不产生可用时间。

### 7.3 FR-003 用户提醒设置

**做什么**：让学生自己控制是否接收提醒，以及什么时间段不要被打扰。

> 优先级 P0 ｜ 用户：学生 ｜ 前置条件：用户进入现有 App 的提醒设置入口 ｜ 预期结果：设置持久化并立即影响后续提醒决策；已排程但未发送的提醒按新设置重新判断

**本期支持两项设置**：

1. **智能提醒开关**：关闭后不生成任何系统主动 Push，已有的未发送排程取消。
2. **免打扰时间**：设置一个每日时间段，该时间段内不发送提醒；跨午夜区间按用户本地日期处理。

**默认值（MVP 设计假设，需上线前验证）**：

| 设置项 | 本期默认值 |
| --- | --- |
| 智能提醒开关 | 默认开启 |
| 免打扰时间 | 默认 21:30–07:00 |
| 每日系统主动 Push 上限 | 1 次 |
| 用户时区 | 取用户档案时区 |

**读取规则**：

- 设置记录不存在或字段缺失时使用默认值，并上报数据质量指标。
- 设置属于**强依赖**：读取失败时不发送提醒，**不采用旧设置或缓存值**。
- 用户修改设置后立即生效，已排程未发送的提醒按新设置取消或调整。

### 7.4 FR-004 已完成任务不提醒

**做什么**：用户完成当天全部必做任务后，不再收到当天的提醒。

> 优先级 P0 ｜ 用户：已完成全部必做任务的学生 ｜ 前置条件：既有任务系统返回全部必做任务已完成 ｜ 预期结果：不生成新的未完成提醒；已有未发送提醒取消，并记录 `TASK_COMPLETED`

**规则细节**：

- 「完成当天任务」的定义是**完成全部必做任务**；未进入任务详情、或只完成部分必做任务，都视为未完成，不关注答题对错。
- 检查发生在两个时点：生成决策时，以及排程到期发送前。任一命中已完成都不再发送。
- 发送前二次校验发现已完成时，取消排程并记录取消原因，不产生发送记录。

### 7.5 FR-005 每日提醒频控

**做什么**：控制触达次数，保证重复调度和失败重试不会给用户多发。

> 优先级 P0 ｜ 用户：所有进入提醒策略的学生 ｜ 前置条件：当天已有提醒发送记录或排程记录 ｜ 预期结果：同一用户同一天最多发送 1 次系统主动 Push；重复执行不产生重复发送

**上限规则**：

- 每位学生每天最多接收 **1 次系统主动 Push**。
- 用户主动触发的「稍后提醒」**不计入**该上限，据此每天最多 2 次 Push：1 次系统主动提醒 + 最多 1 次用户主动延后提醒。
- 当天系统主动 Push 已达上限时，再次评估记录 `DAILY_CAP_REACHED`，不创建第二条系统主动 Push 排程。
- 用户点击提醒但没有完成任务时，当天不立即重复发送。

**幂等要求**：

| 场景 | 期望行为 |
| --- | --- |
| 同一用户、同一天、同一策略版本重复评估 | 返回已有决策或幂等命中结果，不新增重复决策或发送记录 |
| 同一用户同一时刻并发评估或发送 | 通过持久化唯一约束和条件更新拦截，最多产生一次发送 |
| 发送失败后重试 | 复用同一去重标识，最多增加一次发送尝试，不新增独立排程或第二条业务提醒，且不突破每日上限 |

### 7.6 FR-007 一小时后再提醒

**做什么**：用户看到提醒但当下不方便时，可以选择「稍后提醒」，1 小时后通过 Push 再提醒一次。

> 优先级 P0 ｜ 用户：已收到提醒并主动点击「稍后提醒」的学生 ｜ 前置条件：当天仍有未完成必做任务，且仍存在可提醒时间 ｜ 预期结果：生成新排程，或返回不可再次提醒的原因；不改变当天任务完成状态

**渠道与上限规则**：

- 延后提醒使用 **Push 渠道**。
- 该次提醒由用户主动触发，**不占用**当日 1 次系统主动 Push 上限，据此每天最多 2 次 Push。
- 延后提醒产生的这次 Push **不再提供「稍后提醒」入口**，延后链条最多一段，避免当天被反复延后。
- Push 不可用时返回 `NO_AVAILABLE_CHANNEL`。

**幂等与异常规则**：

- 重复点击或重复请求按同一请求标识和 `decision_id` 幂等处理，只产生一个新排程。
- 同一 `decision_id` 的第二次「稍后提醒」请求返回不可再次提醒的结果。
- 发送失败重试不新增独立排程或第二条业务提醒。
- 任务截止时间不足 1 小时时不强行创建排程，返回 `INSUFFICIENT_TIME`。

### 7.7 FR-008 提醒内容

**做什么**：让用户一眼看到还有多少任务、大概要花多久，并直接进入任务入口。

> 优先级 P0 ｜ 用户：收到 Push 的学生 ｜ 前置条件：系统取得最新剩余任务数和预计用时 ｜ 预期结果：内容反映最新任务状态；点击后进入既有任务入口

**首期文案模板**：

```text
标题：今天还有 {remaining_count} 项学习任务
正文：预计用时 {estimated_minutes} 分钟，现在开始刚刚好
按钮：去完成任务
```

**内容规则**：

- 内容必须反映**最新任务状态**，剩余任务数和预计用时在发送前读取。
- 语气使用鼓励、激励的表达，**不使用**恐吓、羞辱或制造焦虑的表述。
- 不展示任务正文、成绩等敏感信息。

## 八、操作日志说明

本功能涉及提醒决策、排程和发送记录，业务侧保留以下两类记录。

**推送任务记录**：`decision_id`、`user_id`、`task_date`、`should_remind`、`scheduled_at`、`channel`、`reason_code`、`strategy_version`、`status`。

**推送发送记录**：`decision_id`、`channel`、`sent_at`、`delivered_at`、`opened_at`、`attempt_no`、`status`、`error_code`。

## 九、权限说明

本功能不新增后台角色权限，也不搭建独立运营后台。学生侧复用现有 App 能力：修改智能提醒开关、设置免打扰时间、点击提醒进入既有任务入口。

系统 Push 权限由操作系统和既有 App 权限体系管理，本功能只读取权限状态；Push 不可用时跳过本次提醒并记录未触达原因。

## 十、埋点说明

### 10.1 埋点目标

记录从提醒决策到任务完成的完整链路，评估智能提醒是否带来可归因的打开和任务完成增量。任务完成状态以既有任务系统为准，智能提醒只负责关联和归因。

### 10.2 公共字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `event_id` | String | 是 | 事件唯一 ID |
| `event_name` | String | 是 | 事件名称 |
| `event_time` | DateTime | 是 | 事件发生时间 |
| `schema_version` | String | 是 | 事件信封版本 |
| `source` | String | 是 | 事件产生方 |
| `user_id` | String | 是 | 用户匿名 ID |
| `task_date` | Date | 是 | 任务所属日期 |
| `timezone` | String | 是 | 用户时区 |
| `decision_id` | String | 关联提醒事件必填 | 一次提醒决策的唯一 ID；未关联决策的 App 打开、设置变更等事件为空 |
| `strategy_version` | String | 关联提醒事件必填 | 提醒策略版本；未关联决策的事件为空 |
| `channel` | String | 否 | 本期取值 `push` |
| `experiment_group` | String | 否 | 由既有实验平台提供时填写实验组或对照组；没有实验平台时为空 |

提醒生命周期事件以及可归因的 `task_started`、`task_completed` 必须携带 `decision_id` 和 `strategy_version`；`AppOpened`、`reminder_preference_updated` 等发生在决策创建前的事件不要求携带决策关联字段。

### 10.3 事件字段

| 事件 | 触发时机 | 事件专属字段 |
| --- | --- | --- |
| `reminder_decision_created` | 完成一次提醒决策 | `should_remind`、`reason_code`、`scheduled_at`、`remaining_count`、`estimated_minutes`、`user_segment`、`decision_source` |
| `reminder_scheduled` | 成功生成提醒排程 | `scheduled_at`、`channel`、`reschedule_reason` |
| `reminder_cancelled` | 已排程提醒被取消 | `cancel_reason`、`cancelled_at` |
| `reminder_snoozed` | 用户点击「稍后提醒」 | `snooze_until`、`snooze_duration_minutes`、`original_scheduled_at` |
| `reminder_sent` / `reminder_failed` | 调用既有 Push 发送 / 发送失败 | `delivery_status` |
| `reminder_delivered` | 渠道确认送达 | `delivered_at` |
| `reminder_opened` | 用户打开 Push | `open_source`、`latency_seconds`、`target_page` |
| `task_started` | 用户从提醒进入任务并开始学习 | `entry_source`、`remaining_count` |
| `task_completed` | 既有任务系统确认全部必做任务完成 | `completed_count`、`required_count`、`completion_duration_seconds`、`completion_source` |
| `reminder_preference_updated` | 用户修改提醒设置 | `changed_fields`、`reminder_enabled`、`quiet_hours_start`、`quiet_hours_end`、`effective_at` |

### 10.4 原因码

| 原因码 | 含义 |
| --- | --- |
| `ELIGIBLE` | 满足提醒条件 |
| `NO_TASK` | 当天没有任务 |
| `TASK_COMPLETED` | 当天任务已完成 |
| `TASK_EXPIRED` | 任务已过期 |
| `REMINDER_DISABLED` | 用户关闭提醒 |
| `DAILY_CAP_REACHED` | 达到每日提醒上限 |
| `QUIET_HOURS` | 当前处于免打扰时间 |
| `INSUFFICIENT_TIME` | 剩余时间不足 |
| `NO_AVAILABLE_CHANNEL` | 没有可用提醒渠道；本期为 Push 未授权或发送失败 |
| `USER_INACTIVE` | 连续 3 天以上未打开 App，判定为流失型，不进入主动 Push 排程 |
| `INSUFFICIENT_HISTORY` | 历史行为数据不足 3 天，按被动型处理并使用默认活跃窗口 |
| `BEHAVIOR_DATA_DEGRADED` | 行为数据读取超时、字段缺失或延迟超限；使用可用信号和默认窗口 |
| `RETURNING_FIRST_DAY` | 回流型首日，当天不发送提醒、不生成 Push 排程 |
| `DEFAULT_WINDOW` | 缺少有效历史行为，使用默认活跃窗口 |

不记录学生姓名、手机号、任务正文、成绩和其他非必要敏感信息。

## 十一、测试说明

### 11.1 测试重点

- 未完成任务的被动型用户生成提醒；已完成任务不生成提醒。
- 免打扰时间延后或不发送；覆盖免打扰起止的临界时间。
- Push 未授权或发送失败时不调用 Push，跳过本次提醒并记录未触达原因。
- 每日 Push 频控生效；重复调度不产生重复提醒；发送失败重试不突破频控。
- 缺少历史行为时使用默认活跃窗口；无历史行为用户使用 19:30，不可用时回退 17:00。
- 发送前任务完成时取消提醒。
- 用户点击「稍后提醒」后重新排程，且不占用当日系统主动 Push 上限、不再提供二次入口。
- 用户关闭提醒后不生成提醒，并取消未发送排程。
- 流失型用户不进入主动 Push 排程；重新打开 App 当天按回流型处理，不发送提醒，次日恢复。
- 自驱型用户按「打开 + 完成」信号组合控制打扰。
- 提醒设置缺失或读取失败时按默认值处理且不误发。

## 十二、旧功能/旧数据处理

### 12.1 是否涉及

是。本功能依赖并优化现有的任务系统、任务完成统计、每日 18:00 固定 Push、Push 权限和历史行为数据。

### 12.2 处理方案

| 旧功能或旧数据 | 处理方案 |
| --- | --- |
| 每日 18:00 固定 Push | 保留作为对照策略和灰度期间的兜底；与智能提醒不重复触达同一用户 |
| 智能提醒实验组 / 对照组 | 实验组使用智能提醒策略，不与固定 Push 同时发送；对照组继续使用原有 18:00 固定 Push |
| 任务状态和完成率 | 以既有任务系统为唯一事实来源，不重新定义、不迁移历史数据 |
| Push 权限 | 读取既有权限状态，不维护第二套权限数据 |
| 历史行为数据 | 只读取既有行为数据用于分层和时间计算，不新建行为数据链路 |

### 12.3 兼容规则

- 同一用户同一天只命中一种策略，每人每天最多 1 次系统主动 Push（用户主动触发的「稍后提醒」不计入）。
- 智能提醒异常需要回退时，关闭后停止新增智能排程并恢复既有固定 Push，历史提醒记录保留。
