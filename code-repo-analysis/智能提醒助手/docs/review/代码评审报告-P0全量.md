## Findings

### CR-001 [P1][状态与并发] 条件更新失败被吞掉后仍调用 Push 渠道，会向已取消的提醒发送

- 状态：**已修复**（2026-09-21）；`advance` 保留条件更新错误，`process` 在 `ErrConditionFailed` 时安静结束当前排程，不调用渠道、不写终态事件、不虚增终态计数。

- 位置：`internal/application/dispatch/service.go:362`（`advance` 对 `port.ErrConditionFailed` 返回 nil）、`internal/application/dispatch/service.go:201`（调用方据此继续发送）、`internal/adapter/storage/sqlite.go:319`（取消集合含 `CLAIMED`/`SENDING`）
- 证据：临时探针 `TestCRProbeChannelCalledWhenConditionUpdateFails`（`UpdateSchedule` 固定返回 `port.ErrConditionFailed`）实测 `counts={Scanned:1 Claimed:1 Sent:1 ...}` 且 `channel_calls=1`；即「排程已被取消或已被其他执行者推进」时仍调用渠道。
- 影响：`CancelPendingSchedules`（技术方案 4.1.1 第 176 行要求取消 `SCHEDULED/CLAIMED/SENDING/RETRY_WAIT`）与抢占之间存在窗口。用户在 dispatch 抢占后完成任务、关闭提醒或评估拒绝时，排程已置 `CANCELLED`，但本次发送仍会走到渠道，产生错误触达，违反 AC-002、AC-010、AC-012 与 FR-004/FR-003 的核心规则；事件还会出现「已取消又已发送」的矛盾序列。
- 建议：`advance`、`cancel`、`markSent`、`markFailed`、`release` 必须把 `ErrConditionFailed` 作为「动作失效」向上返回，由 `process` 记入抢占失败计数并结束本条处理，不再调用渠道。

### CR-002 [P1][可靠性与恢复] 发送链路依赖错误后无法回收 `SENDING` 排程，提醒静默永久丢失

- 状态：**已修复**（2026-09-21）；处理过程使用同一排程指针跟踪 `CLAIMED/SENDING/RETRY_WAIT` 与 `attempt_no`，依赖错误按当前中间态条件释放回 `SCHEDULED`，释放冲突不覆盖并发结果。

- 位置：`internal/application/dispatch/service.go:102`（错误后调用 `release`）、`internal/application/dispatch/service.go:347`（`release` 只命中 `CLAIMED -> SCHEDULED`）、`internal/adapter/storage/sqlite.go:159`（`ListDueSchedules` 只取 `status='SCHEDULED'`，不比较 `lease_until`）、`internal/adapter/storage/sqlite.go:178`（`ClaimSchedule` 写租约但无读取方）
- 证据：临时探针 `TestCRProbeScheduleStuckAfterDependencyErrorPastSending`（真实 SQLite + 投递写入失败）实测 `排程状态=SENDING`、`后续到期扫描可回收条数=0`；`rg -n "reconcile" cmd internal` 无实现，技术方案 4.2.1 第 366 行要求「租约超时后只能由 reconcile 释放」。
- 影响：依赖错误若发生在 `SENDING` 之后（写投递记录失败、渠道调用异常但查询也失败等），排程停在 `SENDING`，既不重试也不再被扫描，`sent` 不增加、无 `reminder_sent`/`reminder_failed` 事件、无告警；用户当天不再收到提醒，操作侧也看不到失败。`CLAIMED` 态在进程崩溃后同样依赖 reconcile。
- 建议：`release` 覆盖 `SENDING/RETRY_WAIT -> SCHEDULED` 并记录依赖错误指标；或按 `lease_until` 过期回收（含 `CLAIMED`）。若本地交付不实现 reconcile，必须在技术方案 9.3 登记该缺口与人工回收方式。

### CR-003 [P1][接口与配置] 本地 HTTP 入口默认关闭 `feature_enabled`，Makefile/文档未开启，业务测试 9 例失败

- 状态：**已修复**（2026-09-21）；程序默认仍保持关闭，`make serve` 与 `make test-api-fresh` 显式传 `-feature-enabled`；关闭态统一返回 `503 FEATURE_DISABLED`、`retryable=false`，OpenAPI 与本地入口文档已同步。

- 位置：`cmd/reminder-service/main.go:82`（`-feature-enabled` 默认 false）、`cmd/reminder-service/serve.go:64`、`Makefile:108`（`test-api-fresh` 未传开关）、`Makefile:68`（`serve` 未传开关）、`docs/implementation/接口-HTTP本地入口.md:50`（声明「服务级 feature_enabled 由装配显式开启（本地入口的用途就是可测试）」）
- 证据：实际启动本地入口后 `POST /internal/v1/reminders/evaluate` 与 `POST /internal/v1/reminders/dispatch-due` 均返回 `HTTP 500 {"code":"DEPENDENCY_UNAVAILABLE","retryable":true}`；CLI 一次性执行输出 `feature_enabled is false` 且退出码 1；`SERVE_ADDR=127.0.0.1:8098 make test-api-fresh` 实测 **9 failed / 11 passed / 20 skipped**（含 EVAL-002~006、EVAL-010、EVAL-011、EVAL-017、DISP-001，失败原因均为 HTTP 500）。
- 影响：本地可测试入口按 `Makefile`/`tests/README.md` 的文档命令启动后不可用，pytest 业务测试无法作为验收证据；且「配置态关闭」被映射为 `500 + retryable=true`，调用方按契约会无限重试，语义与「灰度开关关闭」不符。
- 建议：本地入口装配显式开启开关（`Makefile`、`tests/README.md`、`docs/implementation/接口-HTTP本地入口.md` 同步），或让 `-serve` 默认开启并在文档写明；开关关闭的响应码与 `retryable` 单独定义（技术方案 4.3.1）。

### CR-004 [P1][状态与并发] 偏好变更事件先落库、读偏好失败后重投被去重，关闭提醒不生效

- 状态：**已修复**（2026-09-21）；偏好事实读取、取消与幂等重评估成功后才写事件去重记录，失败重投不再被提前消费；重复事件仍执行幂等业务处理并返回 `Reused=true`。

- 位置：`internal/application/evaluate/preference.go:97`（先写事件）、`internal/application/evaluate/preference.go:102`（去重命中直接 `Reused` 返回）、`internal/application/evaluate/preference.go:111`（之后才读最新偏好，失败即返回错误）
- 证据：临时探针 `TestCRProbePreferenceEventDedupSkipsReevaluation`（真实 SQLite，偏好读取首次失败、底层设置已关闭提醒）实测 `重投返回 reused=true`、`取消调用次数=0`、`排程状态=SCHEDULED`。
- 影响：事件总线重投同一条偏好变更事件时，事件已按 `event_id` 去重，处理函数直接返回 `REUSED`，既没有取消待发送排程也没有重新评估；用户已关闭提醒但当天仍会收到 Push，违反 AC-012 与 FR-003。
- 建议：先读最新偏好并完成取消/重评估，成功后才把事件标记为已处理；或去重命中时仍执行幂等的取消与重评估（副作用幂等，重复执行不产生第二条事件）。

### CR-005 [P2][可靠性与恢复] 决策已提交但事件写失败时，重试命中 `REUSED` 永不补写事件

- 状态：**已修复**（2026-09-21）；`CREATED` 与 `REUSED` 共用确定性事件补写路径，复用决策时读取既有排程并补齐缺失的 `reminder_decision_created`、`reminder_scheduled`。

- 位置：`internal/application/evaluate/service.go:122`（`Reused` 直接返回，不写任何事件）、`internal/application/evaluate/service.go:137`~`160`（事件在决策事务提交后单独写入）；对照技术方案第 230 行「事件发布失败由 outbox 或 reconcile 补发」
- 证据：临时探针 `TestCRProbeReusedDecisionDoesNotRepairMissingEvent`（真实 SQLite，首次 `AppendEvent` 失败一次）实测重试 `reused=true`、`事件此前是否缺失=true`。
- 影响：决策与排程已落库、`reminder_decision_created` 缺失，重试不再补写；本地无 outbox/reconcile，AC-011 要求的「事件可按 `decision_id` 串联」在该序列上出现断链，且调用方无法通过重试自愈。
- 建议：`Reused` 分支按 `event_id` 判断并补写缺失的决策/排程事件，或在技术方案 9.3 登记「本地无 outbox/reconcile，事件缺口需人工补发」并明确处置方式。

### CR-006 [P2][契约与文档] 投递状态 `DELIVERED`/`RECONCILING` 未建模，渠道「送达」回执会被判为 `UNKNOWN`

- 状态：**已修复**（2026-09-21）；P0 投递状态收敛为 `SENDING/SENT/FAILED/UNKNOWN`，不接收真实 `DELIVERED` 回执；用量只统计 `SENT`，`DELIVERED/RECONCILING` 明确移至后续真实渠道能力。

- 位置：`internal/domain/reminder/types.go:95`~`100`（只有 `SENDING/SENT/FAILED/UNKNOWN`）、`internal/domain/reminder/dispatch.go:12`~`21`（未知取值一律归 `UNKNOWN`）、`internal/adapter/storage/sqlite.go:111`（`GetDailyUsage` 却按 `'SENT','DELIVERED'` 统计）；对照技术方案第 364 行「本期投递状态为 `SENDING`、`SENT`、`DELIVERED`、`FAILED`、`UNKNOWN`、`RECONCILING`」
- 证据：代码中没有 `DELIVERED`/`RECONCILING` 常量，也没有任何写入路径；`GetDailyUsage` 的 `'DELIVERED'` 分支在当前实现下不可达。
- 影响：真实渠道返回「送达」时被归一化为 `UNKNOWN`，用量统计按 `SENT`/`DELIVERED` 计数会漏计（当日主动 Push 用量口径失真），事件 `delivery_status` 记为 `UNKNOWN` 也无法反映已送达事实。
- 建议：补齐状态枚举与映射（含 reconcile 相关状态），或把技术方案 4.2.1/4.3.3 的 `DELIVERED` 明确为「本期不接收送达回执」并同步 `GetDailyUsage` 口径；两者不应同时成立。
