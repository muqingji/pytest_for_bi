# BUG-001 修复记录：P0 全量代码评审中的可直接修复项

## 缺陷归属

归属：业务代码、用例与测试资产、工程质量。

依据：CR-001、CR-002、CR-004、CR-005、CR-011 分别定位到 `internal/application/dispatch/service.go`、`internal/application/evaluate/preference.go`、`internal/application/evaluate/service.go` 的条件更新、失败恢复和事件幂等逻辑；CR-008 定位到 `tests/cases/evaluate_reminder.json#EVAL-011` 的运行时钟耦合；CR-009 定位到 `cmd/reminder-service/evaluate_integration_test.go` 的格式问题。

## 复现

```bash
go test -overlay=/tmp/cr-probe/overlay.json -vet=off -run TestCRProbe ./internal/application/{dispatch,evaluate}/
go test -run 'TestDispatchEndsWhenClaimFailsAndWhenConditionUpdatesLose|TestDispatchDoesNotCountCancellationWhenConditionUpdateLoses|TestDispatchReleasesSendingScheduleAfterDependencyFailure|TestPreferenceChangedHandlerRetriesAfterPreferenceReadFailure|TestServiceRepairsMissingEventsWhenDecisionIsReused' ./internal/application/dispatch ./internal/application/evaluate
SERVE_ADDR=127.0.0.1:8098 make test-api-fresh
gofmt -l cmd internal
```

实际：修复前探针确认条件冲突后仍发送/计数、`SENDING` 排程无法回收、偏好事件重投被提前去重、`REUSED` 决策不补事件；`EVAL-011` 会随运行时刻返回 `INSUFFICIENT_TIME`；格式检查输出目标文件。

期望：条件冲突结束当前 worker，依赖失败可恢复，业务成功后才消费偏好事件，`REUSED` 可补事件，`EVAL-011` 稳定验证 `NO_AVAILABLE_CHANNEL`，格式检查无输出。

## 根因

Dispatch 把条件更新失败当成功并始终按 `CLAIMED` 释放；偏好处理在业务副作用之前写去重事件；评估的 `REUSED` 分支在事件写入前提前返回；测试数据使用已过期日期；目标 Go 文件未格式化。

## 改动清单

- `internal/application/dispatch/service.go`：传递条件更新冲突，跟踪当前排程状态与尝试次数，并按当前中间态释放。
- `internal/application/evaluate/preference.go`：业务处理成功后再写偏好事件去重记录，重复事件继续执行幂等重评估。
- `internal/application/evaluate/service.go`：新增确定性决策/排程事件补写路径，供新建和 `REUSED` 共用。
- `tests/cases/evaluate_reminder.json`：`EVAL-011` 使用远期任务日期隔离当前时钟。
- `cmd/reminder-service/evaluate_integration_test.go`：执行 `gofmt`。
- `dev-tools/skills/bug-fix/scripts/check_fix_record.py`：按 `测试文件:测试函数` 逐条校验聚合修复记录，避免多文件、多函数被错误做笛卡尔积。
- 对应 Go 测试文件：增加条件冲突、状态释放、失败重投、事件补写与错误分支回归测试。
- 没有改：PRD、验收标准、技术方案、OpenAPI IDL、迁移、真实外部服务配置，以及 CR-003/006/007/010 的待裁定内容。
