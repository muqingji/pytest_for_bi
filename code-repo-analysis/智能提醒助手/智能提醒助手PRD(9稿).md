## 一、背景

### 1.1 业务背景

我们是一款 AI 教育产品，学生需要在 App 中完成每日学习任务，例如看课、做题等。现有 App 已具备每日任务、任务完成状态统计和任务入口；系统也已有每天 18:00 统一发送固定 Push 的能力。

### 1.2 当前问题

部分学生不会主动打开 App 完成当天任务，导致学习中断和学习效果下降。当前固定 Push 没有结合用户的任务状态、历史学习习惯、提醒偏好和当前时间进行判断，存在以下问题：

- 已完成任务的用户可能仍然收到无效提醒。
- 所有用户在同一时间收到相同提醒，无法适配不同学习习惯。
- 用户关闭 Push 权限后，缺少有效的站内提醒降级。
- 用户处于免打扰时段或已经达到提醒上限时，缺少统一控制。
- 提醒是否有效无法通过统一事件链路进行归因。

### 1.3 现有数据

- DAU 约 50 万，付费学生（有每日任务）约 30 万。
- 约 40%（12 万）学生当天未完成任务即离开 App 或根本未打开。
- 当前任务完成率按学生口径约为 60%。
- 当前固定 Push 每天 18:00 发送。
- Push 到达率约 60%，到达用户中的打开率约 8%，打开后任务完成率约 45%。
- 学生日均在线时长约 25 分钟，主要活跃时段为 16:00–18:00（35%）和 19:00–21:00（45%）。
- 约 30% 的学生连续 3 天以上未打开 App。

## 二、目标

### 2.1 整体业务目标

- 将每日任务完成率从当前 60% 提升至 75%。
- 将 Push 打开率从约 8% 提升至 15% 以上。
- 在提升提醒效果的同时控制重复提醒和用户打扰。

### 2.2 智能提醒的产品贡献目标

75% 和 15%+ 是业务整体目标。本功能聚焦符合提醒条件的目标用户，通过对照实验评估智能提醒对打开率和任务完成率带来的可归因增量；整体业务目标不直接作为单项功能的验收门槛。

### 2.3 指标定义

| 指标层级 | 指标 | 说明 |
| --- | --- | --- |
| 结果指标 | 每日任务完成率 | 当天完成全部必做任务的学生数 / 当天有任务的付费学生数 |
| 结果指标 | Push 打开率 | 打开提醒的用户数 / 成功送达 Push 的用户数；具体统计口径待业务确认 |
| 过程指标 | 到达率 | 成功送达 Push 的数量 / Push 发送数量 |
| 过程指标 | 提醒后任务开始率 | 提醒后进入并开始任务的用户数 / 成功送达或展示提醒的用户数 |
| 过程指标 | 提醒后任务完成率 | 归因窗口内完成任务的用户数 / 成功送达或展示提醒的用户数 |
| 护栏指标 | 重复提醒率 | 同一用户同一天收到重复提醒的比例 |
| 护栏指标 | 通知关闭率 | 用户关闭系统 Push 或智能提醒的比例 |
| 护栏指标 | 投诉、卸载和退订 | 用于观察提醒是否造成负面影响 |

提醒到任务完成的归因窗口、统计周期和实验口径待业务确认；业务指标以发布后的对照实验结果为准。

#### 2.3.1 新需求验收指标

| 指标 | 验收要求 | 对应标准 |
| --- | --- | --- |
| 提醒资格规则正确性 | 资格、免打扰、过期和已完成场景均符合产品规则 | AC-001、AC-002、AC-003、AC-009 |
| 已完成任务提醒泄漏 | 验收场景中不得产生新的未完成任务提醒 | AC-002、AC-010 |
| 每日 Push 重复发送 | 同一用户同一天不得发送第二次 Push；重复调度不得产生重复记录 | AC-005、AC-006、AC-007 |
| 设置变更生效 | 未发送排程使用最新提醒开关和免打扰设置 | AC-012 |
| 事件链路完整性 | 决策、渠道、打开和任务完成事件可通过 `decision_id`、`strategy_version` 关联 | AC-011 |
| 智能提醒可归因增量 | 与固定 Push 或不提醒策略进行对照，具体提升阈值、归因窗口和实验周期待确认 | 待确认 |

### 2.4 历史功能体验防裂化指标

本功能复用既有任务、任务入口和 Push 能力。发布后需持续观察以下历史能力，避免智能提醒接入造成体验回退；量化阈值和统计周期待确认。

| 历史能力 | 基线信息 | 防裂化要求 |
| --- | --- | --- |
| 既有 Push 到达率 | 当前约 60% | 智能提醒实验组的 Push 到达率不应低于既有固定 Push 对照基线；阈值和统计周期待确认 |
| 提醒打开后的任务完成链路 | 当前打开后任务完成率约 45% | 点击提醒后应继续进入既有任务入口，不能因提醒接入导致入口失败或任务完成回传异常；量化阈值待确认 |
| 任务完成状态与完成率统计 | 既有任务系统提供 | 不修改、不迁移历史任务完成数据；发布后统计口径保持一致 |
| 每日 18:00 固定 Push | 既有线上能力 | 对照组或灰度回退时可继续发送；不与智能提醒重复触达同一用户 |

## 三、资源概念说明

### 3.1 本次新增概念

| 概念 | 定义 |
| --- | --- |
| 智能提醒资格 | 系统根据任务状态、用户分层、提醒设置、频控、免打扰和任务有效期判断用户是否具备提醒条件 |
| 个性化提醒时间 | 基于用户最近任务行为、App 活跃时间、默认活跃窗口和任务截止时间计算出的当日提醒时间 |
| 提醒渠道 | 发送提醒的方式，包括既有 Push 和用户进入 App 后展示的站内提醒 |
| 提醒决策 | 一次判断的结果，包括是否提醒、计划时间、渠道、原因和策略版本 |
| 延后提醒 | 用户点击“稍后提醒”后，将当前提醒重新安排到 1 小时后的能力 |
| 提醒策略版本 | 标识当前使用的提醒规则，用于效果分析和问题追踪 |

### 3.2 既有能力与外部依赖

以下能力由现有 App 或业务服务提供，作为本需求的接入依赖，不纳入本期新建范围：

- 每日学习任务及必做任务定义。
- 任务完成状态和每日任务完成率统计。
- 任务详情页、做题流程和任务完成回传。
- 既有 Push 通道及发送基础设施。
- 提醒点击后的任务入口或 Deep Link。

本功能只消费任务状态和任务入口，并在现有 Push 或站内消息能力之上实现提醒资格判断、时机选择、频控、免打扰、延后提醒和渠道编排。

## 四、业务流程梳理

### 4.1 参与角色和职责

| 角色或系统 | 职责 |
| --- | --- |
| 学生 | 完成每日任务，查看和调整提醒设置，接收或打开提醒 |
| 既有任务系统 | 提供当日任务、必做任务、完成状态、截止时间和任务入口 |
| 智能提醒服务 | 评估提醒资格、计算提醒时间、选择渠道、执行频控并记录决策 |
| 既有 Push 服务 | 按智能提醒服务的结果发送 Push，并返回发送和到达状态 |
| App 站内消息能力 | 用户进入 App 后展示轻量站内提醒 |
| 数据与事件系统 | 记录决策、发送、到达、打开、开始和完成事件 |

### 4.2 服务流程

```text
每日评估或状态变化触发
→ 读取既有任务状态、用户历史行为和提醒设置
→ 判断提醒资格
→ 计算个性化提醒时间
→ 校验免打扰、任务截止时间和每日频控
→ 生成并保存提醒决策
→ 到达计划时间前再次检查任务和用户状态
→ Push 可用时调用既有 Push；Push 未授权时等待用户进入 App 展示站内提醒
→ 记录决策、发送、到达、展示、打开和任务完成事件
→ 任务完成后取消当天尚未发送的提醒
```

### 4.3 用户流程

```text
打开 App
→ 查看今日任务和完成进度
→ 查看或调整提醒设置
→ 在合适时间收到 Push，或进入 App 后看到站内提醒
→ 点击提醒进入既有任务入口
→ 开始学习
→ 完成全部必做任务
```

用户不需要每次打开 App 都调整提醒设置；设置入口由现有 App 页面承载。

## 五、方案简述

### 5.1 使用流程与业务流程变化

#### 用户使用流程

```text
打开 App
→ 查看今日任务和完成进度
→ 查看或调整提醒设置
→ 在合适时间收到 Push，或进入 App 后看到站内提醒
→ 点击提醒进入既有任务入口
→ 开始学习并完成今日必做任务
```

#### 业务流程变化

| 环节 | 现状 | 本期调整 |
| --- | --- | --- |
| 提醒触发 | 每天 18:00 面向所有用户发送固定 Push | 先判断任务状态、用户分层、提醒设置和频控，再决定是否提醒 |
| 提醒时间 | 所有用户同一时间接收 | 结合用户近期学习行为和任务截止时间安排提醒 |
| 提醒渠道 | 主要使用 Push | Push 不可用时，用户进入 App 后展示站内提醒 |
| 任务完成后的处理 | 固定 Push 可能继续发送 | 任务完成后取消当日尚未发送的提醒 |
| 运营与效果评估 | 无统一的提醒决策链路 | 记录决策、发送、到达、打开和任务完成事件 |

### 5.2 方案原则

1. 首期重点服务当天有未完成任务的被动型学生。
2. 自驱型学生重点控制无效打扰。
3. 流失型学生不通过提高提醒频次解决，由独立召回策略承接。
4. 任务完成系统和 Push 基础能力复用现有能力。
5. 首期采用可解释、可测试的规则策略，不以大模型或复杂机器学习为前提。
6. 每位学生每天最多接收 1 次 Push。

| 功能编号 | 功能名称 | 优先级 | 范围说明 |
| --- | --- | --- | --- |
| FR-001 | 提醒资格判断 | P0 | 判断当日是否需要提醒 |

| FR-003 | 用户提醒设置 | P0 | 支持提醒开关和免打扰时间 |
| FR-004 | 已完成任务不提醒 | P0 | 复用既有任务状态，避免无效提醒 |
| FR-005 | 每日提醒频控 | P0 | 每日最多一次 Push |
| FR-006 | Push 关闭后的站内降级 | P0 | 用户进入 App 后展示站内提醒 |
| FR-007 | 一小时后再提醒 | P0 | 用户点击后重新安排提醒，具体渠道约束待确认 |
| FR-008 | 提醒内容 | P0 | 展示剩余任务数和预计用时 |

## 六、风险与影响评估

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 提醒时间计算错误 | 用户在不合适时间收到提醒，打开率下降 | 使用可解释规则，默认窗口兜底，并记录策略版本 |
| 已完成任务仍被提醒 | 造成明显打扰和投诉 | 发送前再次读取任务状态，完成后取消未发送提醒 |
| Push 与站内提醒重复 | 同一用户被重复触达 | 同一用户每天只允许一种策略和一次 Push，渠道状态统一记录 |
| 免打扰设置未生效 | 用户体验和信任受损 | 设置修改后立即影响后续决策，补充边界测试 |
| 流失型用户被过度召回 | 退订、投诉或卸载增加 | 不通过提高提醒频次解决，进入 P2 召回策略 |
| 用户关闭 Push 后无法触达 | 目标用户覆盖不足 | 用户进入 App 后展示站内提醒，并记录不可用渠道原因 |
| 指标口径不一致 | 无法判断功能效果 | 在上线前确认打开率和完成率的分母、归因窗口和统计周期 |
| 未成年人隐私风险 | 产生合规和信任风险 | 不记录姓名、手机号、任务正文、成绩等非必要信息 |

## 七、方案详情

### 7.1 FR-001 提醒资格判断

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 仅触达当天确有学习任务且仍需完成的用户，减少无效提醒 |
| 用户 | 当天有学习任务的学生 |
| 前置条件 | 系统能够读取任务状态、用户分层和提醒设置 |
| 行为 | 每天评估用户是否满足提醒条件 |
| 预期结果 | 只有当日存在未完成必做任务、用户允许提醒、任务有效且未达到频控时，才生成提醒资格 |
| 不提醒条件 | 无任务、全部完成、任务过期、关闭提醒、达到上限 |

### 7.2 FR-002 个性化提醒时间

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 让提醒时间贴近用户的实际学习习惯，提升提醒被打开和执行的机会 |
| 用户 | 符合提醒资格的被动型学生 |
| 前置条件 | 存在有效历史行为，或可以使用默认活跃窗口 |
| 行为 | 优先参考最近任务开始/完成时间，其次参考 App 打开时间；数据不足时使用默认活跃窗口 |
| 预期结果 | 生成用户当天的 `scheduled_at`，且不违反免打扰和任务截止时间 |
| 规则 | 默认活跃窗口为 16:00–18:00 和 19:00–21:00；无有效历史时使用默认窗口，具体默认发送时刻待确认 |

### 7.3 FR-003 用户提醒设置

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 保障用户对提醒频率和接收时段的自主控制 |
| 用户 | 学生 |
| 前置条件 | 用户进入现有 App 的提醒设置入口 |
| 行为 | 修改智能提醒开关或免打扰时间 |
| 预期结果 | 设置持久化，并立即影响后续提醒决策；已排程但未发送的提醒按新设置重新判断 |

### 7.4 FR-004 已完成任务不提醒

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 避免用户已完成任务后仍收到提醒，降低打扰和投诉风险 |
| 用户 | 已完成全部必做任务的学生 |
| 前置条件 | 既有任务系统返回全部必做任务已完成 |
| 行为 | 系统生成决策或执行已有排程前检查任务状态 |
| 预期结果 | 不生成新的未完成提醒；已有未发送提醒取消，并记录 `TASK_COMPLETED` |

### 7.5 FR-005 每日提醒频控

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 控制触达频次，避免重复调度导致重复发送 |
| 用户 | 所有进入提醒策略的学生 |
| 前置条件 | 当天已有提醒发送记录或排程记录 |
| 行为 | 系统再次执行提醒评估或调度 |
| 预期结果 | 同一用户同一天最多发送 1 次 Push；重复执行不产生重复发送 |

### 7.6 FR-006 Push 关闭后的站内降级

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 为关闭系统 Push 的用户保留轻量触达路径，不新增任务页面 |
| 用户 | 未授权系统 Push 且有未完成任务的学生 |
| 前置条件 | Push 权限关闭，用户进入 App |
| 行为 | 不调用 Push；用户进入今日任务相关页面时展示简短站内提醒 |
| 预期结果 | 站内提醒可用时完成曝光和点击记录；站内提醒不可用时跳过本次提醒并记录 `NO_AVAILABLE_CHANNEL` |

### 7.7 FR-007 一小时后再提醒

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 给用户一次主动延后学习的选择，同时避免无控制地重复打扰 |
| 用户 | 已收到提醒并主动点击“稍后提醒”的学生 |
| 前置条件 | 当天仍有未完成必做任务，且当天仍存在可提醒时间 |
| 行为 | 将提醒重新安排到 1 小时后，并重新校验免打扰、截止时间和频控 |
| 预期结果 | 生成新的排程或返回不可再次提醒原因；不改变当天任务完成状态 |
| 待确认 | “每天最多 1 次 Push”与已发送 Push 后再次提醒的渠道关系；初步方案为改用站内提醒，最终以业务确认结果为准 |

### 7.8 FR-008 提醒内容

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 让用户快速了解剩余任务和预计用时，并进入既有任务入口 |
| 用户 | 收到 Push 或站内提醒的学生 |
| 前置条件 | 系统取得最新剩余任务数和预计用时 |
| 行为 | 使用结构化、简短且不制造焦虑的文案 |
| 预期结果 | 内容反映最新任务状态，点击后进入既有任务入口 |

首期文案模板：


## 九、权限说明

本功能不新增后台角色权限，也不搭建独立运营后台。

学生侧复用现有 App 能力：

- 修改智能提醒开关。
- 设置和修改免打扰时间。
- 点击提醒进入既有任务入口。

系统 Push 权限由操作系统和既有 App 权限体系管理；本功能只读取权限状态，并根据状态选择 Push 或站内提醒渠道。

## 十、埋点说明

### 10.1 埋点目标

记录从提醒决策到任务完成的完整链路，评估智能提醒是否带来可归因的打开和任务完成增量。任务完成状态以既有任务系统为准，智能提醒只负责关联和归因。

### 10.2 公共字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `event_id` | String | 是 | 事件唯一 ID |
| `event_name` | String | 是 | 事件名称 |
| `event_time` | DateTime | 是 | 事件发生时间 |
| `user_id` | String | 是 | 用户匿名 ID |
| `task_date` | Date | 是 | 任务所属日期 |
| `timezone` | String | 是 | 用户时区 |
| `decision_id` | String | 是 | 一次提醒决策的唯一 ID |
| `strategy_version` | String | 是 | 提醒策略版本 |
| `channel` | String | 否 | `push` 或 `in_app` |
| `experiment_group` | String | 否 | 实验组或对照组 |

### 10.3 事件字段

| 事件 | 触发时机 | 事件专属字段 |
| --- | --- | --- |
| `reminder_decision_created` | 完成一次提醒决策 | `should_remind`、`reason_code`、`scheduled_at`、`remaining_count`、`estimated_minutes`、`user_segment`、`decision_source` |
| `reminder_scheduled` | 成功生成提醒排程 | `scheduled_at`、`channel`、`dedupe_key`、`reschedule_reason` |
| `reminder_cancelled` | 已排程提醒被取消 | `cancel_reason`、`previous_status`、`cancelled_at` |
| `reminder_snoozed` | 用户点击“稍后提醒” | `snooze_until`、`snooze_duration_minutes`、`original_scheduled_at` |
| `reminder_sent` | 调用既有提醒渠道发送 | `attempt_no`、`delivery_status`、`error_code` |
| `reminder_delivered` | 渠道确认送达 | `delivered_at` |
| `reminder_failed` | 渠道发送失败 | `attempt_no`、`error_code`、`will_retry` |
| `reminder_impression` | 站内提醒实际展示 | `page`、`placement`、`display_type` |
| `reminder_opened` | 用户打开 Push 或站内提醒 | `open_source`、`latency_seconds`、`target_page` |
| `task_started` | 用户从提醒进入任务并开始学习 | `entry_source`、`remaining_count` |
| `task_completed` | 既有任务系统确认全部必做任务完成 | `completed_count`、`required_count`、`completion_duration_seconds`、`completion_source` |
| `reminder_preference_updated` | 用户修改提醒设置 | `changed_fields`、`reminder_enabled`、`quiet_hours_start`、`quiet_hours_end`、`effective_at` |

### 10.4 原因码

| 原因码 | 含义 |
| --- | --- |
| `ELIGIBLE` | 满足提醒条件 |
| `NO_TASK` | 当天没有任务 |
| `TASK_COMPLETED` | 当天任务已完成 |
| `TASK_EXPIRED` | 任务已过期 |
| `REMINDER_DISABLED` | 用户关闭提醒 |
| `DAILY_CAP_REACHED` | 达到每日提醒上限 |
| `QUIET_HOURS` | 当前处于免打扰时间 |
| `INSUFFICIENT_TIME` | 剩余时间不足 |
| `NO_AVAILABLE_CHANNEL` | 没有可用提醒渠道 |
| `USER_INACTIVE` | 用户连续多日未活跃，进入低频策略 |
| `DEFAULT_WINDOW` | 缺少有效历史行为，使用默认活跃窗口 |

不记录学生姓名、手机号、任务正文、成绩和其他非必要敏感信息。

## 十一、测试说明

### 11.1 测试重点

- 未完成任务的被动型用户生成提醒。
- 已完成任务不生成提醒。
- 免打扰时间延后或不发送。
- Push 未授权时不调用 Push，进入 App 后展示站内提醒。
- 站内提醒不可用时记录 `NO_AVAILABLE_CHANNEL`。
- 每日 Push 频控。
- 重复调度不产生重复提醒。
- 发送失败重试不突破频控。
- 缺少历史行为时使用默认活跃窗口。
- 发送前任务完成时取消提醒。
- 用户点击“稍后提醒”后重新排程。

## 十二、旧功能/旧数据处理

### 12.1 是否涉及

是。本功能依赖并优化现有任务系统、任务完成统计、每日 18:00 固定 Push、Push 权限和历史行为数据。

### 12.2 处理方案

| 旧功能或旧数据 | 处理方案 |
| --- | --- |
| 每日 18:00 固定 Push | 保留作为对照策略和灰度期间的兜底策略 |
| 智能提醒实验组 | 使用智能提醒策略，不与固定 Push 同时发送 |
| 对照组 | 继续使用原有 18:00 固定 Push |
| 任务状态和完成率 | 以既有任务系统为唯一事实来源，不重新定义或迁移 |
| Push 权限 | 读取既有权限状态，不维护第二套权限数据 |
| 历史行为数据 | 优先使用最近 7 天有效数据，数据不足时使用默认活跃窗口 |
| 历史发送记录 | 保留原始记录，新事件通过 `strategy_version` 和 `decision_id` 区分 |
| 历史打开率和完成率 | 作为上线前基线，不回写、不重算 |
| 既有任务入口 | 继续复用，不新建任务详情页或做题流程 |

### 12.3 兼容规则

- 同一用户同一天只能命中固定 Push 或智能提醒中的一种策略。
- 同一用户同一天最多发送 1 次 Push。
- 任务完成后取消尚未发送的提醒。
- 灰度异常时停止智能提醒排程，不删除历史记录，恢复原固定 Push。
- 不修改历史任务完成数据、历史 Push 记录和历史用户行为数据。
