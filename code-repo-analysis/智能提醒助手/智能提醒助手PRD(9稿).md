## 一、背景

### 1.1 业务背景

我们是一款 AI 教育产品，学生需要在 App 中完成每日学习任务，例如看课、做题等。现有 App 已具备每日任务、任务完成状态统计和任务入口；系统也已有每天 18:00 统一发送固定 Push 的能力。

### 1.2 当前问题

部分学生不会主动打开 App 完成当天任务，导致学习中断和学习效果下降。当前固定 Push 没有结合用户的任务状态、历史学习习惯、提醒偏好和当前时间进行判断，存在以下问题：

- 已完成任务的用户可能仍然收到无效提醒。
- 所有用户在同一时间收到相同提醒，无法适配不同学习习惯。
- 用户关闭 Push 权限后，缺少 App 内提示，用户即使打开 App 也得不到引导。
- 用户处于免打扰时段或已经达到提醒上限时，缺少统一控制。
- 提醒是否有效无法通过统一事件链路进行归因。

### 1.3 现有数据

- DAU 约 50 万，付费学生（有每日任务）约 30 万。
- 约 40%（12 万）学生当天未完成任务即离开 App 或根本未打开。
- 当前任务完成率按学生口径约为 60%。
- 当前固定 Push 每天 18:00 发送。
- Push 到达率约 60%，到达用户中的打开率约 8%，打开后任务完成率约 45%。
- 学生日均在线时长约 25 分钟，主要活跃时段为 16:00–18:00（35%）和 19:00–21:00（45%）。
- 约 30% 的学生连续 3 天以上未打开 App。

> 口径说明：原始诉求给出的 30% 采用“连续 3 天以上未打开 App”口径。本 PRD 的用户分层沿用同一口径判定流失型（见 3.3），因此人群占比可与原始诉求数据直接对照；若后续调整观察窗口，需要同步更新本节与 3.3 节。

## 二、目标

### 2.1 整体业务目标

- 将每日任务完成率从当前 60% 提升至 75%。
- 将 Push 打开率从约 8% 提升至 15% 以上。
- 在提升提醒效果的同时控制重复提醒和用户打扰。

### 2.2 智能提醒的产品贡献目标

75% 和 15%+ 是业务整体目标。本功能聚焦符合提醒条件的目标用户，通过对照实验评估智能提醒对打开率和任务完成率带来的可归因增量；整体业务目标不直接作为单项功能的验收门槛。

### 2.3 指标定义

所有比例指标按用户数去重统计，不按发送量或设备数统计；归属日期使用用户本地时区的 `task_date`。

| 指标层级 | 指标 | 说明 |
| --- | --- | --- |
| 结果指标 | 每日任务完成率 | 当天完成全部必做任务的学生数 / 当天至少有一项必做任务的付费学生数；与当前 60% 基线同口径，无任务日不计入分母 |
| 结果指标 | Push 打开率 | 当天打开 Push 的去重用户数 / 当天 Push 成功送达的去重用户数；仅 `reminder_delivered` 计入分母，已发送但送达未确认不计入 |
| 过程指标 | 到达率 | 成功送达 Push 的数量 / Push 发送数量 |
| 过程指标 | 提醒后任务开始率 | 归因窗口内由提醒入口开始任务的去重用户数 / 当日有效触达去重用户数 |
| 过程指标 | 提醒后任务完成率 | 归因窗口内完成全部必做任务的去重用户数 / 当日有效触达去重用户数 |
| 护栏指标 | 重复提醒率 | 同一用户同一天收到重复提醒的比例 |
| 护栏指标 | 通知关闭率 | 用户关闭系统 Push 或智能提醒的比例 |
| 护栏指标 | 投诉、卸载和退订 | 用于观察提醒是否造成负面影响 |

口径定义：

- 有效触达用户数：本期为 Push 成功送达的去重用户数。同一用户同一天多次触达（含延后提醒）只计一次，归因窗口起点取当天首次有效触达时刻。站内提醒的成功展示口径随 FR-006 移入 P1，不计入本期指标。
- 归因窗口主口径：从当天首次有效触达时刻起，至用户本地 24:00，窗口不跨天。辅助口径为触达后 24 小时，仅用于观察跨天补完，不用于验收结论。
- 归因事件：打开使用 `reminder_opened` 并按 `open_source` 区分渠道；开始使用 `task_started` 并按 `entry_source` 确认来自提醒入口；完成使用 `task_completed`，且已完成数量等于必做数量。
- 渠道披露：本期只统计 Push 渠道；站内提醒不参与本期分母与分子，相关口径随 FR-006 移入 P1。
- 统计周期：日报按 `task_date`、`channel` 和 `strategy_version` 维度产出；阶段结论以连续不少于 14 天聚合，覆盖周中与周末的行为差异。
- 已完成任务后取消的提醒不计入分母。实验周期、分流比例和上线阈值属非 P0 事项，见 13.1。

#### 2.3.1 新需求验收指标

| 指标 | 验收要求 | 对应标准 |
| --- | --- | --- |
| 提醒资格规则正确性 | 资格、免打扰、过期和已完成场景均符合产品规则 | AC-001、AC-002、AC-003、AC-009 |
| 已完成任务提醒泄漏 | 验收场景中不得产生新的未完成任务提醒 | AC-002、AC-010 |
| 每日 Push 重复发送 | 同一用户同一天不得发送第二次 Push；重复调度不得产生重复记录 | AC-005、AC-006、AC-007 |
| 设置变更生效 | 未发送排程使用最新提醒开关和免打扰设置 | AC-012 |
| 事件链路完整性 | 决策、渠道、打开和任务完成事件可通过 `decision_id`、`strategy_version` 关联 | AC-011 |
| 智能提醒可归因增量 | 与固定 Push 或不提醒策略进行对照；指标口径已确认（见 2.3），提升阈值、分流比例和实验周期属非 P0 事项 | 非 P0，见 13.1 |

### 2.4 历史功能体验防裂化指标

本功能复用既有任务、任务入口和 Push 能力。发布后需持续观察以下历史能力，避免智能提醒接入造成体验回退；量化阈值和统计周期属上线后监控（非 P0），在发布前确认。

| 历史能力 | 基线信息 | 防裂化要求 |
| --- | --- | --- |
| 既有 Push 到达率 | 当前约 60% | 智能提醒实验组的 Push 到达率不应低于既有固定 Push 对照基线；阈值和统计周期待确认 |
| 提醒打开后的任务完成链路 | 当前打开后任务完成率约 45% | 点击提醒后应继续进入既有任务入口，不能因提醒接入导致入口失败或任务完成回传异常；量化阈值待确认 |
| 任务完成状态与完成率统计 | 既有任务系统提供 | 不修改、不迁移历史任务完成数据；发布后统计口径保持一致 |
| 每日 18:00 固定 Push | 既有线上能力 | 对照组或灰度回退时可继续发送；不与智能提醒重复触达同一用户 |

## 三、资源概念说明

### 3.1 本次新增概念

| 概念 | 定义 |
| --- | --- |
| 智能提醒资格 | 系统根据任务状态、用户分层、提醒设置、频控、免打扰和任务有效期判断用户是否具备提醒条件 |
| 个性化提醒时间 | 基于用户最近任务行为、App 活跃时间、默认活跃窗口和任务截止时间计算出的当日提醒时间 |
| 提醒渠道 | 发送提醒的方式。本期 P0 为既有 Push；用户进入 App 后展示的站内提醒属 P1 范围，见 FR-006 |
| 提醒决策 | 一次判断的结果，包括是否提醒、计划时间、渠道、原因和策略版本 |
| 延后提醒 | 用户点击“稍后提醒”后，将当前提醒重新安排到 1 小时后的能力 |
| 提醒策略版本 | 标识当前使用的提醒规则，用于效果分析和问题追踪 |

### 3.2 既有能力与外部依赖

以下能力由现有 App 或业务服务提供，作为本需求的接入依赖，不纳入本期新建范围：

- 每日学习任务及必做任务定义。
- 任务完成状态和每日任务完成率统计。
- 任务详情页、做题流程和任务完成回传。
- 既有 Push 通道及发送基础设施。
- 提醒点击后的任务入口或 Deep Link。

本功能只消费任务状态和任务入口，并在现有 Push 能力之上实现提醒资格判断、时机选择、频控、免打扰和延后提醒。

站内提醒展示能力虽属既有能力，但本期不作为 P0 依赖接入：P0 不调用、不设计、不验收站内渠道。Push 未成功触达时的站内承接与回流首日的站内承接列入 P1，随 FR-006 一并规划。

### 3.3 用户分层定义与判定规则

用户分层决定提醒策略。分层结果不落库为固定标签，在每日评估或 App 打开事件触发的评估中按行为数据实时计算，用户行为变化当天即可生效。

#### 3.3.1 用于分层判定的用户行为信号

下表是分层判定的全部输入数据：每个信号怎么取值、按什么口径计算，以及用在 3.3.2 判定顺序的哪一步。分层只依赖用户行为数据，不依赖任务内容。

| 信号 | 取值 | 含义与口径 | 在分层判定中的作用 |
| --- | --- | --- | --- |
| `inactive_days` | ≥0 | 距评估时点的连续未打开天数 | 第 2 步判定流失型：≥ 3 时不进入主动 Push 排程 |
| `days_since_last_open` | ≥0 或空 | 本次打开 App 前，上一次打开距今天的本地日期间隔；仅在 App 打开事件中计算，无历史打开记录时为空 | 第 3 步判定回流型：当日已打开且 ≥ 3 时命中回流首日 |
| `open_days_prev_7d` | 0–7 | 再往前 7 天（T-3 至 T-9）打开 App 的天数 | 只作历史打开窗口的审计信号，不参与分层判定 |
| `complete_days_7d` | 0–7 | 最近 7 天完成全部必做任务的天数 | 第 4 步判定自驱型：≥ 5 天 |
| `reminder_attributed_complete_days_7d` | 0–7 | 最近 7 天中“收到提醒后完成”的天数 | 第 4 步判定自驱型：≤ 1 天 |
| `history_days_available` | 0–7 | 可读取的历史行为天数 | 第 1 步判定数据不足：< 3 天时按被动型处理并记录 `INSUFFICIENT_HISTORY` |

窗口取值说明：`complete_days_7d` 和 `reminder_attributed_complete_days_7d` 使用 7 天窗口，因为 3 天样本过小，容易让用户在自驱型与被动型之间反复切换；`open_days_prev_7d` 同为 7 天窗口，仅用于审计。窗口长度已确认为本期默认值，且为可配置参数。

信号有效性说明：`open_days_prev_7d` 是历史打开窗口的审计信号，不再参与回流判定；回流判定改用 `days_since_last_open`，见 3.3.2。

#### 3.3.2 分层判定顺序与对应提醒策略

按以下顺序判定，命中即结束；五种结果互斥且穷尽。

| 顺序 | 人群 | 判定规则 | 本期策略 |
| --- | --- | --- | --- |
| 1 | 数据不足 | `history_days_available` < 3 | 按被动型处理并使用默认活跃窗口，记录 `INSUFFICIENT_HISTORY` |
| 2 | 流失型 | `inactive_days` ≥ 3 | 不进入主动 Push 排程，记录 `USER_INACTIVE`，由 P2 召回策略承接 |
| 3 | 回流型 | 当日已打开 App（`inactive_days` = 0），且 `days_since_last_open` ≥ 3 | 回流首日不发送提醒、不生成 Push 排程；次日起恢复常规 Push 提醒；“时间优先取最近 1–2 天活跃时段”随站内承接移入 P1 |
| 4 | 自驱型 | `complete_days_7d` ≥ 5 且 `reminder_attributed_complete_days_7d` ≤ 1 | 已完成不提醒；未完成时最多一次低打扰提醒 |
| 5 | 被动型 | 其余（有打开、完成产出低） | 本期 P0 重点服务：按活跃习惯与任务截止时间提醒 |

规则要点：

- 判定顺序不可交换。先判数据不足，再判流失，避免新用户被误判为流失型而失去提醒机会。
- 回流型排在流失型之后：用户重新打开 App 后 `inactive_days` 归零，当天即从流失型转为回流型，不需要等待观察期或人工干预。
- 回流判定使用显式首日条件：当日已打开 App 且 `days_since_last_open` ≥ 3 时，当日即为回流首日，阈值与流失窗口同为 3 天且可配置。不再用 `open_days_prev_7d` = 0 推算，因为该窗口在次日仍然成立，会让用户持续命中回流型而无法恢复常规 Push。
- 回流首日由 App 打开事件触发评估，当日不发送提醒、不生成 Push 排程，记录 `RETURNING_FIRST_DAY`；次日由每日评估恢复常规 Push 资格。`days_since_last_open` 在 App 打开事件中取本次打开前的上一次打开间隔，不需要跨日保存分层状态。
- 回流型的提醒时间优先使用最近 1–2 天的活跃时段，而不是默认活跃窗口。刚回到 App 的用户，近期行为比历史均值更能代表当前作息。该规则在 P0 没有生效场景（回流首日不发送提醒），随站内承接一并移入 P1，保留为 P1 口径。
- 回流首日做降温处理：用户当天已经主动打开 App，再叠加 Push 会造成同一天两次打扰，因此首日不发送提醒，次日起恢复常规 Push。原“首日只保留站内提醒”的方案随站内提醒一并移入 P1。
- 阈值（流失 3 天、自驱型完成 5 天、提醒归因完成 1 天）和窗口（完成 7 天）已确认为本期默认值，且均为可配置项；回流时间取最近 1–2 天活跃时段随站内承接移入 P1。

#### 3.3.3 分层判定示例：回流用户

| 日期 | 行为 | 分层结果 | 提醒策略 |
| --- | --- | --- | --- |
| T-10 至 T-4 | 每天打开并完成任务 | 自驱型 | 已完成不提醒 |
| T-3 至 T-1 | 未打开 App | 流失型 | 不进入主动 Push 排程 |
| T（今天） | 打开 App 并进入任务页 | 回流型（`inactive_days` = 0 且 `days_since_last_open` ≥ 3） | 当天不发送提醒，不生成 Push 排程，记录 `RETURNING_FIRST_DAY` |
| T+1 | 进入次日每日评估 | 按常规规则重新判定 | 恢复常规 Push 资格；仍需通过任务、设置、免打扰和频控校验 |

## 四、业务流程梳理

### 4.1 参与角色和职责

| 角色或系统 | 职责 |
| --- | --- |
| 学生 | 完成每日任务，查看和调整提醒设置，接收或打开提醒 |
| 既有任务系统 | 提供当日任务、必做任务、完成状态、截止时间和任务入口 |
| 智能提醒服务 | 评估提醒资格、计算提醒时间、选择渠道、执行频控并记录决策 |
| 既有 Push 服务 | 按智能提醒服务的结果发送 Push，并返回发送和到达状态 |
| App 站内消息能力 | P1 预留：用户进入 App 后展示轻量站内提醒；本期不接入 |
| 数据与事件系统 | 记录决策、发送、到达、打开、开始和完成事件 |

### 4.2 服务流程

```text
每日评估或状态变化触发
→ 读取既有任务状态、用户历史行为和提醒设置
→ 判断提醒资格
→ 计算个性化提醒时间
→ 校验免打扰、任务截止时间和每日频控
→ 生成并保存提醒决策
→ 到达计划时间前再次检查任务和用户状态
→ Push 可用时调用既有 Push；Push 未授权或发送失败时跳过本次提醒并记录未触达原因
→ 记录决策、发送、到达、打开和任务完成事件
→ 任务完成后取消当天尚未发送的提醒
```

### 4.3 用户流程

```text
打开 App
→ 查看今日任务和完成进度
→ 查看或调整提醒设置
→ 在合适时间收到 Push
→ 点击提醒进入既有任务入口
→ 开始学习
→ 完成全部必做任务
```

用户不需要每次打开 App 都调整提醒设置；设置入口由现有 App 页面承载。

## 五、方案简述

### 5.1 使用流程与业务流程变化

#### 用户使用流程

```text
打开 App
→ 查看今日任务和完成进度
→ 查看或调整提醒设置
→ 在合适时间收到 Push
→ 点击提醒进入既有任务入口
→ 开始学习并完成今日必做任务
```

#### 业务流程变化

| 环节 | 现状 | 本期调整 |
| --- | --- | --- |
| 提醒触发 | 每天 18:00 面向所有用户发送固定 Push | 每日评估或状态变化先判断任务状态、用户分层、提醒设置和频控；回流首日由 App 打开事件触发评估、当天不发送提醒且不生成 Push 排程 |
| 提醒时间 | 所有用户同一时间接收 | 结合用户近期学习行为和任务截止时间安排提醒 |
| 提醒渠道 | 主要使用 Push | 本期只使用 Push 单渠道；Push 未成功触达时跳过本次提醒并记录未触达原因，站内承接列入 P1 |
| 任务完成后的处理 | 固定 Push 可能继续发送 | 任务完成后取消当日尚未发送的提醒 |
| 运营与效果评估 | 无统一的提醒决策链路 | 记录决策、发送、到达、打开和任务完成事件 |

### 5.2 方案原则

1. 本期 P0 重点服务当天有未完成任务的被动型学生，以及重新打开 App 的回流型学生；回流首日不发送提醒，避免与用户主动打开形成双重打扰。
2. 自驱型学生重点控制无效打扰。
3. 流失型学生（连续 3 天以上未打开 App）不通过提高提醒频次解决，由独立召回策略承接；用户重新打开 App 后按回流型恢复常规提醒。
4. 任务完成系统和 Push 基础能力复用现有能力。
5. 首期采用可解释、可测试的规则策略，不以大模型或复杂机器学习为前提。
6. 每位学生每天最多接收 1 次系统主动 Push；用户主动触发的“稍后提醒”不计入该上限，据此每天最多 2 次 Push。
7. 站内提醒及其承接逻辑（Push 未成功触达、回流首日）不纳入本期 P0，统一列入 P1，见 7.6。

### 5.3 本期 MVP 核心需求场景

本期 MVP 聚焦“当天有未完成任务的被动型学生与回流型学生，在合适时间收到一次受控提醒，并能完成后续学习闭环”。核心场景如下；详细需求定义见第七章，验收映射见第十一章。

| 场景编号 | 用户场景 | 触发条件 | 系统行为 | 预期结果 | 对应需求 |
| --- | --- | --- | --- | --- | --- |
| MVP-001 | 被动型学生有未完成任务 | 当日存在未完成必做任务，用户允许提醒且未达到上限 | 结合历史行为、默认活跃窗口和截止时间生成提醒排程 | 在可用时间发送一次相关提醒 | FR-001、FR-002、FR-008 |
| MVP-002 | 用户已完成或没有有效任务 | 任务全部完成、无任务或任务已过期 | 不创建可发送提醒；已有未发送排程取消 | 不产生无效提醒 | FR-001、FR-004 |
| MVP-003 | 用户处于免打扰时段 | 当前时间落在用户设置的免打扰区间 | 延后到下一个可用窗口，并重新检查截止时间 | 免打扰期间不发送 | FR-002、FR-003 |
| MVP-004 | 用户关闭系统 Push | Push 权限不可用 | 不调用 Push，跳过本次提醒并记录未触达原因；站内承接列入 P1 | 不重复调用 Push，缺口记入监控 | FR-001、FR-005 |
| MVP-005 | 用户主动选择稍后提醒 | 当天仍有未完成任务，用户点击“稍后提醒” | 计划一小时后通过 Push 再次提醒，重新检查任务、免打扰、截止时间和频控 | 不占用当日系统主动 Push 上限地提供一次延后机会，延后提醒不再提供“稍后提醒”入口 | FR-007 |
| MVP-006 | 调度重复执行或并发执行 | 同一用户同一天重复评估或发送 | 使用决策幂等和每日 Push 上限拦截重复动作 | 最多发送一次 Push，不产生重复记录 | FR-005 |
| MVP-007 | 用户在提醒前完成任务或修改设置 | 排程尚未发送时任务完成、关闭提醒或修改免打扰 | 发送前二次校验并取消或调整排程 | 使用最新状态，避免过期提醒 | FR-003、FR-004、FR-005 |
| MVP-008 | 流失用户重新打开 App | 连续 3 天以上未打开的用户当天打开 App | App 打开事件触发回流评估；当天不发送提醒、不生成 Push 排程；次日由每日评估恢复常规 Push 资格 | 回流当天不被流失策略拦截，且不产生双重打扰 | FR-001、FR-002 |

## 六、风险与影响评估

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 提醒时间计算错误 | 用户在不合适时间收到提醒，打开率下降 | 使用可解释规则，默认窗口兜底，并记录策略版本 |
| 已完成任务仍被提醒 | 造成明显打扰和投诉 | 发送前再次读取任务状态，完成后取消未发送提醒 |
| Push 与站内提醒重复 | 同一用户被重复触达 | 本期只有 Push 单渠道，同一用户每天只允许一种策略并最多 1 次系统主动 Push；跨渠道去重随 P1 站内承接定义 |
| 免打扰设置未生效 | 用户体验和信任受损 | 设置修改后立即影响后续决策，补充边界测试 |
| 流失型用户被过度召回 | 退订、投诉或卸载增加 | 不通过提高提醒频次解决，进入 P2 召回策略 |
| 用户关闭 Push 后无法触达 | 本期无替代渠道，Push 未授权或发送失败的用户当天不会被触达 | 本期接受该缺口并记入监控；站内提醒承接列入 P1，明确其不承担召回职责，只承接 App 内转化 |
| 指标口径不一致 | 无法判断功能效果 | 在上线前确认打开率和完成率的分母、归因窗口和统计周期 |
| 未成年人隐私风险 | 产生合规和信任风险 | 不记录姓名、手机号、任务正文、成绩等非必要信息 |

## 七、方案详情

### 7.1 FR-001 提醒资格判断

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 仅触达当天确有学习任务且仍需完成的用户，减少无效提醒 |
| 用户 | 当天有学习任务的学生 |
| 前置条件 | 系统能够读取任务状态、用户分层和提醒设置 |
| 行为 | 每天评估用户是否满足提醒条件 |
| 预期结果 | 只有当日存在未完成必做任务、用户允许提醒、任务有效且未达到频控时，才生成提醒资格 |
| 不提醒条件 | 无任务、全部完成、任务过期、关闭提醒、达到上限 |

### 7.2 FR-002 个性化提醒时间

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 让提醒时间贴近用户的实际学习习惯，提升提醒被打开和执行的机会 |
| 用户 | 符合提醒资格的被动型学生，以及回流型学生 |
| 前置条件 | 存在有效历史行为，或可以使用默认活跃窗口 |
| 行为 | 优先参考最近任务开始/完成时间，其次参考 App 打开时间；数据不足时使用默认活跃窗口；回流首日由 App 打开事件触发评估，当天不发送提醒（最近 1–2 天活跃时段随站内承接移入 P1） |
| 预期结果 | 生成用户当天的 `scheduled_at`，且不违反免打扰和任务截止时间；回流首日当天不发送提醒、不生成 Push 排程 |
| 规则 | 默认活跃窗口为 16:00–18:00 和 19:00–21:00；无有效历史时使用默认窗口，默认发送时刻主值为 19:30、兜底值为 17:00 |

默认发送时刻规则：无有效历史行为的用户优先取用户本地 19:30，因为 19:00–21:00 是当前占比 45% 的最高活跃时段。当 19:30 落在免打扰区间或晚于“任务截止前 1 小时”时，回退到 16:00–18:00 窗口内的 17:00。两个时刻都不可用时记录 `QUIET_HOURS` 或 `INSUFFICIENT_TIME`，不发送提醒。默认发送时刻为可配置参数。

### 7.3 FR-003 用户提醒设置

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 保障用户对提醒频率和接收时段的自主控制 |
| 用户 | 学生 |
| 前置条件 | 用户进入现有 App 的提醒设置入口 |
| 行为 | 修改智能提醒开关或免打扰时间 |
| 预期结果 | 设置持久化，并立即影响后续提醒决策；已排程但未发送的提醒按新设置重新判断 |
| 默认值 | 智能提醒开关默认开启；免打扰时间默认 21:30–07:00；每日系统主动 Push 上限默认 1 次；时区取用户档案时区；站内提醒（P1）跟随智能提醒总开关 |
| 读取规则 | 设置记录不存在或字段缺失时使用默认值，并上报数据质量指标；设置读取失败时不发送提醒，不采用旧设置或缓存值 |

### 7.4 FR-004 已完成任务不提醒

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 避免用户已完成任务后仍收到提醒，降低打扰和投诉风险 |
| 用户 | 已完成全部必做任务的学生 |
| 前置条件 | 既有任务系统返回全部必做任务已完成 |
| 行为 | 系统生成决策或执行已有排程前检查任务状态 |
| 预期结果 | 不生成新的未完成提醒；已有未发送提醒取消，并记录 `TASK_COMPLETED` |

### 7.5 FR-005 每日提醒频控

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 控制触达频次，避免重复调度导致重复发送 |
| 用户 | 所有进入提醒策略的学生 |
| 前置条件 | 当天已有提醒发送记录或排程记录 |
| 行为 | 系统再次执行提醒评估或调度 |
| 预期结果 | 同一用户同一天最多发送 1 次系统主动 Push；重复执行不产生重复发送；用户主动触发的“稍后提醒”不计入该上限 |

### 7.6 FR-006 App 内未完成任务提示（站内提醒）

| 项目 | 内容 |
| --- | --- |
| 优先级 | P1（2026-09-20 从 P0 移出） |
| 本期处理 | 本期不实现。P0 不调用站内渠道、不设计站内展示、不进入本期验收；Push 未授权或发送失败时跳过本次提醒并记录未触达原因，回流首日当天不发送提醒（见 3.3.2）。以下规则保留为 P1 承接口径，实施前按承接方案细化 |
| 设计目的 | 为当天尚未通过 Push 成功触达的未完成用户保留 App 内轻量提示，把“已打开 App”转化为“开始任务”；不新增任务页面 |
| 用户 | 当天有未完成必做任务、且尚未被 Push 成功触达的学生，包括 Push 未授权、发送失败、未生成 Push 排程和回流首日不出 Push 的情形 |
| 前置条件（P1） | App 打开事件已触发；用户进入今日任务相关页面；当日存在未完成必做任务；当天尚未展示过站内提醒 |
| 行为（P1） | 不额外调用 Push；用户进入今日任务相关页面时展示一次简短站内提醒 |
| 预期结果（P1） | 站内提醒可用时记录曝光与点击；不可用时跳过本次提醒并记录 `NO_AVAILABLE_CHANNEL` |
| 不再展示（P1） | 任务已完成、用户已关闭提醒、当天已展示过站内提醒，或用户已通过 Push 点击进入任务 |
| 触发范围（P1） | 覆盖 Push 未授权、Push 发送失败、未生成 Push 排程和回流首日不出 Push 四类未成功触达场景；Push 已送达但未被点击时不展示，视为已完成触达 |
| 每日上限（P1） | 同一用户同一天最多展示 1 次站内提醒，包含延后提醒产生的再次展示，与每日 Push 上限对齐 |
| 不可用定义（P1） | 站内开关关闭、当日无可用承载页面、站内服务不可用或展示超时，统一归因为 `NO_AVAILABLE_CHANNEL`；用户当天未进入 App 属于未触达，排程保留到当日 24:00 失效，不记为不可用 |

### 7.7 FR-007 一小时后再提醒

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 设计目的 | 给用户一次主动延后学习的选择，同时避免无控制地重复打扰 |
| 用户 | 已收到提醒并主动点击“稍后提醒”的学生 |
| 前置条件 | 当天仍有未完成必做任务，且当天仍存在可提醒时间 |
| 行为 | 将提醒重新安排到 1 小时后，并重新校验免打扰、截止时间和频控 |
| 预期结果 | 生成新的排程或返回不可再次提醒原因；不改变当天任务完成状态 |
| 渠道规则 | 延后提醒使用 Push 渠道；该次提醒由用户主动触发，不占用当日 1 次系统主动 Push 上限，据此每天最多 2 次 Push；延后提醒产生的这次 Push 不再提供“稍后提醒”入口；Push 不可用时返回 `NO_AVAILABLE_CHANNEL` |

## 九、权限说明

本功能不新增后台角色权限，也不搭建独立运营后台。

学生侧复用现有 App 能力：

- 修改智能提醒开关。
- 设置和修改免打扰时间。
- 点击提醒进入既有任务入口。

系统 Push 权限由操作系统和既有 App 权限体系管理；本功能只读取权限状态。本期只使用 Push 渠道，Push 不可用时跳过本次提醒并记录未触达原因；站内提醒渠道列入 P1。

## 十、埋点说明

### 10.1 埋点目标

记录从提醒决策到任务完成的完整链路，评估智能提醒是否带来可归因的打开和任务完成增量。任务完成状态以既有任务系统为准，智能提醒只负责关联和归因。

### 10.2 公共字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `event_id` | String | 是 | 事件唯一 ID |
| `event_name` | String | 是 | 事件名称 |
| `event_time` | DateTime | 是 | 事件发生时间 |
| `user_id` | String | 是 | 用户匿名 ID |
| `task_date` | Date | 是 | 任务所属日期 |
| `timezone` | String | 是 | 用户时区 |

不记录学生姓名、手机号、任务正文、成绩和其他非必要敏感信息。

## 十一、测试说明

### 11.1 测试重点

- 未完成任务的被动型用户生成提醒。
- 已完成任务不生成提醒。
- 免打扰时间延后或不发送。
- Push 未授权或发送失败时不调用 Push，跳过本次提醒并记录未触达原因。
- 每日 Push 频控。
- 重复调度不产生重复提醒。
- 发送失败重试不突破频控。
- 缺少历史行为时使用默认活跃窗口。
- 发送前任务完成时取消提醒。
- 用户点击“稍后提醒”后重新排程。
- 用户关闭提醒后不生成提醒并取消未发送排程。
- 流失型用户不进入主动 Push 排程；重新打开 App 当天按回流型恢复提醒。
- 自驱型用户按“打开 + 完成”信号组合控制打扰。
- 回流首日不发送提醒并记录 `RETURNING_FIRST_DAY`；次日恢复常规 Push 提醒。
- 无历史行为用户使用默认发送时刻 19:30，不可用时回退 17:00。
- 延后提醒使用 Push 渠道，不占用当日系统主动 Push 上限，且延后提醒不再提供“稍后提醒”入口。
- 提醒设置缺失或读取失败时按默认值处理且不误发。

站内提醒相关测试点（触发范围、每日 1 次上限、与 Push 已送达的互斥关系、不可用原因码）属 P1，随 FR-006 一并规划，本期不纳入验收。

## 十二、旧功能/旧数据处理

### 12.1 是否涉及

是。本功能依赖并优化现有任务系统、任务完成统计、每日 18:00 固定 Push、Push 权限和历史行为数据。

### 12.2 处理方案

| 旧功能或旧数据 | 处理方案 |
| --- | --- |
| 每日 18:00 固定 Push | 保留作为对照策略和灰度期间的兜底策略 |
| 智能提醒实验组 | 使用智能提醒策略，不与固定 Push 同时发送 |
| 对照组 | 继续使用原有 18:00 固定 Push |
| 任务状态和完成率 | 以既有任务系统为唯一事实来源，不重新定义或迁移 |
| Push 权限 | 读取既有权限状态，不维护第二套权限数据 |
| 历史行为数据 | 优先使用最近 7 天有效数据，数据不足时使用默认活跃窗口 |
| 历史发送记录 | 保留原始记录，新事件通过 `strategy_version` 和 `decision_id` 区分 |
| 历史打开率和完成率 | 作为上线前基线，不回写、不重算 |
| 既有任务入口 | 继续复用，不新建任务详情页或做题流程 |

### 12.3 兼容规则

- 同一用户同一天只能命中固定 Push 或智能提醒中的一种策略。
- 同一用户同一天最多发送 1 次系统主动 Push；用户主动触发的“稍后提醒”不计入该上限。
- 任务完成后取消尚未发送的提醒。
- 灰度异常时停止智能提醒排程，不删除历史记录，恢复原固定 Push。
- 不修改历史任务完成数据、历史 Push 记录和历史用户行为数据。
