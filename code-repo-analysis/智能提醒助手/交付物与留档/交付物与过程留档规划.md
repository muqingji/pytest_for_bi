# 智能提醒助手：交付物与过程留档规划

## 1. 结论先行

题目页面明确要求提交两类核心作品：

1. Markdown 格式的 PRD。
2. 可以实际运行和测试的项目代码。

评审标准关注四个方面：

- 产品能力：是否抓住真正的问题，是否理解用户和业务，是否做出合理的方案取舍。
- 工程开发能力：代码结构是否清晰，质量是否稳定，实现是否扎实，是否能支撑产品方案。
- AI 应用能力：是否合理利用 AI 提升分析、设计、开发或测试效率，是否具备良好的 AI 协同能力。
- 表达完整性：PRD 是否清晰、结构完整，交付内容是否容易理解。

所以，留档目标不是记录所有过程，而是让评审者能够回答：

~~~text
你发现了什么问题？
为什么选择这个方案？
哪些能力进入 MVP，哪些明确不做？
代码是否实现并验证了关键判断？
你如何使用 AI，如何验证 AI 的结果？
~~~

## 2. 十个阶段的留档建议

| 阶段 | 是否建议留档 | 推荐载体 | 留档重点 | 评审价值 |
| --- | --- | --- | --- | --- |
| 需求分析 | 是 | PRD 前置章节或 docs/01-requirements-analysis.md | 事实、未知信息、假设、指标口径、用户问题 | 产品能力、表达完整性 |
| 产品方案 | 是 | PRD 或 docs/02-product-solution.md | 目标用户、流程、策略、范围、取舍、非目标 | 产品能力、表达完整性 |
| PRD | 必须 | 根目录 PRD.md | 完整需求、规则、异常、埋点、指标、验收标准、风险 | 题目硬性要求、表达完整性 |
| 验收标准 | 是 | PRD 验收章节或 docs/acceptance-criteria.md | Given/When/Then、正常/边界/失败场景、需求与测试映射 | 产品落地能力、工程质量 |
| 技术方案 | 强烈建议 | docs/technical-design.md 或 README 章节 | 架构、模块、模型、接口、决策引擎、幂等、重试、简化项 | 工程开发能力、表达完整性 |
| 开发任务拆分 | 建议精简留档 | docs/implementation-plan.md 或 decisions.md | MVP 优先级、实现顺序、完成范围、V2 列表 | Owner 意识、方案取舍 |
| 编码 | 必须 | 项目源代码、配置、演示数据 | 关键产品规则有对应实现，代码可运行、可测试 | 工程开发能力 |
| 测试 | 必须保留证据 | 自动化测试 + docs/test-report.md | 测试命令、结果、核心场景、失败路径、限制 | 工程开发能力、交付可信度 |
| 质量准出 | 建议留档 | docs/release-checklist.md | 全新环境验证、测试通过、依赖和密钥检查、已知问题 | 工程交付能力、Owner 意识 |
| 打包提交 | 必须执行，过程可简化 | README、提交包清单、最终 ZIP | 目录结构、启动命令、测试命令、排除缓存和敏感信息 | 表达完整性、最终可运行性 |

## 3. 推荐最终交付结构

建议最终 ZIP 使用下面的结构：

~~~text
smart-reminder/
├── README.md
├── PRD.md
├── AI_USAGE.md
├── go.mod / package.json
├── cmd/ 或 app/
├── internal/ 或 src/
├── tests/
├── demo-data/
├── docs/
│   ├── technical-design.md
│   ├── acceptance-criteria.md
│   ├── test-report.md
│   ├── release-checklist.md
│   └── decisions.md
└── .gitignore
~~~

如果希望控制文档数量，可以合并为：

~~~text
README.md
PRD.md
AI_USAGE.md
docs/technical-design.md
docs/test-report.md
src/ 或 internal/
tests/
demo-data/
go.mod 或 package.json
~~~

其中需求分析、产品方案、验收标准和关键决策统一放进 PRD；质量准出清单合并到测试报告最后一节。

## 4. 各阶段具体应记录什么

### 4.1 需求分析：记录问题定义和口径边界

建议留档：

- 题目明确给出的事实数据。
- 任务完成率 60% 的推导过程：30 万有任务学生中，12 万未完成，因此按学生口径推导为 18 万完成、完成率 60%。
- Push 到达率、打开率和打开后完成率的定义区别。
- 未知口径：发送对象、统计分母、归因窗口、任务完成定义、时区等。
- 为继续设计而采用的假设。
- 核心问题定义，以及哪些学生最可能从提醒中受益。
- 不把整体完成率 75% 全部归因于提醒功能的判断。

不需要留档：

- 所有原始搜索过程。
- 每一次没有形成决策的草稿。
- 与题目无关的竞品资料堆积。

### 4.2 产品方案：记录为什么这样做

建议留档：

- 首期目标人群及选择依据。
- MVP、非目标和 V2 的边界。
- 用户流程、系统流程和关键交互。
- 提醒规则及优先级。
- 频控、免打扰、权限关闭、任务完成、连续不活跃等异常策略。
- 关键取舍及被否决方案，例如：
  - 首期采用规则引擎，而不是为了体现 AI 强行接入大模型。
  - 每日最多一次 Push，而不是高频轰炸。
  - 流失型用户进入低频召回标记，而不是提高提醒次数。

评审者需要看到的是判断结论和依据，不是功能数量。

### 4.3 PRD：记录交付契约

PRD 是硬性提交物，至少应包含：

1. 背景和问题定义。
2. 已知事实、未知信息和假设。
3. 目标、非目标、指标和护栏指标。
4. 目标用户和用户故事。
5. 核心流程。
6. 功能需求和提醒规则。
7. 异常场景和边界条件。
8. 埋点、归因和实验方案。
9. MVP、V2 和明确不做的内容。
10. 验收标准。
11. 技术约束、风险、隐私和已知限制。

PRD 不需要写成几十页，每一节都应帮助开发、测试或评审做出判断。

### 4.4 验收标准：记录如何证明做对了

至少覆盖：

- 未完成任务的被动型用户能够生成提醒。
- 已完成任务的用户不会收到提醒。
- 免打扰时间不会发送提醒。
- Push 权限关闭时正确降级。
- 每日频控有效。
- 重复调度不会生成重复发送。
- 发送失败的重试不会突破幂等和频控。
- 缺失行为数据时使用默认策略。

验收标准可以和 PRD 合并，但不能只存在于聊天记录中。代码测试应能反向对应这些场景。

### 4.5 技术方案：记录产品判断如何落到代码

建议留档：

- 系统边界和模块职责。
- 用户、任务、提醒偏好、决策、发送记录、行为事件等领域模型。
- 决策引擎的输入、输出和规则优先级。
- 调度、频控、幂等键、重试和状态流转。
- 时间、时区、跨天和截止时间处理。
- 事件和 strategy_version 设计。
- Demo 使用内存、本地数据库或 Mock 的地方，以及生产环境替代方案。
- API 或主要函数的调用关系。

不需要留档：

- 没有实际使用的复杂中间件设计。
- 与 MVP 无关的完整生产部署拓扑。
- 只为显得复杂而添加的技术名词。

### 4.6 开发任务拆分：记录优先级和完成边界

这部分不是平台硬性要求，但能体现 Owner 意识。建议只保留一页以内：

| 优先级 | 任务 | 结果 |
| --- | --- | --- |
| Must | 决策引擎、任务状态、提醒记录、事件记录、核心测试 | 形成业务闭环 |
| Should | 设置页、站内提醒、时间推进、场景演示 | 提升可演示性 |
| Could/V2 | 真实 Push、机器学习、A/B 平台、复杂召回 | 不影响 MVP 成立 |

最好记录实际完成情况和未完成原因，但不需要记录每次编码操作或每条命令。

### 4.7 编码：代码本身就是主要证据

必须保证：

- 项目可以从 README 指令启动。
- 核心规则不是只写在页面 Mock 中，而是由可测试的业务模块实现。
- 产品方案中的关键字段和策略版本在代码中有对应体现。
- 失败路径、边界条件和重复执行有处理。
- 示例数据可以稳定复现文档中的演示场景。
- 不包含密钥、个人路径、缓存和无关构建产物。

不需要保留所有中间版本代码、未采用的 AI 代码片段或实验分支。

### 4.8 测试：保留可复核的质量证据

建议保留：

1. 自动化测试代码。
2. docs/test-report.md 测试报告。

测试报告至少记录：

- 环境和启动方式。
- 测试命令。
- 测试总数和通过结果。
- 决策引擎覆盖的业务分支。
- 端到端演示场景。
- 已知限制和未覆盖范围。

测试重点应对应产品规则，而不是只测试 HTTP 200 或页面是否渲染。

### 4.9 质量准出：记录我确认它可以交付

建议保留一份简短清单：

- 全新环境可以安装依赖。
- README 中的启动命令有效。
- 核心测试全部通过。
- 至少 3–5 个演示场景可复现。
- PRD、代码、测试和演示数据保持一致。
- 未包含密钥、缓存、node_modules、虚拟环境和本地绝对路径。
- 已知限制已写明。
- ZIP 解压后仍可以按 README 运行。

这份记录不需要写成流水账，勾选项加执行日期和命令即可。

### 4.10 打包提交：记录评审者如何运行

最终提交包至少要让评审者知道：

- 项目是什么。
- 如何安装和启动。
- 如何运行测试。
- 如何进入 Demo。
- 有哪些默认用户和场景。
- 哪些功能是 MVP，哪些是 V2。
- 当前实现的简化项和限制是什么。

README 是最终交付的入口，不建议让评审者从多个文档中猜启动方式。

## 5. AI 应用能力如何留档

评审标准包含 AI 应用能力，建议单独提交 AI_USAGE.md，内容保持短且具体。

建议记录四类信息：

| 内容 | 需要说明什么 |
| --- | --- |
| AI 参与工作 | 需求反驳、指标核算、方案补充、代码草拟、测试场景生成、代码审查等 |
| 人工判断 | 哪些核心决策由本人确定，例如目标用户、频控、规则优先级和 MVP 边界 |
| 验证方式 | 如何通过题目数据、单元测试、功能演示和人工检查验证 AI 输出 |
| 修正案例 | AI 曾经提出但被否决或修改的方案，以及原因 |

推荐写法是“AI 做了什么、我做了什么、如何验证”，不要只写“本项目使用了 AI 辅助开发”。

不建议把完整聊天记录或大量提示词全部放入 ZIP。评审需要的是可验证的协作说明，而不是噪音。

## 6. 留档优先级

### 必须留档

- PRD.md。
- 可运行的项目代码。
- README 和运行说明。
- 自动化测试代码。
- 最终提交的演示数据或可复现的 Demo 场景。
- AI 使用说明，建议作为独立文件提交。

### 强烈建议留档

- 需求分析中的事实、假设和指标口径。
- 技术方案。
- 验收标准。
- 测试报告。
- 关键决策和取舍记录。

### 可合并或省略

- 独立的产品方案文档：可以合并到 PRD。
- 独立的开发任务拆分：可以合并到 README 或决策记录。
- 独立的质量准出报告：可以合并到测试报告或 README 的提交检查章节。
- 每日进度、命令历史、所有草稿和完整 AI 聊天记录：不建议提交。

## 7. 与评审标准的对应关系

| 评审标准 | 最重要的证据 |
| --- | --- |
| 产品能力 | PRD 中的问题定义、目标用户、指标口径、MVP 边界、规则取舍、非目标和风险 |
| 工程开发能力 | 可运行代码、清晰模块、决策引擎测试、幂等/频控/异常处理、技术方案、测试报告 |
| AI 应用能力 | AI_USAGE.md、AI 输出验证记录、人工决策和修正案例 |
| 表达完整性 | README、结构清晰的 PRD、可复现运行命令、文档与代码的一致性 |

## 8. 最终原则

平台明确表示不要求功能复杂或一次性覆盖所有内容，评审更看重边界清楚、优先级合理、关键实现能够支撑核心判断。

因此，留档应遵循三个原则：

1. 留结论和证据，不留流水账。
2. 每个重要产品判断，都能在代码或测试中找到对应。
3. 每个进入提交包的文档，都应该帮助评审理解、运行或验证项目。
