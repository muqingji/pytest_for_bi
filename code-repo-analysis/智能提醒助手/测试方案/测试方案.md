# 智能提醒助手测试方案

> 本文记录如何验证产品方案和技术实现，不定义产品需求。产品需求见“需求拆解/产品方案/产品方案.md”，评审汇总见“需求拆解/产品方案/智能提醒助手产品方案5稿.md”，验收场景见“需求拆解/验收标准/验收标准.md”。
>
> 本期范围：只验证 Push 单渠道闭环（FR-001 至 FR-005、FR-007、FR-008）；站内提醒承接随该需求移入 P1，相关用例本轮不执行。

## 1. 测试目标

验证以下核心假设的业务闭环是否成立：

> 对当天有未完成任务的被动型学生，在更可能学习的时间发送一次受频控和免打扰保护的提醒，可以带来可观察的打开和任务完成行为。

本地 Demo 不用于证明线上 Push 打开率已经从 8% 提升到 15%，只验证决策逻辑、事件链路和异常控制是否正确。

## 2. 测试数据

用户、任务、行为和提醒设置的构造方式见“数据构造/数据构造说明.md”。

## 3. Demo 验证流程

Demo 控制台的操作顺序如下：

~~~text
选择预置用户
→ 查看任务状态和提醒设置
→ 生成提醒决策
→ 查看是否提醒、时间、渠道和决策原因
→ 推进模拟时间到提醒时间
→ 模拟发送提醒
→ 模拟打开提醒或完成任务
→ 查看事件时间线和任务状态变化
~~

时间推进是测试辅助能力，不是面向学生的产品功能。它用于避免演示时等待真实时间。

## 4. 测试分层

### 4.1 决策引擎单元测试

- 用户已经完成任务时不提醒。
- 被动型用户在候选活跃窗口生成提醒。
- 自驱型用户减少不必要提醒。
- 流失型用户不被高频轰炸。
- 回流用户当天不发送提醒、不生成 Push 排程，次日起恢复常规 Push。
- 免打扰时段正确延后。
- 每日系统主动 Push 频控正确生效，延后提醒按 SNOOZE 独立计量。
- Push 权限关闭（未授权）时不调用 Push、跳过本次提醒并记录未触达原因，不做渠道降级。
- 延后提醒使用 Push、不占用当日系统主动 Push 上限，且不再提供“稍后提醒”入口。
- 相同幂等键不会重复发送。
- 发送失败重试不会突破频控。
- 缺失行为数据使用默认策略。

### 4.2 集成测试

- API 或应用入口能够调用决策引擎。
- 决策、发送和事件记录状态能够正确流转。
- 任务完成后尚未发送的提醒会被取消。
- 重复执行调度不会新增重复发送记录。

### 4.3 端到端演示

至少演示以下流程：

1. 被动型用户生成提醒并完成任务。
2. 已完成用户不生成提醒。
3. 免打扰用户被延后提醒。
4. Push 关闭用户不调用 Push、跳过本次提醒并记录未触达原因。
5. 延后提醒生成一小时后的 Push 排程且不占用当日系统主动 Push 上限。
6. 重复调度命中幂等控制。

## 5. 事件验证

每次 Demo 操作应能检查以下事件：

- reminder_decision_created
- reminder_sent
- reminder_delivered
- reminder_opened
- task_started
- task_completed

事件至少包含 decision_id、strategy_version、user_id、task_date、channel 和 event_time；本期 channel 取值只出现 push，reminder_impression 属 P1、本期不产生。

## 6. 探索性测试

- 快速重复点击生成决策和发送。
- 在提醒前完成任务。
- 修改到免打扰开始和结束的临界时间。
- 传入缺失行为数据。
- 重启应用后重新执行同一调度。
- 发送失败后重复触发重试。
- 点击“稍后提醒”后再次对延后提醒发起 snooze。
