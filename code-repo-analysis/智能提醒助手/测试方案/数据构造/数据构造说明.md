# 智能提醒助手测试数据构造说明

> 本文只定义测试和 Demo 使用的模拟数据，不定义产品需求，也不替代技术方案中的领域模型。
>
> 本期范围：只构造 Push 单渠道数据（FR-001 至 FR-005、FR-007、FR-008）；站内提醒承接随该需求移入 P1，相关 Fixture 与场景本轮不构造。

## 1. 构造目标

用最少的一组可重复数据覆盖提醒产品的主要用户类型、时间边界和异常场景，确保评审者可以稳定复现相同结果。

数据构造用于验证规则，不代表真实线上用户分布，也不能用于推导真实业务指标。

## 2. 用户 Fixture

| 用户 ID | 用户类型 | 历史行为 | 今日状态 | 关键设置 | 预期用途 |
| --- | --- | --- | --- | --- | --- |
| user-self-driven | 自驱型 | 经常主动完成 | 已完成全部任务 | Push 开启 | 验证已完成不提醒 |
| user-passive | 被动型 | 晚饭后完成概率较高 | 有未完成任务 | Push 开启 | 验证个性化提醒时间 |
| user-inactive | 流失型 | 连续 3 天以上未打开（最近 3 天均未打开） | 有未完成任务 | Push 开启 | 验证流失型不进入主动 Push 排程 |
| user-returning | 回流型 | 前 7 天无打开，最近 3 天内有打开 | 有未完成任务 | Push 开启 | 验证回流首日当天不发送提醒、不生成 Push 排程 |
| user-returning-day2 | 回流次日的被动型 | 前 7 天有打开，完成产出偏低 | 有未完成任务 | Push 开启 | 验证回流次日起恢复常规 Push 提醒 |
| user-quiet | 被动型 | 晚饭后完成概率较高 | 有未完成任务 | 当前处于免打扰时段 | 验证延后策略 |
| user-no-push | 被动型 | 有历史活跃数据 | 有未完成任务 | Push 关闭 | 验证 Push 未授权时跳过本次提醒并记录未触达原因 |
| user-no-history | 被动型 | 无历史行为数据 | 有未完成任务 | Push 开启 | 验证默认窗口 |
| user-duplicate | 被动型 | 有历史活跃数据 | 有未完成任务 | 已有同日提醒记录 | 验证幂等和频控 |
| user-snooze | 被动型 | 有历史活跃数据，当天已收到一次系统主动 Push | 有未完成任务 | Push 开启 | 验证延后提醒使用 Push、不占当日上限且无再次入口 |

## 3. 任务数据

每个用户至少包含：

- task_date
- total_required_tasks
- completed_tasks
- estimated_minutes
- deadline
- task_status

建议覆盖以下任务状态：

| 状态 | 示例 | 预期用途 |
| --- | --- | --- |
| COMPLETED | 5/5 已完成 | 不生成未完成提醒 |
| PENDING | 2/5 已完成 | 进入提醒决策 |
| EXPIRED | 当前时间晚于截止时间 | 不发送普通提醒 |
| COMPLETED_BEFORE_SEND | 生成决策后、发送前完成 | 取消旧提醒 |

## 4. 行为数据

有历史行为的用户至少包含最近 7 天：

- App 打开时间段。
- 任务完成时间段。
- 是否在收到提醒后完成任务。
- 连续未打开天数。

示例行为特征：

~~~text
user-passive
  app_open_windows: 19:00-21:00
  task_complete_windows: 19:30-20:30
  inactive_days: 0

user-inactive
  app_open_windows: none in recent 7 days
  task_complete_windows: none in recent 7 days
  inactive_days: 3
~~~

## 5. 提醒设置数据

每个用户至少包含：

- reminder_enabled
- push_enabled
- quiet_hours_start
- quiet_hours_end
- timezone
- daily_reminder_cap（系统主动 Push 每日上限，默认 1 次；`SNOOZE` 用量独立计量）

边界数据应覆盖：

- 免打扰开始时间前一分钟。
- 免打扰结束时间后一分钟。
- 跨午夜的免打扰区间。
- 任务截止时间前后各一个时间点。
- 当天已经达到系统主动 Push 上限（1 次）。
- 当天已发送 1 次系统主动 Push 且用户又触发了一次延后提醒（同一天 Push 总数达到 2 次）。

## 6. 场景与预期结果

| 场景 | 输入 | 预期结果 |
| --- | --- | --- |
| 被动型正常提醒 | user-passive，有未完成任务，处于活跃窗口 | 生成提醒，时间落在候选窗口 |
| 已完成任务 | user-self-driven，任务全部完成 | 不提醒，原因 TASK_COMPLETED |
| 免打扰 | user-quiet，当前在免打扰区间 | 延后或不提醒 |
| Push 关闭 | user-no-push，Push 不可用 | 不调用 Push，跳过本次提醒，记录未触达原因 `NO_AVAILABLE_CHANNEL` |
| 连续不活跃 | user-inactive，连续 3 天以上未打开 | 不进入主动 Push 排程，记录 `USER_INACTIVE` |
| 回流首日 | user-returning，前 7 天无打开但最近 3 天内有打开 | 当天不发送提醒、不生成 Push 排程，记录 `RETURNING_FIRST_DAY` |
| 延后提醒 | user-snooze，当天已收到一次系统主动 Push 后点击“稍后提醒” | 生成一小时后的 Push 排程，不占用当日系统主动上限，且不再提供再次入口 |
| 回流次日 | user-returning-day2，回流判定已失效 | 恢复正常 Push 提醒 |
| 无历史数据 | user-no-history，无行为特征 | 使用默认活跃窗口 |
| 重复调度 | user-duplicate，已存在同日记录 | 命中幂等，不重复发送 |

## 7. 数据使用边界

- 数据只用于本地 Demo 和自动化测试。
- 不使用真实学生姓名、手机号、设备标识或其他敏感信息。
- 不根据这些模拟数据宣称 Push 打开率已经达到 15%+。
- 数据变更后必须同步更新测试预期和测试报告。
- 站内提醒承接相关 Fixture（承载页面、站内回执）属 P1，不在本期数据集中构造。
