BI 整体系统架构流程图

视角：端上 · 查询侧 · 大数据侧协同的整系统。 每张图上方都有「节点是什么 / 起什么作用」讲解；先读讲解，再看图。

图 1 · 整体系统全景流程（主图）

这张图在讲什么

BI 不是只有数仓。完整系统分三侧协同：端上负责看与点，查询侧负责权/配/查/导，大数据侧负责数据进得来、算得完。

区块是什么起什么作用
① 端上宿主页 + bi-xkcharts 图表组件库渲染图表、下钻/明细/联动；发 HTTP 查数
② 接入CEP/FCP 网关鉴权、路由到 BI 服务、生成 trace、限流
③ 查询侧crm-report / fs-bi-stat / udf / dev / metadata / task / sql*门户编排、统计图查询、权限注入、SQL、订阅导出
④ 大数据侧同步 + warehouse ODS/DWS业务数据入仓、预聚合、视图就绪
⑤ 存储与总线CH / PG / Redis / MQ分析数据、配置、缓存、异步事件
读法：用户从端上进入 → 网关进查询侧 → 查询侧读 CH/PG/Redis；同时大数据侧持续把业务数据生产成可查的分析态，并经 MQ/HTTP 与查询侧咬合。

图 2 · 读路径：统计图出图流程

这张图在讲什么

用户打开一张统计图时，请求如何从端上走到数据返回并渲染。这是读路径，默认读预聚合结果，不实时扫业务库。

节点是什么起什么作用
用户 / 宿主页业务页面或驾驶舱壳提供入口、全局筛选、容器
bi-xkcharts统计图前端组件库拉配置/数据，翻译成 ECharts 并交互
CEP/FCP网关鉴权路由、trace、把请求打到 BISTAT
fs-bi-stat统计图查询服务权限注入、SQL 生成执行、编排缓存
metadata/权限/组织配置与权限上下文决定“能看什么、怎么算”
Redis查询结果缓存相同条件短时间命中，降低 CH 压力（默认约 10 分钟）
ClickHouse分析库提供预聚合/明细查询结果
warehouse数仓服务可选返回 latestCalTime（数据更新到点）
一句话：端上只负责画；fs-bi-stat 负责按权限查好数；数从 CH 预聚合来，Redis 负责短缓存加速。

图 3 · 写路径：数据生产到可查

这张图在讲什么

业务数据如何变成统计图可查的分析数据。这是写路径/数据生产路径，不是用户点开报表的读路径。

总流程：业务先写业务库 → 同步搬进 ClickHouse → MQ 通知可算 → DWS 预聚合 → StatView 标记就绪 → fs-bi-stat 才能稳定查到新数。

图中每个节点是什么、起什么作用

节点是什么起什么作用
业务 PostgreSQL CRM/PaaS 等业务系统的事务库（订单、客户、商机等真实业务数据所在库） 真相源。业务增删改先落这里。BI 一般不直接拿它做大规模分析扫表，而是作为同步源头。
copier / ODS Transfer 数据同步组件（如 paas-bi-copier、warehouse 的 ODS Transfer/DBTransferService） 搬运工。从业务 PG 抽增量/存量，映射转换后写入 ClickHouse ODS/明细；成功后常发计算事件。
ClickHouse BI 分析型数据库（列存，适合聚合分析） 分析仓库。存同步明细 + DWS 预聚合结果（如 agg_data/dim_data），供查询侧读取。
RocketMQ 消息队列 传话筒/任务单。把“同步完成”和“开始聚合”解耦；削峰、异步、可重试，避免同步线程被重计算拖死。
warehouse DWS fs-bi-warehouse 的汇总计算层（事件驱动） 预加工车间。消费计算事件，按规则做聚合/拓扑级联，把汇总写回 ClickHouse，让统计图查询变快。
StatView 刷新 统计视图就绪/刷新环节（视图变更事件消费与预计算校验） 完工灯。标记某张统计图依赖的数据已算完可查；支撑“数据更新于 xx 时间”等就绪信息。
fs-bi-stat 查询侧统计图服务（应用层，不是数仓） 点菜口/传菜口。不负责生产数据；在数据就绪后读取 CH 预聚合结果，结合权限/配置返回给前端出图。

容易混淆

  • 业务 PostgreSQL ≠ BI 配置 PostgreSQL：前者是订单/客户等业务源；后者存图配置、元数据、规则（控制面）。
  • ODS vs DWS：ODS 偏明细入仓；DWS 偏汇总预聚合。
  • fs-bi-stat 不生产数据：它出现在写路径末端，表示“生产完成后由谁把数变成可出图”。
人话故事：业务员改订单（业务 PG）→ 搬运工抄进分析仓（copier/ODS → CH）→ 贴任务单（MQ）→ 车间预汇总（DWS）→ 点亮完工灯（StatView）→ 传菜口按菜单出菜（fs-bi-stat → 前端）。

图 5 · 配置变更如何驱动数仓计算

这张图在讲什么

管理员在 BI 里启停统计图/聚合规则后，如何影响到数仓是否继续算。体现控制面在查询侧，数据面在大数据侧。

节点是什么起什么作用
管理员操作启停图/规则发起控制面变更
fs-bi 更新 PG 规则查询侧改配置库状态记录“还要不要算这张图”
MQ 通知 warehouse规则/离线等事件消息把控制决策传给数仓
DWS 停/起算数仓计算开关省资源或恢复预聚合
CH 结果变化分析库数据状态变化后续查询读到新状态
端上/查询侧读路径消费者用户最终感知启用/停用效果
fs-bi 不自己停 CH 计算线程，而是改规则 + 发 MQ；warehouse 收到后才真正停算/起算。
