# PRD 转验收标准

## Goal

把需求规则转成可判定的验收基线，同时保证两件事：

1. **可追溯**：每条 AC 能反查到需求规则，每条 P0 需求至少有一条 AC。
2. **可判定**：一条 AC 一个结论，结论具体到能被"是/否"回答，且不越界写实现与操作步骤。

执行边界：

- PRD 是唯一需求事实源；产品方案只补背景，冲突时以 PRD 为准。
- 只产出验收标准文档。不改 PRD、不改技术方案、不改测试方案。
- 不写测试数据取值、不写用例步骤、不写接口字段；这些分别属于数据构造说明与测试方案。
- 缺失信息标"待确认"，不虚构判定阈值、原因码或统计口径。
- 本期只覆盖 P0；P1/P2 只记录边界，不写成验收项。

## When to Use

适用：

- "生成验收标准""补一套 AC""把 PRD 规则拆成验收场景"。
- "审查 / 回查验收标准""颗粒度是否合适""覆盖是否完整"。
- "AC 覆盖了哪些 FR""哪些规则还没有验收项"。

不适用：

- 编写 PRD 或产品方案。
- 编写测试用例、测试方案、测试报告。
- 编写技术方案（用 `prd-to-tech-design`）。

## Workflow

### 0. 确认输入

必需：9 稿 PRD。尽量具备：产品方案、既有验收标准、技术方案（用于检查口径一致）。
缺少 PRD 时停止生成，说明缺什么。

### 1. 抽取验收点

从 PRD 逐条抽取：每条 FR 的规则、判定顺序、原因码、边界条件、用户可控项。
按 `references/ac-writing-guide.md` 第 6 节覆盖矩阵，把每个 FR 映射到需要覆盖的维度；映射为空说明该需求无需验收或抽取有遗漏。

### 2. 拆分 AC

按"一个判定结果一条 AC"拆分，使用统一编号 `AC-0NN` 与统一句式（Given / And / When / Then / And）。
拆分自检：

- 每条 AC 的 Then 能否只用"是/否"回答。
- 一条 AC 是否只有一个触发（When）。
- 相邻两条 AC 的差异是否明确（条件不同或结论不同）。

### 3. 补齐边界与异常

对每条 P0 规则补：正常分支、前置不满足、已完成或已失效、频控上限、重复与并发、失败与未知状态、时间边界、设置变更、用户主动操作、数据与隐私。
不适用的维度不必强写，但要在文档中一句说明原因。

### 4. 自动回查

~~~bash
python3 dev-tools/skills/prd-to-acceptance-criteria/scripts/check_acceptance_criteria.py \
  --ac <验收标准.md> --prd <PRD.md> [--prd <产品方案.md>]
~~~

阻塞项必须修完并重跑，直到阻塞项为 0；建议项逐条判断修或记录理由。

### 5. 人工审查

按 `references/ac-quality-checklist.md` 第 7 节确认颗粒度、拆分方式、业务方关心点、与 PRD 口径一致性，以及"有没有写得很全但没人会验"的条目。

### 6. 交付

输出验收标准文件 + 回查报告。报告不合格时不交付，先说明阻塞原因。

## Output

| 项目 | 要求 |
| --- | --- |
| 产物 | 验收标准 `.md`；回查报告默认随消息给出，要求落盘时写 `docs/acceptance-criteria-review.md` |
| 命名与路径 | 默认 `<需求目录>/需求拆解/验收标准/验收标准.md`；不擅自改名、搬移或归档既有文件 |
| 结构 | 按主题分节（决策规则、频控与幂等、时间与数据异常、事件记录、设置与内容等），每节下按 `### AC-0NN：结论` 排列 |
| 单条格式 | `Given / And / When / Then / And` 五段式，Then 必须含判定依据（原因码、状态、数量或时间约束） |
| 回查报告 | 分"阻塞项 / 建议项 / 待确认"，每条带 `文件:行号` 与修复建议 |
| 结尾 | 一句话结论：是否可进入评审与执行，以及未闭环的风险 |
