# 测试场景与用例评审

独立评审测试场景清单与测试用例清单，产出分级评审意见与可复核的评审结论。用户要求评审、复审或封板评审用例时，使用本 skill。

## Goal

产出一份**可复核**的评审报告：

1. **结论**：通过 / 有条件通过 / 不通过，且结论与意见级别一致。
2. **分级意见**：阻塞项、建议项、待裁定项，每条带证据（`文件:行号`）与修复建议。
3. **覆盖缺口基线**：评审者独立推导出的、产物里没有的场景。

三个不变式：

- **先独立推导，再看产物**：评审者先不看被评审内容，从 PRD 与验收标准独立推一份基线场景集，再与产物比对。跳过这一步的评审只能做格式检查，不算评审。
- **有证据才算意见**：每条意见必须能指回文档原文或产物具体位置。指不回去的降级为“待确认”，不写进意见。
- **只评不改**：本 skill 不改被评审文档、不改需求文档、不替作者填默认值或判定点。改动必须由作者按 `test-case-design` 的变更流程执行。

## When to Use

适用：

- “评审这份测试场景清单 / 测试用例”。
- “给我一份用例评审意见”。
- “用例要封板了，先评一遍”。
- “作者按意见改完了，复审一遍”。
- 用户要在 `test-case-design` 的门禁 A / B / C 上扮演评审角色时，作为评审依据。

不适用：

- 生成场景或用例（用 `test-case-design`）。
- 执行测试、跑命令、写测试报告（用 `test-plan-to-test-report`）。
- 修改 PRD、验收标准、技术方案（用 `prd-refinement`、`prd-to-acceptance-criteria`、`prd-to-tech-design`）。
- 实现业务代码（用 `tech-design-implementation`）。

## 与 test-case-design 的边界

| | test-case-design | test-case-review |
| --- | --- | --- |
| 视角 | 作者自检 | 第三方评审 |
| 目标 | 产出合规的场景与用例 | 找出缺口、错引用与不可执行项 |
| 手法 | 按检查清单自查 + 回查脚本 | 独立重推导 + 逐条实读原文核验 |
| 产物 | 场景清单、用例清单、封板记录 | 评审报告 |
| 能否改产物 | 能 | 不能 |

自检通过不等于评审通过。本 skill 不重复跑 `check_test_cases.py` 的格式检查，但要求评审者确认该脚本已跑过且阻塞项为 0；否则评审结论不得为“通过”。

## 评审对象与来源

评审对象可以是任何来源的场景清单与用例清单：`test-case-design` 的产物、人工补充的条目、他人手写或外部交付的版本。来源不同，评审基线不同。

对非 `test-case-design` 来源的产物（人工补充、外部交付）：

| 缺失项 | 定级 | 理由 |
| --- | --- | --- |
| 来源出处 | 不直接判为臆想，先要求作者补溯源 | 人工补充常先有结论后补依据；补不出出处、且判定点与文档冲突时才是阻塞项 |
| 判定点 | 阻塞 | 无法判定通过与否 |
| 前置条件 | 阻塞 | 无法构造，无法执行 |
| 预期结果 | 阻塞 | 无法判定通过与否 |
| 优先级 | 阻塞 | 无法排期、无法抽样评审 |
| 编号与格式规范 | 建议 | 只要求全局唯一、可被引用 |

## 评审顺序：AI 评审先于人工评审

本 skill 的评审是人工评审的前置步骤，不替代人工评审：

1. AI 评审（本 skill）产出评审报告与分级意见。
2. 作者按阻塞项与建议项修订；待裁定项交用户裁定。
3. 阻塞项清零后，才可提交人工评审。
4. 人工评审通过才等于门禁通过。

硬性约束：

- 存在未处理阻塞项时，不得提交人工评审。
- 本 skill 的“通过”结论不构成门禁通过，只表示“可以提交人工评审”。
- 待裁定项在人工评审前必须已有用户裁定记录，不得把未决口径带进人工评审。
- 人工评审提出的意见若超出门禁范围（如要求改需求），按上游问题登记，不在本 skill 内处理。

三道门禁（A 场景、B 用例、C 封板）的顺序约束以 `test-case-design` 为准。

## 权威来源与顺序

| 来源 | 用途 |
| --- | --- |
| PRD | 规则的唯一事实源；用于独立重推导与核验判定点 |
| 验收标准 | `AC-xxx` 主干；用于独立重推导与覆盖矩阵闭合性核验 |
| 技术方案 | 契约、状态流转、异常与降级链路；用于核验可测性与分层 |
| 测试方案 | 分层与 Demo 流程；用于核验场景落在正确层级 |
| 数据构造说明 / Fixture | 前置条件能否构造的事实源 |
| 被评审产物 | 场景清单、用例清单、封板记录 |
| 业务代码（阶段五后） | 核验“代码补充类用例”是否与实际分支一致 |

引用核验要求**实读原文**：逐条打开被引用的文件并读到该行，确认该行内容确实支持这条判定。只做格式检查（路径存在、行号未越界）不算核验。

## Workflow

### 阶段 0：评审准备

1. 确认评审对象与版本（场景清单 / 用例清单 / 两者 / 封板记录），记录版本号或文件哈希。
2. 确认 `check_test_cases.py` 已执行且阻塞项为 0；未执行则在报告里记为前置缺口。
3. 按评审强度确定范围。默认 **standard**：P0 全量评审；P1 按覆盖维度分层抽样（每个覆盖维度至少一条），投诉、误发、越权等风险项强制纳入；P2 只核验是否已显式登记。抽样结果与漏评风险必须在报告里单独声明。
4. 确认评审时机：门禁 A（场景）/ 门禁 B（用例）/ 门禁 C（封板前）/ 阶段五后复审。

### 阶段 1：独立重推导（防锚定）

**在阅读被评审产物之前**完成：

1. 只读 PRD 与验收标准，独立推出一份基线场景集：每条含 AC/FR 归属、判定点、场景类型。
2. 覆盖 PRD 的判定顺序、每个原因码、每条频控与免打扰规则。
3. 基线推导深度固定为 **standard**：覆盖主路径、判定顺序每一步、每个原因码、频控与免打扰规则；不展开等价类划分与边界取点。只有用户明确要求 deep 时才展开到等价类一级。
4. 基线只记“应该有什么”，不写具体预期取值。

5. 然后与产物比对，把差异分为三类：

| 差异 | 含义 | 处理 |
| --- | --- | --- |
| 基线独有 | 产物漏了 | 阻塞项，附出处 |
| 产物独有 | 可能臆想，也可能有据补充 | 核验溯源；无据则为阻塞项 |
| 名称不同但判定点等价 | 表述差异 | 提示项，不算缺口 |

### 阶段 2：逐条核验溯源

对每条场景与用例的每个引用，实读原文后判定：

| 判定 | 含义 | 级别 |
| --- | --- | --- |
| 支持 | 原文明确写了该规则 | — |
| 相关但不充分 | 引用的段落相邻，但没写该判定 | 阻塞 |
| 不支持 | 引用错位，该行是别的规则 | 阻塞 |
| 无法解析 | 文件不存在或行号越界 | 阻塞 |

重点抽查高风险形态：引用指向章节标题行而非规则行；引用指向表格里的别的行；引用指向已改稿的旧行号；多个场景引用同一行但各自推导出不同判定。

### 阶段 3：逐维评审

按 `references/review-dimensions.md` 的十个维度逐条打分并记录证据：

1. 溯源正确性（阶段 2 结论）。
2. 覆盖完整性：AC 矩阵闭合；FR 的每个分支、判定顺序每一步、每个原因码都有场景。
3. 等价类与边界值正确性：有效/无效/边界三类是否齐全；无效等价类是否被合并成一条；边界取点是否覆盖“等于、前 1、后 1”。
4. 判定点可观测性：断言落在哪一层、是否有观测手段；HTTP 层观测不到的结论是否已登记为不可测项。
5. 预期结果确定性：是否唯一、可判定；是否出现“符合预期”“正常返回”等空话。
6. 优先级合理性：不高于来源需求；P0 是否膨胀；高频打扰、投诉、数据泄露类风险场景是否漏标 P0。
7. 前置条件可构造性与契约一致性：字段名是否与数据构造契约一致；是否存在现有 Fixture 无法表达的状态。
8. 可复现性：时间依赖（有无固定测试时钟）、随机性、执行顺序依赖、外部状态依赖。
9. 一致性与范围：本期范围（P0/P1/P2 边界）、与测试方案分层一致、文档无重复矛盾、编号无回收。
10. 风险与不可测项登记：不可测项是否显式登记，而不是被静默省略。

### 阶段 4：形成结论与分级

- **阻塞项**：错引用、覆盖缺口、不可构造前置条件、不可判定预期、越权优先级、未登记不可测项、摘要或结论与内容矛盾。
- **建议项**：表述、归类、可读性、编号组织、可合并的重复用例。
- **待裁定项**：口径冲突、文档自身矛盾、不可测项是否接受、范围是否扩大、优先级争议。**不由评审者替用户选一个**，列入待裁定并说明候选方案与影响面。

结论规则：

| 结论 | 条件 |
| --- | --- |
| 不通过 | 存在任一阻塞项 |
| 有条件通过 | 无阻塞项，存在待裁定项或建议项 |
| 通过 | 无阻塞项、无待裁定项、无“未处理”状态的建议项 |

评审结论**不等于**门禁通过：本 skill 的“通过”只表示可以提交人工评审，人工评审通过才等于门禁通过。

### 阶段 5：人工裁定

把待裁定项与阻塞项逐条交用户，说明：证据、受影响的场景或用例、影响范围、候选方案、需要用户作出的确切决定。用户回答前不得给出“通过”或“有条件通过”。

### 阶段 6：复审闭环

1. 作者改完后再评一次，只复审**变更点 + 受影响项**，并核对变更是否引入新的引用错位。
2. 未处理项必须有用户裁定记录，不得静默消失。
3. 每次复审递增报告版本，保留历史结论。

## 人工确认触发条件

出现以下任一情况时停止并请求确认：

- 发现文档之间口径冲突（PRD / 验收标准 / 技术方案 / IDL / 代码）；
- 发现文档自身矛盾（同一规则两处表述不一致）；
- 出现不可测项，需要决定“登记为不可测”还是“放弃该场景”；
- 覆盖缺口是否可以接受（本期不覆盖）需要用户拍板；
- 优先级争议，或需要把场景降级/移出本期范围；
- 需要修改需求文档本身才能评审通过；
- 用户要求跳过独立重推导或跳过待裁定环节；
- 复审时发现改动超出原意见范围。

确认请求必须说明：证据（`文件:行号` 或场景/用例编号）、受影响的场景与用例、影响范围、候选方案、需要用户作出的确切决定。用户回答前不得继续。

## Output

| 项目 | 要求 |
| --- | --- |
| 产物 | 评审报告；默认不给修订版产物，不改被评审文档 |
| 默认路径 | `<需求目录>/测试方案/测试用例评审报告.md`；已有同名文件时沿用并递增版本 |
| 意见编号 | `RV-0NN`，全局唯一，不因处理完成而回收 |
| 意见必填字段 | 级别（阻塞/建议/待裁定）、位置（`文件:行号` 或场景/用例编号）、证据、问题、影响、修复建议、状态（未处理/已处理/不处理并附裁定记录） |
| 报告结构 | 评审对象与版本、评审范围与抽样说明、结论、独立重推导基线对比、阻塞项、建议项、待裁定项、不可测项登记、复审记录 |
| 溯源格式 | `文件路径:行号`，多个用顿号分隔；路径相对仓库根目录 |
| 表述要求 | 禁止“建议完善”“需要补充”这类无落点意见；每条意见必须能直接指导作者改动 |
| 结尾 | 一句话结论：评审结论、阻塞项数量、待裁定项数量、是否可以提交人工评审 |
