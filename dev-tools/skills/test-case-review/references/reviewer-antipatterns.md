# 评审者反模式

评审者自身出错的方式，比作者更多。每次评审结束前逐条自查。

## 1. 只做格式检查

跑了一遍 `check_test_cases.py` 看到 0 阻塞，就给出“通过”。脚本只查编号、字段与可解析性，**引用指向章节标题行**这类问题脚本抓不到，必须实读原文。

## 2. 声称核验过溯源，实际只看格式

引用路径存在、行号未越界 ≠ 引用正确。判定“溯源正确”之前必须读到那一行，并确认该行写的就是这条规则。

## 3. 凭印象说覆盖不足

写“建议补充边界场景”而不给出缺失的场景与出处，作者无法执行。正确写法是指出缺哪条规则（`文件:行号`）、该规则应对应什么判定点。

## 4. 意见不可复现

没有证据、没有位置的意见无法被复核，也无法在复审时确认是否已处理。缺证据的怀疑只能进“待确认”。

## 5. 替作者改判定点

评审者不得把“延后到下一个窗口”直接写成唯一预期，也不得替作者选默认值、阈值或口径。这类问题一律进“待裁定”，附候选方案与影响面。

## 6. 等级通胀

把所有意见都标成阻塞，会让门禁失去筛选作用，也让作者无法排优先级。拿不出阻塞证据的进建议项。

## 7. 越界评需求

发现需求本身有问题（如指标口径不一致），按上游问题登记，不在本 skill 内改需求，也不因此判用例不合格。

## 8. 锚定效应

先看了作者的场景清单，再“独立推导”，推导结果会被作者的编号与措辞带偏。阶段 1 必须在读产物之前完成。

## 9. 只看新增不看存量

复审时只看改动点，忽略改动对既有引用与编号的影响（改稿后行号漂移是高频问题）。复审至少要覆盖“变更点 ＋ 受影响项”。

## 10. 通过得太快

结论为“通过”的前提是：无阻塞项、无待裁定项、无未处理建议项，且 `check_test_cases.py` 已跑过。缺任一条都只能给“有条件通过”。
