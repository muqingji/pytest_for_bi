# 多模块集成测试

## 目标

验证一个已实现功能的多个生产模块能否在真实装配下正确协作。重点是模块边界和接口契约，不是重复验证领域函数的单元逻辑，也不是替代面向用户的业务验收测试。

本 skill 只负责：

- 跨两个或以上生产模块的调用链验证；
- 端口与适配器的契约验证；
- SQLite/迁移/事务/唯一键与应用流程的组合验证；
- 模块间状态、事件、错误和幂等结果的传播验证；
- 并发、重复请求、context 取消和数据库失败在模块边界上的传播验证；
- 输出可复核的集成测试命令和结果。

本 skill 不负责：

- 编写 PRD、验收标准、技术方案或测试方案；
- 从文档推导测试场景和测试用例；
- 验证完整用户业务流程或业务指标；
- 编写 Python HTTP 业务验收测试、App 测试或真实 Push 测试；
- 代替单元测试、业务测试或测试报告 skill；
- 修改业务代码来让集成测试通过。

## 适用边界

一个测试只有同时满足以下条件，才属于本 skill：

1. 执行了两个或以上生产模块；
2. 至少跨越一个真实模块边界，例如应用层到领域层、应用层到 Repository、Repository 到 SQLite、HTTP 装配到应用服务；
3. 断言模块之间的输入、输出、持久化或状态变化；
4. 不依赖测试执行顺序，不使用上一个测试留下的数据库或全局状态。

以下不计为多模块集成测试：

- 只调用 `internal/domain/reminder` 函数的测试；
- 只验证 Mock 是否被调用而不检查业务状态或持久化结果；
- 只运行测试环境 harness 自检；
- 只调用一个 HTTP 接口并断言固定响应的业务用例；
- `go test ./...` 的单元测试结果本身；
- `make test-api`、Python `tests/subjects` 或 Allure 业务验收结果；
- 真实生产 Push、用户服务、事件总线或调度平台的联调结果，除非用户明确提供可用环境并单独授权。

## 权威输入

开始前必须读取：

1. 当前功能进度记录 `docs/implementation/FR-*.md`；
2. 技术方案 `### 3.4 模块划分`、4.x 流程、数据模型、异常链路和测试建议；
3. 验收标准中与当前功能有关的 AC，仅用于确定跨模块的关键判定，不在本 skill 中重新设计业务用例；
4. 测试方案中的测试分层和模块集成测试要求；
5. 测试数据构造说明和现有 Fixture；
6. 当前生产代码、迁移、接口定义和已有集成测试；
7. `AI_USAGE.md` 中影响当前功能的人工决策。

文档与代码冲突时，不自行选择产品口径。记录证据并进入人工确认门禁。

## 当前项目的集成边界

本项目当前 Go 模块集成测试优先验证以下装配：

```text
application/evaluate
  -> domain/reminder
  -> port.TaskRepository / PreferenceRepository / BehaviorRepository
  -> adapter/task / adapter/user
  -> adapter/storage.SQLite
  -> migrations / decision / schedule / event
```

当 HTTP 适配器已经实现并被本轮功能涉及时，才增加：

```text
HTTP DTO / handler
  -> application service
  -> domain
  -> repository / SQLite
  -> response and persisted state
```

不要因为测试文件存在就假定 HTTP、Dispatch、Snooze、真实 Push 或事件总线已经实现。先以代码和技术方案确认实际装配。

## 开始前检查

先执行并记录：

```bash
git status --short --branch
git diff --check
rg --files internal cmd docs/implementation tests
```

确认以下输入：

- 当前 FR、AC 和技术方案模块；
- 本轮至少涉及的两个生产模块；
- 前置功能是否已经通过自己的准出门禁；
- 测试需要的 Fixture、时钟、数据库和外部依赖替身；
- 迁移版本和旧版本数据库升级路径；
- 现有集成测试与单元测试的边界。

如果功能尚未实现、模块边界未登记、外部依赖契约未知或前置 FR 未完成，停止并报告，不用集成测试替代实现工作。

## 工作流程

### 1. 锁定集成范围

输出集成范围表：

| 项目 | 内容 |
| --- | --- |
| FR/AC | 当前功能和关联 AC |
| 模块 A/B/... | 实际生产包或适配器 |
| 入口 | 应用服务、CLI 或已实现的 HTTP 入口 |
| 真实边界 | SQLite、迁移、序列化、事务或装配边界 |
| 外部替身 | 任务、用户、行为、Push、事件等接口的契约替身 |
| 关键断言 | 跨模块输入输出、状态、事件和持久化结果 |
| 不在范围 | 业务验收、真实外部服务、未实现模块 |

一次只验证一个已完成的功能切片。不同 FR 的集成测试不得混在同一套结果里，除非技术方案明确它们共享同一条模块链路，并在范围表中写出理由。

### 2. 设计集成装配

集成测试必须使用真实的被测模块和项目实际装配方式：

- 领域规则使用生产实现，不复制一份规则到测试；
- 应用服务使用生产实现，不绕过应用层直接操作数据库；
- Repository 使用 SQLite 或项目规定的真实本地存储实现；
- 外部依赖只能替换在端口边界，替身必须遵守接口契约；
- 使用注入时钟、临时数据库和独立 Fixture，禁止读取共享 Demo 数据库；
- 每个测试独立迁移数据库，并在结束后关闭连接、清理临时资源；
- 测试编排中的关键业务原因、跨模块目的和异常路径使用中文注释，不能只写“setup”或“call service”。

禁止通过修改业务代码、关闭约束、跳过迁移、直接写内部表或预置不可能状态来制造“可通过”结果。

### 3. 必查跨模块链路

按本轮涉及范围选择并记录：

#### 正常装配

- 输入从入口传入应用层后，是否完整到达领域规则；
- 领域结果是否正确传到 Repository；
- 决策、排程和事件是否在数据库中形成一致结果；
- 从数据库读回的数据是否能被下一模块正确消费；
- 时钟、时区、策略版本、用户 ID 和 task date 是否在边界间保持一致。

#### 失败传播

- 任务、偏好、行为、用量读取失败的错误是否按强/弱依赖规则传播；
- 行为弱依赖降级是否不伪造历史、不误判回流或归因；
- 数据库写入失败、唯一键冲突、事务回滚和 context 取消是否不会留下半条状态；
- 事件写入失败是否有明确结果，不能无声吞掉或伪造成功；
- 外部替身返回超时、未知状态、空数据和非法数据时，调用方是否遵守契约。

#### 状态和幂等

- 重复评估是否返回已有决策，不新增排程或事件副作用；
- 重复事件是否只产生一次业务副作用，而不是只忽略数据库 INSERT；
- 偏好变化、任务完成、频控拒绝或回流冷却是否清理可发送排程；
- 决策版本、排程版本、状态和取消原因是否一致；
- `decision_id`、`schedule_id`、`event_id` 和幂等键是否能跨模块关联。

#### 并发和资源

- 同一用户/日期并发评估是否只有一个有效决策和排程；
- 并发更新是否不会丢失较新的设置或状态；
- 数据库连接、事务、HTTP server、goroutine 和临时文件是否释放；
- `-race` 下是否无数据竞争；
- 测试是否对执行顺序、机器当前时间或已有数据库状态敏感。

#### 迁移和兼容

- 空库是否能按顺序迁移；
- 已有版本 1 数据库是否能升级到当前版本；
- 迁移重复执行是否安全；
- 迁移中途失败是否回滚且不会记录错误版本；
- 旧数据的 NULL、枚举、公共事件信封和索引是否仍可被代码读取。

### 4. 编写或补齐集成测试

只修改以下范围：

- 项目约定的集成测试文件；
- 测试专用 Fixture、测试替身和测试配置；
- 必要的集成测试说明或证据文件。

不修改生产业务逻辑。测试发现生产缺陷时保留失败证据，停止并报告，不通过放宽断言、增加特殊分支或 skip 绕过。

每条集成测试至少断言一项跨模块结果，优先断言：

- 返回结果与持久化记录同时正确；
- 状态、版本、原因码和取消原因；
- 排程是否存在、唯一和可发送；
- 事件信封和 payload 的关联字段；
- 重试/重复请求后的记录数与幂等结果；
- 事务失败后的数据库状态。

不要只断言 HTTP 200、函数无 error 或 Mock 调用次数。

### 5. 执行门禁

先运行本轮集成测试，再运行回归集成测试。Go 项目至少执行：

```bash
go test -count=1 <本轮涉及的集成测试包或测试文件>
go test -race -count=1 <本轮涉及的集成测试包>
go test -count=1 ./...
```

迁移、事务或并发涉及本轮时，额外执行：

```text
空库迁移
旧版本数据库升级
重复迁移
迁移失败回滚
并发评估或重复请求
context 取消
数据库锁/唯一键冲突
```

命令必须使用临时数据库和确定性时钟。测试结果必须区分：通过、失败、跳过、未执行。任何 skip、ignore 或 pending 都不能计入“集成测试全部通过”。

本 skill 不执行以下命令作为业务结论：

- `make test-api`；
- Python `tests/subjects`；
- 真实 Push/App/用户服务/事件总线调用；
- 仅 harness 自检的 `make test-selftest`。

这些结果如需执行，交给业务测试或真实联调流程，并在本 skill 的输出中标记为范围外。

## 失败和人工确认门禁

出现以下任一情况，必须停止并报告：

- 生产代码尚未实现或模块边界不清；
- 集成测试失败且原因可能是业务代码缺陷；
- PRD、AC、技术方案、IDL、代码和测试预期冲突；
- 需要修改生产代码才能让集成测试通过；
- 需要跳过、忽略或放宽断言；
- 需要新增未定义字段、状态、表、迁移或外部能力；
- 真实外部依赖能力未知，但测试试图宣称已验证；
- 数据库迁移会破坏旧数据或无法证明可回滚；
- 测试结果依赖当前时间、共享数据库、执行顺序或未声明的环境状态。

确认请求必须说明：

- 证据和文件/行号；
- 受影响的 FR/AC、模块和集成链路；
- 失败的实际结果与预期结果；
- 候选处理方式和推荐方案；
- 是否需要转交 `tech-design-implementation` 修复业务代码；
- 需要重跑的测试和回查。

## 输出

本 skill 只输出集成测试结果，不生成完整业务测试报告。输出必须包括：

1. 集成范围表和实际装配的模块；
2. 真实模块与测试替身的边界；
3. 集成测试文件/Fixture；
4. 每条测试验证的跨模块断言；
5. 执行命令和真实结果；
6. 通过、失败、跳过、未执行数量；
7. 迁移、事务、幂等、并发和失败传播结果；
8. 明确声明未执行的业务测试、真实联调和线上验证；
9. 失败 finding 或人工确认请求；
10. 结论：集成测试通过、阻塞、部分通过或未执行。

推荐格式：

```text
集成范围：application/evaluate + domain/reminder + adapter/storage
真实边界：SQLite 迁移、事务、唯一键、事件表
测试替身：TaskRepository、PreferenceRepository、BehaviorRepository

测试结果：通过 X，失败 Y，跳过 Z，未执行 W
命令：go test -race -count=1 ./internal/...

跨模块断言：
- 评估结果 -> decision/schedule 持久化：通过
- 重复评估 -> 唯一决策和单条排程：通过
- 事件写入失败 -> 结果：失败/未验证
- 旧库迁移 -> 事件信封字段可读：通过

范围外：未执行 Python 业务验收、真实 Push、线上调度和性能容量验证
结论：<通过 / 阻塞 / 部分通过 / 未执行>
```

## 与其他 skill 的协同

| Skill | 关系 |
| --- | --- |
| `tech-design-implementation` | 上游：业务功能和单测完成后，本 skill 验证模块装配；发现生产缺陷时转回修复 |
| `test-case-design` | 上游：提供已审批的集成场景边界；本 skill 不重新设计业务用例 |
| `test-plan-to-test-report` | 下游：需要完整测试报告时消费本 skill 的命令和结果；本 skill 不负责报告 |
| `code-review` | 并行审查：本 skill 提供跨模块运行证据，Code Review 评估代码风险和缺陷 |

## 不应做的事

- 不把单元测试、harness 自检或 Python 业务测试冒充多模块集成测试；
- 不修改生产业务代码来迎合集成测试；
- 不使用共享 Demo 数据库、当前系统时间或测试执行顺序作为隐含前置；
- 不用 skip、ignore、pending 或放宽断言伪造通过；
- 不把本地替身结果描述成真实外部服务或线上能力；
- 不因集成测试通过而宣称业务验收、性能、容量或生产联调完成。
