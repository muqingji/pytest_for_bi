# PRD 转技术方案

## Goal

把产品需求文档转成可评审、可落地的后端技术方案，并同时保证两件事：

1. **结构合规**：1~9 章与公司模板一致，必填章节不缺失，可选章节不随意删除。
2. **内容闭环**：每条 P0 需求都有实现落点，异常链路、幂等、数据契约、变更保障齐备，且不复述 PRD 内容。

执行边界：

- PRD 是唯一需求事实源；产品方案与需求分析稿只用于补背景。冲突时以 PRD 为准，并把分歧记入第 9 章评审记录。
- 只产出文档。不改代码、不改 PRD、不改模板文件。
- 缺失信息一律标“待确认”并集中到第 9 章，不虚构接口地址、BAM 链接、数据库类型、厂商能力、压测数据或线上实验结果。

## When to Use

适用：

- “按 9 稿 PRD 生成技术方案”“把产品方案转成技术方案”。
- “审查 / 评审 / 回查这份技术方案”“看看方案是否完整、是否有冗余”。
- “技术方案和 PRD 对不对得上”“AC 是否都有覆盖”。

不适用：

- 编写或修改 PRD、产品方案等产品文档。
- 生成业务代码、IDL 代码或 DDL 脚本。

## Workflow

### 0. 确认输入

必需：9 稿 PRD、模板 `code-repo-analysis/模版/技术方案/后端技术方案.md`。
尽量具备：产品方案 5 稿、验收标准、既有技术方案（审查模式）。
缺少 PRD 或模板时停止生成，说明缺什么、需要谁提供。

### 1. 抽取需求映射

按 `references/prd-input-mapping.md` 逐条抽取：FR / AC → 模块、接口或定时任务、数据表、状态、异常处理与待确认项。
抽取后先自检：每条 P0 至少要有“模块 + 入口 + 数据落点 + 异常处理”，四项缺一即回补或标记待确认。

### 2. 生成章节骨架

按模板列出 1~9 章及关键子节，标注（选）与必填。可选章节若确实不涉及，写“不涉及 + 原因”，不要删除标题。

### 3. 逐章填充

按 `references/prd-input-mapping.md` 的章节职责写入，硬约束：

- 第 4 章异常链路（超时、失败、未知状态、取消、降级、回滚）不少于正文 40%。
- 涉及有价资源流动（积分、奖励、卡券、任务进度、补偿下发）必须给出幂等设计。
- 错误码区分正常、错误、未知状态，不滥用 `ServiceUnavailable`、`ServiceInternalError`。
- 接口写清命名规范、限流评估、鉴权与敏感字段保护；IDL 注释含义并列出枚举值。
- 定时任务写清分片、幂等、重跑、积压与监控指标。
- 第 7 章成本评估必填，给量级与影响因素，不用空话占位。
- 第 1 章只给文档链接和一句话需求摘要，不复述 PRD 的业务背景、指标定义与产品规则。

### 4. 自动回查

~~~bash
python3 dev-tools/skills/prd-to-tech-design/scripts/check_tech_design.py \
  --design <技术方案.md> --prd <PRD.md> [--prd <验收标准.md>]
~~~

阻塞项必须全部修完并重跑，直到阻塞项为 0；建议项逐条判断是修还是记录理由。

### 5. RD leader 审查

按 `references/rd-leader-checklist.md` 逐组判断，每条结论都给出文件位置证据。脚本查不出的判断题由这一步负责：需求边界是否被放大、依赖强弱与容灾是否成立、成本与排期是否可执行、冗余是否只是换个说法重复。

### 6. 交付

输出技术方案文件 + 回查报告。报告不合格时不交付方案，先说明阻塞原因。

## Output

| 项目 | 要求 |
| --- | --- |
| 产物 | 技术方案 `.md`；回查报告默认随交付消息给出，用户要求落盘时写 `docs/tech-design-review.md` |
| 命名与路径 | 沿用项目现有位置，默认 `技术方案/技术方案.md`；不擅自改名、搬移或归档 |
| 结构 | 严格 1~9 章，使用 `## 1. 需求背景` 这类编号标题，便于脚本与模板比对 |
| 回查报告 | 分“阻塞项 / 建议项 / 待确认”三段，每条带 `文件:行号` 证据与修复建议 |
| 结尾 | 一句话结论：是否可进入评审，以及仍未闭环的风险点 |
