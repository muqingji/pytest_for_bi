# 需求抽取与章节职责

用于第 1 步抽取和第 3 步填充。技术方案的每一章都要能追溯到 PRD 的某一节；追溯不到的章节，要么删掉，要么说明它是纯技术约束。

## 1. 抽取清单

从 PRD 与验收标准中提取以下六类信息，作为生成技术方案的输入：

| 类别 | 抽取内容 | 用途 |
| --- | --- | --- |
| 需求清单 | FR 编号、名称、优先级、规则位置 | 第 2 章目标、第 9 章映射表 |
| 验收清单 | AC 编号与判定条件 | 第 5 章测试建议、第 9 章映射表 |
| 规则与决策顺序 | 判定顺序、优先级、短路条件 | 第 4.1 时序、4.2 状态机 |
| 数据结构 | 实体、字段、唯一性要求、保留周期 | 第 4.5 数据库、4.6 缓存 |
| 事件与指标 | 事件名、原因码、指标口径 | 第 4.5 数据、6.1 业务监控 |
| 依赖与未决项 | 外部系统、假设、待确认 | 第 1 章、3.2、9 章 |

## 2. 每条 FR 的抽取模板

对每条 P0 需求填四个空，缺项即回补或标记待确认：

| 空位 | 含义 | 例（以资格判断为例） |
| --- | --- | --- |
| 模块 | 由哪个模块负责 | `domain/reminder` 的 `EligibilityRule` |
| 入口 | 从哪里被触发 | 每日评估任务 / 设置变更事件触发重评估 |
| 数据落点 | 读写哪些表或实体 | 读任务、偏好、行为；写决策与事件 |
| 异常 | 依赖不可用、状态冲突时怎么办 | 任务系统超时失败关闭，不发送 |

## 3. 章节职责映射

| PRD 内容 | 技术方案章节 | 落点要求 |
| --- | --- | --- |
| 文档信息、背景 | 1 需求背景 | 只放链接与一句话摘要，不复述业务背景 |
| 一页结论、目标分层、指标 | 2 目标 | 转成技术目标 + 验证方式；指标口径引用 PRD，不重写 |
| 目标用户与场景、范围与依赖 | 3.2 应用架构、3.4 模块划分 | 划清系统边界与既有能力的接入方式 |
| 提醒机制、判定顺序 | 4.1 关键交互流程、4.2 状态机 | 判定顺序必须与 PRD 逐条对应，可加实现位置 |
| 用户可控性 | 4.3 接口定义、4.4 定时任务 | 设置变更如何立即生效、已排程如何重算 |
| 可解释与可归因、事件与原因码 | 4.3 接口、4.5 数据、6.1 业务监控 | 事件名与原因码必须与 PRD 完全一致 |
| 权限与隐私要求 | 4.3 接口安全 | 鉴权、验签、敏感字段最小化 |
| 已有功能的兼容要求 | 6.2 灰度应急、6.3 上线方案 | 写清回退后旧功能如何恢复 |
| 假设与待确认 | 9 评审记录 | 逐条给影响面、责任人与是否阻塞开发 |
| 验收标准 AC | 5 测试建议、9 评审记录 | 每条 AC 至少有一条测试建议 |

## 4. 覆盖规则

- P0 需求必须全部有实现落点；缺一条即阻塞。
- P1 只写边界与影响，不写实现细节。
- P2 仅在第 9 章记录"本次不实现 + 原因"，不得出现在详细方案里。
- PRD 未给出、但实现必需的参数（默认发送时刻、限流阈值、保留周期），统一记入第 9 章待确认，不擅自填值。
