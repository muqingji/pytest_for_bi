# 反模式清单

用于第 3 步写作和第 5 步审查。每类都给出识别特征和替代写法。

## 1. 冗余类

| 反模式 | 识别特征 | 替代写法 |
| --- | --- | --- |
| 复述 PRD | 第 1 章出现业务背景、用户画像、指标定义、规则表 | 第 1 章只放链接与一句话摘要；规则只在第 4 章以"实现落点"形式出现 |
| 同一结论多处复述 | 幂等、频控、回滚结论在 3~4 处各写一遍 | 只在一个权威位置定义，其他位置引用小节号 |
| 重复表格 | 同一份字段表在接口章和数据章各贴一遍 | 数据章为唯一定义处，接口章只引用 |
| 模板章节改名 | 把"5 测试建议"改成"质量保障"等自定义章节 | 保持模板编号与标题，内容不足时写明"本次不涉及 + 原因" |
| 空话占位 | "性能满足业务需求""后续持续优化" | 给数字、量级或待确认 + 责任人 |

## 2. 虚构类

| 反模式 | 识别特征 | 替代写法 |
| --- | --- | --- |
| 编造地址与配置 | 直接写出 BAM 链接、真实库名、厂商凭证、生产域名 | 写"待接入时确认"，并在第 9 章登记 |
| 编造数据 | 声称"压测 QPS 可达 xx""打开率提升到 xx%" | 给容量上限估算，明确标注是估算而非实测 |
| 假设下游能力 | 默认下游支持幂等、支持状态查询而不核实 | 写清"能力待核对"，并给出不支持时的兜底方案 |
| 假设既有数据完整 | 默认历史设置、历史行为一定可读 | 写清"缺失时降级策略"（如使用默认窗口） |

## 3. 残缺类

| 反模式 | 识别特征 | 替代写法 |
| --- | --- | --- |
| 只写成功路径 | 全篇无超时、失败、未知状态处理 | 按"正常 / 失败 / 未知"三态分别写处理策略 |
| 异常链路占比过低 | 第 4 章几乎全是正向流程 | 异常链路不低于正文 40% |
| 无幂等 | 涉及发奖、积分、进度、补偿却只写"重试" | 给出幂等键、唯一约束、条件更新 |
| 状态只有图没有条件 | 画了状态图但没说迁移触发条件与并发控制 | 补迁移条件表 + 条件更新语句语义 |
| 缓存当事实源 | 用缓存判断是否已发送、是否达上限 | 频控与幂等以持久化唯一约束为准 |
| 客户端决定结果 | 请求体里接受 `should_remind`、`channel` 等决策字段 | 决策只能由服务端计算，请求只传身份与日期 |
| 待确认散落 | 正文各处"待确认"十几个，第 9 章反而空 | 全部集中到第 9 章，逐条给影响面与责任人 |
| Demo 当生产 | 把内存实现、Mock 渠道、时间注入写成正式方案 | 明确区分"本地实现"与"生产方案"两列 |

## 4. 自查提问

写完第 3 步后自问：

1. 删掉所有 PRD 内容后，这份方案是否还能独立指导开发？
2. 每个"会失败"的地方，是否都写了失败后系统做什么？
3. 同一条规则，全文是否只定义了一次？
4. 方案里的每个数字，来自 PRD、来自估算，还是我编的？
5. 如果下游全部不可用，系统会发送错误提醒还是不发？
