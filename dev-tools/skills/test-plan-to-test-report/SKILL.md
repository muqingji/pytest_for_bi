# 测试方案执行与测试报告

依据已确认的测试方案和验收标准执行测试，把结果写进可复核的测试报告。用户要求跑测试、补测试、验证 AC 覆盖或更新测试报告时，使用本 skill。

## Goal

证明实现与验收标准一致，并让每条结论都能被第三方复现：

1. **覆盖可追踪**：建立 `AC -> 测试用例 -> 测试代码 -> 执行命令与结果` 的追踪关系，不留无归属的用例和无用例的 AC。
2. **证据可复核**：每条结论都对应可复制的命令和真实输出，未执行的检查明确标注为未执行。
3. **边界诚实**：区分单元测试、Mock 联调和真实环境联调，不把 Mock 结果表述成真实渠道或线上指标结论。

执行边界：

- 本 skill 只执行测试并写测试报告，不修改 PRD、验收标准、技术方案和测试方案。
- 测试暴露需求或实现问题时，记录证据并按人工确认门禁停止；不得为了让测试通过而放宽断言、跳过用例或修改验收口径。
- 测试代码只写在项目约定的测试位置，不修改被测业务逻辑来迎合测试。

## When to Use

适用：

- “按测试方案执行测试并更新测试报告”。
- “补齐单元测试 / 集成测试 / 端到端演示用例”。
- “检查 AC 是否都有对应用例和结果”。
- “跑一遍测试，把命令、输出和未覆盖范围留档”。

不适用：

- 编写或修改 PRD、产品方案（用 `prd-refinement`）。
- 生成或审查验收标准（用 `prd-to-acceptance-criteria`）。
- 生成或审查技术方案（用 `prd-to-tech-design`）。
- 实现功能或改业务代码（用 `tech-design-implementation`）；本 skill 只补测试和测试报告。
- 以本地 Mock、Fixture 或 SQLite 代替真实环境联调并宣称生产可用。

## 权威来源与范围

写测试前，必须定位并阅读：

- 测试方案：测试目标、测试分层、Demo 验证流程、事件验证要求和探索性测试清单；
- 测试数据构造说明：测试用户、任务、行为与边界数据定义；
- 验收标准：`AC-xxx` 场景，作为用例与覆盖判定依据；
- 技术方案：模块、契约、异常链路和未决项，用于判断哪些行为可测、哪些仍是 Mock；
- 当前功能进度记录（如 `docs/implementation/FR-00X-*.md`）：本轮实现范围和已声明的未完成项；
- 现有测试代码与项目测试命令（例如 Go 项目 `go test ./...`）；
- 待更新的测试报告（如 `docs/test-report.md`）及其现有结构。

以最新的人工作为最终确认的决策为准。测试方案与实际实现不一致时，不得自行调整测试口径：记录差异、证据和候选处理方式，按人工确认门禁停止。

按功能切片推进，一次只覆盖一个已完成实现的 FR。未实现的功能不得通过跳过断言、放宽期望或伪造输出使其“通过”，只能登记为未覆盖并写明原因。

## Workflow

### 0. 确认输入

确认测试方案、测试数据构造说明、验收标准、技术方案和本轮功能进度记录齐备；确认本轮要覆盖的 FR 与其 AC 列表。

### 1. 建立 AC 追踪矩阵

在追踪矩阵中列出全部相关 AC，逐条标明本轮覆盖或未覆盖。未覆盖的必须写明原因、影响和承接的后续切片，不允许直接省略。矩阵格式见 [test-case-template.md](references/test-case-template.md)。

### 2. 设计用例与分层

按测试方案的分层（单元、集成、端到端、探索性）为每条 AC 设计用例，覆盖正常、拒绝、终止、边界、幂等、频控、失败与异常分支。每条用例写明前置数据、操作、预期结果和判定依据。

### 3. 补齐测试代码与 Fixture

只在项目测试约定位置新增或修改测试与 Fixture；Fixture 与生产业务数据分离，不写入真实个人信息。时间、随机和外部失败通过注入控制，保证用例可单独、可重复运行。

### 4. 执行并记录证据

逐条执行命令，原样保留命令与结果，区分通过、失败、跳过和未执行四类状态。失败用例如实保留，不合并、不省略。

### 5. 报告回查

运行回查脚本：

~~~bash
python3 dev-tools/skills/test-plan-to-test-report/scripts/check_test_report.py \
  --report "code-repo-analysis/智能提醒助手/docs/test-report.md" \
  --ac "code-repo-analysis/智能提醒助手/需求拆解/验收标准/验收标准.md" \
  --cases <用例矩阵文件，如已单独维护>
~~~

阻塞项必须为 0；建议项逐条判断是补测还是记录理由。脚本只做结构与覆盖的机械检查，判定仍需人工复核。

### 6. 更新测试报告

按 [test-report-template.md](references/test-report-template.md) 更新测试报告：环境、命令、结果表、AC 覆盖与追踪、演示记录、已知限制和未覆盖范围。

### 7. 完成门禁

只有用例全部执行、结果与预期一致、回查阻塞项为 0，且没有未确认的问题时，才能标为完成。未执行项必须显式写明；影响结论的缺陷必须记录并按人工确认门禁处理。

## 人工确认触发条件

出现以下任一情况时，必须在继续执行前停止：

- 测试方案、验收标准与实现行为三者不一致；
- 某条 AC 无法判定通过或不通过；
- 用例需要放宽断言、跳过分支或修改验收口径才能通过；
- 需要修改业务代码才能让测试通过（改代码走 `tech-design-implementation`，并单独确认）；
- 测试发现真实缺陷，需要决定是修缺陷还是登记为已知限制；
- 需要引入新的测试依赖、外部服务或真实渠道联调；
- 结论涉及线上指标、性能或并发，而当前只有 Mock 或本地环境证据。

确认请求必须说明证据、受影响的 AC 与用例、影响范围、候选方案和需要用户作出的确切决定。用户回答前不得继续。

## Output

| 项目 | 要求 |
| --- | --- |
| 产物 | 测试代码与 Fixture、测试执行证据、更新后的测试报告 |
| 报告路径 | 默认 `docs/test-report.md`，沿用其现有结构 |
| 报告内容 | 按 [test-report-template.md](references/test-report-template.md)：测试环境、执行命令、结果表、AC 覆盖与追踪、演示记录、已知限制、未覆盖范围 |
| 证据格式 | 命令与结果成对出现；结果表区分通过 / 失败 / 跳过 / 未执行 |
| 未执行项 | 必须写明未执行原因与影响，不得声称已经完成 |

不要创建宽泛的测试计划文档，不要修改无关文件，也不要为了报告好看而合并或省略失败用例。
