# 用例追踪矩阵与用例写法

## 1. 追踪矩阵

每条 AC 至少要有一行；本轮不覆盖的 AC 也必须出现在矩阵中，处理列写明原因，不允许直接省略。

| AC | 用例 ID | 测试分层 | 用例名称 | 自动化位置 | 命令 | 状态 | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AC-001 | TC-001 | 单元 | 被动型用户生成 Push 排程 | `internal/domain/reminder/evaluator_test.go` | `go test ./internal/domain/reminder -run TestEvaluatePassiveUserCreatesPushSchedule -v` | 通过 | should_remind=true，channel=push |

字段约定：

- **测试分层**：`单元`、`集成`、`端到端`、`探索性` 四类之一，与测试方案第 4 章一致。
- **状态**：`通过`、`失败`、`跳过`、`未执行` 四类之一，与测试报告结果表一致。
- **自动化位置**：测试文件路径；手工探索性用例填 `手工`。
- **命令**：可直接复制执行的最小命令，含用例过滤参数。
- **结果**：可观察的判定值，不写“正常”“符合预期”这类无信息结论。

## 2. 单个用例写法

~~~text
用例 ID：TC-001
对应 AC：AC-001
分层：单元
前置数据：user-passive；今日任务 required=5 / completed=2；提醒开启；Push 已授权；当日未达上限
操作：以固定时钟调用决策评估
预期：should_remind=true；channel=push；reason_code=ELIGIBLE；生成 1 条 SCHEDULED 排程
判定依据：决策结构体字段与排程表记录
~~~

要求：

- 前置数据引用已有 Fixture 路径或明确字段值，不写“一些用户数据”。
- 预期结果必须是可观察值（字段、状态、记录数、错误码），不写主观描述。
- 时间、随机、外部失败通过注入或假实现控制，保证用例可重复。
- 一个用例只验证一个判定点；多个判定点拆成多条用例。

## 3. 必须覆盖的分支

按 AC 逐条确认以下分支是否有对应用例，缺哪类就在矩阵中显式登记：

| 分支类型 | 说明 |
| --- | --- |
| 正常路径 | AC 描述的主流程 |
| 前置不满足 | 无任务、权限关闭、已达上限、数据缺失 |
| 终止或取消 | 任务已完成、任务已过期、决策被取消 |
| 幂等与并发 | 重复执行不新增记录，重复调度命中唯一约束 |
| 频控上限 | 达到上限后不再发送，不因重试突破上限 |
| 失败与异常 | 渠道失败、外部未知状态、缺渠道时的拒绝原因 |
| 时间边界 | 免打扰起止临界、跨天、计划时间早于当前时间 |
| 数据边界 | 空值、零值、最小可判定数据量 |

## 4. 未覆盖登记

未覆盖的 AC 必须写明：原因（未实现 / 非本轮范围 / 依赖外部环境）、影响（哪些结论因此不能给出）、后续切片（哪个 FR 承接）。
