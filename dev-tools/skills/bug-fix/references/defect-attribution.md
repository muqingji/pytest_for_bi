# 缺陷归属判定

修复前必须判定缺陷属于哪一层。判错的代价：去改不该改的地方、掩盖真实问题、让下次还会再犯。

## 判定顺序

1. **先看是不是业务代码的问题**：把预期行为对照 PRD / 验收标准 / 技术方案 / IDL。如果代码在正确输入下
   返回了与文档不符的结果，属于业务代码。
2. **再看引擎是否自洽**：`tests/common/` 的加载、执行、断言行为是否符合它自己的文档与用法。
   例如路径参数没解析时抛 `ValueError` 是引擎的正确行为，不是缺陷。
3. **再看是不是用例数据写错**：请求体、路径、`path_params`、占位符、预期字段与枚举是否写对。
4. **最后看文档之间是否冲突**：PRD / AC / 技术方案 / IDL 互相矛盾或缺失。

## 各层的判定证据与处理

| 归属 | 判定证据 | 处理 |
| --- | --- | --- |
| 业务代码 | 正确输入下行为违反文档；或文档明确、实现缺失；或状态机 / 幂等 / 边界实现错误 | 本 skill 主路径 |
| 用例与测试资产 | 引擎与实现都对，用例数据写错：漏 `path_params`、断错字段、`request_id` 没写死、占位符引用未执行的步骤 | 转 `test-case-to-automation`；不要动业务代码 |
| 引擎或脚本 | `tests/common/*.py`、`dev-tools/**/scripts/*.py` 自身逻辑或用法文档错误 | 可修，但走本 skill 同一套验证（回归用例 + 全量验证 + CR） |
| 契约文档 | PRD 与 AC 冲突；技术方案与 IDL 字段 / 枚举不一致；文档缺少某条规则 | 停止，退回 `prd-to-tech-design` / `prd-to-acceptance-criteria` 或发起人工确认 |

## 判定要求

- 依据必须能指到具体位置，例如 `internal/domain/reminder/evaluator.go:88`、
  `tests/cases/snooze_reminder.json#SNZ-001`、`docs/api/reminder-service.openapi.yaml` 的某个 schema。
- 允许写「暂时无法判定」，但必须同时说明缺哪份证据、下一步怎么取证，不允许直接开工。
- 一个缺陷可以同时暴露两层问题（例如业务代码错 + 用例断言太松）。这时按业务代码修主问题，
  另一层单独登记为独立缺陷，不合并修。

## 反例

- 看到用例跑不过就改 Go 代码：若缺陷其实是用例漏了 `path_params`，改代码只会越改越偏。
- 看到引擎抛错就去注释掉校验：抛错是引擎在正确 fail loud，注释掉会让畸形的请求静默发出去。
- 看到文档冲突就按代码现状改文档：这属于用实现反推契约，必须走人工确认。
