# 三个门禁的自检清单

每个门禁由用户拍板，但提交前必须自己先过一遍对应清单，并把结论随材料一起给出。

## 1. 门禁 A：场景审批

提交前自检：

- [ ] 每条场景都有 `文件:行号` 来源，且行号指向规定本身而不是复述它的地方。
- [ ] 每条 P0 需求至少有一条场景；没有的写明原因。
- [ ] 场景覆盖维度逐条过了一遍，不适用的维度写了一句为什么。
- [ ] 优先级与来源需求的优先级一致，没有把 P1 抬成 P0，也没有把 P0 降成 P2。
- [ ] 引用默认值/阈值的地方都标注了“设计假设”并带出处。
- [ ] 没有把 P1/P2 或“不进入本期验收”的条目做成 P0 场景。
- [ ] 待确认清单里每条都写全了缺口、影响、候选、需要谁定。
- [ ] 每条场景的判定点是可观察量，不是主观描述。

提交材料：场景清单 + 覆盖矩阵（AC/FR → 场景）+ 未覆盖项与原因 + 待确认清单。

## 2. 门禁 B：用例评审

提交前自检：

- [ ] 每条场景至少一条用例；没有的写明原因，不直接省略。
- [ ] 每条用例的字段齐全：场景、优先级、前置条件、测试步骤、预期结果、来源。
- [ ] 用例优先级不高于其场景优先级；降级的写了理由。
- [ ] 前置条件用的是字段字典里的字段名，能直接交给数据构造 skill。
- [ ] 预期结果里没有“正常”“符合预期”这类空话。
- [ ] 步骤可被第三方按顺序执行，不含内部函数名或表名。
- [ ] 依赖未决项的预期结果标明了依赖哪条待确认。
- [ ] 数据缺口清单已单独成节。

提交材料：用例清单 + 场景到用例的覆盖关系 + 每条场景的用例数 + 数据缺口清单 + 依赖未决项的部分。

## 3. 门禁 C：封板

封板前逐项确认：

- [ ] 门禁 A、B 均已通过，阶段五补全后又重新过了一次 B。
- [ ] 回查脚本阻塞项为 0。
- [ ] 待确认项要么已闭环，要么明确登记为未闭环风险并写明影响。
- [ ] 影响范围已评估：列出受影响场景、回归范围、明确不需要回归的结论。
- [ ] 用例来源类型已标注（文档推导 / 代码补充），比例合理。
- [ ] 用例总数与优先级分布已统计。

封板产出：冻结版本号、封板日期、总数与优先级分布、未闭环项清单、变更规则。

## 4. 封板后的变更规则

封板不等于不可改，但改必须留痕：

1. 提变更申请，写清改动内容与原因。
2. 评估影响范围：影响哪些场景与用例、哪些已完成的测试结论会失效。
3. 走一次门禁 B；涉及场景增删的还要补走门禁 A。
4. 版本号递增，在封板记录的变更历史里追加一行，不改写原记录。

## 5. 提交材料时的写法

每条结论都给可核对的位置，不写“整体没问题”：

~~~text
门禁 B 自检：3 项未过
- TC-014 预期结果写的是“提醒正常发送”，无判定依据 → 建议改为可观察字段
- TC-021 优先级 P0 高于其场景 SC-009（P1） → 建议降为 P1 或补理由
- SC-007 无对应用例 → 待确认：该场景是否本轮实现
~~~

无问题时就写一句“门禁 B 自检通过，阻塞项 0”，不要补空话。
