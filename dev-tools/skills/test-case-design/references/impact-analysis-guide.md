# 阶段五：按业务代码补用例与影响范围评估

触发时机：某个功能切片实现完成（`tech-design-implementation` 声明完成、联调通过）之后。目标不是重写用例，而是补齐文档推不出来的部分，并说清这次改动动了谁。

## 1. 读代码的边界

阶段五才允许把代码当依据，且只用于三类结论：

| 可用 | 不可用 |
| --- | --- |
| 代码里有、文档没写的分支，补成新用例 | 用代码实现反推需求应该是什么 |
| 代码实际取值与文档不一致，登记差异并上报 | 直接按代码改掉文档推导的预期结果 |
| 依赖注入点、可观测出口，决定用例在哪一层测 | 把内部函数名、表名、私有结构写进用例 |

发现代码与文档不一致时，不自行裁定，按人工门禁停止：给出 `文件:行号` 与代码位置、受影响的场景与用例、候选方案（改代码 / 改文档 / 登记为已知差异）。

## 2. 补用例的四个来源

| 来源 | 说明 | 标记 |
| --- | --- | --- |
| 未覆盖分支 | 代码里存在但文档推导漏掉的分支，例如额外的拒绝原因、短路判断 | 代码补充 |
| 实现约束 | 事务、唯一键、锁、重试次数等实现带来的可观察行为 | 代码补充 |
| 依赖异常 | 依赖超时、降级、熔断的返回路径 | 代码补充 |
| 文档已写但之前判定不可测 | 现在有了观测出口，例如新增查询接口或渠道桩 | 文档推导（恢复） |

补齐的新用例要回填到对应场景下；如果找不到能挂靠的场景，说明可能漏了一个场景，回到阶段一补场景并重走门禁 A。

## 3. 影响范围评估

对每个本轮改动，按下面四问输出，不允许只写“影响不大”：

1. **受影响的场景**：列出被本次改动覆盖或改动的 `SC-` 编号。
2. **需要回归的范围**：共用同一段决策逻辑、同一张表、同一个契约的既有场景，逐个列出。
3. **明确不需要回归的结论**：写明为什么不需要，例如“未改动该分支的判断顺序”。
4. **失效的既有用例**：因契约、字段或判定顺序变化而不再成立的用例，列出编号与处理方式（改 / 删 / 保留并标注）。

输出成表，便于评审者逐行核对：

~~~markdown
## 影响范围评估

| 本轮改动 | 受影响场景 | 需回归范围 | 明确不需回归 | 失效用例 |
| --- | --- | --- | --- | --- |
| 新增免打扰判断位于频控之前 | SC-003、SC-011 | SC-001（同一决策顺序）、SC-005（频控分支） | SC-016（回流分支不在该顺序内） | TC-008 预期原因码变化，需更新 |
~~~

## 4. 与门禁 B 的衔接

阶段五补完之后，用例清单整体重新提交门禁 B，重点让评审者看三件事：

- 新增用例的来源类型与是否挂靠到了正确的场景；
- 影响范围评估里“不需回归”的结论是否成立；
- 因本次改动而失效或修改的既有用例。

## 5. 常见错误

- 把“代码就是这么写的”当成需求依据，直接改掉文档推导的预期结果。
- 只补正常路径的新用例，不评估对既有场景的回归范围。
- 影响范围写成“本次改动影响面较小，无需回归”，没有任何逐条核对。
- 新用例没有挂靠场景，形成一个游离的用例编号。
