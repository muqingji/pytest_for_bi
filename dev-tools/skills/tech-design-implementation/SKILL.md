# 技术方案代码实现

根据项目技术方案实现下一个已批准的后端功能。用户要求将技术方案转成代码、继续增量开发后端功能，或要求完成某个功能并进行测试和联调时，使用本 skill。

## Goal

把已确认的技术方案逐项落成可运行、可测试、可复核的后端代码，并保证需求、方案、代码三方一致：

1. **范围合规**：只实现已确认的 P0 功能，不扩大 PRD、技术方案或验收标准的范围。
2. **契约一致**：每个功能建立 `FR -> AC -> 技术方案章节 -> 3.4 模块 -> 代码模块 -> 单测 -> 联调场景` 的追踪关系，逐项对齐，且实现范围不超出技术方案已登记的模块。
3. **证据可复核**：单测、联调、双文档回查、开关与回滚都有可复现的命令、结果和留档。

执行边界：

- 本 skill 用于代码实现，不用于编写 PRD 或自行发明技术方案。PRD 和验收标准定义产品行为预期；技术方案定义实现契约。不得扩大任何一方的范围。
- 编码过程中不得修改 PRD、验收标准或技术方案。如果实现暴露出设计缺陷或不一致，必须停止，说明证据和候选方案，等待确认。只有得到确认后，才能修改相关方案文档，并重新进行方案回查和实现更新。

## When to Use

适用：

- “按技术方案实现 FR-00X”“继续实现下一个后端功能”。
- “把某个功能落成代码并补单测”“实现后做简单联调”。
- “回查代码与 PRD/验收标准/技术方案是否一致”。

不适用：

- 编写或修改 PRD、产品方案（用 `prd-refinement`）。
- 生成或审查验收标准（用 `prd-to-acceptance-criteria`）。
- 生成或审查技术方案（用 `prd-to-tech-design`）。
- 以 Mock 或本地 Fake 代替真实环境联调并宣称生产可用。

## 权威来源与范围

修改代码前，必须定位并阅读：

- 最新 PRD：产品行为、业务规则和口径的唯一来源；
- 技术方案：实现契约，含第 9 章的未决项与边界；
- 验收标准：`AC-xxx` 场景，作为功能验收与单测覆盖依据；
- 测试方案：Demo 验证流程、测试分层和事件验证要求；
- 测试数据构造说明：测试 Fixture 与 Demo 数据定义；
- 项目已有的依赖、构建、测试和迁移约定；
- 目标范围内的现有代码和未提交修改；
- `AI_USAGE.md` 或项目等价记录：人工决策与修正案例的留痕位置；
- 技术方案模版（如 `code-repo-analysis/模版/技术方案/后端技术方案.md`）：结构回查依据。

以最新的人工作为最终确认的决策为准。缺失或矛盾的行为、表结构、接口、状态、重试规则、安全规则或兼容要求，不得作为猜测的依据；必须停止并向用户确认。

按已确认的顺序实现 P0 功能。除非用户明确提升优先级或确认实现，否则不得实现 P1、P2 和标记为待确认的事项。

技术方案第 9 章的未决事项必须先逐条判定与当前功能的关系：阻塞当前功能的，先确认再编码；判定不阻塞的，必须在进度记录中写明判定依据。不得因为未决项影响面较大而整体搁置已可实现的规则层功能，也不得在未确认的情况下先行落地表结构或调度实现。

## 不可违反的规则

1. 每次新开发都按技术方案 `### 3.4 模块划分` 逐条推进。开工前先锁定本轮涉及的模块行（一个垂直切片可能落在多个模块），把该行的“职责、入口、主要落点、异常边界”登记进进度记录，作为本轮的实现范围与验收口径；该模块四项逐条落地且异常边界已验证后，才能进入下一个模块。不得跳过模块边界直接写应用层或适配器，也不得在未登记模块的情况下新增代码位置。
2. 一次只实现一个功能的完整垂直切片。当前功能未达到准出门禁前，不得开始下一个功能。
3. 每个功能都必须建立 `FR -> AC -> 技术方案章节 -> 3.4 模块 -> 代码模块 -> 单测 -> 联调场景` 的追踪关系。
4. 遵守技术方案中的架构。保持领域层/应用层/端口层/适配器层边界和依赖方向，不得把业务规则放进 Handler、Repository、Mock 或传输层。
5. 每个功能必须有单元测试，且单元测试通过后才能开始联调。已有回归测试也必须通过，功能才能标记为完成。
6. 实现后先根据 PRD 和验收标准检查行为，不得增加猜测出来的行为；再根据技术方案检查实现。一旦不一致，必须进入人工确认门禁，不能静默重设计。
7. 任何无法从已确认文档或已有仓库约定确定的实现决策都必须由人确认：包括范围、默认值、状态流转、表结构语义、接口契约、重试行为、权限、隐私、兼容性、性能限制和外部服务能力。不得把不确定事项隐式变成默认值。
8. 业务数据必须有真实的表结构设计和迁移/模型实现。测试 Fixture 和 Demo 数据是独立资产，不能替代生产持久化设计。
9. Mock 必须遵守外部接口契约，并覆盖正常、明确失败、超时、未知状态、空数据、重复请求和非法数据路径。
10. 编写可维护的代码和注释。注释解释不变量、原因、安全约束或非显然的取舍；不要为显而易见的语法写注释。
11. 不得使用破坏性 Git 操作，也不得覆盖用户无关的修改。编辑范围必须限定在当前功能及其测试、迁移、配置和验证留档内。
12. 待确认事项分两类处理：产品与业务口径类可由人工决策，决策后必须回写文档；外部服务能力类（幂等、状态查询、配额、鉴权、数据库与调度平台能力）只能核对事实，不得写成“已确认”。
13. 任何确认结论必须回写到 PRD、验收标准和技术方案三处，并重跑回查脚本。只口头确认、不回写文档的结论不得作为实现依据。
14. 不得声称未经执行的验证。性能、容量、线上指标、真实渠道联调等未验证时必须写明“未验证”，也不得用模拟数据推导线上结论。

## 增量实现流程

### 0. 前置检查

1. 使用 `rg --files` 定位项目根目录和相关文件。
2. 检查 `git status --short`；保留无关修改，编辑前仔细检查与当前功能重叠的修改。
3. 确认 PRD、技术方案、验收标准、测试方案、测试数据构造说明、构建命令、测试命令和迁移约定都存在。缺少必需输入时停止并询问。
4. 锁定本轮模块：读取技术方案 `### 3.4 模块划分`，确定本轮涉及的模块行及其依赖顺序，把每行的“职责、入口、主要落点、异常边界”登记进进度记录。依赖未就绪时先实现前置模块，不并行铺开。
5. 读取技术方案第 9 章的未决项，逐条判定与当前功能的关系：阻塞项必须先确认；不阻塞的要写明依据。未确认的阻塞项不得开始对应实现。
6. 校验编号存在性：用 `rg` 确认本功能的 FR 与 AC 编号在 PRD 和验收标准中真实存在，避免追踪关系写错编号。
7. 运行已有基线测试或最小可用验证。记录在当前功能之前就存在的失败，不得默认为本次改动导致。

### 1. 选择并定义一个功能

选择下一个依赖已就绪的、已确认的 P0 功能。提取该功能的用户、前置条件、行为、预期结果、边界和关联 AC。阅读技术方案对应的模块、入口、数据模型、状态流转、错误处理和可观测性映射。

本轮实现范围以第 0 步锁定的模块行为准：该功能落在哪个（哪些）模块，就只在这些模块的写入范围内实现；需要新增模块或跨越 `3.4` 未列出的代码位置时，先走人工确认门禁。

同时从技术方案第 5 章（测试建议）中摘出属于本功能的 AC 覆盖清单，作为本功能的单测待覆盖项，逐条在进度记录中登记。

编码前，使用 [feature-progress-template.md](references/feature-progress-template.md) 创建或更新进度记录。如果任何必填字段无法从文档或仓库中确定，必须在编码前向用户确认。

### 2. 按模块实现垂直切片

按第 0 步锁定的模块，逐个模块实现最小但完整的切片。每个模块都要覆盖该模块行的“职责、入口、主要落点、异常边界”四项，实现内容至少包括：

- 领域规则和值对象；
- 应用用例和流程编排；
- 端口接口；
- 适配器和持久化；
- API/调度入口；
- 迁移、索引、约束和 Repository 行为；
- 技术方案要求的结构化错误、日志、指标和事件；
- 单元测试 Fixture 和遵守契约的 Mock。

生产代码、迁移、单元测试 Fixture 和 Demo 数据必须保持分离。不得引入 PRD 和技术方案未要求的 UI、后台、新产品策略或基础设施组件。

### 3. 持久化与数据安全门禁

对功能写入的每个业务实体，必须确认：

- 表/模型和迁移存在；
- 主键、唯一键、索引、状态/版本字段、时间戳和保留假设明确；
- 幂等键和并发更新行为已经实现；
- 迁移与现有数据兼容，并具备回滚或关闭策略；
- Repository 不隐藏产品决策。

如果技术方案没有确定数据库引擎、表结构语义或迁移策略，必须停止并询问。不得静默选择本地数据库，也不得把内存 Fake 当成生产存储。

### 4. 单测门禁

针对当前功能相关路径，补充正常、边界、失败、未知状态、重试、幂等、并发和隐私敏感场景的单元测试。测试必须断言业务结果和状态变化，不能只断言 HTTP 状态码或 Mock 是否被调用。

第 1 步摘出的 AC 覆盖清单必须逐条对应到具体用例，并在进度记录中勾选；确实无法覆盖的，写明原因和待确认项。

运行当前功能的单测，然后运行已有回归测试。除非用户明确接受并记录已有失败，否则单测和回归测试未通过时不得开始联调。

### 5. 简单联调门禁

单测门禁通过后，通过真实应用装配和符合契约的测试替身或可用测试服务，运行一条小型端到端链路。验证输入、输出、持久化、状态流转、事件关联、重试和重复请求。必须标明结果是“真实联调”还是“Mock 联调”；不能把 Mock 联调描述成生产服务验证。

### 6. 双文档回查门禁

联调后：

1. 重新阅读 PRD 和验收标准，确认每个预期行为和拒绝路径都已实现，并记录未实现或含义不清的事项。
2. 重新阅读对应的技术方案章节，确认模块边界、接口、表结构、状态机、错误处理、重试、可观测性和回滚行为一致；并核对实现没有跨越 `### 3.4 模块划分` 的边界，也没有引入未登记的模块或代码位置。
3. 运行确定性回查脚本，并把命令与结果写入进度记录：

~~~bash
python3 dev-tools/skills/prd-to-tech-design/scripts/check_tech_design.py \
  --design <技术方案.md> --prd <PRD.md> --prd <验收标准.md>
python3 dev-tools/skills/prd-to-acceptance-criteria/scripts/check_acceptance_criteria.py \
  --ac <验收标准.md> --prd <PRD.md>
~~~

阻塞项必须为 0 才算通过；建议项逐条判断是修还是记录理由。人工阅读与脚本结论不一致时，以脚本给出的位置证据为准继续排查。
4. 任一回查发现不一致或设计不完整，都必须使用 [confirmation-template.md](references/confirmation-template.md) 停止并向用户确认，不得静默“修正”方案。

### 7. 完成门禁

只有代码、迁移、单元测试、联调检查、回归测试、PRD 回查、技术方案回查和进度证据全部完成，且没有未确认阻塞项时，才能将功能标记为完成。

完成前还必须确认开关与回退：

- 功能开关默认关闭或按技术方案约定取值，且可显式开启；
- 渠道（Push、站内提醒）可独立关闭；
- 回退路径已确认：关闭开关后停止智能排程、恢复既有策略、不删除历史记录；
- 未演练的回退或性能场景必须写明“未演练/未验证”。

如果人工作出的决策、范围修正或方案确认实质影响实现，必须更新 `AI_USAGE.md` 或项目等价记录。

## 人工确认触发条件

出现以下任一情况时，必须在编辑或继续执行前停止：

- PRD 与技术方案不一致；
- 某个 AC 没有可实现的技术契约；
- 实现需要新增文档未定义的字段、接口、状态、重试、默认值、权限、表或外部能力；
- 迁移可能修改或使现有数据失效；
- 外部服务的幂等、状态查询、配额、鉴权或失败语义未知；
- 技术方案第 9 章的未决项阻塞当前功能；
- 测试结果与产品预期不一致；
- 拟议修复会扩大范围或改变已确认决策；
- 用户修改与当前编辑文件重叠，且修改意图不清楚。

确认请求必须说明证据、受影响的 FR/AC、影响、候选方案、推荐意见和需要用户作出的确切决定。用户回答前不得继续。

确认请求还必须写明结论去向：需要回写哪些文档（PRD 章节 / 验收标准 AC / 技术方案章节）、是否需要重跑回查脚本、是否需要记入 `AI_USAGE.md`。结论回写完成且回查通过后，才能作为实现依据继续。

## 代码质量与安全

- 保持依赖方向单向，通过接口或领域服务明确可复用行为。
- 优先使用小函数和具名领域类型，避免无类型 Map 和重复条件判断。
- 使用结构化错误和稳定错误码，区分正常业务拒绝、明确失败和外部未知状态。
- 不得让缓存成为频控、幂等、任务完成或类似资金状态的唯一事实来源。
- 使用仓库既有鉴权约定保护内部接口；校验资源归属和事件签名。
- 只存储和记录当前功能所需的最少匿名标识和状态。不得记录姓名、手机号、任务正文、成绩、Token 或凭证。
- 配置、功能开关和重试上限必须显式且可测试。
